# GAP9 SDK kernel sweep: static compiler-output comparison

**Static metrics only.** Everything below is compile status, code size and instruction counts read from object files. Nothing was executed: there are no cycle counts, and no output was checked for correctness. Instruction-count changes are reported as such and say nothing about speed (loop trip counts, hardware-loop behaviour and memory latency are not modelled). A simulator is being built separately; see "sim/ hook".

## Summary

Kernels that compile, out of 12 SDK/plan kernel TUs (k01–k11, k10 split into a/b) and 15 anchor functions (k12):

| compiler | O2 kernels | O3 kernels | O2 anchor | O3 anchor | clip probe |
|---|---|---|---|---|---|
| ref18 | 4/12 | 3/12 | 10/15 | 10/15 | ok |
| port19 | 4/12 | 3/12 | 10/15 | 10/15 | ok |
| port20 | 5/12 | 4/12 | 15/15 | 15/15 | ok |
| gcc | 12/12 | 12/12 | 15/15 | 15/15 | ok |

- ref18 and port20 compile the same plan kernels except: port20 additionally compiles k09_cmplx_fix, k12_copy_loop, k12_dot16_loop, k12_dot8_loop, k12_packed_add8_loop, k12_sum_loop; port20 fails where ref18 succeeds: none. port19 matches ref18's status everywhere.
- port20 − ref18 on kernels both compile: matmul_worker O2 -4 B / -1 insns; matmul_worker O3 -4 B / -1 insns; KerParMatMulDSP_Fix16 O2 +24 B / +6 insns; KerParMatVectDSP_f32 O2 -4 B / +0 insns; KerParMatVectDSP_f32 O3 -4 B / -1 insns; dotprod_i8 O2 -2 B / -1 insns; dotprod_i8 O3 -2 B / -1 insns. Per-family changes are in the table below.
- Every failure also happens on ref18 (the fork's pre-existing bugs listed in the survey), except the port20 rows noted above; no flags or sources were changed to avoid them.
- `p.clip` for `clip(x,-128,127)`: all LLVM compilers emit immediate 7, GAP9 GCC emits 8 (see "p.clip immediate").

Generated by `run.py` (which calls `report.py`); raw data in `results.json`, exact commands in `commands.json`, objects, disassembly, symbol tables and compiler stderr in `build/<compiler>/<opt>/`.

| function | opt | ref18 | port19 | port20 | gcc |
|---|---|---|---|---|---|
| clip_s8 | O2 | a0, a0, 0x7 | a0, a0, 0x7 | a0, a0, 0x7 | a0, a0, 0x8 |
| clip_s8 | O3 | a0, a0, 0x7 | a0, a0, 0x7 | a0, a0, 0x7 | a0, a0, 0x8 |
| clipu_u8 | O2 | a0, a0, 0x9 | a0, a0, 0x9 | a0, a0, 0x9 | a0, a0, 0x9 |
| clipu_u8 | O3 | a0, a0, 0x9 | a0, a0, 0x9 | a0, a0, 0x9 | a0, a0, 0x9 |

For `[-128,127]` the three LLVM compilers encode `0x7` and GAP9 GCC encodes `0x8`; for `clipu [0,255]` all four agree. With GVSoC's `p.clip` semantics (clamp to `[-2^(N-1), 2^(N-1)-1]`, per the survey) the LLVM immediate would clamp to `[-64,63]`. This is inherited from ref18 (port19 and port20 match it) and is unconfirmed until run on the simulator. The same one-lower immediate appears in real SDK code: `gap_clip(x,15)` expands to `__builtin_pulp_clip(x,-32768,32767)`; in k05 `KerParMatMulDSP_Fix16` the LLVM compilers encode 0xf and GCC 0x10 (k07 `KerParMatAdd_DSP_Fix16` also uses it but crashes all LLVM compilers). Other measured functions containing `p.clip` (their source is `gap_clip(x,15)`, i.e. `clip(x,-32768,32767)`): k05_matmul_dsp_fix16 ref18 O2: 15x p.clip, imm 0xf; k05_matmul_dsp_fix16 port19 O2: 15x p.clip, imm 0xf; k05_matmul_dsp_fix16 port20 O2: 15x p.clip, imm 0xf; k05_matmul_dsp_fix16 gcc O2: 15x p.clip, imm 0x10; k05_matmul_dsp_fix16 gcc O3: 15x p.clip, imm 0x10; k05_matmul_dsp_fix16 port20fix O2: 15x p.clip, imm 0x10; k05_matmul_dsp_fix16 port20fix2 O2: 15x p.clip, imm 0x10; k05_matmul_dsp_fix16 port20fix2 O3: 16x p.clip, imm 0x10; k07_matadd_dsp_fix16 gcc O2: 1x p.clip, imm 0x10; k07_matadd_dsp_fix16 gcc O3: 1x p.clip, imm 0x10; k07_matadd_dsp_fix16 port20fix2 O2: 1x p.clip, imm 0x10; k07_matadd_dsp_fix16 port20fix2 O3: 1x p.clip, imm 0x10.

## sim/ hook

This sweep produces objects only and does not read or write `sim/`, which belongs to the separate simulator work (target gvsoc2 `ri5ky_testbench`, survey sections 3 and 5). To time these objects the runtime harness needs, per kernel:

- a fixed input set: deterministic data (seeded PRNG or tables) sized per kernel, e.g. FIR taps + samples (k01/k02), int16/fp32 matrices with dimensions (k03–k07), pre-emphasis/window buffers (k08), complex int16 vectors (k09), N-point complex data plus a small Q15 twiddle table (k10a/k10b), int8 vectors (k11), and scalar inputs spanning the clip bounds (clip.c);
- a call stub that fills the kernel's argument struct (`KerFirSeq`, `MatMul_DSP_T`, `KerMatAdd_DSP_T`, ...) and calls the kernel object built here, unchanged;
- a result checksum over the output buffer (e.g. CRC32 or 64-bit sum), with a golden value from GCC's object and/or a host build, compared exactly for integer kernels and with a stated tolerance for fp32;
- cycle readout around N repetitions via the testbench MMIO counter (`0x10000008`/`0x1000000C`), one shared harness/crt0/link script, only the kernel `.o` changing per compiler;
- the clip probe first: its checksum decides whether `p.clip ...,7` is a miscompile before any `gap_clip` kernel is timed.

## Reproduce

`python3 run.py` (from any directory; deletes and rebuilds `build/`, rewrites `results.json`, `commands.json`, `report.md`; about 5 s on 16 threads). Rerunning reproduces `report.md` and all metrics exactly; clang objects are bit-identical, GAP9 GCC objects differ only in a per-compile `nonce=` string outside `.text`.

# B156: why clang emits no GAP9 packed SIMD for plain C loops, and what enabling it takes

(Markdown content. Saved as report.txt because the Write tool refuses .md files in this harness.)

Investigation only. No compiler source on any branch was changed, nothing was committed.
Date 2026-10-07. Compiler: integration head `26e7268c3127` (`toolchains/port-20-bench`, assertions on).
Reference: GAP9 GCC 7.1.1. Simulator: GVSoC `ri5ky_testbench` (`benchmarks/gap9-sweep/sim`).

Everything below is reproduced by `./reproduce.sh` in this directory (section 7 lists the files).

## Summary

**Root cause.** The loop vectorizer, the SLP vectorizer and VectorCombine all run at -O2/-O3, and all three
return on their first line because the RISC-V target tells them the machine has **zero vector registers and a
0-bit vector register** unless the RVV extension is enabled. The PULP packed types `v2i16`/`v4i8` are legal in the
back end, and the cost model already prices them as legal, but the three "is there a vector unit" hooks only
know about RVV. No flag or pragma gets past that gate.

**What an experiment shows.** With a 6-line private patch that answers "31 registers, 32 bits" for xgap9
(`exp-tti.patch`, scratch build, not proposed as the fix), 30 probe loops and 5 straight-line blocks vectorize
(35 of the 45 functions in `loops2.c`) and the back end selects `pv.*` instructions for them. All 44 simulated
loops give the same results as GCC -O2 and as stock clang, at 11 lengths and 8 pointer-alignment combinations.
With misaligned word access also allowed, the simple loops reach GCC -O3 speed (add16: 684 cycles against GCC's
686; stock clang 2074). Clang then also vectorizes loops GCC does not (abs, clip, average, and with a forced
option the 16-bit dot product: 552 cycles against GCC's 1051).

**What stands between the experiment and a shippable feature.**

1. Misaligned packed loads and stores are split into byte/half accesses today, which makes vectorized code
   barely faster than scalar and sometimes slower. GAP9 GCC uses misaligned `lw`/`sw` freely, also in scalar code.
2. Three back-end crashes are reachable as soon as the vectorizers run (one of them in the SDK's `FftLibraryFix.c`).
3. The cost model accepts loops the back end then scalarises (multiply, saturating add, variable shift).
4. Half precision cannot be vectorized at all: `<2 x half>` is not a legal type and the 82 packed
   float instructions have no selection patterns (existing backlog B90 task T5 / B115).

**Size of the work** (details in section 6): about 150-300 lines of compiler code plus tests for GCC parity on
simple integer loops, 150-250 more for dot products and sum reductions, and 500-800 for half precision, most of
which is B90-T5 and is needed anyway. Uncertainty is roughly +/-50%; the largest unknowns are code size at -O2
and whether the hardware-loop pass converts the vector loop.

## 1. Do the vectorizers run, and what do they decide?

They are in the pipeline and return immediately.

```
$ opt -passes='default<O3>' -debug-pass-manager loops.O0.ll      (stock opt, xgap9 features)
Running pass: LoopVectorizePass on add16 (16 instructions)
Running pass: SLPVectorizerPass on add16 (14 instructions)
Running pass: VectorCombinePass on add16 (14 instructions)

$ opt -passes='default<O3>' -debug-only=loop-vectorize,SLP loops.O0.ll
SLP: Didn't find any vector registers for target, abort.         (3 times, once per function)
```

The loop vectorizer prints nothing at all, not even "LV: Checking a loop", and
`-Rpass-missed=loop-vectorize -Rpass-analysis=loop-vectorize` produce no remark. That is the early exit at the
top of the pass, before any loop is looked at:

| pass | gate (upstream llvmorg-20.1.8, same lines in the fork) | condition that fires for xgap9 |
|---|---|---|
| loop vectorizer | `llvm/lib/Transforms/Vectorize/LoopVectorize.cpp:10767-10769` | `getNumberOfRegisters(vector class) == 0` and `getMaxInterleaveFactor(1) < 2` |
| SLP vectorizer | `llvm/lib/Transforms/Vectorize/SLPVectorizer.cpp:18540` | `getNumberOfRegisters(vector class) == 0` |
| VectorCombine | `llvm/lib/Transforms/Vectorize/VectorCombine.cpp:3160` | `getNumberOfRegisters(vector class) == 0` |

## 2. What the target tells them

Line numbers are in `wt/int-20` at `26e7268c3127`.

| hook | answer for xgap9 without V | where it comes from |
|---|---|---|
| `getNumberOfRegisters(VRRC)` | **0** | `RISCVTargetTransformInfo.h:371-387`: `ST->hasVInstructions() ? 32 : 0` |
| `getRegisterClassForType(Vector=true)` | `VRRC` (the RVV class) | `RISCVTargetTransformInfo.h:394-396` |
| `getRegisterBitWidth(RGK_FixedWidthVector)` | **0 bits** | `RISCVTargetTransformInfo.cpp:327-336`: `useRVVForFixedLengthVectors() ? LMUL*VLEN : 0`; `useRVVForFixedLengthVectors()` needs `hasVInstructions()` (`RISCVSubtarget.cpp:199-202`) |
| `getRegisterBitWidth(RGK_ScalableVector)` | 0 | same function |
| `getMaxInterleaveFactor(VF)` | **1** for every VF | `RISCVTargetTransformInfo.h:359-366` and `RISCVSubtarget.h:258-260` (`hasVInstructions() ? MaxInterleaveFactor : 1`) |
| `getMinVectorRegisterBitWidth()` | **0** | `RISCVTargetTransformInfo.h:138-140` |
| `getMaximumVF(elem, opcode)` (SLP) | 1 | `RISCVTargetTransformInfo.cpp:2411-2424`: `max(1, 0 / ElemWidth)` |
| `isLegalMaskedLoad/Store` | false | `RISCVTargetTransformInfo.h:226-234` (`!hasVInstructions()`) |
| `supportsScalableVectors`, `enableScalableVectorization` | false | `RISCVTargetTransformInfo.h:97-99` |
| `enableInterleavedAccessVectorization()` | **true**, unconditionally | `RISCVTargetTransformInfo.h:368` (matters once the gate is open, see crashes C2/C3) |
| are `v2i16`/`v4i8` legal for the cost model? | **yes** | `RISCVISelLowering.cpp:140-143` registers both in GPR classes, so `getTypeLegalizationCost` returns them unsplit |

The cost model is therefore already usable. `opt -passes='print<cost-model>'` on `cost.ll` with the stock opt
(`out/cost.default.txt`):

| instruction | cost | comment |
|---|---:|---|
| `add <2 x i16>`, `add <4 x i8>` | 1 | correct (`pv.add.h/.b`) |
| `shl`/`ashr <2 x i16>`, `icmp`, `smin` | 1 | correct |
| `load`/`store <2 x i16>` align 4 | 1 | correct (`lw`/`sw`) |
| `load`/`store <2 x i16>` align 2, `<4 x i8>` align 1 | 1 | **too low today**: the back end emits 4 / 10 instructions (section 4) |
| `select <2 x i1>` | 3 | real code is 5 instructions |
| `mul <2 x i16>` / `<4 x i8>` | 5 / 7 | too low: no packed multiply exists, real code is 7 / 14 instructions |
| `sadd.sat <2 x i16>` | 11 | scalarised in the back end |
| `sext <2 x i16> to <2 x i32>` | 3 | |
| `add <4 x i16>` | 2 | split in two |
| `fmul <2 x half>` | 4 | not a legal type, scalarised |

**RVV-only assumptions.**

- The three gate hooks above. They are the whole reason for B156.
- The cost functions were already made safe for PULP in the fork, by returning before the RVV code that asserts
  in `getMinRVVVectorSizeInBits()`: `getShuffleCost` (`RISCVTargetTransformInfo.cpp:396-401`),
  `getScalarizationOverhead` (`:693-698`), `getVectorInstrCost` (`:1984-1989`), `getMemoryOpCost` (`:1800-1804`),
  and the `!useRVVForFixedLengthVectors()` early returns in the arithmetic, compare, cast and reduction costs.
  With the gate open none of these asserted on 45 + 13 + 10 probe loops and 35 SDK files. But the three guards
  return a **flat cost of 1 for any fixed vector**, including `<8 x i16>` shuffles and full scalarisation. That was
  harmless while nothing asked; it is wrong once the vectorizers ask.
- The "assert RVV-VLEN" of the old LLVM 18 fork (`benchmarks/gap9-sweep/report.md`, k01/k05 at -O3) is still
  present in the **back end**, not in TTI: `RISCVTargetLowering::isExtractSubvectorCheap`
  (`RISCVISelLowering.cpp:2320-2340`) reads `getRealMinVLen()` for every fixed vector, and `isInterleaveShuffle`
  (`:4657-4660`, called from `isShuffleMaskLegal` `:5880`) reads `getELen()`. Both assert without V. They are
  only reached by vector IR wider than one packed register, which the vectorizers produce (crashes C2 and C3).
- Upstream has no answer to copy. Its later support for GPR-held vectors (P extension, `dfdc69b4c27d`,
  `6d516c6e28a1`, `4540415f19d9`, first released in llvmorg-23.1.0) added the same kind of cost-function guards
  the fork has, and still returns `hasVInstructions() ? 32 : 0` for the vector register count. Upstream RISC-V
  does not auto-vectorize to GPR-held vectors in any release in this clone. Upstream's CORE-V `XCVsimd` at
  20.1.8 is assembler-only (`RISCVInstrInfoXCV.td:396`), with no vector types in `RISCVISelLowering.cpp`.

## 3. Can it be forced without source changes?

**No.** Every flag was tried on `../loops.c` with the stock clang; all give 0 packed instructions.

| attempt | result | why |
|---|---|---|
| `-mllvm -force-vector-width=2` / `=4` | 0 `pv.*` | read inside the vectorizer, after the gate |
| `-mllvm -force-target-max-vector-interleave=2` | 0 | only read in `selectInterleaveCount` (`LoopVectorize.cpp:4968`), not at the gate |
| `-mllvm -force-target-num-vector-regs=16` (also with forced width) | 0 | only read in the register-pressure estimate (`LoopVectorize.cpp:4941`) |
| `-mllvm -riscv-v-fixed-length-vector-lmul-max=8` | 0 | multiplies a VLEN of 0 |
| `-mllvm -vectorizer-min-trip-count=1` | 0 | after the gate |
| `-fslp-vectorize` | 0 | already on; SLP aborts at its gate |
| `#pragma clang loop vectorize(enable) vectorize_width(2)` (`pragma.c`) | 0, and clang warns `loop not vectorized: the optimizer was unable to perform the requested transformation` | pragma is read after the gate |
| adding V: `-march=rv32imcv_xgap9` | rejected: `'f' and 'zfinx' extensions are incompatible` | and RVV code would not run on the chip anyway |

### The experiment: open the gate in a private build

`exp-tti.patch` (6 added lines, scratch worktree and build outside the port tree) makes the three hooks answer
31 registers / 32 bits / minimum 32 bits when Xpulpv2 is present and V is not. Only `opt` comes from that build;
clang's front end and `llc` are the stock toolchain. Two configurations: as is ("exp"), and with the existing
target feature `unaligned-scalar-mem` added ("exp-ualign").

**What the vectorizers do** (`out/exp/*/loops2.status.tsv`, `out/exp/base/lv_costs.loops2.tsv`):

- 30 loops in `loops2.c` are vectorized at VF 2 (16-bit) or VF 4 (8-bit), interleave count 1; 5 straight-line
  blocks are SLP-vectorized. Example decision for add16: scalar cost 6, VF 2 cost 6 (3.0 per lane), VF 2 chosen.
- Reductions into an `int` (dot16, dot8, sum16, sum8, max16r, sad8) and 32-bit loops are left scalar: "Vectorization
  is possible but not beneficial", because `<2 x i32>` is not a legal type. Nothing bad happens to them.
- Half-precision loops are left scalar for the same reason (`<2 x half>` not legal, VF 1 chosen).
- At -O2 the same loops vectorize (GCC only vectorizes at -O3). At -Os 3 loops and 4 SLP blocks. At -O1/-Oz none.

**What the back end does with that IR.** Add16, experiment with `unaligned-scalar-mem`, as simulated:

```
        lp.setup x0, t1, 8          # hardware loop
        p.lw     t1, 4(a4!)
        p.lw     a5, 4(t2!)
        pv.add.h a5, a5, t1
        p.sw     a5, 4(t0!)
```

This is GCC's vector body instruction for instruction. Without `unaligned-scalar-mem` the same loop is 15
instructions for 2 elements (`lhu lhu lhu lhu slli or slli or pv.add.h srli sh sh addi addi addi`).

**Correctness and speed on GVSoC** (`run_sim.sh`, `simdrv.c`; `out/sim/table.tsv` has all 44 loops). Cycles for
256 elements, "all pointers 4-byte aligned / all pointers off by one element". Results are hashed over 11
lengths (0 to 65) and all 8 alignment combinations of the three pointers.

What the table says:

- **Results:** 43 of 44 loops are identical across all nine builds, including the overlapping-pointer calls of
  the no-restrict loops and both forced variants. The one difference is GCC -O3 on max16rn, and it is the
  simulator: GCC's reduction epilogue uses `pv.shuffle2.h`, whose operands GVSoC swaps (existing backlog B113).
  Clang's experimental code for that loop uses `pv.extract.h` + `p.max` and agrees with the scalar builds.
- **With misaligned word access allowed, the experiment equals GCC -O3** on every loop GCC vectorizes
  (add, sub, and, min, max, shift by constant, add constant, compare-select, relu), and beats it on
  abs16, clip16 and avg8, which GCC leaves scalar.
- **Without it the gain is small and two loops get slower than stock clang** (mul16 +7%, sat16 +6%).
- **Pointers that are not 4-byte aligned cost one extra cycle per access** in the simulator (add16: 1067 instead
  of 684). GCC avoids most of that by peeling scalar iterations until one pointer is aligned; LLVM's loop vectorizer
  has no alignment peeling. Even fully misaligned, the vector loop is faster than GCC's scalar loop (1067 against 1312).
- **The hardware loop decides between "parity" and "half of the gain".** The column "no hw loop" is the same
  module handed to `llc` as text instead of bitcode: identical IR, different use-list order, and the PULP
  hardware-loop pass no longer converts the vector loop (10 `lp.setup` in the object instead of 34). Add16 is then
  1062 cycles instead of 684. This is existing backlog B23 (stock clang's scalar add16 has no hardware loop either,
  which is why it needs 2074 cycles against GCC -O2's 1312).
- **Forced in-loop reduction gives `p.lw p.lw pv.sdotsp.h` for the 16-bit dot product**, 552 cycles against 1051
  for GCC -O3, which does not vectorize it. The same option makes 8-bit dot products slower (2472), because the
  back end has no match for the 4-lane form (section 4).

## 5. What GAP9 GCC does

Float16 (`loops_f16.c`, shaped like the SDK's `WindowingReal2Real_f16` and `CmplxMagSquared_f16`, the two stages
`benchmarks/dsp-bench/mfcc-app/report.md` names):

|---|---|---|

| dot product into a float16 | not vectorized (strict FP order) | |

**Trip counts.** Unknown `n`: full shape below. Known 64 or 63: the same shape with the count as a constant
(34 / 26 instructions). Known 4 bytes or 2 halves: one straight-line packed operation, 5 instructions. Global
arrays with a known count are treated like pointers (GCC still emits the alignment prologue).

**`restrict`.** Without it GCC emits a run-time overlap test (`p.sletu` comparisons of the pointer ranges) and
keeps both versions: "loop versioned for vectorization because of possible aliasing". Add16 grows from 47 to
72 instructions with two hardware loops, and costs about 17 extra cycles per call.

**Loop shape** (add16, unknown `n`, 47 instructions against 12 at -O2):

1. Guard for `n <= 0`, and a jump to the scalar code when `n` is too small.
2. **Alignment peeling**: if the first load pointer is not 4-byte aligned, one scalar iteration (up to 3 for
   bytes). Only that one pointer is aligned; the other load and the store use plain `p.lw`/`p.sw` at whatever
   alignment they have. So GAP9 GCC treats misaligned word access as legal.
3. **Hardware loop around the packed body**: `lp.setup` then `p.lw !`, `p.lw !`, `pv.add.h`, `p.sw !`
   (4 instructions for 2 elements, post-increment on all three pointers).
4. **Remainder**: straight-line scalar code for the last 1 iteration (16-bit) or up to 3 (8-bit), not a loop.

GCC also uses misaligned access in scalar code, and clang does not (`unaligned_scalar.c`):

```
int rd(const struct P *p){ return p->v; }      /* packed struct, v at offset 1 */
GCC -O2:    lw a0,1(a0)                                    1 instruction
clang -O2:  4 x lbu, 3 x slli, 3 x or                      10 instructions
clang -O2 -mno-strict-align:  lw a0, 1(a0)
```

### Risks

- **Correctness.** The experiment's integer code was right on every loop simulated, but the coverage is 44 small
  loops, 11 lengths and 8 alignment combinations, on a simulator with known packed-instruction bugs (B113 `pv.shuffle2`, B151 `vfmre`).
  Lane order and misaligned access should be confirmed on the board before this is on by default. The
  hardware-loop fuzzer generates exactly the kind of loops that will now vectorize and should be rerun.
- **Misaligned access.** The claim that it is legal and costs one cycle rests on GCC's generated code and on
  GVSoC. It has not been measured on a board in this investigation.
- **Hardware loops.** The gain halves when the vector loop does not become a hardware loop, and whether it does
  currently depends on IR use-list order (B23). The scalar remainder loop is a second loop per function; the
  pass must not regress on functions that now contain two (earlier B03/B82 were about duplicate setups).
- **Post-increment.** The vector body needs `p.lw`/`p.sw` post-increment on a packed type; this works today
  (`RISCVISelLowering.cpp:736-742`) but only once the access is a single word (A2). The fork deliberately has no
  post-increment `f32` store because the hardware-loop pass rejects a store as induction update (`:744-749`);
  the same interaction should be checked for `p.sw` of a packed value. In the experiment it formed a hardware loop
  with `p.sw` as the last instruction.
- **Cost-model regressions on SDK code.** Static sweep of the 35 DSP library files (`sdk_sweep.sh`,
  `out/sdk/*.tsv`), vectorizers on, misaligned access on for both sides: 14 loops and 8 SLP groups vectorize in 5
  fixed-point files, 1 file crashes `llc` (C2), 28 functions change. Fixed-point FIR, MatMul, DCT and zero-padding
  functions grow by 7-70% in instruction count (KerFirSeqBaseline 40 to 64, KerParMatMulDSP_Fix16 606 to 692)
  with the same number of `pv.sdotsp.h`; whether they get faster was not measured. A second effect is easy to
  miss: **VectorCombine also switches on**, and it rewrites the SDK's hand-written vector code. In the float16alt
  FFT/DFT files the number of `pv.extract.h` drops (22 to 10 in `_DIT_DFT_MR`) and inlining decisions change
  (four `Ker*DftMR_Real_f16` wrappers shrink from about 110 to 30 instructions because a callee is no longer
  inlined). None of that was simulated.
- **Code size.** On the probe file, .text at -O2 goes from 1430 to 3376 bytes and at -O3 to 4888 (GCC -O3:
  4904; GCC -O2: 1430). At -Os it shrinks slightly (1392 to 1262). The SDK builds mostly at -O2/-Os, so
  whether to vectorize at -O2 is an owner decision.
- **Remark crash C4.** Anyone building with `-Rpass-missed=loop-vectorize` hits an upstream assertion on
  float16 reduction loops once vectorization is on.
- **Fork surface.** There is no upstream RISC-V precedent for auto-vectorizing to GPR-held vectors (section 2),
  so A1, A4 and B1 are fork-only code in `RISCVTargetTransformInfo.*` that every future port carries.

### Uncertainty

List A's line count is well grounded: A1 was built and run, A2(a) was run as a feature flag, A3's three
crashes have reproducers and an obvious place to fix. The spread comes from A2 (2 lines or 100, an owner choice)
and A4 (how many scalarised operations need a tuned cost; I found five, the SDK may have more). List B rests on
one forced experiment for the 16-bit case and on reading the patterns for the 8-bit case. List C is an estimate
from the instruction list, not from an experiment. Performance numbers are GVSoC cycles on one core; no board
measurement was made, and the SDK kernels were only compared statically.

THE DENOMINATOR QUESTION
------------------------
There are two honest denominators:
  617 = files GAP9 GCC compiles with the survey's GCC mode (SDK -D/-I/-f flags, -Werror
        removed). Our P count against it: 610/617 = 98.9%.
  609 = files GAP9 GCC compiles with the SDK's own flags, -Werror included (run.py mode
        gccsdk). Our P count against it: 609/609 = 100%.
GCC fails 8 of the 617 with the SDK's -Werror: the 7 files below, plus
tools/autotiler_v3/BasicKernels/CNN_Libraries_HWPE/ne16_el1/RNN_BasicKernels_NE16.c
(GCC: -Werror=sign-compare; P compiles it). So every file clang still fails is one that the
SDK's own build rejects with GCC as well. Those files build only when the SDK is configured
with CONFIG_DISABLE_WERROR.

Secondary (like for like with the SDK warning flags, run.py sdkflags / sdknowerror modes):
clang with the SDK's -W flags and -Werror compiles 534/609, and without -Werror 549/617.
These two modes use run.py's SDK_ARCH, which at bc82384aaee0 has no -mPE=8, so the 68
CoreCount files fail there for that reason alone. The remaining 7 sdkflags-only failures are
clang -Werror diagnostics that GCC 7 does not issue: -Wsometimes-uninitialized (pi_lfs.c,
read_fs.c), -Wuninitialized (ota.c, updater.c, CNN_BasicKernels_NE16.c), -Wformat
(malloc_internal.c) and -Wunsequenced (CNN_Copy.c). They matter for a drop-in -Werror build
through the wrapper, not for the P number.

REMAINING FAILURES IN P: 7 files (all of them also fail GAP9 GCC with the SDK -Werror)
--------------------------------------------------------------------------------------
Root-cause bucket for all 7: clang-only implicit-declaration error. C99 and later removed
implicit function declarations. Clang 20 makes -Wimplicit-function-declaration an error by
default; GCC 7 only warns. All 7 are SDK source bugs (a missing #include, or a trace macro
that is not defined in this configuration). All 7 compile with
-Wno-error=implicit-function-declaration (pe8lenient: 7/7 ok, 0 crashes). What is left after
that is only -Wint-conversion warnings from the implicit int return values. None of the 7
involves a builtin, fp16, vectors or the back end.

LINK READINESS (compile-only survey; not linked)
-------------------------------------------------
Method: llvm-nm -u on the 610 P objects, compared with llvm-nm --defined-only of GAP9 GCC's
lib/gcc/riscv32-unknown-elf/7.1.1/rv32imcxgap9/ilp32/libgcc.a (3056 symbols). Undefined
__* names that libgcc does not define were filtered down to compiler-runtime and builtin
names. SDK-internal __pi_*/__os_*/__cli_* symbols and linker-script symbols were ignored,
because the SDK's own sources and link script provide them.
35 of the 610 objects reference a symbol that neither GAP9 libgcc nor the SDK provides:
  32  __truncsfbf2 (float -> float16alt/bfloat16 conversion). GAP9 libgcc has only
      __truncdfohf2 / __extendohfdf2 (double <-> float16alt) and __truncdfhf2 /
      __extendhfdf2. There is no sf -> bf16 helper, because GCC does this conversion
      inline. Files: all 9 CNN_Libraries_fp16/*_fp16.c, all 9 CNN_Libraries_fp16x/*_f16a.c,
      CNN_Libraries/CNN_Copy.c, the DSP *f16a.c files (CmplxFunctionsf16a, PiecewiseMathf16a,
      FirBasicKernelsf16a, MatMulDSPf16a, DctLibraryf16a, DftLibraryf16a, FftLibraryf16a,
      MfccLibraryf16a, PreProcessingf16a), MatAddDSP.c, MatMulDSP.c, MatVectDSP.c and
      ISP_Libraries/ResizeBasicKernels.c. (M2a: 5 objects.) The objects will not link
      against the GAP9 toolchain until clang lowers f32 -> bf16 inline for xgap9, or a
      runtime provides __truncsfbf2.
   5  an undefined __builtin_pulp_* symbol, so the object compiles but emits a call to a
      builtin that does not exist. This is a silent false "ok":
        __builtin_pulp_v2hftov2hi   CNN_Libraries_fp16/CNN_Bias_Linear_Activation_fp16.c,
                                    CNN_Libraries_fp16x/CNN_Bias_Linear_Activation_f16.c, _f16a.c
        __builtin_pulp_v2hitov2hf_u DSP_Libraries/FastMathFunctions/PiecewiseMathf16.c, f16a.c
      Both names are in the 18 still-missing builtins. The call sites are the Cvt_v2h_v2s /
      Cvt_v2u_v2h macros in DSP_Libraries/FloatDefines.h, which reach the files through
      FastFloatApprox16.h. That header has `#pragma GCC diagnostic ignored
      "-Wimplicit-function-declaration"`, so clang is silent. The int result is then cast
      to a 4-byte vector, which is legal, so no later error appears either. The survey
      counts these 5 as ok (rc 0, no diagnostic). They compiled for the first time in M3
      (all 5 failed at M2a). Without these 5 false oks: 605/617.
   1  examples/gap9/libs/openmp/main.c references __kmpc_fork_call /
      __kmpc_for_static_init_4u / __kmpc_for_static_fini (the LLVM OpenMP runtime ABI).
      The SDK provides GCC's GOMP_* runtime, not __kmpc_*. This is not new: the M2a object
      has the same references.
(32 + 2 + 1 = 35 distinct objects: 3 of the 5 builtin objects also use __truncsfbf2; the 2
that do not are PiecewiseMathf16.c and CNN_Bias_Linear_Activation_f16.c.)
Link-clean against the GAP9 GCC toolchain's runtime: 610 - 35 = 575/617 objects (93.2%).

## The problem

Backlog B89 (P1): instruction selection loops forever on two adjacent 16-bit float loads followed by two stores when Xpulpv2 is enabled and Zhinx is not. Found in the SDK's `DftLibraryf16a.c` (`_DIT_DFT_MR`, 300 s timeout in "RISC-V DAG->DAG Pattern Instruction Selection"). Reproducers: benchmarks/sdk-compile-survey/hang-isel-f16-pair-xpulpv.c (`_Float16`), hang-isel-bf16-pair-xpulpv.c (`__bf16`), hang-isel-bf16-pair-xpulpv.ll. It hangs with `--target=riscv32-unknown-elf -march=rv32imc_zfinx_xpulpv2 -mabi=ilp32 -O2`; not without Xpulpv2, not at -O0, not with +zhinx for `_Float16`. Inherited from ref-18. Probable cause (unconfirmed): a DAG combine merges the pair into a v2i16/v2f16 load/store that the PULP packed-SIMD lowering (GPRAV2 register class, custom lowering in RISCVISelLowering.cpp) turns back into the original form, and the combiner repeats forever.

Confirm the loop with `-debug-only=isel,dagcombine` (a debug build of llc if needed, or `-print-after-all` bisection), find the two transformations that undo each other, cite the upstream commit that introduced the combine side if it is upstream, and fix it on the PULP side (e.g. make the PULP lowering not report v2f16/v2bf16 as legal/custom when there is no FP16 support, or make the combine's legality query answer consistently) following how upstream handles the same situation for its own packed types (P-extension / XCV SIMD code at llvmorg-20.1.8). The fix must not change code for integer packed SIMD (GAP9 sweep assembly byte-identical, including the SIMD kernels) and must keep float16 storage code correct: verify the reproducers compile quickly and give the right values on GVSoC against GCC (GCC uses its own float16 type; a byte-copy comparison of the loaded/stored values is enough). Note: another task (half-precision types, later) will build on this code — keep the change minimal and explain it.

## The problem

Backlog B81: in PULPFixupHwLoops.cpp (llvm/lib/Target/RISCV/PULP/) the block-offset bookkeeping uses `bool offsetIncrease`, so when the pass inserts padding/instructions it adds 1 to later block offsets instead of the real byte size. The offsets decide whether a loop's end label fits the short `lp.setupi`/`lp.setup` immediate ranges or needs the long form, so near the range limits the pass can pick a form whose immediate does not fit — the reviewer of 20/F013 found fuzz seed 6635 at -O3 fails with "fixup value out of range" on both int-20 and the F013 build, possibly this bug (tasks/20/F013.result.json and F013.review.json; fuzzer at benchmarks/hwloop-fuzz/). Read notes/20/F013.md first: F013 (landed today) restructured this pass (loop-end marker PseudoLOOPend, padding nops in their own block) — work on top of it. Note: PULPHardwareLoops.cpp is owned by another running task (20/F020): do not edit it.

Fix the bookkeeping to use real instruction sizes (getInstSizeInBytes, as upstream's branch relaxation and the Hexagon/ARM constant-island style passes do — cite the reference), make the range decision use the corrected offsets with the same margins the ISA immediates allow (lp.setupi end offset field width, lp.setup's; confirm widths in the fork's instruction definitions and GVSoC lp_setup_exec/lp_setupi_exec in pulp_v2.hpp:903-945), and make sure an out-of-range case falls back to a form that fits instead of failing. Build near-limit tests: loops whose body size straddles each immediate limit by -4/-2/0/+2/+4 bytes, with and without compressed instructions, nested, with padding; compare selected forms and run them on GVSoC against GCC (GCC's choices are a reference, not an oracle). Report seed 6635: fixed or a different cause.

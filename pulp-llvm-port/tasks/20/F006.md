## The problem

PERFORMANCE feature (owner request, 2026-09-27): enable PULP post-increment ("load-and-advance") loads and stores for 32-bit float data on Xpulpv2 targets that keep floats in integer registers (Zfinx), as GAP9 GCC already does. This is not a port break and not a crash fix; it is a missed optimisation inherited from the LLVM 18 fork.

Evidence (read benchmarks/gap9-sweep/runtime/runtime_report.md and the disassembly under benchmarks/gap9-sweep/runtime/build/{port20fix,gcc}/O2/k06_matvect_dsp_f32/kernel.dis): on the SDK kernel KerParMatVectDSP_f32 (k06) LLVM needs 32.7% more cycles than GAP9 GCC. GCC's inner loop uses four `p.lw rd, 0x8(rs!)` post-increment loads feeding fmadd.s; LLVM uses plain `lw` plus a separate `addi` per pointer. Cause (conductor-verified): llvm/lib/Target/RISCV/RISCVISelLowering.cpp restricts post-increment to integer types — `getIndexedAddressPartsPulp` (~line 21995: "Xpulp supports i8, i16, and i32 post-increments only") and the `setIndexedLoadAction/setIndexedStoreAction(ISD::POST_INC, ...)` list (~line 720: i8, i16, i32, v2i16, v4i8; no f32). Under Zfinx a float is 32 bits in a GPR, so `p.lw`/`p.sw` (and the register-offset forms if the fork supports them for i32) are valid for f32.

Wrinkle you must handle correctly: since LLVM 20 upstream keeps Zfinx f32 values in register class GPRF32 (X*_W sub-registers, upstream bc91f3cdd57c), while the fork's p.lw/p.sw instructions use GPR. Add the needed selection patterns/pseudos so post-increment f32 loads/stores produce/consume GPRF32 values correctly, following how upstream selects ordinary Zfinx loads/stores (e.g. LW_INX/SW_INX in RISCVInstrInfoF.td / RISCVInstrInfoZfinx at llvmorg-20.1.8) and how the fork/upstream CORE-V XCVmem post-increment patterns are written; cite file:line. Gate it on Xpulpv2 AND Zfinx (without Zfinx, floats live in F registers and p.lw cannot load them — leave that case unchanged). Consider f64 out of scope (rv32 Zdinx pairs) unless trivially safe; say what you did.

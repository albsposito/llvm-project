## The problem

Backlog B91: `__builtin_pulp_CoreCount()` is folded to a constant by GAP9 GCC (from `-mPE=8`, the number of cluster cores), and all 68 CNN kernel files use it in a static initializer (`static int ActiveCore = gap_ncore();` — find the wrapper in the SDK headers). With our clang it is a run-time call/CSR read, so those files fail with "initializer element is not a compile-time constant". Survey evidence: benchmarks/sdk-compile-survey/report.md ("GCC-only" bucket).

Find exactly what GCC does: which options exist (`-mPE=`, `-mFC=`, others), their defaults, what `__builtin_pulp_CoreCount()` returns with and without `-mPE`, whether any other builtin is folded from these options (e.g. cluster id / FC flags), and whether GCC treats the call as an integer constant expression or only folds it (test in a static initializer, in an array bound, in `_Static_assert`, in a `case` label, and at -O0). Then give clang the equivalent: a driver option spelled like GCC's (clang-driver cluster: Options.td / clang/lib/Driver) passed down to wherever the fork handles `__builtin_pulp_CoreCount`, so the builtin folds to that constant in exactly the contexts GCC accepts — clang needs the builtin to be evaluable as a constant for static initializers (clang/lib/AST/ExprConstant.cpp is an upstream file: if you must touch it, use an Upstream-File-Edit trailer and keep the hunk minimal, e.g. one PULP case in the builtin evaluator; look first for a fork-owned way). Without the option, behaviour must stay as today (run-time read). Unknown option values must be diagnosed the way GCC does. Document the chosen spelling and semantics in the change note for SDK users.

# 19/E007: replace removed StringRef::equals with == in the -mno-fdiv driver handling

## What upstream changed

Upstream LLVM deleted the `equals` method of `StringRef` (its string-view type) in `3fa409f2318e` "[ADT] Remove StringRef::equals (#98735)", after deprecating it in `de483ad51389` "[ADT] Deprecate StringRef::equals (#92351)". The replacement is the `==` operator, which compares two strings for exact equality. The fork's `-mno-fdiv` handling in the clang driver still called `feat.equals(...)`, so it stopped compiling.

## Why this is equivalent

The fork code removes any `+fdiv` / `-fdiv` target feature from the feature list when the user passes `-mno-fdiv`, then adds `+nofdiv`. Before, it tested each feature with `feat.equals("+fdiv")` and `feat.equals("-fdiv")`; now it tests `feat == "+fdiv"` and `feat == "-fdiv"`. At `llvmorg-19.1.7`, `operator==(StringRef, StringRef)` (`llvm/include/llvm/ADT/StringRef.h:866`) does the same length check plus byte comparison that the removed `equals` did, so the set of removed features is identical. Upstream made the same mechanical change across the driver in `135d92f90316` "[Driver] Use StringRef::operator== instead of StringRef::equals (NFC) (#91698)" (e.g. `ObjectMode.equals("64")` became `ObjectMode == "64"` in `clang/lib/Driver/Driver.cpp`). No vendor-extension (XCV) reference applies; this is a spelling change only.

## What breaks if this is wrong

If the comparison were wrong, `-mno-fdiv` would either leave a stray `-fdiv` feature (which LLVM would reject or misinterpret) or fail to add `+nofdiv`, so the compiler would keep emitting `fdiv.s`/`fsqrt.s` instructions for cores that lack them. `clang/test/Driver/riscv-arch.c` and `clang/test/Preprocessor/riscv-nofdiv.c` (both in the lit oracle) check the driver's feature output and the `nofdiv` macro and would fail.

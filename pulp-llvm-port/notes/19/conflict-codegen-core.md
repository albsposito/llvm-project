## Escalations (judgement calls; fork code kept as-is)

- ESCALATE 1 (`RISCVInstrInfo.cpp`, branch immediates): at 19, upstream's `RISCVCC::getBrCond(CC, Imm)` (from `f4d2f7a3b798`) returns `CV_BEQIMM`/`CV_BNEIMM` when the condition has an immediate operand. `insertBranch` and `reverseBranchCondition` use it, so a fork `P_BEQIMM`/`P_BNEIMM` branch that `analyzeBranch` parses (the fork's `getCondFromBranchOpc` cases) and later re-inserts (for example after branch folding) now comes back as `CV_BEQIMM`. `CV_BEQIMM` is predicated on `HasVendorXCVbi` and has a different encoding: `CVInstImmBranch<0b110>` vs the fork's `Pulp_Immediate_Branch<0b010>`. At 18, `getBrCond(CC)` had no immediate form and would have produced `BEQ` with an immediate operand, so this path may already have been broken or unreachable. Someone has to decide whether `getBrCond` needs a PULP branch (`Imm && STI.hasPULPExtV2() ? P_BEQIMM : CV_BEQIMM`, but `getBrCond` is a free function with no subtarget) or whether the fork's `getCondFromBranchOpc` cases should be tagged so that they round-trip. Not changed here. It is a build/test-phase decision and needs the `hwloop`/`branch` lit tests to confirm.
- ESCALATE 2 (`RISCVISelDAGToDAG.cpp`, `ISD::LOAD` order): I placed the fork's `tryPulpIndexedLoad` before upstream's XCVmem block. The reference for this choice is upstream's own XTHead-then-XCVmem order in the same case (`RISCVISelDAGToDAG.cpp`, `case ISD::LOAD`, int-19 tree around line 1632). If a target enabled both `xpulpv` and `xcvmem`, PULP opcodes would win. The same question exists in lowering: `getPostIndexedAddressParts` returns early for XCVmem before the fork's PULP path is reached, so with both enabled the XCVmem address rules apply. The two orders disagree, but it only matters if both extensions are enabled, and in practice they are exclusive.
- ESCALATE 3 (`RISCVISelLowering.cpp`, `CC_RISCV`): upstream's `RVVArgDispatcher` (`91dd844aa499`) precomputes one vector register per vector argument, in order, and is consumed by `getNextPhysReg()`. Its `constructArgInfos` also counts the PULP fixed-length v2i16/v4i8 arguments: it calls `getContainerForFixedLengthVector`, and the fork's hunk makes that return v4i8/v2i16. The fork path never calls `getNextPhysReg()` for those arguments. This is harmless when V is off (the plan is never used). If a target had both V and Xpulpv2, the dispatcher's index would drift and later RVV arguments would get the wrong register. The fork at 18 already sent every vector to GPRs when Xpulpv2 was on, so behaviour for PULP-only targets is unchanged. `CC_RISCV_FastCC` (`LocVT.isVector()` → `RVVDispatcher.getNextPhysReg()`) has no PULP case, which was already true at 18 in its `allocateRVVReg` form. A fastcc function with a v4i8 argument on Xpulpv2 would reach the dispatcher and get a V register. Check with the fork's packed-SIMD calling-convention tests in the build/test phase.

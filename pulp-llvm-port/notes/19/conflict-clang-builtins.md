## How the builtins were converted

- Layout follows upstream's vendor-builtin file at 20: `BuiltinsRISCVXCV.td` (`class RISCXCVBuiltin<prototype, features> : TargetBuiltin`, included from the end of `BuiltinsRISCV.td`, line 153 at `llvmorg-20.1.0`). The fork's class is `PULPBuiltin<prototype, features>` with `Spellings = ["__builtin_" # NAME]`. Def names are the builtin names without `__builtin_` (`pulp_mac`, `ssr_push`, `sdma_stat`, `bitinsert`), so every spelling, and every `RISCV::BI__builtin_*` ID used by Sema/CodeGen, is exactly what it was.
- Attributes: `"nc"` became `[NoThrow, Const]`, `"n"` became `[NoThrow]` (grouped with `let Attributes = ... in { }` blocks, as upstream does). Feature guards are copied unchanged (`"xssr"`, `"xdma"`, `"xpulpv"`). Order and section comments kept, including the `// NOTE: normal builtin in GCC` comment on `bitinsert`.
- Prototypes: converted by a script, and each one was checked by re-running the conversion backwards with a copy of the emitter's parser. For every non-vector prototype the regenerated type string is the same byte for byte as the old `.def` string, including modifier order (e.g. `UIi` is written `unsigned _Constant int`, `IUi` is written `_Constant unsigned int`, `ULLi` is written `unsigned long long int`).
- Vector prototypes (`V2s`, `V4c`, GCC `vector_size` vectors) are written `_Vector<2, short>` / `_Vector<4, char>`, which the emitter turns into `V2s` / `V4c`. 24 builtins (`dotup*`, `dotusp*`, `sdotup*`, `sdotusp*`, `avgu*`, `maxu*`, `minu*`, `srl*`) had a `U` in front of a vector *parameter* (`UV2s`). The emitter cannot parse `unsigned _Vector<2, short>` as a parameter (it splits parameters at the comma inside `<2, short>`), so those parameters are written `_Vector<2, short>` and the generated string loses the `U` (`UiUV2sUV2s` becomes `UiV2sV2s`). This does not change the type: clang's `DecodeTypeFromStr` (`clang/lib/AST/ASTContext.cpp`, `case 'V'`) ignores a `U` in front of `V` and decodes the element type on its own, so `UV2s` and `V2s` were already the same signed-short vector at 18. Where the `U` is in front of a *return* vector (`maxu2`, `minu2`, `srl2`, ...), `unsigned _Vector<...>` parses fine and the string keeps its `U` exactly. (Side observation, not changed: this means the fork's "unsigned" vector builtins have always taken and returned signed-element vectors.)

## ESCALATE

- ESCALATE: the 19.1.7 builtins emitter only knows `_ExtVector<N, T>` (Clang ext_vector, mangled `E`). Support for `_Vector<N, T>` (GCC vector, mangled `V`, the type the fork's 18 builtins use) was added upstream in `508263824f4e` "[Clang] Start moving X86Builtins.def to X86Builtins.td (#106005)", which is in 20, not 19. As written, `BuiltinsRISCVXpulp.td` will fail TableGen at 19 on the 64 vector builtins ("Unknown Type: _Vector<2, short>"). Two options: (a) backport that commit's three-line parser hunk into `clang/utils/TableGen/ClangBuiltinsEmitter.cpp` (an upstream file the fork does not touch: needs `Upstream-File-Edit:`; the hunk disappears at step 20 because upstream has it); or (b) write the vectors as `_ExtVector<N, T>`. That changes the builtins' vector types from GCC vectors to ext_vectors, which changes behaviour for user code (different type, different conversion rules), so I did not do it. Recommendation: (a). The decision belongs to the build-fix phase / owner; the pick keeps the exact fork types.

# 19/E006: teach the Mempool scheduling model about the scheduling classes upstream added in LLVM 19

Written for a reader who does not know LLVM. Four sections, all required (policy_check.py checks the headings).

## What upstream changed

A scheduling model tells the compiler how long each kind of instruction takes on a given core. Every instruction is tagged with a "scheduling class", and every model that gives timing for some classes must say something about every class: either give it a cost or declare it unsupported. Between LLVM 18 and 19 upstream added new classes, and llvm-tblgen now stops with `RISCVSchedMempool.td:15: Processor does not define resources for WriteVAESMVV_M1`, because the fork's Mempool model predates them. The new classes, by upstream commit:

- `56b8bd77445f` [RISCV] Add Sched classes for vector crypto instructions (#90068): all `WriteV*` Zvk* classes (first error, `WriteVAESMVV_M1`).
- `6da1966bc503` [RISCV] Add scheduling information for SiFive VCIX (#86093): the `WriteVC_*` classes (next error, `WriteVC_FPR16VV_M1`).
- `89f87c387627` [RISCV][MC] Add MC layer support for the experimental zabha extension (#80005): `WriteAtomicB`/`WriteAtomicH` and their reads (next error, `WriteAtomicB`).
- `a0c7714525b6` [RISCV] Split div vs rem scheduling information [nfc] (#84385): the old `WriteIDiv` class, used by both divide and remainder, was split so that `REM`/`REMU` now use a new `WriteIRem` class (and `WriteIRem32`/`ReadIRem`/`ReadIRem32` for RV64) (last error, `WriteIRem`).

These were found one at a time (llvm-tblgen stops at the first) on a scratch copy; after all four were handled `-gen-subtarget` passes. The Snitch model (`RISCVSchedSnitch.td`) defines no timing at all, so it is not affected and is unchanged.

## Why this is equivalent

- Vector crypto, SiFive VCIX and Zabha: Mempool cores implement none of these extensions (the model already lists the vector extension as unsupported). The fork now adds `defm : UnsupportedSchedZabha;`, `defm : UnsupportedSchedXsfvcp;` and `defm : UnsupportedSchedZvk;`, exactly the three lines upstream added to its own in-order Rocket model for the same commits (`llvm/lib/Target/RISCV/RISCVSchedRocket.td:254,264,265` at `llvmorg-19.1.7`; same in `RISCVSchedSyntacoreSCR1.td:112,121,122`). No Mempool instruction uses these classes, so nothing it compiles changes.
- Divide vs remainder: this is not a new extension but an existing class being split, so marking `WriteIRem` unsupported would have *changed* behaviour (at 18, `REM` on Mempool was costed as a 16-cycle divide; unsupported would make it fall back to a default cost). Instead the fork does what upstream's own NFC split commit did for every existing model: give `WriteIRem` the same resources and latency as `WriteIDiv` (Mempool: 16 cycles, divider busy 14), mark `WriteIRem32` unsupported next to the already-unsupported `WriteIDiv32` (Mempool is RV32 only), and add `ReadAdvance<ReadIRem/ReadIRem32, 0>` next to the existing `ReadIDiv` entries. Reference: `llvm/lib/Target/RISCV/RISCVSchedSyntacoreSCR1.td:59-62` at `llvmorg-19.1.7` (`WriteIRem*` share the `WriteIDiv*` block) and `RISCVSchedRocket.td` in `a0c7714525b6`. Verified in the generated tables (scratch copy, `logs/19-E006.scratch-tblgen.log`): in `MempoolModelSchedClasses` the `WriteIDiv_ReadIDiv_ReadIDiv` and `WriteIRem_ReadIRem_ReadIRem` entries are identical (`7, 2, 34, 1, 1, 2`), so `REM` is scheduled exactly as at 18.

No existing Mempool entry's latency or resources was changed.

## What breaks if this is wrong

If the `WriteIRem` copy were wrong, `-mcpu=mempool-rv32` code containing `%` (remainder) would be scheduled differently: the instruction order around `rem`/`remu` in llc output would change versus LLVM 18, visible in any fork CodeGen test that checks Mempool code with remainders, or as a cycle-count change in a Mempool benchmark that uses modulo in hot loops. If one of the unsupported lines were missing, llvm-tblgen would fail and nothing would build. No fork test is known to check Mempool scheduling of `rem` specifically; that is a missing test.

# 19/E005: rename the fork's `powerOf2Minus1` and `trailing1sPlus1` to `powerOf2Minus1_pulp` and `trailing1sPlus1_pulp` so they no longer collide with upstream's XCValu helpers

Written for a reader who does not know LLVM.

## What upstream changed

Upstream commit `56f0ecd6db92` "[RISCV] Implement Intrinsics Support for XCValu Extension in CV32E40P (#85603)" added instruction-selection patterns for the CORE-V `cv.clip`/`cv.clipu` intrinsics. To do that it defined two helper records in `RISCVInstrInfoXCV.td:719-720`: `powerOf2Minus1` (matches a constant of the form 2^n - 1) and `trailing1sPlus1` (turns that constant into n + 1, the operand the clip instruction encodes). The PULP fork already had helpers with the same two names in `RISCVInstrInfoXpulp.td` for its own `p.clip`/`p.clipu`. TableGen stopped with `def already exists: powerOf2Minus1`, and after that with `def already exists: trailing1sPlus1`.

## Why this is equivalent

The fork's two records keep their definitions exactly as they were. Only the names change, in `RISCVInstrInfoXpulp.td` (2 definitions, 7 uses, all in that file):

- `powerOf2Minus1` becomes `powerOf2Minus1_pulp`. It is used by the `P_CLIP`/`P_CLIPU` patterns on the fork's `clip`/`betweenu` fragments and on `int_riscv_pulp_clip`/`int_riscv_pulp_clipu`.
- `trailing1sPlus1` becomes `trailing1sPlus1_pulp`. It is used by the same `P_CLIP`/`P_CLIPU` patterns.

A search of `llvm/`, `clang/` and `lld/` finds no other use of these names outside `RISCVInstrInfoXpulp.td` and upstream's `RISCVInstrInfoXCV.td`. Upstream's file is untouched.

The fork's copies and upstream's copies are **not equivalent**, so reusing upstream's is not an option:

- The fork's `powerOf2Minus1` is a `TImmLeaf`, which matches only "target constants". Those are the immediate operands of the `llvm.riscv.pulp.clip*` intrinsics and the fork's `clip`/`betweenu` fragments. Upstream's is an `ImmLeaf`, which matches ordinary constants. With upstream's record, the fork's intrinsic patterns would stop matching and `p.clip`/`p.clipu` would no longer be selected from the builtins.
- The fork's `trailing1sPlus1` counts trailing ones in the sign-extended value truncated to 32 bits (`countr_one<uint32_t>(N->getSExtValue())`). Upstream's counts them in the zero-extended 64-bit value (`countr_one(N->getZExtValue())`). Both give the same answer for the constants these patterns accept on RV32, but they are different code.

I checked the result with `llvm-tblgen -gen-dag-isel` on a scratch copy that also had E003's `uimm6_lsb0` rename (not part of this commit). It prints two separate predicates and transforms: `Predicate_powerOf2Minus1_pulp` + `trailing1sPlus1_pulp` on `timm` operands, under `hasPULPExtV2()` for `P_CLIP`/`P_CLIPU`, and upstream's `Predicate_powerOf2Minus1` + `trailing1sPlus1` on `imm` operands, under `hasVendorXCValu()` for `CV_CLIP`/`CV_CLIPU`.

**Completeness of this task.** After these two renames, plus E003's rename applied locally for testing only, no `def already exists` error is left. I ran every TableGen backend that `RISCVCommonTableGen` uses (asm-matcher, asm-writer, compress-inst, macro-fusion, dag-isel, disassembler, instr-info, emitter, pseudo-lowering, register-bank, register-info, searchable-tables, subtarget, global-isel, the three GlobalISel combiners, and riscv-target-def) on a scratch copy. The only error left is a different problem, `RISCVSchedMempool.td:15: Processor does not define resources for WriteVAESMVV_M1` (the Mempool scheduling model misses resources for scheduling classes added upstream), and it is not part of this task.

Following upstream's own vendor code, vendor-private records get a vendor-marked name instead of a generic one. CORE-V does this with `cv_tuimm2`, `cv_tuimm5`, `cv_uimm10` and `CV_LO5`/`CV_HI5` next to these helpers in `llvm/lib/Target/RISCV/RISCVInstrInfoXCV.td:705-717` at `llvmorg-19.1.7`. E003 used the same `_pulp` suffix for `uimm6_lsb0_pulp`.

## What breaks if this is wrong

If a use were missed, TableGen would fail outright with an unknown-def error, so a missed rename cannot build silently. If the fork's patterns were wrongly pointed at upstream's records, `p.clip`/`p.clipu` would stop being selected. The fork's builtin/intrinsic tests for clip would show it, because the output would contain a compare/select sequence (or a selection failure) instead of `p.clip`/`p.clipu`. Those are `llvm/test/CodeGen/RISCV/intrinsics/xpulpv.ll` and `clang/test/CodeGen/RISCV/riscv-xpulpv2-intrinsics.c`. If upstream's records had been changed, the XCValu test `llvm/test/CodeGen/RISCV/xcvalu.ll` (`cv.clip`/`cv.clipu`) would show it.

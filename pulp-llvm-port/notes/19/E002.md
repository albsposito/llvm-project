# 19/E002: teach the 19.1.7 builtins generator the `_Vector<N, T>` type (backport of 508263824f4e)

## What upstream changed

`a8d4a024e6be` "[Clang][RISCV] Refactor builtins to TableGen" deleted `BuiltinsRISCV.def` at 19, so the fork's builtins were rewritten as TableGen records in `clang/include/clang/Basic/BuiltinsRISCVXpulp.td` (see `notes/19/conflict-clang-builtins.md`). Those records are turned back into the old type strings by `clang/utils/TableGen/ClangBuiltinsEmitter.cpp`. At 19 that generator only understands Clang "extended" vectors, written `_ExtVector<N, T>` (added by `9b672de99760` "[clang][Builtins] Parse clang extended vectors types. (#83584)"). The fork's 64 SIMD builtins use GCC-style vectors (`V2s`, `V4c`), written `_Vector<N, T>`, which the generator only learned in LLVM 20 (`508263824f4e` "[Clang] Start moving X86Builtins.def to X86Builtins.td (#106005)"). So TableGen stopped with `Unknown Type: _Vector<2, short>`.

## Why this is equivalent

This change copies, unchanged, the emitter hunk of `508263824f4e` (three edits: treat `_Vector<` like `_ExtVector<` when splitting parameters at commas, accept `_Vector` as a type keyword, and emit `V<N>` instead of `E<N>` for it). It does not change how any existing `_ExtVector` or scalar type is generated. With it, the generated `BuiltinsRISCV.inc` holds exactly the fork's LLVM 18 builtin table: I compared all 174 fork builtins (`__builtin_pulp_*`, `__builtin_ssr_*`, `__builtin_sdma_*`, `__builtin_bitinsert`) against `BuiltinsRISCV.def` at the fork head `6547028f925c`. All 174 are present with identical attributes and feature strings; 150 type strings are byte-identical (including all 40 vector builtins without a `U` on a vector parameter, e.g. `__builtin_pulp_add4` = `V4cV4cV4c`), and the other 24 differ only by the already documented `U` dropped in front of a vector *parameter* (`UiUV2sUV2s` becomes `UiV2sV2s`), which clang's type decoder ignores anyway (`ASTContext.cpp` `DecodeTypeFromStr`, `case 'V'`). A `U` in front of a vector *return* type is kept (`__builtin_pulp_maxu2` = `UV2sV2sV2s`). The alternative, writing the vectors as `_ExtVector`, was rejected by the conductor because it would change the builtins' types. Upstream reference for this exact code: the same lines at `llvmorg-20.1.0`, `clang/utils/TableGen/ClangBuiltinsEmitter.cpp:181-190`. The edit disappears at step 20, where upstream already has it.

## What breaks if this is wrong

If the generator emitted a wrong vector code (for example `E` instead of `V`), the PULP SIMD builtins would take Clang ext_vector types instead of GCC vectors: user code passing `v2s`/`v4s` typedef'd vectors (`__attribute__((vector_size))`) to `__builtin_pulp_add4`, `__builtin_pulp_dotsp2`, etc. would be rejected or implicitly converted, and `clang/test/CodeGen/RISCV` PULP SIMD builtin tests would fail at Sema. If it dropped lanes, the tests would fail with type mismatch errors. Nothing else in clang uses `_Vector` at 19, so no upstream builtin can change.

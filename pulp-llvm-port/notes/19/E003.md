# 19/E003: rename the fork's `uimm6_lsb0` operand to `uimm6_lsb0_pulp` so it no longer collides with upstream's Xwchc operand

Written for a reader who does not know LLVM.

## What upstream changed

Upstream commit `3c5f929ad093` "[RISCV] Add QingKe "XW" compressed opcode extension (#97925)" added support for WCH's Xwchc instructions. It defined a new TableGen operand named `uimm6_lsb0` (`RISCVInstrInfoXwch.td:62`) and the matching assembler check `RISCVOperand::isUImm6Lsb0()` in `RISCVAsmParser.cpp`. The PULP fork already had its own operand and assembler check with exactly those names, so TableGen stopped with `def already exists: uimm6_lsb0` (and the C++ would have had two functions with the same name).

## Why this is equivalent

The two operands only share a name; they are not the same thing. Upstream's accepts only a constant, encodes it as-is and decodes 6 bits. The fork's accepts a constant or a bare symbol (a label), encodes it shifted right by one (`getImmOpValueAsr1`) and decodes 13 bits. Merging them would change the Xwchc instructions, so instead the fork's copy gets a fork-private name, and upstream's stays exactly as upstream wrote it:

- `RISCVInstrInfoXpulp.td`: `def uimm6_lsb0` becomes `def uimm6_lsb0_pulp`, and its assembler class `UImmAsmOperand<6, "Lsb0">` becomes `UImmAsmOperand<6, "Lsb0Pulp">`. The class is now called `UImm6Lsb0Pulp`, its check is `isUImm6Lsb0Pulp`, and its diagnostic is `Match_InvalidUImm6Lsb0Pulp`. Nothing else in the definition changes (same predicate, encoder, decoder, and MC operand predicate).
- `RISCVAsmParser.cpp` (mc cluster, separate commit): the fork's `isUImm6Lsb0()` is renamed `isUImm6Lsb0Pulp()`, and its body is unchanged. Upstream's `isUImm6Lsb0()` is not touched.

No instruction in the fork uses this operand, at 18 (`6547028f925c`, checked with `git grep`) or at the step-19 integration head, so no instruction's encoding, parsing or selection can change. The name changes in exactly three places, and a search of `llvm/`, `clang/` and `lld/` finds no other use. I ran `llvm-tblgen -gen-asm-matcher` on a scratch copy of the `.td` files, with the unrelated `powerOf2Minus1`/`trailing1sPlus1` collisions masked. The output has two separate match classes: `MCK_UImm6Lsb0`, which calls upstream's `isUImm6Lsb0()` and is used by `qk.c.lhu`/`qk.c.sh`, and `MCK_UImm6Lsb0Pulp`, which calls the fork's `isUImm6Lsb0Pulp()`.

Following upstream's own vendor code, vendor-private operands get a vendor-marked name instead of reusing a generic one. CORE-V does this with `CVrrAsmOperand`/`CVrr` in `llvm/lib/Target/RISCV/RISCVInstrInfoXCV.td:509,515` at `llvmorg-19.1.7`.

## What breaks if this is wrong

If the rename missed a place, TableGen or the `LLVMRISCVAsmParser` build fails outright, with an unknown def or a missing `isUImm6Lsb0Pulp` member. If upstream's operand had been changed instead, the Xwchc tests would show it: `llvm/test/MC/RISCV/xwchc-*.s` (the `qk.c.lhu`/`qk.c.sh` offset range and its error message). No fork test uses the fork's operand, because no fork instruction uses it. A PULP instruction that used it later would rely on it taking symbols and shifting the value by one, and no test covers that today.

# 19/E004: declare the 21 smallfloat extensions as RISCVExtension so -march accepts them again

## What upstream changed

Up to LLVM 18, the list of RISC-V extension names that `-march=` accepts (and the version of each) was a hand-written table in `llvm/lib/Support/RISCVISAInfo.cpp`; the fork added 27 rows to it, among them the 21 smallfloat extensions `xfalthalf` ... `xfexpauxvecaltquarter`, all version 0.1. Upstream commit `80628ee0d555` "[RISCV] Generate RISCVISAInfo table from RISCVFeatures.td. (#89955)" deleted that table: TableGen now generates it from every record of the class `RISCVExtension` (introduced by `a6c028299cbc` "[RISCV] Add extension information to RISCVFeatures.td. NFC (#89326)"). A feature declared as a plain `SubtargetFeature` is invisible to the generated table, so the smallfloat names would be rejected by `-march` and missing from the `snitch` CPU's default ISA string.

## Why this is equivalent

Before: each smallfloat extension was declared twice, once as a `SubtargetFeature<"xf...", "HasExtXf...", "true", desc>` in `llvm/lib/Target/RISCV/RISCVInstrInfoXsmallfloatGen.td` (what the backend sees) and once as a row `{"xf...", {0, 1}}` in the old ISAInfo table (what the driver/`-march` parser sees). Now the 21 definitions are `RISCVExtension<"xf...", 0, 1, desc>`, which is a subclass of `SubtargetFeature`: same record name, same feature string, same description, no implied features (as before), and the same subtarget field name, because `RISCVExtension`'s default field name is the record name with `Feature` replaced by `Has` (`FeatureExtXfalthalf` -> `HasExtXfalthalf`, exactly the old explicit value). So the `Has*` predicates, `RISCVSubtarget` accessors and all instruction definitions are untouched, and the version 0.1 now comes from the record instead of the deleted table. This follows the CORE-V declarations (`FeatureVendorXCVbitmanip` and siblings, `llvm/lib/Target/RISCV/RISCVFeatures.td:1207-1262` at `llvmorg-19.1.7`) and how the registration pick converted the fork's `xpulpv`/`xfrep`/`xdma`/`xssr`/`xmempool` in `RISCVFeatures.td`.

`RISCVInstrInfoXsmallfloatGen.td` says it was "Automatically generated by parse_opcodes (noah95/riscv-opcodes)". That generator is not in the fork, so it cannot be regenerated here; the 21 definitions were edited by hand (mechanical substitution, checked by script that every record name/field name pair matched the default rule). If the file is ever regenerated, the generator must emit `RISCVExtension<"name", 0, 1, desc>` for the feature lines, or this defect comes back.

Verification: the real build of `RISCVTargetParserTableGen`/`RISCVCommonTableGen` still stops on an unrelated duplicate definition (`uimm6_lsb0`, a separate task), so I ran `llvm-min-tblgen -gen-riscv-target-def` on a scratch copy of the RISCV .td files with only that collision renamed. Before this change the generated extension table held 1 `xf*` row (`xfrep`); after it holds all 21 smallfloat names at 0.1 plus `xfrep`, and the `snitch` CPU's default march grows from `rv32m2p0_a2p1_f2p2_d2p2_zfh1p0_xdma0p1_xfrep0p1_xssr0p1` to also include all 21 `xf*0p1`, matching what the CPU's feature list says. `llc -mattr=+xfalthalf` could not be tried because `llc` does not build yet (other clusters' errors).

## What breaks if this is wrong

`clang -march=rv32imf_xfalthalf...` would fail with "unsupported non-standard user-level extension"; the `snitch` CPU (`-mcpu=snitch`) would silently lose all smallfloat instructions in its default ISA string, so smallfloat code would stop assembling/compiling for it; and the `RiscvExtensionsHelp`/`PrintSupportedExtensions` expectations in `llvm/unittests/TargetParser/RISCVISAInfoTest.cpp` (the fork's relocated `xf*` rows) would not match. If a field name had changed, the build would fail in `RISCVSubtarget` at the `hasExtXf*()` accessors.

# 19/E009: ask for the loop and dominator analyses through their new "wrapper pass" names

## What upstream changed

At 19 upstream began moving machine-code analyses to the new pass manager. `837dc542b151` "[CodeGen][NewPM] Split `MachineDominatorTree` into a concrete analysis result (#94571)" turned `MachineDominatorTree` into a plain result object and moved the old pass role into a new class `MachineDominatorTreeWrapperPass`, which hands the tree out through `getDomTree()`. `79d0de2ac37b` "[CodeGen][NewPM] Port `machine-loops` to new pass manager (#97793)" did the same for `MachineLoopInfo`, whose pass role moved to `MachineLoopInfoWrapperPass` with the accessor `getLI()`. Because the old names are no longer passes, they have no pass `ID` and no `initialize...Pass` function, which is what the four build errors (E002, E003, E005, E006) report.

## Why this is equivalent

Three fork passes asked the pass manager for these analyses by the old names: `PULPHardwareLoops.cpp` (loop info and dominator tree), `PULPFixupHwLoops.cpp` (loop info) and `SNITCHFrepLoops.cpp` (loop info and dominator tree). Each request is renamed to the wrapper pass: `addRequired<X>()` becomes `addRequired<XWrapperPass>()`, `INITIALIZE_PASS_DEPENDENCY(X)` becomes `INITIALIZE_PASS_DEPENDENCY(XWrapperPass)`, and `getAnalysis<X>()` becomes `getAnalysis<XWrapperPass>().getLI()` / `.getDomTree()`. The wrapper runs the same analysis code as the old pass did and returns the very same `MachineLoopInfo` / `MachineDominatorTree` object, so the pointers the fork passes store (`MLI`, `MDT`) point to identical data and every later use is untouched. The pass order is also unchanged, because the pass manager schedules the wrapper where it used to schedule the old pass. This is exactly the edit upstream made in the same commits to `HexagonHardwareLoops.cpp`, the pass `PULPHardwareLoops.cpp` was derived from: `llvm/lib/Target/Hexagon/HexagonHardwareLoops.cpp:121-122` (`addRequired`), `:371-372` (`INITIALIZE_PASS_DEPENDENCY`) and `:387-389` (`getAnalysis<...WrapperPass>().getLI()` / `.getDomTree()`) at `llvmorg-19.1.7`. CORE-V has no machine passes, so Hexagon is the closest reference.

## What breaks if this is wrong

If a wrapper were not registered as a dependency, `llc` would abort at pass-pipeline setup with "Unable to schedule" or an unregistered-pass assertion whenever the PULP hardware-loop or Snitch FREP pass runs; if the wrong analysis were fetched, the passes would stop recognising loops and emit no `lp.setup`/`lp.counti` (PULP) or `frep` (Snitch) instructions. `llvm/test/CodeGen/RISCV/xpulp-hwloop.ll`, `freploop.ll` and `freploop-nested.ll` check those instructions and would fail; the `O0/O3-pipeline.ll` tests would show a changed pass list.

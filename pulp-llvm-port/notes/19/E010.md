# 19/E010: follow the move of LowLevelType.h to llvm/CodeGenTypes

Written for a reader who does not know LLVM.

## What upstream changed

Upstream commit `184ca39529a9` "[llvm] Move CodeGenTypes library to its own directory (#79444)" moved the headers of the small CodeGenTypes library (low-level types, machine value types) out of `llvm/include/llvm/CodeGen/` into a new directory `llvm/include/llvm/CodeGenTypes/`. The file `llvm/CodeGen/LowLevelType.h` was renamed to `llvm/CodeGenTypes/LowLevelType.h` (99% similarity, the content is unchanged; the commit says "No behavior change"). No forwarding header was left behind, so every `#include` of the old path stops compiling.

## Why this is equivalent

Two fork files, `RISCVExpandSDMAInsts.cpp` (line 23) and `RISCVExpandSSRInsts.cpp` (line 57), included the header by its old path. The change only rewrites those two `#include` lines to the new path. The header they now pull in is the same file with the same declarations, so the compiled code of the SSR and SDMA expansion passes is identical. Upstream updated its own users the same way in the same commit, for example `llvm/lib/Target/ARM/ARMCallLowering.cpp:36` at `llvmorg-19.1.7` (`#include "llvm/CodeGenTypes/LowLevelType.h"`).

## What breaks if this is wrong

If the include pointed at a different header, the two files would fail to compile (a build error, not a silent change), because nothing else provides that header. There is no way for this edit to change generated code; the SSR/SDMA lit tests `llvm/test/CodeGen/RISCV/{ssr-pseudo-instructions.mir,ssr-register-merging.mir,ssr-register-reserving.ll,sdma-intrinsics.ll,sdma-pseudo-instructions.mir}` would still catch any change in the expansion passes' output.

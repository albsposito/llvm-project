# 19/E011: pass the register-info argument explicitly to `readsRegister` in the hardware-loop fixup pass

## What upstream changed

Upstream commit `f6d431f208c0` "[CodeGen] Make the parameter TRI required in some functions. (#85968)" removed the default value (`= nullptr`) of the second parameter, `const TargetRegisterInfo *TRI`, of `MachineInstr::readsRegister` and eight sibling helpers (`killsRegister`, `definesRegister`, `modifiesRegister`, ...) in `llvm/include/llvm/CodeGen/MachineInstr.h`. Callers must now say explicitly whether they want sub/super-register aliasing checked (pass a `TRI`) or not (pass `nullptr`). The fork's `PULPFixupHwLoops.cpp` still called `MI.readsRegister(bumpReg)` with one argument, so it stopped compiling ("too few arguments to function call, expected 2, have 1").

## Why this is equivalent

Before: `MI.readsRegister(bumpReg)`, which at LLVM 18 meant `MI.readsRegister(bumpReg, nullptr)` through the default argument. Now: `MI.readsRegister(bumpReg, /*TRI=*/nullptr)`. The value passed is identical, so the function computes exactly the same thing: whether the instruction reads exactly `bumpReg` (the loop counter/bump register), without alias expansion. This also matches the very next line of the fork code, `MI.modifiesRegister(bumpReg, nullptr)`, which already passed `nullptr` explicitly. It is the same mechanical change upstream applied to all its own callers in that commit, including RISC-V ones: `llvm/lib/Target/RISCV/RISCVISelLowering.cpp` (`MI.readsRegister(RISCV::FRM, /*TRI=*/nullptr)`) and `llvm/lib/Target/RISCV/RISCVInsertReadWriteCSR.cpp`, and the Hexagon code (e.g. `HexagonExpandCondsets.cpp`, `HexagonInstrInfo.cpp`) next to the Hexagon hardware loop pass the PULP passes derive from. No CORE-V reference applies (this is a generic CodeGen API change, not an extension feature).

## What breaks if this is wrong

The call decides whether the pass may delete the loop's counter ("bump") update after converting a loop into a PULP hardware loop (`lp.setup`): if the register is read after the loop before being rewritten, the update must stay. If the check were wrong (for example if it stopped seeing reads), the pass would delete a counter update that later code still reads, and programs using a loop counter after a hardware loop would compute wrong values; `llvm/test/CodeGen/RISCV/xpulp-hwloop.ll` would show extra or missing `addi` instructions around `lp.setup`. Because the argument value is unchanged, no output change is expected. If the fix were missing, `LLVMRISCVCodeGen` (and therefore `llc`/`clang`) does not build.

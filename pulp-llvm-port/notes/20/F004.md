# 20/F004: stop the RISC-V cost model from treating Xpulpv2 packed vectors as RVV vectors

Written for a reader who does not know LLVM. This is a pre-existing fork defect (present in ref-18, step 19 and step 20), not a port break; owner decision 2026-09-27 authorises fixing it.

## What upstream changed

Nothing upstream broke this. The defect comes from the fork: commit `f1b7aebff8c2` (Federico Ficarelli, 2022-08-25, "[LLVM/PULP/SNITCH] Support for PULP and Snitch cores/platforms") made the packed types `v2i16` and `v4i8` legal in general-purpose registers when Xpulpv2 is enabled (`RISCVISelLowering.cpp`, `addRegisterClass(MVT::v2i16, &RISCV::GPRAV2RegClass)`). The upstream RISC-V cost model (`RISCVTargetTransformInfo.cpp`) assumes that any legal vector type is an RVV (V extension) vector, and asks for the RVV register length, which asserts "Tried to get vector length without Zve or V extension support!" when V is off. Upstream later hit the same assumption itself and fixed it, first for "a private extension which also uses the vector type" (`6d516c6e28a1`, LLVM 22) and then for the ratified P extension, which, like Xpulpv2, keeps packed SIMD values in GPRs (`dfdc69b4c27d`, `4540415f19d9`, LLVM 22/23).

Call chain seen on `FirBasicKernelsFix.c` at -O3, function `KerFirSeq`: SimpleLoopUnswitch (non-trivial unswitching, which only runs at -O3) -> `TargetTransformInfo::getInstructionCost` -> `RISCVTTIImpl::getMemoryOpCost` -> `RISCVTargetLowering::getLMULCost` -> `RISCVSubtarget::getMinRVVVectorSizeInBits` (assert). A small IR sample (`logs/20-F004.cost.ll`) with `opt -passes='print<cost-model>'` showed three more entry points with the same defect: `getVectorInstrCost` (insert/extract element), `getScalarizationOverhead` and `getShuffleCost`.

## Why this is equivalent

Before: any cost query on a `<2 x i16>`/`<4 x i8>` load, store, insert/extract element, shuffle or build-vector crashed the compiler (assertions build) or read an undefined RVV length (release build). After: those queries no longer take the RVV-only route.

- `getMemoryOpCost`: the RVV "LMUL" multiplier is applied only when V is present, exactly upstream `6d516c6e28a1`. Loads/stores of the packed types now cost 1 (one `p.lw`/`p.sw`), as for a 32-bit scalar.
- `getShuffleCost`, `getScalarizationOverhead`, `getVectorInstrCost`: with Xpulpv2 and a fixed-length vector type, return cost 1 before the RVV analysis, the same guard and value upstream uses for the P extension (`llvm/lib/Target/RISCV/RISCVTargetTransformInfo.cpp:693, 1020, 2547` at `llvmorg-23.1.0`, predicate `ST->hasStdExtP()`; here `ST->hasPULPExtV2()`, the predicate that makes the types legal). This is one instruction for Xpulpv2 (`pv.extract.h`, `pv.insert.b`, `pv.shuffle2.h`, `pv.pack`), so it is a reasonable first model; upstream marks it TODO for a finer model, as does this change.
- `getCastInstrCost` is **not** changed: upstream guards it too, but in this fork it already falls back to the generic model when V is absent and does not crash, so leaving it keeps cast costs identical to before (sext `<4 x i8>`->`<4 x i16>` = 3, trunc = 0).

Nothing changes for targets with V (the new checks are false there) or for targets without Xpulpv2. No code generation logic is touched; only the cost numbers that optimisation passes use to decide whether a transform pays off.

Costs after the fix (throughput, `opt -mattr=+xpulpv,+zfinx -passes='print<cost-model>'`, full output in `logs/20-F004.verify.log`): load/store v2i16/v4i8 = 1; add/sub/and/shl/smax/abs = 1; mul v2i16 = 5 (expanded to scalar); icmp = 1; select = 3; extract/insert element = 1; shuffles = 1; reduce.add v2i16 = 3; bitcast = 1. Before the fix every one of these queries asserted on the first load.

## What breaks if this is wrong

If the guard is missing, `-O3` compiles of GAP9 DSP kernels that use packed vectors (`FirBasicKernelsFix.c`, the sweep's `k01_fir_fix16.c` and `k05_matmul_dsp_fix16.c`) crash in SimpleLoopUnswitch with the getMinRVVVectorSizeInBits assertion, and any IR pass that costs a packed-vector instruction (SLP/loop vectoriser, unroll, inliner, SimplifyCFG speculation) can crash the same way. If the cost values are poorly chosen, the symptom is performance only: loops unswitched or unrolled more or less than GCC would, visible in the gap9-sweep instruction counts, not in correctness. No existing lit test covers cost queries on Xpulpv2 types (the fork tests all pass before and after); a regression test is proposed in the result file, not added (task rule).

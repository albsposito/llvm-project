# 20/E007: merge the fork's Xpulpv2 post-increment preference into upstream's new getPreferredAddressingMode

## What upstream changed

Upstream commit `f590963db836` "[RISCV] Implement RISCVTTIImpl::getPreferredAddressingMode for HasVendorXCVmem (#120533)" (between llvmorg-19.1.7 and llvmorg-20.1.8) added its own `RISCVTTIImpl::getPreferredAddressingMode`. This is the hook that tells the loop optimizer (Loop Strength Reduction) which addressing form to aim for. Upstream's version returns "post-increment" for the CORE-V `XCVmem` extension on 32-bit targets. Otherwise it defers to the generic default, which is "no preference" (`AMK_None`, `TargetTransformInfoImpl.h:276`). The fork has carried a function with the same name since LLVM 18. It returns "post-increment" when Xpulpv2 is enabled and `AMK_None` otherwise. At LLVM 20 the file therefore had two definitions, and the compiler rejected it with `redefinition of 'getPreferredAddressingMode'`. The header has only one declaration: the fork's duplicate declaration merged into upstream's at the same line (`RISCVTargetTransformInfo.h:391`), so only the .cpp needed a change.

## Why this is equivalent

The fork's separate function at the end of the file is gone. Its check is now the first statement of upstream's function:

```
if (ST->hasPULPExtV2())                   return AMK_PostIndexed;   // fork, unchanged
if (ST->hasVendorXCVmem() && !is64Bit)    return AMK_PostIndexed;   // upstream, unchanged
return BasicTTIImplBase::getPreferredAddressingMode(L, SE);         // upstream, = AMK_None
```

Case by case (before = LLVM 18/19 fork, or upstream 20.1.8, as applicable):

| Subtarget | Before | After |
|---|---|---|
| Non-PULP, no XCVmem (every upstream RISC-V target) | upstream: base default = `AMK_None` | Xpulpv2 check is false, XCVmem check is false, falls through to the same base default = `AMK_None`. Unchanged. |
| Non-PULP, XCVmem, rv32 | upstream: `AMK_PostIndexed` | Xpulpv2 check is false, so upstream's XCVmem line returns `AMK_PostIndexed`. Unchanged. |
| Non-PULP, XCVmem, rv64 | upstream: base default = `AMK_None` | Falls through to the base default. Unchanged. |
| PULP (Xpulpv2), rv32, the real PULP targets | fork: `AMK_PostIndexed` | First line returns `AMK_PostIndexed`. Unchanged. |
| PULP (Xpulpv2), rv64 | fork: `AMK_PostIndexed` (the fork never checked XLEN) | First line returns `AMK_PostIndexed`, with no XLEN check, as in the fork. Unchanged. |
| Xpulpv2 and XCVmem together | fork alone: `AMK_PostIndexed` | `AMK_PostIndexed`. Both branches give the same answer, so their order only matters for rv64, where putting the fork first keeps its answer. |

The fork's old fallback `return TTI::AMK_None;` and upstream's `BasicTTIImplBase::getPreferredAddressingMode` return the same value, because `BasicTTIImplBase` does not override the hook and inherits `TargetTransformInfoImplBase::getPreferredAddressingMode` → `AMK_None`. Both sides' behaviour therefore holds, and nothing needed escalating. The structure follows upstream's own per-vendor dispatch in this function: one `if (ST->hasVendorX…) return …;` line per extension before the base fallback (`llvm/lib/Target/RISCV/RISCVTargetTransformInfo.cpp:2397` at llvmorg-20.1.8).

Verified: without the change, `RISCVTargetTransformInfo.cpp.o` fails on the step-20 integration head `17f78490c034` with the redefinition error (logs/20-E007.repro.log, no probe hack). With the change it compiles (logs/20-E007.verify.log). The other `LLVMRISCVCodeGen` errors in that log are in `RISCVRegisterInfo.cpp` and `RISCVISelDAGToDAG.cpp`, which belong to other tasks.

## What breaks if this is wrong

- If the PULP preference were lost, loops over arrays on PULP targets would stop using post-increment loads and stores (`p.lw rd, imm(rs1!)` and the like). Each access would become a plain `lw` plus a separate `addi` of the pointer, and code size and cycle counts in downstream PULP kernels would grow. The fork has no lit test that pins LSR's post-increment choice for Xpulpv2 specifically. The closest oracles are the downstream instruction-mix check and the fork's `llvm/test/CodeGen/RISCV/xpulp-hwloop.ll` / `intrinsics/xpulpv.ll`. A dedicated Xpulpv2 counterpart of `xcvmem-heuristic.ll` is missing.
- If upstream's behaviour were changed, `llvm/test/CodeGen/RISCV/xcvmem-heuristic.ll` (added by `f590963db836`) would fail for XCVmem. For plain RISC-V, LSR output in many `llvm/test/CodeGen/RISCV` loop tests (for example `lsr-legaladdimm.ll`) would change.

# 20/E006: restore the RISCVMachineFunctionInfo.h include that the SSR register reservation needs

Written for a reader who does not know LLVM.

## What upstream changed

Upstream commit `82d5dd28b4de` "[RISCV] Remove unused includes (NFC) (#115814)" ran an include-cleaner over the RISC-V backend and removed `#include "RISCVMachineFunctionInfo.h"` from `RISCVRegisterInfo.cpp`, because upstream's own code in that file no longer used the per-function RISC-V info class. The PULP fork's code in the same file still does: it asks the per-function info which SSR (stream semantic register) data movers the function uses, so without the include the compiler no longer knows the type `RISCVMachineFunctionInfo` or its member `getUsedSSR()`.

## Why this is equivalent

Before (LLVM 19) the header was included directly by `RISCVRegisterInfo.cpp` and the fork's Xssr block in `getReservedRegs` read `RVFI->getUsedSSR()` to reserve `F0_D..F7_D` for each SSR lane in use. This change only puts the same include line back; the fork code itself is unchanged, so the set of reserved registers is exactly what it was. This is the same way upstream's own files that read the per-function info at `llvmorg-20.1.8` get it: they include the header directly, for example `llvm/lib/Target/RISCV/RISCVFrameLowering.cpp:14` (used at line 248 as `MF.getInfo<RISCVMachineFunctionInfo>()`).

## What breaks if this is wrong

If the include were missing, `LLVMRISCVCodeGen` does not compile (the two errors of this task). If the SSR reservation were wrong at run time, code compiled for Snitch with `+xssr` would allocate `ft0..ft7` while those registers are mapped to SSR streams, which the fork test `llvm/test/CodeGen/RISCV/ssr-register-reserving.ll` and downstream Snitch kernels would show as wrong register use or corrupted stream data. This change does not alter that logic, only makes it compile.

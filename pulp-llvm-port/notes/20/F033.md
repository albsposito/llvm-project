# 20/F033: make `#pragma frep infer` work end to end (Sema, diagnostics, codegen, -O0)

Written for a reader who does not know LLVM. Backlog B76. This is a fork defect that predates the port, not a regression from LLVM 20.

## What upstream changed

Nothing in `llvmorg-19.1.7..llvmorg-20.1.8` broke this. The pragma has never worked in any build of the fork (ref-18, int-20). The fork code dates from `f1b7aebff8c2` "[LLVM/PULP/SNITCH] Support for PULP and Snitch cores/platforms" on `pulp/integer_SIMD_fix`. That commit sits on an LLVM that already had upstream `fa4e72971e05` "Automate common diagnostic checking for statement attributes" (LLVM 13). Since fa4e72971e05, clang's Sema checks every statement attribute against the argument count declared in `Attr.td`, unless the attribute sets `HasCustomParsing`. The fork parser (`Parser::ParsePragmaFrep`) passes two arguments, the pragma name and the option, just as `ParsePragmaLoopHint` does for `#pragma clang loop` and `#pragma unroll`. But the fork's `Frep` attribute declares one argument and does not set `HasCustomParsing`. So Sema rejected the documented spelling with "'frep' attribute takes one argument" before any code was generated.

## Why this is equivalent

Before, the fork's README spelling `#pragma frep infer` was a hard compile error. The only way to get FREP inference was the global `-mllvm -snitch-frep-inference` flag. Now:

1. **Sema accepts the pragma.** `Attr.td` sets `let HasCustomParsing = 1` on `Frep`. This is exactly what upstream `LoopHint` does for the same two-identifier argument pattern (`clang/include/clang/Basic/Attr.td:4346` at llvmorg-20.1.8, parser at `clang/lib/Parse/ParseStmt.cpp:2537`). `handleFrepAttr` already reads both arguments, so no Sema logic changes.
2. **Codegen and the backend pass are unchanged in the normal case.** Clang's CodeGen still emits `call void @llvm.riscv.frep.infer()` in front of the loop. Instruction selection turns it into `PseudoFrepInfer` (`RISCVInstrInfoXfrep.td`). `SNITCHFrepLoops::isMarkedForInference` finds that pseudo in the loop preheader and runs the same inference as the global flag, but for that loop only. The marker is an intrinsic call, not IR metadata. The old "frep" metadata code in `addFrepMetadata` was already commented out in the fork.
3. **printf errors become clang warnings, reusing existing diagnostics (no new .td entries).** The warnings follow upstream's `#pragma riscv intrinsic` handler (`clang/lib/Parse/ParsePragma.cpp:4162` at llvmorg-20.1.8) and `#pragma unroll` (same file, `:3760`):
   - `#pragma frep` and `#pragma frep(infer)` give `warn_pragma_expected_identifier` ("expected identifier in '#pragma frep' - ignored").
   - `#pragma frep bogus` gives `warn_pragma_invalid_argument` ("unexpected argument 'bogus' to '#pragma frep'; expected 'infer'").
   - `#pragma frep infer extra` gives `warn_pragma_extra_tokens_at_eol`. The check now runs before the option's trailing tokens are collected. Before, it was dead code: the pragma was kept, and "Not EOF" was printed on stdout.
   - All are in `-Wignored-pragmas`, which is on by default, and each pragma is ignored, as upstream does.
   - The printf branches in `HandlePragmaFrep`, `ParsePragmaFrep` and `handleFrepAttr` could not be reached, because the handler only forms the annotation for `infer`. They became asserts of that invariant.
   - `#pragma clang frep infer` is not a fork spelling. It gets upstream's standard `-Wunknown-pragmas` warning (on with `-Wall`), which is unchanged.
4. **Two crashes that the Sema fix would otherwise expose are fixed.**
   - **Non-Xfrep targets.** On GAP9 (`-march=rv32imcxgap9`) or plain `rv32imafd`, the intrinsic has no selection pattern, so the backend stopped with "Cannot select: intrinsic %llvm.riscv.frep.infer". CodeGen now emits the marker only when the target has `xfrep` (`getTarget().hasFeature("xfrep")`). Elsewhere the hint is dropped, as a loop hint is.
   - **-O0 and `optnone`.** The FREP pass skips these functions. It returned before its "drop leftover PseudoFrepInfer" sweep, and the asm printer asserted "Cannot print this instruction". The sweep is now a helper (`removeFrepInferPseudos`), and the skip path also calls it (passes cluster, `SNITCHFrepLoops.cpp`).
5. **The marker is found in any attribute position.** `EmitStmt` only looked at `Attrs[0]`. With `#pragma unroll 1` written before `#pragma frep infer`, both attributes sit on one statement and Frep is second, so the marker was silently not emitted. It now scans the list.

Checks (logs `logs/20-F033.repro.log`, `logs/20-F033.verify.log`):
- The README-style SSR dot product with a constant trip count gets `frep.o a0, 1, 0, 0` at -O1, -O2, -O3 and -Os with `-mcpu=snitch`, with the pragma before or after `#pragma unroll 1`.
- The same loop without the pragma has no frep, and its output is byte-identical to int-20 at -O0, -O2 and -O3.
- -O0 and `optnone` compile, with no frep.
- GAP9 sweep: all 54 base (int-20) vs mine objects are byte-identical.

## What breaks if this is wrong

- **Sema, parser or diagnostics.** `#pragma frep infer` before a `for` loop would again be a compile error, or its warnings would go missing. No lit test covers the pragma; see the proposed test in the result file.
- **CodeGen gate.** Snitch code (`-mcpu=snitch`) with the pragma would lose its `frep.o`/`frep.i` instructions. Or GAP9/generic RISC-V code with the pragma would stop in the backend with "Cannot select".
- **Pass helper.** -O0 builds of pragma-annotated code would crash in the asm printer.
- **Code without the pragma** is unaffected: GAP9 sweep and Snitch output are byte-identical.
- **Known limits, not fixed here** (listed in the result file):
  - The FREP inference pass does not handle loops with a runtime trip count behind a zero-trip guard. The global flag has the same limit.
  - The pass produces wrong code for a loop-carried FP accumulator (it reads the initial value every iteration). ref-18 and int-20 with the global flag produce the same code, so the pragma only makes that existing bug reachable from source.

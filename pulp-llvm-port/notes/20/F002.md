# 20/F002: `__builtin_pulp_clip` and `__builtin_pulp_bextract[u]` emit an immediate one off from the PULP encoding

Written for a reader who does not know LLVM. Four sections, all required (policy_check.py checks the headings).

## What upstream changed

Nothing. This is a defect in fork code, not a port break. Both instruction-selection patterns were introduced by fork commit `f1b7aebff8c2` "[LLVM/PULP/SNITCH] Support for PULP and Snitch cores/platforms" (Federico Ficarelli, 2022-08-25), found with `git log -S'(trailing0s imm:$lowerBound)' pulp/integer_SIMD_fix -- llvm/lib/Target/RISCV/` and `git log -S'int_riscv_pulp_bextractu' pulp/integer_SIMD_fix -- llvm/lib/Target/RISCV/`. The code is unchanged in the LLVM 18 fork (`toolchains/ref-18`), the step-19 port and the step-20 integration head `b6cd96bd3726` (`llvm/lib/Target/RISCV/RISCVInstrInfoXpulp.td`). The owner decided on 2026-09-27 to fix the fork bugs found while benchmarking the GAP9 SDK DSP kernels on the port (survey `benchmarks/gap9-sweep-survey.md` section 4, item 4; the bextract case was found by the cycle benchmark, kernel k12_bit_extract).

## Why this is equivalent

This is a bug fix, so the generated code is meant to change. Both bugs are the same kind of mistake in the same block of builtin patterns: the value the programmer writes is passed to the instruction without converting it to the number the instruction's encoding field expects.

**p.clip.** The PULP instruction `p.clip rD, rs1, Is2` clamps to `[-2^(Is2-1), 2^(Is2-1)-1]` (GVSoC `gap_sdk_release/gvsoc2/core/models/cpu/iss/include/isa/pulp_v2.hpp:1930-1937`, `p_clipi_exec`). So `__builtin_pulp_clip(x, -128, 127)` (what the SDK macro `gap_clip(x, 7)` expands to, `tools/autotiler_v3/Emulation/GapBuiltins.h:51`) needs `Is2 = 8`. The fork computed `Is2` as the number of trailing zeros of the lower bound (-128 gives 7), which clamps to [-64, 63]. Now it computes it as "trailing ones of the upper bound plus one" (127 gives 8), the transform the fork already used for `p.clipu` and for the recognised min/max idiom, and which upstream CORE-V uses for `cv.clip` (`llvm/lib/Target/RISCV/RISCVInstrInfoXCV.td:723-727` and `:771-773` at `llvmorg-20.1.8`: `trailing1sPlus1` of the upper bound). GAP9 GCC emits `p.clip a0,a0,8`, `16` and `1` for [-128,127], [-32768,32767] and [-1,0]; the fixed build now emits the same (encoding `14851533` for the first, identical to GCC's word).

Other clip forms were checked and were already right: `__builtin_pulp_clipu(x,0,255)` gives `p.clipu ...,9` like GCC (GVSoC `p_clipui_exec`, same file :1940); `p.clipr`/`p.clipur` (register forms, GVSoC :1949/:1958, bound in a register: `low = -rs2-1, high = rs2`) map directly and match GCC; the plain-C min/max idiom that matches `p.clipr` (`min(max(x,~b),b)`) is correct.

**p.extract / p.extractu.** `p.extract[u] rD, rs1, Is3, Is2` extracts `Is3+1` bits at offset `Is2` (GVSoC same file :1987-2002, `p_extracti_exec`/`p_extractui_exec`: `width = UIM_GET(0) + 1`). `__builtin_pulp_bextract[u](x, Size, Off)` takes the width `Size` (GCC diagnostic "Size>0 ... (Size+Offset)<=32"; SDK emulation macros `GapBuiltins.h:560-561`). The fork passed `Size` straight into the width-minus-one field, so `bextractu(a,8,8)` extracted 9 bits, and `Size=32` failed instruction selection ("Cannot select: intrinsic %llvm.riscv.pulp.bextract"). Now the pattern accepts Size 1..32 and encodes `Size-1`: `p.extractu a0,a0,7,8` (`ce851533`), matching GAP9 GCC's word exactly. The other width-carrying builtins (`binsert`, `bset`, `bclr`) take a bit mask and already encoded mask-width-minus-one; they match GCC (`7,8` for an 8-bit field at 8) and are unchanged.

Numerical check on GVSoC (`benchmarks/gap9-sweep/sim`): a test with 32 inputs through clip [-128,127], [-32768,32767], [-1,0], clipu [0,255] and [0,0], clipr/clipur, the min/max idioms, and bextract/bextractu at (8,8), (16,16), (1,0), (5,4), (32,0) gives 79 mismatches with the unfixed step-20 build (28 with ref-18, clip only), 0 with the fixed build and 0 with GAP9 GCC. The simulator's own `sim/tests/clip.c` now reports "CLIP: ALL OK".

## What breaks if this is wrong

Any C code using the SDK macros `gap_clip`, `gap_bitextract` or `gap_bitextractu` (for example `DctLibraryFix.c`, `MatAddDSP.c`, `MatMulDSP.c` in the SDK DSP library) would saturate or extract at the wrong width: int8/int16 saturation clamps to half the range, bit-field extraction takes one extra bit, and results differ from GCC builds on the simulator or hardware. The fork lit test `llvm/test/CodeGen/RISCV/intrinsics/xpulpv.ll` only checks that some `p.clip`/`p.extract` immediate is printed (`{{[0-9]+}}`), so it does not catch either value; a test checking the exact immediates is missing (proposed in the result file, not added, per the task rules).

# 20/F034: accept the GAP9 runtime's GNU-as spellings p.mul, p.lX/p.sX without '!', and .func/.endfunc

Written for a reader who does not know LLVM. Four sections, all required (policy_check.py checks the headings).

## What upstream changed

Nothing upstream broke this. It is a **pre-existing fork gap** (backlog B109). The GAP9 SDK's hand-written runtime assembly (12 `.S` files under `rtos/`) uses five idioms that the GAP9 toolchain's GNU assembler (binutils 2.28) accepts and LLVM's assembler rejects, so an all-LLVM SDK build needed 5 source edits in those files (`benchmarks/sdk-clang/make_patched_mirror.sh`, edits 1-5). Reproduced with `build/int-20` (integration head `ccfd68f6ac76`), log `logs/20-F034.repro.log`:

1. `p.mul rd, rs1, rs2`: "unrecognized instruction mnemonic".
2. `p.lw rd, imm(rs1)` (and `p.lb/lbu/lh/lhu/sb/sh/sw`) with an immediate offset and **no** post-increment `!`: "invalid operand for instruction". The fork only knew the post-increment form `imm(rs1!)` and the register-offset forms `rs2(rs1)` / `rs2(rs1!)`.
3. `.func name` / `.endfunc`: "unknown directive".
4. `.weak x` followed by `.global x`: "x changed binding to STB_GLOBAL".
5. `%tiny(sym)`: "unrecognized operand modifier".

What GNU as does with each (assembled with `riscv32-unknown-elf-as -march=rv32imcxgap9`, dumped with `objdump -dr`), and where the difference comes from:

- (1) and (2) are **PULP-specific aliases**. PULP binutils' opcode table (`opcodes/riscv-opc.c` of pulp-platform/pulp-riscv-binutils-gdb, the `"Xpulpv2"` rows) lists `p.mul` with the plain `MATCH_MUL` encoding and `p.lb/p.lbu/p.lh/p.lhu/p.lw` "d,o(s)" and `p.sb/p.sh/p.sw` "t,q(s)" with the plain `MATCH_LB`...`MATCH_SW` encodings. GNU as emits exactly `mul`, `lw`, `sw`, ... (same bytes, same `%lo` relocations), and gates `p.mul` on Xpulpv2 alone (it assembles with `-march=rv32ixpulpv2`, without M). The fork's PULP load/store definitions come from fork commits `f1b7aebff8c2` "[LLVM/PULP/SNITCH] Support for PULP and Snitch cores/platforms" and `ac3041771cba` "FIX: Adding the support for the Xpulpv addressing modes (post-increment, memory-memory)" (found with `git log pulp/integer_SIMD_fix -S'"p.lw"'` / `-S'Post-increment addressing mode (PULPV2'`), which never added these aliases.
- (3) is a **generic GNU-as directive**. GNU as (`gas/read.c`, `do_s_func`) uses `.func`/`.endfunc` only to emit STABS debug info when run with `--gstabs`; otherwise it checks that they pair up ("missing .func", ".endfunc missing for previous .func") and emits nothing (the GNU object has no `.stab` section). Upstream LLVM MC has never implemented it (no `.func` handler in `llvm/lib/MC/MCParser` at `llvmorg-20.1.8`); it is not a deliberate rejection, just an obsolete debug format LLVM does not produce.
- (4) is a **deliberate upstream rejection**, since `8f8b5e5587c3` "[MC] Error for .globl/.local which change the symbol binding and warn for .weak" (2020-10, D90108, first in LLVM 12): GNU as lets `.weak` win over a later `.global`, MC used to let the last directive win; the commit makes a changed binding an error because silently overriding is error-prone (`llvm/lib/MC/MCELFStreamer.cpp:186-193` at `llvmorg-20.1.8`). **Not changed here** (generic MC file the fork does not own, and upstream chose this on purpose). The SDK-side fix is to put `.weak` after the `.global` (edit 5), which both assemblers turn into the same WEAK symbol.
- (5) is a **GAP binutils private relocation operator**. `%tiny(sym)` makes GNU as emit `R_RISCV_12_I` (59) for loads and `R_RISCV_12_S` (60) for stores: the absolute address of `sym` in the 12-bit immediate, used with `x0` as base for the variables GAP9 places in the aliased window at 0x4..0x7FF. GNU ld accepts 0..0x7FF and reports "relocation truncated to fit" for 0x800, 0x900 and 0xFFFFF800 (probed with `--defsym`). Upstream uses 59/60 for `R_RISCV_PLT32`/`R_RISCV_SET_ULEB128` (`RISCV.def:56-57`), which is why lld cannot link GNU-as SDK objects (B105/B110). **Not implemented here**, see "Why this is equivalent".

## Why this is equivalent

Two fork-owned files change, one commit each.

**`RISCVInstrInfoXpulp.td` (cluster insn-tablegen).** New assembler-only aliases, predicated on `[IsRV32, HasPULPExtV2]` like the rest of the PULP instructions, placed after the instruction definitions and away from the `LOOPsetup` records:
- `p.lb/p.lbu/p.lh/p.lhu/p.lw rd, imm12(rs1)` → `LB/LBU/LH/LHU/LW`, and `p.sb/p.sh/p.sw rs2, imm12(rs1)` → `SB/SH/SW`, with the same operand classes as the base instructions (`GPRMem`, `simm12`), so the range check and `%lo(...)` handling are the base ones (2048 is rejected, as GNU as rejects it).
- The zero-offset spellings `p.lX rd, (rs1)` / `p.sX rs2, (rs1)`, as upstream does for `lw $rd, (${rs1})` (`llvm/lib/Target/RISCV/RISCVInstrInfo.td:1049` at `llvmorg-20.1.8`); GNU as accepts those too.
- `p.mul rd, rs1, rs2` → `MUL`, gated like GNU as on Xpulpv2 only.
- `EmitPriority = 0`, so the printer and disassembler keep printing `lw`/`mul`, exactly what GNU objdump shows for the GNU-as objects. The shape follows the CORE-V aliases `cv.muls` etc. (`llvm/lib/Target/RISCV/RISCVInstrInfoXCV.td:152` at `llvmorg-20.1.8`) and the fork's own `flah`/`fsah` aliases in `RISCVInstrInfoXsmallfloat.td`.
Existing forms are untouched: `p.lw t1, 4(t0!)`, `p.lw t1, t0(t1)`, `p.lw t1, t0(t1!)` still assemble to the PULP encodings (checked).

**`RISCVAsmParser.cpp` (cluster mc).** `parseDirective` handles `.func name[, label]` and `.endfunc` when the PULP extension is enabled (so upstream RISC-V targets keep "unknown directive"). Like GNU as without `--gstabs`, it emits nothing and only enforces the pairing, with GNU's messages ("missing .func", ".endfunc missing for previous .func"). The directive code follows upstream's `.variant_cc` handler in the same file (`RISCVAsmParser.cpp:3346` at `llvmorg-20.1.8`). GNU as for RISC-V produces DWARF, never STABS, unless asked, and the SDK does not ask.

**Why `%tiny` and `.weak`+`.global` stay SDK edits.** `.weak`+`.global` is an upstream design decision in a generic file (above). `%tiny` would need a new operand modifier, a new fixup and a relocation number: GNU's 59/60 collide with upstream relocations, and the fork's `RISCV.def` already reserves `R_RISCV_12_I/12_S` as 68/69 (unused by any code), which GNU ld would not understand, and lld support would be needed either way. That is an interoperability decision for the owner (B105/B110), not a trivially safe change. The SDK-side replacement `%tiny(sym)` → `%lo(sym)` gives identical instruction bytes for the SDK's symbols (all in 0x4..0x7FF); only the link-time range check is lost.

**Verification** (all with this branch's `build/20-F034`):
- A probe with every alias and the existing PULP forms: `.text` byte-identical to GNU as (`objdump -d` of both). `p.lw a0, 2048(a1)` and `p.sw a0, -2049(a1)` are rejected (as by GNU as); RV64 rejects the aliases.
- The 12 SDK `.S` files, preprocessed once with GAP9 GCC (`-E -x assembler-with-cpp -DASSEMBLY_LANGUAGE`, SDK include/define flags): int-20 clang gave 79 errors in 11 of them; this branch leaves only the `%tiny` (22 errors, 3 files; the fourth file's `%tiny` lines are compiled out in this configuration) and `.weak`/`.global` (1, `gap_iet.S`) errors. With only those two SDK edits applied, every file's object is **byte-identical** (`objdump -d`) to int-20 clang's object for the fully edited sources of `make_patched_mirror.sh`, so the aliases and the directive do exactly what the SDK edits did. Against GNU as, 4 files (`freertos_task`, `port_asm`, `cluster-dma`, `asm_util`) have byte-identical `.text`; the other 7 differ only by generic, pre-existing assembler differences unrelated to this change (LLVM compresses `jalr`/`li` where GNU as 2.28 does not, and resolves local branches that GNU leaves to the linker for relaxation). None of the SDK's `p.` alias uses has compressible registers, so none is affected by the one difference below.
- Setup B of the sdk-clang ladder (clang + integrated assembler + ld.lld) with a mirror that has only the remaining edits (`%tiny`→`%lo`, `.weak` reorder, and the unrelated `system_exit` header edit 6): 5 edited `.S` files instead of 12, 3 SDK edits instead of 6. `helloworld`, `perf`, `helloworld_cxx`, `os/kernel/queue`, `mem_slab`, `watchdog/simple` build, link and run on GVSoC2 `gap.gap9.evk` with output identical to GCC's builds (cycle numbers and core print order masked).
- Lit: `llvm/test/MC/RISCV` (incl. the fork's `xpulp/` test), `llvm/test/CodeGen/RISCV`, `clang/test/CodeGen/RISCV` pass; the only failure is the known `rvv/vsetvli-insert-zve64f.mir` (B41), which fails identically on int-20.

**Known difference from GNU as.** LLVM compresses the resulting base instruction when its registers allow it (`p.lw a0, 0(a1)` becomes `c.lw`, 2 bytes), because the RISC-V assembler compresses every eligible instruction; GNU as 2.28 does not compress the `p.` spelling (it does compress plain `lw`). Same behaviour, smaller code; it only matters for hand-written code that counts bytes. No SDK use is affected.

## What breaks if this is wrong

- **Wrong base instruction or operand order in an alias:** the SDK runtime (cluster controller `cluster-cc.S`, PE entry `cluster-pe-team.S`, interrupt table `gap_iet.S`, `lz4depack.S`) would load/store the wrong address or multiply the wrong registers; cluster forks in `helloworld`/`perf` would hang or print garbage on GVSoC2, and the byte comparison against the edited sources would show it.
- **Alias shadowing the PULP forms:** a post-increment or register-offset `p.lw` would assemble as a plain `lw`, silently dropping the address update; the fork's `llvm/test/MC/RISCV/xpulp/xpulp-asm-parser.s` and the probe's `p.lw t1, 4(t0!)`/`t0(t1)` lines would change encoding.
- **Aliases printed instead of base names:** disassembly and `-S` output would say `p.lw` for every `lw`; `llvm/test/CodeGen/RISCV` and `llvm/test/MC/RISCV` CHECK lines would fail.
- **`.func` swallowing something it should not:** an input GNU as rejects would assemble silently; only the pairing checks guard this.
- No lit test covers the new spellings or the directive (tests are not edited by workers); a proposed MC test is in the result file.

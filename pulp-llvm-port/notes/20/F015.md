# 20/F015: make C comparisons with a small constant select p.beqimm/p.bneimm

Pre-existing fork defect (backlog B31), present in `toolchains/ref-18`; fixed at step 20 on the owner's request.

## What upstream changed

Nothing upstream broke this at step 20. The fork's two selection patterns for PULP's immediate branches (`p.beqimm` / `p.bneimm`: "branch if a register equals / differs from a 5-bit signed constant") were added by fork commit `f1b7aebff8c2` [LLVM/PULP/SNITCH] Support for PULP and Snitch cores/platforms, and describe the branch as `brcond (seteq x, C)`. Upstream `41759c3d92c5` [RISCV] Add RISCVISD::BR_CC similar to RISCVISD::SELECT_CC (LLVM 13, well before the fork's base) changed RISC-V so every conditional branch is rewritten into its own node, `riscv_brcc x, C, cond`, before instruction selection runs. The fork patterns were therefore never tried on anything they could match: clang emitted `li t, C` + `beq/bne x, t` (two instructions and a spare register) where GAP9 GCC emits one `p.beqimm`/`p.bneimm`. The upstream CORE-V vendor extension, which has the same instructions (`cv.beqimm`/`cv.bneimm`), got its selection patterns written against `riscv_brcc` in `f4d2f7a3b798` [RISCV] Codegen support for XCVbi extension (#89719).

## Why this is equivalent

The two patterns keep their meaning (same instructions, same operand order, same `simm5` immediate range -16..15, same predicate block `[IsRV32, HasPULPExtV2]`); only the node they match changes from `brcond (seteq/setne x, C)` to `riscv_brcc x, C, SETEQ/SETNE`, exactly as CORE-V does at `llvm/lib/Target/RISCV/RISCVInstrInfoXCV.td:814-817` at `llvmorg-20.1.8`. Only the branch-pattern hunk of `RISCVInstrInfoXpulp.td` is touched (the clip patterns 20/F012 edits are elsewhere in the file).

One deliberate difference from CORE-V: CORE-V adds `AddedComplexity = 2`, which makes `x == 0` also become `cv.beqimm x, 0`. The PULP patterns are left at the default priority, so for `x == 0` the generic pattern wins and the compiler keeps `beqz`/`bnez` (which the C extension can shrink to a 2-byte `c.beqz`/`c.bnez`); every other constant in -16..15 now selects the PULP instruction. This is exactly what GAP9 GCC does (`riscv32-unknown-elf-gcc -march=rv32imcxgap9 -O2`: `bnez` for 0, `p.beqimm` for -16, 5, 15, and `li`+`beq` for 16 and -17). The range matches the hardware: GVSoC decodes the constant as a signed 5-bit field in bits 20-24 (`gvsoc2/core/models/cpu/iss/isa_gen/isa_pulpv2.py:119-121` `Format_SB2`, `SignedImm(1, Range(20, 5))`) and compares it with the full 32-bit register (`include/isa/pulp_v2.hpp:1600`, `(int32_t)REG_GET(0) == SIM_GET(1)`); the fork's `Pulp_Immediate_Branch` class (`RISCVInstrInfoXpulp.td:327`) encodes `simm5` in that rs2 field.

Branch analysis already understands these instructions correctly since 20/F009 (condition codes `COND_P_BEQIMM`/`COND_P_BNEIMM`), so later passes that reverse or relax a branch keep the constant; with this change that path is now reached from C. Verified:

- `logs/20-F015.repro.log` / `logs/20-F015-repro/`: `t.c` at -O2: GAP9 GCC 9 immediate branches, ref-18 0, int-20 0, this change 10 (O0/O1/O3/Os 10, Oz 9). Boundaries: -16 and 15 use `p.b*imm`, 16 and -17 keep `li`+`bne`, 0 keeps `beqz`.
- GVSoC (`logs/20-F015.gvsoc.log`, `logs/20-F015-repro/run.sh`, `br.c`): the boundary-semantics hash over 14 functions x 81 inputs and both kernel results are identical for GCC, int-20 and this change. Kernel `classify` (a non-inlined function with four compares against small constants, called 2000 times): 43850 cycles (int-20) to 39951 cycles (this change), -8.9% (GCC 31799). Kernel `interp` (loop; the constants were already hoisted out of the loop, so the gain is two setup instructions and two free registers): 37465 to 37463.
- 20/F009's reproducer (`logs/20-F015.f009-repro.log`, same inputs, output redirected): branch-folder and branch-relaxation still give `P_BNEIMM $x10, 3` / `P_BNEIMM $x10, -7` + `PseudoBR`; GVSoC `checks=64 bad=0`. A C-level version (`logs/20-F015.relaxc.log`, `relaxc.c`: `if (x == -7)` / `if (x != 12)` around a 12 KB body) now gives a relaxed `p.beqimm a0,-7` + `j` and `p.bneimm a0,12`; GVSoC `checks=80 bad=0`.

## What breaks if this is wrong

If the pattern selected the PULP instruction with a wrong operand or out-of-range constant, programs comparing with small constants would branch the wrong way (silent wrong results) or the assembler would reject the immediate; the GVSoC checks above and the random-loop fuzzer (result file) show it. If the priority were wrong, `x == 0` would become a 4-byte `p.beqimm x, 0` instead of a compressible `beqz` (code size grows, visible in the GAP9 sweep). No lit test checks that `p.beqimm` is selected from IR today; a test is proposed in the result file (`proposed_test`). Select-shaped comparisons (`return x == 3 ? a : b`, or `if (x == C) return K;` turned into a select) still use `li`+`beq`, because PULP has no select-with-immediate pseudo like CORE-V's `Select_GPR_Using_CC_Imm`; listed as a separate item in the result file.

# 20/T010: regression tests for tonight's step-20 fixes (owner exception B40)

Written for a reader who does not know LLVM. This task adds nine new test files and changes no existing test and no compiler code. The owner approved it on 2026-09-27 (`notes/20/owner-test-exceptions.md#b40`).

## What upstream changed

Nothing upstream. These tests guard fixes the port made at step 20 to the fork's own code. Each of those fixes was reviewed and landed without a lit test, so lit could not catch the defect if it came back:

- 20/F001 `8d0ecbdbeb08` (clang-builtins): the `__builtin_pulp_*RN` rounding argument is checked against 2^(Norm-1).
- 20/F002 `624576f35fb2` (insn-tablegen): the `p.clip`/`p.clipu` immediate is the bit width, and the first `p.extract[u]` immediate is size-1.
- 20/F003 `d9911b451327` (passes): the hardware-loop pass handles count-down loops and constant trip counts.
- 20/F004 `e507c8f22d6a` (codegen-core, TTI): cost queries on the Xpulpv2 packed types `<2 x i16>` and `<4 x i8>` no longer take the RVV-only path.
- 20/F005 `c01ac9742d94` (passes): the hardware-loop fixup pass handles block layouts made by block placement and tail duplication.
- 20/F006 `abe1ba6bf62d` (codegen-core): float loads use post-increment `p.lw` under Zfinx.
- 20/R001 `1f7560cdee23` (insn-tablegen): a hardware loop with a constant trip count can be written to an object file (`lp.setupi` label fixup).
- 20/E007 `99275eb2f491` (codegen-core, TTI): after the merge with upstream `f590963db836` "[RISCV] Implement RISCVTTIImpl::getPreferredAddressingMode for HasVendorXCVmem (#120533)", Xpulpv2 still tells loop strength reduction to prefer post-increment addressing.

## Why this is equivalent

No compiler behaviour changes. The commit only adds test files, and `data/fork-tests.txt` already lists all nine paths (added in harness commit `77e0563d8a0b`, the same names). Each test's expected output is the output of the integration build `build/int-20` (integration head `abe1ba6bf62d`). The CHECK lines of the `.ll` files come from LLVM's update scripts: `update_llc_test_checks.py`, `update_mir_test_checks.py` and `update_analyze_test_checks.py`. Two files have no update script. The clang `-verify` test uses expected-diagnostic comments (the proposed diagnostics from `tasks/20/F001.result.json`). The `llvm-objdump` test checks encodings copied from int-20's objdump output. The regen report has details (`notes/20/T010-regen.md`).

Two tests are not where the task text suggested, so that the harness actually runs them. The harness lit suite (`config.env` `LIT_PATHS`) covers `llvm/test/CodeGen/RISCV` and `clang/test/CodeGen/RISCV`, but not `llvm/test/Analysis/CostModel/RISCV` or `clang/test/Sema`. So the F004 cost-model test is `llvm/test/CodeGen/RISCV/xpulpv2-simd-cost-model.ll`, and the F001 Sema test is `clang/test/CodeGen/RISCV/riscv-xpulpv2-rn-builtins-range.c`.

Each test passes on int-20 and fails on `toolchains/port-20` (port-20-green, before these fixes). E007 is the exception, because its fix landed before port-20-green. I isolated each fix with the intermediate toolchains `port-20fix` (`6e4c7f2a471f`: F002, F004, R001, F001 landed) and `port-20fix2` (`d9911b451327`: also F005, F003; lacks only F006). For E007 I used a local probe build with the Xpulpv2 branch disabled (reverted afterwards). Evidence is in `logs/20-T010.before-after.log`.

## What breaks if this is wrong

If a test is wrong in the too-strict direction, it fails on a correct compiler and a future step's worker has to regenerate it. That is visible, not silent. If a test is too weak, the defect it guards can come back unnoticed:

- the Sema test: GAP9 SDK code (`GapBuiltins.h` passes `(n), (1<<((n)-1))`) would be rejected, or wrong rounding values accepted;
- clip/extract: `p.clip`/`p.extract` would clamp or extract one bit off, which is a silent wrong result on hardware;
- hwloop-countdown/layout: the compiler would crash in the PULP hardware-loop passes, or produce wrong results (F005 fuzzer: 52 silent miscompiles);
- hwloop-obj: clang would crash when writing an object file for any constant-count loop;
- cost model: the compiler would crash at -O3 on packed-SIMD DSP kernels;
- postinc-f32: float loops would lose `p.lw` (slower), or `p.lw` would appear with F registers (wrong code);
- LSR heuristic: the second pointer would lose its post-increment load (slower).

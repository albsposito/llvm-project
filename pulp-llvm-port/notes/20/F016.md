# 20/F016: add the two GAP9 PMSIS builtins `__builtin_pulp_event_unit_read_fenced` and `__builtin_pulp_OffsetedWritePtr`

Pre-existing fork gap (backlog B87), present in `toolchains/ref-18` too (`use of unknown builtin`); filled at step 20 on the owner's request.

## What upstream changed

Nothing upstream broke this. The fork never defined these two builtins, which GAP9 GCC provides and which the GAP9 SDK's PMSIS headers call from `static inline` helpers included by almost every PMSIS file: `evt_read32()` (`rtos/pmsis/archi/chips/gap9/include/archi/event_unit/event_unit.h:41,47`), `hal_eu_read32()` (`.../hal/cluster/cluster_event_unit.h:57`) and `GAP_WRITE_PTR()` (`.../archi/gap_utils.h:29`). Clang therefore rejected those files: 398 of the 408 SDK files that GCC compiles and our clang did not (SDK compile survey, `benchmarks/sdk-compile-survey/report.md`). The sibling builtins these two are modelled on (`__builtin_pulp_event_unit_read`, `__builtin_pulp_OffsetedWrite`, their intrinsics and ISel patterns) were added by fork commit `f1b7aebff8c2` [LLVM/PULP/SNITCH] Support for PULP and Snitch cores/platforms, and the intrinsics were moved to their own file by `97efefdcc54e` Move our own intrinsics to dedicated td files (`git log pulp/integer_SIMD_fix -S'event_unit_read'` / `-S'OffsetedWrite'`).

## Why this is equivalent

Each builtin is added the same way as its fork sibling, in three places, one commit per owning cluster:

1. **clang-builtins** (`clang/include/clang/Basic/BuiltinsRISCVXpulp.td`, new block at the end): `int __builtin_pulp_event_unit_read_fenced(void *base, int offset)` and `void __builtin_pulp_OffsetedWritePtr(void *value, void *base, int offset)`, feature `xpulpv`. These are the exact prototypes GAP9 GCC declares (probed from its diagnostics: "expected 'void *'", "expected 'int'", and `_Generic` on the result gives `int`; `logs/20-F016-repro/p.c`, `p2.c`). `void *` matters: `hal_eu_read32` passes `(void *) base`, which C++ would reject for an `int *` parameter. Without `xpulpv` clang says "needs target feature xpulpv", like every sibling. No Sema code is needed (the siblings have none).
2. **intrinsics** (`llvm/include/llvm/IR/IntrinsicsRISCVXpulp.td`): `llvm.riscv.pulp.event.unit.read.fenced` and `llvm.riscv.pulp.OffsetedWritePtr`, each tied to its builtin with `ClangBuiltin<>`, so clang's existing generic path (`clang/lib/CodeGen/CGBuiltin.cpp`, `getIntrinsicForClangBuiltin`) emits the call. No clang code generation file is edited.
3. **insn-tablegen** (`llvm/lib/Target/RISCV/RISCVInstrInfoXpulp.td`, next to the `event_unit_read` patterns): immediate offset selects `p.elw rd, imm(rs1)` / `sw rs2, imm(rs1)`; register offset selects `add` + `p.elw rd, 0(tmp)` / `p.sw rs2, rs3(rs1)`, the same choice the sibling patterns make.

Semantics, checked against GAP9 GCC (`riscv32-unknown-elf-gcc -march=rv32imcxgap9 -mPE=8 -mFC=1`):

- **p.elw is a full compiler memory barrier in GCC's `_fenced` variant and not in the plain one.** With `_fenced`, GCC keeps a store before it that a later store to the same address overwrites, reloads a value read before it, and reloads a global read before it; with plain `__builtin_pulp_event_unit_read` it removes the first store and reuses both loads (`logs/20-F016-repro/t2.c`, `t3.c`). The new intrinsic has no memory attribute (so LLVM assumes it may read and write any memory) and `IntrHasSideEffects`, and `PULP_ELW` is `hasSideEffects = 1` at machine level. Result: it is never removed, merged, hoisted or reordered across other memory operations. Clang output for those cases matches GCC instruction for instruction (`mine-t2.s`), two calls give two `p.elw`, four unrolled loop iterations give four, and in a loop the `p.elw` stays inside the hardware-loop body like GCC's. When the result is unused, clang writes it to `zero` (upstream `RISCVDeadRegisterDefinitions` does this for every load with an unused result; the RISC-V spec requires a load to `x0` to still perform the access, and GVSoC's `Lsu::elw` still issues the request). The fork's existing `event_unit_read` intrinsic already has the same properties, so clang is stricter than GCC for the plain variant; this change does not touch it.
- **OffsetedWritePtr is a store that must never be dropped.** GCC tags it "Offseted Write volatile" and keeps it even to a dead local array. The new intrinsic uses the fork's `PulpWriteMemIntrinsic` properties (`IntrWriteMem`, base `WriteOnly` + `NoCapture`; the value operand is a pointer that escapes, so it is not `NoCapture`). IR passes cannot delete it (it may write any memory and is not `willreturn`), and the selected `sw`/`p.sw` has no memory operand, so machine passes keep it and keep it ordered with every other memory access. Verified: kept to a dead local array at -O2/-O3, two in a row stay two, a plain load after it is re-read, and a later plain store to the same address does not remove it (`t.c`, `t2.c`, `t4.c`). Plain C stores next to it can still be optimized as C allows (GCC happens to keep a dead plain store before it; that is legal either way). `IntrHasSideEffects` is deliberately not used, because TableGen rejects a side-effecting pattern whose result `SW`/`P_SW_rr` is declared `hasSideEffects = 0`.

Encodings (`logs/20-F016-repro/cmp/`, GCC vs this clang at -O0/-O2/-Os): the same instruction with the same addressing form in every function, for example `p.elw a0,60(a0)` = `03c56503` for both, and `p.sw a2,a1(a0)` = `00c565a3` for both. The differences: register choice; the immediate `OffsetedWritePtr` form is a 2-byte `c.sw` in clang where GCC emits a 4-byte `sw`, because GCC prints a fixed template that its assembler does not compress (same instruction, same effect); `p.elw zero` for an unused result. Clang also accepts a non-constant `event_unit_read_fenced` offset (`add` + `p.elw 0`), which GCC rejects ("offset expected to be immediate value") and so avoids only by inlining, and offsets above 2047, for which GCC prints an `p.elw a5,4100(a4)` that its own assembler rejects.

Upstream reference: CORE-V has the same event-load instruction (`cv.elw`, `llvm/lib/Target/RISCV/RISCVInstrInfoXCV.td:657-665` at `llvmorg-20.1.8`) but no builtin or intrinsic for it; the builtin record layout follows `clang/include/clang/Basic/BuiltinsRISCVXCV.td:31` (`RISCXCVBuiltin<"int(int, int)", "xcvalu">`), already mirrored by the fork's `PULPBuiltin` class.

## What breaks if this is wrong

- A wrong prototype makes PMSIS files fail to compile again (SDK compile survey: parity falls back towards 33.9%) or warn in C++.
- If `p.elw` lost its barrier properties, the compiler could move a shared-memory load or store across a barrier or wait on the event unit, or merge two waits into one: cluster synchronization would break silently on GAP9 hardware (a core reads data before the barrier releases it). GVSoC's `ri5ky_testbench` has no event unit, so no simulator test shows this; the assembly checks in this note and the proposed lit tests are the guard.
- If `OffsetedWritePtr` were dropped or given the wrong operand order, pointer-valued device or descriptor writes (for example DMA or UDMA descriptor links in the PMSIS drivers) would be lost or go to the wrong address. The GVSoC test `logs/20-F016-repro/elw.c` (`logs/20-F016.gvsoc.log`) writes pointers with both forms and reads them back with `p.elw` from async and slow memory: `err=0` at -O0/-O2/-Os/-O3, matching GCC.
- Checks run on the branch rebased onto integration head `ccfd68f6ac76`: SDK compile survey strict mode 209 -> 476 of 617 GCC-compilable files (33.9% -> 77.1%), 267 files newly compile, none regress, no newly unblocked file crashes or hangs (`logs/20-F016.survey.log`, `logs/20-F016-repro/survey-newly-ok.json`); GAP9 sweep, 54 kernel objects at -O2/-O3, disassembly identical to the integration-head clang and objects different only in the 35 bytes of the version hash in `.comment`; lit: see the result file.
- No lit test covers either builtin today; `proposed_test` in the result file lists clang CodeGen, Sema and llc tests.

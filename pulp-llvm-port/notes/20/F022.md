# 20/F022: keep Snitch SSR push/pop calls in place (stop LLVM from hoisting, merging or deleting them)

## What upstream changed

Upstream `e5c7cde5c812` "[NFC][TableGen] Refactor `getIntrinsicFnAttributeSet` (#106587)" (in `llvmorg-19.1.7..llvmorg-20.1.8`, found with `git log -- llvm/utils/TableGen/IntrinsicEmitter.cpp` and `git log -G'IntrHasSideEffects should affect'`) rewrote how TableGen turns an intrinsic's properties into IR attributes. Up to LLVM 19, an intrinsic that was declared both "only reads memory" (`IntrReadMem`) or "only writes memory" (`IntrWriteMem`) *and* "has side effects" (`IntrHasSideEffects`) *and* "may throw" (`Throws`) got **no** attributes at all: the old gate `(ME != unknown && !hasSideEffects)` skipped them (`llvmorg-19.1.7:llvm/utils/TableGen/IntrinsicEmitter.cpp:595`). The "NFC" refactor replaced the gate with `getEffectiveME(Int) != unknown`, so since LLVM 20 these intrinsics are declared `memory(read)` / `memory(write)`. The fork's `llvm.riscv.ssr.pop` and `llvm.riscv.ssr.push` were exactly this combination, and the fork's own comment shows it relied on them staying attribute-free ("The `Throws` attribute ensures that the push/pop don't get removed from loops by the LICM pass").

An attribute audit of all 179 fork intrinsics (every `llvm.riscv.*` intrinsic from `IntrinsicsRISCVXpulp.td` and `IntrinsicsRISCVXsnitch.td`, declared in one IR file and printed by `opt -S` of each toolchain; `logs/20-F022/attrs-*.ll`, `cmp.py`) shows that only these two changed between ref-18, port-19 and step 20:

| intrinsic | ref-18 | port-19 | int-20 (before) | this change |
|---|---|---|---|---|
| `llvm.riscv.ssr.pop` | none | none | `memory(read)` | none |
| `llvm.riscv.ssr.push` | none | none | `memory(write)` | none |
| the other 177 | unchanged | unchanged | unchanged | unchanged |

## Why this is equivalent

An SSR pop reads the next element of a hardware data stream (register `ft0`/`ft1`/`ft2`), and a push writes the next element of an output stream. Every call advances the stream, so two pops of the same stream return different values and a pop can never move out of its loop. LLVM's IR optimisers do not look at `IntrHasSideEffects` (that flag only matters in instruction selection); they look at the memory attribute. With `memory(read)`:

- `clang -O2` on the F014 reproducer (`logs/20-F022/frep-indep.c`) hoists both pops out of the 128-iteration inner loop. The integration head reads the stream once per loop instead of 128 times, and in the unrolled outer loop it reads it after `__builtin_ssr_disable()` and before the next enable (`frep-indep.20-F022_base.s`: `fdiv.d fa4, ft0, ft1` in the preheader/exit blocks instead of the loop body).
- `opt -passes='default<O2>'` merges two consecutive `pop(0)` calls into one (`logs/20-F022/ssr-ir.ll`, function `cse_pop`; `ssr-ir.before.txt` vs `ssr-ir.after.txt`). The callers also get marked `nofree memory(read)`, so calls to a helper that pops could be merged in turn.

The fix removes `IntrReadMem` from `int_riscv_ssr_pop` and `IntrWriteMem` from `int_riscv_ssr_push` (`llvm/include/llvm/IR/IntrinsicsRISCVXsnitch.td`, intrinsics cluster). Their memory effects become "unknown", which is exactly what ref-18 and port-19 produced (audit table above: attributes now identical to both for all 179 intrinsics). This follows how upstream declares its own stream (channel) intrinsics: `int_xcore_in` / `int_xcore_out` have no memory property (`llvm/include/llvm/IR/IntrinsicsXCore.td:42` and `:47` at `llvmorg-20.1.8`).

Without a memory property, TableGen infers that the instructions selected for these intrinsics may both load and store, and it refuses the fork patterns (`RISCVInstrInfoXssr.td:189/191`, "Pattern doesn't match mayLoad = 0 / mayStore = 0") because the pseudos `PseudoSSRPush`/`PseudoSSRPop` said "never loads" / "never stores". So the second commit (insn-tablegen cluster) sets `mayLoad = 1, mayStore = 1` on both pseudos. That is what TableGen infers for upstream's XCore stream instructions `IN_2r` / `OUT_2r` (`llvm/lib/Target/XCore/XCoreInstrInfo.td:853` and `:835` at `llvmorg-20.1.8`, patterns on `int_xcore_in`/`int_xcore_out`, no explicit flags). The pseudos already had `hasSideEffects = 1`, which makes every machine pass treat them as fixed barriers, so the extra flag does not change the machine code: `llc` output for the fork SSR/FREP tests and the F014 reproducers is byte-identical at -O0..-O3 under three flag sets (`logs/20-F022/llc-cmp/summary2.txt`: 219 identical; the other 33 runs crash identically before and after, pre-existing, `differ-are-crashes.txt`). There is no CORE-V equivalent (CORE-V has no stream registers).

After the change, `clang -O2` on the reproducer keeps `fdiv.d fa4, ft0, ft1` inside every inner loop, the same as port-19 (`frep-indep.20-F022_mine-wrap.s` vs `frep-indep.port-19_bin.s`), and the optimised IR matches port-19 apart from an unrelated upstream `nuw` flag on constant GEPs.

## What breaks if this is wrong

If the stream intrinsics again get a read-only or write-only memory attribute, Snitch programs that use `__builtin_ssr_pop`/`__builtin_ssr_push` in loops compute wrong results silently: the loop reuses one stream element for all iterations, and the stream is left out of step for the rest of the program (the reproducer above shows it). Nothing in the current lit suite catches it: the fork test `clang/test/CodeGen/RISCV/riscv-ssr-intrinsics.c` checks only single calls at -O0-style IR, and `llvm/test/CodeGen/RISCV/freploop*.ll` start from IR where the pops are already inside the loop. A missing regression test is proposed in the result file. If the pseudo flags were wrong in the other direction (dropping `mayStore` on pop), the build fails at TableGen time, as seen during this task. GAP9 is not affected: all 54 GAP9 sweep kernel objects are byte-identical to the integration head (`logs/20-F022/sweeproot/b/gap9-compare.txt`).

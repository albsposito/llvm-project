# 20/F013: make the PULP hardware-loop fixup pass produce code the machine verifier accepts, with no change to the generated code

Written for a reader who does not know LLVM. This is a pre-existing fork defect (backlog B05; present in ref-18, port-19 and step 20), not a port break.

## What upstream changed

Nothing upstream broke this. The defective code is the fork's `llvm/lib/Target/RISCV/PULP/PULPFixupHwLoops.cpp`, added by `f1b7aebff8c2` (Federico Ficarelli, 2022-08-25, "[LLVM/PULP/SNITCH] Support for PULP and Snitch cores/platforms"; `git log pulp/integer_SIMD_fix -S'splitMBBAt'` / `-S'setLabelMustBeEmitted'` find only this commit). ref-18 and port-19 `llc -verify-machineinstrs` on `xpulp-hwloop.ll` show the same 4 errors as step 20.

LLVM has a self-check, the *machine verifier* (`-verify-machineinstrs`), which checks after every pass that the compiler's internal program is consistent: every register an instruction reads must be known to hold a value there ("live"), each block's list of possible next blocks (its *successors*) must match the jumps at its end, and so on. It exists to catch miscompiles early. Every function containing a PULP hardware loop failed it after the last fork pass, "PULP Hardware Loop Fixup", so the check was useless for hardware-loop code (and aborted compilation when enabled). Four independent mistakes in that pass:

1. **Blocks created without live registers.** The pass moves the loop's last instruction into a new block (to put the loop-end label on it) and splits the `lp.setup` into its own block, but gave the new blocks no, or a wrong, list of live-in registers. The split helper stepped back only to *after* `lp.setup`, so the loop count register it reads was missing, and it also listed all unsaved callee-saved registers. Verifier: "Using an undefined physical register".
2. **Invisible back edge.** The block holding the loop's last instruction has the loop header as a successor (the hardware jumps back there at the end address), but no instruction in the block says so. Verifier: "MBB has unexpected successors which are not branch targets, fallthrough, ...". (The F005 result attributed this to the `lp.setup` block; it is the loop-end block. The `lp.setup` block itself was fine: `lp.setup` is a terminator that branch analysis rightly treats as "not understood", which the verifier accepts.)
3. **Malformed nops.** The nops the pass inserts (`addi x0, x0, 0`) had their destination x0 marked as a read instead of a write. Verifier: "Explicit definition marked as use" (hidden behind 1 and 2 before).
4. **Nops after a block's final instruction.** A loop shorter than two instructions is padded with nops placed after `lp.setup` in the same block; but `lp.setup` is a block terminator, and nothing may follow terminators. Verifier: "Non-terminator instruction after the first terminator" (found by the loop fuzzer once 1-3 were fixed: 138 of the 495 builds of fuzz seeds 1-165).

## Why this is equivalent

Only the compiler's internal bookkeeping changes; the emitted instructions, their order, their addresses and (with -g) the debug information do not.

- **Live-ins (1):** each block the pass creates (loop-end block, split `lp.setup` block, nop pad block) gets its live-in registers computed by LLVM's standard helper `computeAndAddLiveIns`, from the successors' live-ins and the block's own instructions. This is how upstream code that creates blocks late does it, e.g. RISC-V's own atomic expansion pass (`llvm/lib/Target/RISCV/RISCVExpandAtomicPseudoInsts.cpp:421-422, 551-554` at `llvmorg-20.1.8`), which runs right after this pass. Live-in lists are metadata; no instruction depends on them this late (only the atomic expansion pass and the asm printer follow).
- **Back edge (2):** the loop-end block now ends with `PseudoLOOPend <header>`, a new pseudo-instruction of size 0 that means "the hardware may jump back to the header here". The asm printer emits nothing for it (`RISCVAsmPrinter::emitInstruction`), so object code and assembly are unchanged, and the loop-length computation in the pass is unchanged (size 0). This is exactly upstream Hexagon's design: its hardware loops also jump back without an instruction of their own, and LLVM marks the loop end with the terminator `ENDLOOP0` (`llvm/lib/Target/Hexagon/HexagonPseudo.td:92`), which its MC lowering turns into no instruction word (`llvm/lib/Target/Hexagon/HexagonMCInstLower.cpp:98-101`). ARM's low-overhead loops likewise end in an explicit terminator (`t2LoopEnd`, `ARMInstrThumb2.td:5696`). RISC-V branch analysis (`RISCVInstrInfo::analyzeBranch`) would otherwise read the marker as a compare-and-branch with operands it does not have, so it reports blocks ending in it as "not understood", as ARM's `analyzeBranch` does for `t2LoopEnd` ("unrecognized terminator", `ARMBaseInstrInfo.cpp:417`); nothing after this pass rewrites branches. CORE-V (`XCV*`) has no hardware-loop code generation upstream, so there is no closer RISC-V reference.
- **Debug information (-g):** the marker must also leave the line table (`.debug_line`) alone, which a size-0 instruction does not do by itself. It is marked `isMeta` (a meta instruction: no code), so the debug-info writer records no line row for it and the asm printer's instruction statistics skip it, as upstream AMDGPU does for its zero-size emit-nothing pseudos (`WAVE_BARRIER`/`SCHED_BARRIER`/`IGLP_OPT`, `llvm/lib/Target/AMDGPU/SIInstructions.td:364-405`). It also carries no source location: the debug-info writer uses the last located instruction of a block as the line the block leaves with, to decide whether the next block's first line gets `is_stmt` (a breakpoint position; `DwarfDebug::findForceIsStmtInstrs`, `llvm/lib/CodeGen/AsmPrinter/DwarfDebug.cpp:2334-2463`). The first version of this change gave the marker the `lp.setup`'s location and was rejected in review: with -g, 146 of 183 hardware-loop fuzz objects got extra line rows. `isMeta` alone still dropped `is_stmt` on some rows (26 of 200 fuzz objects, e.g. seed 7008 -O2); with both, the line table is identical.
- **Nops (3):** `BuildMI(..., ADDI, X0)` / `RegState::Define` marks x0 as the written register; the encoded instruction is the same `nop`.
- **Pad block (4):** when `lp.setup` ends its block, the padding nops go into a new block placed right after it (falling through into the old next block) instead of after `lp.setup` in the same block. Same bytes at the same addresses, and blocks that jump to the old next block's label still skip the nops, exactly as before (a first attempt that put the nops at the start of that block changed such a jump target in fuzz seeds 938/960 -O3, so it was not kept). The assembly text gains one label line (`.LBB0_n:`) before the nops, and later local label numbers can shift by one; the object code is identical.
- `LOOP0setup`/`LOOP1setup` are unchanged (still non-branch terminators): marking them as branches would change what block placement and branch folding do earlier in the pipeline, i.e. change code.

## What breaks if this is wrong

If a live-in list is wrong, the verifier reports "undefined physical register" again, or (theoretically) a later pass could reuse a register that is still needed; only the atomic expansion pass runs after this pass. If the marker influenced debug information, -g builds would show extra `.debug_line` rows or rows losing `is_stmt` at the loop end or loop header (breakpoints move in gdb), visible with `llvm-dwarfdump --debug-line` against the integration build. If `PseudoLOOPend` were emitted, every hardware loop would contain an extra (invalid) instruction: visible as a changed `lp.setup` range or disassembly in `xpulp-hwloop-obj.ll`, `xpulp-hwloop*.ll` and every sweep kernel with a hardware loop, and as GVSoC failures. If the pad block were placed wrongly, loops of one instruction would change length (fuzzer, `lp.setup` range).

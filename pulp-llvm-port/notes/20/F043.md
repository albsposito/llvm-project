# 20/F043: mul/mac N/RN and clip/clipu builtins accept an immediate that is constant only after optimisation, as GAP9 GCC does

Written for a reader who does not know LLVM. Four sections, all required (policy_check.py checks the headings).

## What upstream changed

Nothing upstream broke this. It is a pre-existing gap in fork code (backlog B93, checkpoint M2a item 4). The builtins were declared with `_Constant` immediates (a C "integer constant expression", checked while parsing) since fork commit `f1b7aebff8c2` "[LLVM/PULP/SNITCH] Support for PULP and Snitch cores/platforms" (the checks in `SemaRISCV.cpp` and the `ImmArg` intrinsics). It was found with `git log pulp/integer_SIMD_fix -S'NormArgNum' -- clang/lib/Sema` and `-S'mul_mac_N_RN' -- llvm/include/llvm/IR`. The same rule is in the LLVM 18 fork.

GAP9 GCC (`riscv32-unknown-elf-gcc -march=rv32imcxgap9`) checks these immediates later, after its optimisations, when it emits the instruction. So it accepts `int Prec = 10; __builtin_pulp_mulsN(x, y, Prec)` and a clip bound that becomes constant when an `always_inline` function is inlined. Clang rejected both with "argument to '__builtin_pulp_mulsN' must be a constant integer". That blocked 11 SDK files (the fp16 CNN conv/matmul kernels use `int Prec=10; gap_mulsN(..., Prec)`, 396 call sites; the two NE16 kernels call `OUT_CLIP(acc, OutUnsigned, OutDatasize)` inside an `always_inline` kernel whose `OutDatasize` is a parameter, 20 `gap_clip` / 20 `gap_clipu` sites).

The task expected GCC to accept true run-time values and emit a register form. It does not. Probing GCC (`logs/20-F043/sweep/`, and 30 hand probes) shows:

- A true run-time value (function parameter, global variable) is always an error: "invalid argument to built-in function on arg N". So is any non-literal immediate at -O0.
- At -O1/-O2/-O3/-Os, a value that GCC's optimiser turns into a constant (local variable, `static` variable never written, `const` variable, parameter of an inlined function) is accepted. It gets exactly the same instruction as the literal.
- Such a constant still has to pass the range rules. Norm must be <= 31. For the RN forms, 1 <= Norm <= 31 and Round == 2^(Norm-1). Clip bounds must be -2^(N-1) and 2^(N-1)-1, and clipu bounds 0 and 2^(N-1)-1, with 1 <= N <= 30. Otherwise GCC reports "Builtin __builtin_pulp_mul{hh,}{s,u}NRr ... expects Norm and Round cst, Norm<=31, Round==2^(Norm-1)" or "Builtin __builtin_pulp_clip (X, Min, Max) expects Min and Max cst, Min=-2^(N-1), Max=2^(N-1)-1".

So there is no run-time lowering to add. The fix moves the check to the point where GCC does it.

## Why this is equivalent

Calls whose immediates are integer constant expressions (every call that compiled before) are unchanged. Clang emits the same IR (the same `ImmArg` intrinsic with the same constants) and runs the same Sema checks with the same diagnostics. That includes F011's clip rule. The only change is for calls that were rejected before.

What changed:

- `clang/include/clang/Basic/BuiltinsRISCVXpulp.td`: 18 prototypes (`mul{s,u,hhs,hhu}{N,RN}`, `mac{s,u,hhs,hhu}{N,RN}`, `clip`, `clipu`) lose `_Constant`. Without `_Constant`, the generic "must be a constant integer" error is no longer raised at parse time. The argument types are unchanged.
- `clang/lib/Sema/SemaRISCV.cpp` (new `getPulpDeferredImmArgStart` and a block at the top of `CheckBuiltinFunctionCall`): if every immediate argument is an integer constant expression, the existing checks run exactly as before. Otherwise Sema accepts the call and leaves the check to the back end.
- `clang/lib/CodeGen/CGBuiltin.cpp` (new `EmitPULPDeferredImmBuiltin`, called in `EmitBuiltinExpr` just before the generic builtin-to-intrinsic path). If every immediate is an integer constant expression, it emits the existing `llvm.riscv.pulp.<op>` intrinsic with those constants. This is what the generic path emitted while the arguments were `_Constant`. Otherwise it emits a new `llvm.riscv.pulp.<op>.deferred` intrinsic that takes the argument values as they are.
- `llvm/include/llvm/IR/IntrinsicsRISCVXpulp.td` (own block after `clipu_r`): the 18 `.deferred` intrinsics. They have the same operands as the existing ones but no `ImmArg`, because IR may carry a non-constant there until the optimiser folds it.
- `llvm/lib/Target/RISCV/RISCVISelLowering.cpp` (new `lowerPulpDeferredImmIntrinsic`, called first in `LowerINTRINSIC_WO_CHAIN`). At instruction selection, after all IR optimisation, each immediate operand of a `.deferred` call must be a constant that passes GCC's rule (above). If it does, the call becomes the existing `ImmArg` intrinsic node, and the existing patterns select the same instruction as for a literal. If it does not, the compiler reports an error, as GCC does ("argument 3 to '__builtin_pulp_mulsN' must be a constant integer (it is not constant after optimization)", "normalization argument ... must be in range [0, 31] (got 40)", "arguments to '__builtin_pulp_mulsRN' must be a normalization N in range [1, 31] and a rounding value 2^(N-1) (got 10 and 5)", "bounds of '__builtin_pulp_clip' must be -2^(N-1) and 2^(N-1)-1 with 1 <= N <= 30 (got -4 and 127)"). It then continues with an undefined value, so the compile fails with that message instead of crashing.

Why new intrinsics instead of dropping `ImmArg` from the existing ones: `ImmArg` is what stops IR passes from merging `c ? mulsN(x,y,3) : mulsN(x,y,4)` into one call with a phi of 3 and 4 (`canReplaceOperandWithVariable`, llvm/lib/Transforms/Utils/Local.cpp). Dropping it would put every existing constant call at risk of a new error. With separate intrinsics, only calls that used to be rejected take the new path.

Upstream reference. Upstream has no RISC-V builtin that is checked after optimisation. CORE-V's `mac` N/RN builtins require literals (`llvm/include/llvm/IR/IntrinsicsRISCVXCV.td:37-43`, `ImmArg`), and its `alu_addN`/`alu_clip` take any value and fall back to a register instruction (`clang/include/clang/Basic/BuiltinsRISCVXCV.td:31-41`, `llvm/lib/Target/RISCV/RISCVInstrInfoXCV.td:723,771`), which GCC's PULP builtins do not have. The mechanism follows upstream's GCC-compatible "diagnose after optimisation" design for `__attribute__((error/warning))`, commit `846e562dcc6a` "[Clang] add support for error+warning fn attrs": the call is carried through IR and the back end reports a `DiagnosticInfo` error during instruction selection. The diagnostic uses `DiagnosticInfoUnsupported`, as upstream `RISCVISelLowering.cpp:20596` does at llvmorg-20.1.8. The CGBuiltin argument emission mirrors upstream `EmitScalarOrConstFoldImmArg` (`clang/lib/CodeGen/CGBuiltin.cpp`).

## What breaks if this is wrong

If the Sema relaxation were too wide, a builtin that GCC rejects would compile. It cannot do so silently: a non-constant or out-of-range value reaches the back end, which reports it. The sweep's run-time and global forms show that (all rejected, as in GCC). If the back-end rule were too loose, a wrong immediate would give a wrong clamp or shift, and the sweep (accept/reject vs GCC) and GVSoC (`sim/`) would show it. If it were too strict, SDK kernels such as `CNN_Conv_BasicKernels_fp16.c` and `CNN_BasicKernels_NE16.c` would fail with "... is not constant after optimization" or a range message. The survey shows none.

If the ICE path had changed, existing code would change, and the GAP9 sweep, `clang/test/CodeGen/RISCV/riscv-xpulpv2-intrinsics.c` and the literal rows of the sweep would show it. All three are unchanged.

Known limit, shared with GCC: whether a value "becomes constant" depends on the optimiser. Code that relies on it fails at -O0 in both compilers. In principle an IR pass could also merge two deferred calls with different constants into one call with a phi (the deferred intrinsics have no `ImmArg`), which would then be reported as non-constant. None of the tested branch shapes (`c ? g(x,y,3) : g(x,y,4)`, if/else, OUT_CLIP with a run-time selector, at O1/O2/O3/Os) does this. No lit test covers the new path; see `proposed_test` in the result file.

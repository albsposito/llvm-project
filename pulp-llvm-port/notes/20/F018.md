# 20/F018: GCC's `-mPE=<N>` makes `__builtin_pulp_CoreCount()` a compile-time constant; fix the run-time CoreCount read

Written for a reader who does not know LLVM. The four sections required by `templates/change-note.md` come first. The SDK user documentation and the measurements follow them.

## What upstream changed

Nothing upstream broke this. It is a **pre-existing fork gap and a pre-existing fork defect**. Both are present in the LLVM 18 fork and in `toolchains/ref-18` (ref-18 says `unknown argument: '-mPE=8'` and rejects `static int x = __builtin_pulp_CoreCount();`).

- The gap: the fork added `__builtin_pulp_CoreCount` in `f1b7aebff8c2` "[LLVM/PULP/SNITCH] Support for PULP and Snitch cores/platforms" (2022-08-25), but never added GCC's `-mPE=` option. So the builtin is always a run-time read. GAP9 GCC folds it to the `-mPE` value, and the SDK depends on that: all 68 AutoTiler CNN kernel files contain `static int ActiveCore = gap_ncore();`, where `gap_ncore()` is `__builtin_pulp_CoreCount()` (`tools/autotiler_v3/Emulation/GapSystem.h:63`). Clang rejects them with "initializer element is not a compile-time constant" (backlog B91).
- The defect: `ffb655febeca` "[LLVM/PULP] Lower pulp_CoreCount same as GCC" (2022-08-26) lowered the run-time read as `lw 0(0x1A103000) & 0x12`. GCC emits `p.lw 18(0x1A103000)`: 18 (0x12) is the load **offset**, and the fork used it as an AND **mask**. The result is wrong, and silently so: 0 on GAP9 according to the SDK-build research (`benchmarks/sdk-clang/report.txt`, blocker 2), so the PMSIS cluster team fork ran on no cores.

Rule 8 asks for an upstream commit. Since nothing upstream caused this, the note cites the fork commits above (the `_common_sdk.txt` rule) and the upstream reference this change follows: `1c2ed36741c6` "[clang][x86] Add constexpr support for BMI/TBM BEXTR intrinsics" (in `llvmorg-19.1.7..llvmorg-20.1.8`). That commit shows how upstream makes a *target* builtin constant-evaluable: a `Constexpr` attribute in the builtin `.td` plus a case in `IntExprEvaluator::VisitBuiltinCallExpr`.

## Why this is equivalent

What GAP9 GCC 7.1.1 does (`riscv32-unknown-elf-gcc -march=rv32imcxgap9`), measured. The raw outputs are in `logs/20-F018/`: `contexts.txt`, `options.txt`, `siblings.txt`.

- `-mPE=N` with N > 0 turns `__builtin_pulp_CoreCount()` into the **integer constant expression** N. GCC folds it in the front end, so the fold also happens at -O0.
  - GCC accepts it in a static initializer, an expression in a static initializer, a file-scope array bound, `_Static_assert`, a `case` label, an enumerator and a bit-field width, at -O2 and -O0.
  - Without `-mPE`, all 7 contexts are errors. A local array still works (as a VLA), and `__builtin_constant_p` compiles.
- `-mPE=0`, and no `-mPE` at all, both mean a run-time read: `p.lw 18(0x1A103000)`.
- `-mPE` does not change any predefined macro. The `-dM -E` output is the same with and without `-mPE=8 -mFC=1`.
- Accepted values: decimal (`010` means 10) or `0x` hexadecimal, non-negative. `-1`, `abc`, `8abc`, `+8`, ` 8`, `0xg` and an empty value are errors ("argument to '-mPE=' should be a non-negative integer" / "missing argument"). The last `-mPE` wins.
- Other options and builtins driven by them:
  - `-mFC=` sets `__builtin_pulp_HasFc()` to a constant: 1 if FC != 0, else 0. With `-mFC=0` or without `-mFC`, `__builtin_pulp_IsFc()` is 0.
  - `__builtin_pulp_CoreCount_m1()` folds to N-1. GCC does not fold it for N=1.
  - CoreId and ClusterId are never folded.
  - GCC also has `-mL2=`, `-mL1Cl=`, `-mL1Fc=`, `-mchip=` and `-mconf=`, which fold nothing we use.
  - These are **not** implemented here (one root cause per task). They are listed as follow-ups in the result file.

What clang does now:

1. **Driver** (`clang/include/clang/Driver/Options.td`, `clang/lib/Driver/ToolChains/Clang.cpp` `AddRISCVTargetArgs`):
   - accepts `-mPE=<N>` in decimal or `0x` hex, 0 to 2147483647, with the last one winning;
   - diagnoses any other value with clang's standard `unsupported argument '<v>' to option '-mPE='`, the same diagnostic upstream uses for `-mrvv-vector-bits=` a few lines above;
   - forwards the value in canonical decimal to cc1;
   - warns "unsupported option" for non-RISC-V targets.
2. **cc1** stores the value in `TargetOptions::PULPClusterCores` (0 = not given).
3. **Constant evaluator** (`clang/lib/AST/ExprConstant.cpp`):
   - `__builtin_pulp_CoreCount` is marked `Constexpr` (`BuiltinsRISCVXpulp.td`), and one case returns `PULPClusterCores`.
   - If the value is 0, or the target lacks Xpulpv, evaluation fails. In that case everything is exactly as before: the call is not a constant, and CodeGen emits `llvm.riscv.pulp.CoreCount`.
   - When evaluation succeeds, clang's CodeGen already emits a constant for any constant-evaluable builtin (`CGBuiltin.cpp` `EmitBuiltinExpr`), so the function body becomes `li a0, 8` at every -O level. It is `ret i32 8` in IR at -O0.
4. **Run-time read** (`RISCVInstrInfoXpulp.td`): the pattern is now `lw 18(lui 0x1A103)`. That is the same address and offset as GCC, with `lw` instead of GCC's `p.lw`, which is the same load.

Result: in all 30 context × option cases, clang accepts or rejects exactly what GCC does (`contexts.txt`).

Other builtins that read the same register or CSR, checked as the conductor asked (`siblings.txt`). None has the offset-vs-mask confusion. Two differ from GCC in other ways; they are reported, not fixed:

| Builtin | GCC | Fork | Result |
|---|---|---|---|
| ClusterId | bits 5..10 of mhartid | same | matches |
| HasFc | 0 without `-mFC` | 0 | matches |
| CoreId | `mhartid & 0x1f` (`p.bclr 26,5`) | `mhartid & 0xf` | differs only for core ids ≥ 16, which GAP9 does not have |
| IsFc (with `-mFC=1`) | `p.extract` (signed): 0 / -1 | 0 / 1 | differs in sign; without `-mFC`, GCC folds IsFc to 0 while the fork reads the CSR |

Deliberate deviation from GCC: GCC's handling of very large `-mPE` values is erratic.

- `-mPE=2147483647` gives -2147483648.
- `-mPE=2147483648` gives the run-time read.
- `-mPE=4294967295` is rejected.
- `-mPE=4294967297` gives 1.

Clang accepts up to 2147483647 and returns it unchanged, and rejects larger values. Clang also diagnoses an empty value with the same error as a bad value, where GCC says "missing argument".

Upstream references at `llvmorg-20.1.8`:

- `clang/lib/AST/ExprConstant.cpp:13821`: `case clang::X86::BI__builtin_ia32_bextr_u32`, a constexpr target builtin. The PULP case sits just before it.
- `clang/include/clang/Basic/BuiltinsX86.td:841`: the `Constexpr` attribute on a target builtin.
- `clang/lib/Driver/ToolChains/Clang.cpp:2191`: `-mrvv-vector-bits=` validation and forwarding, the closest RISC-V driver reference.
- `clang/include/clang/Driver/Options.td:5212`: `-mcode-object-version=`, a vendor hardware configuration stored in `TargetOptions`.

## What breaks if this is wrong

- **Fold missing:** the 68 CNN kernel files (`CNN_Libraries*`) fail again with "initializer element is not a compile-time constant". A static `_Static_assert(__builtin_pulp_CoreCount() == 8)` in user code fails.
- **Wrong value:** per-core arrays sized by `gap_ncore()` (for example `static int Reduct[8]`) and the cluster team fork use the wrong core count. That causes silent out-of-bounds writes or idle cores, visible on GVSoC as missing per-core output (helloworld prints fewer than 8 core lines).
- **Behaviour without `-mPE` changed by mistake:** `clang/test/CodeGen/RISCV/riscv-xpulpv2-intrinsics.c` (`test_builtin_pulp_CoreCount` expects the intrinsic call) would fail. It passes.
- **Run-time pattern wrong:** GAP9 apps built without `-mPE` would see a wrong core count again. No lit test checks this pattern's assembly; see `proposed_test` in the result file.

Missing tests (not added, rule 2):

- a Driver test for `-mPE=` values and diagnostics;
- a CodeGen test that `-mPE=8` gives `ret i32 8` at -O0;
- a Sema test for the 7 constant contexts with and without `-mPE`;
- an llc test for the `lw 18(...)` run-time read.

## For SDK users: `-mPE=<N>`

- `clang --target=riscv32-unknown-elf -march=rv32imc_xgap9 -mPE=8 ...` works like GAP9 GCC's `-mPE=8`. `__builtin_pulp_CoreCount()` (and so `gap_ncore()`, `AT_NCORE()`, `pi_cl_cluster_nb_pe_cores()`) is the integer constant 8. It can be used anywhere C requires a constant: static initializers, array sizes, `case` labels, `_Static_assert`, enumerators, bit-field widths. The GAP9 SDK passes `-mPE=8`.
- Without `-mPE`, or with `-mPE=0`, the value is read from memory at run time, from the same address GCC uses (0x1A103012). On GAP9 this address is not a documented core-count register in the public SDK memory map (it lies in the uDMA area), so always pass `-mPE=8` for GAP9, as the SDK does with GCC.
- `-mFC=`, `__builtin_pulp_CoreCount_m1()` (`gap_ncorem1()`) and the other GCC `-mL2=/-mL1Cl=/-mL1Fc=/-mchip=/-mconf=` options are not supported yet. A drop-in wrapper must still drop `-mFC=1`.

## Measurements

- **SDK compile survey:** see the result file for final numbers.
  - Measured before the rebase on int-20 at `7459255b6120`, strict mode, with `-mPE=8` added to the clang flags: the "not a compile-time constant" error disappears from all 68 CNN files (68 → 0).
  - None of the 68 compiles yet, because each still has other errors (unknown `float16` types, the missing F016 builtins, vector-type mismatches). No new error kind appears in any of them.
  - In `fp16probe` mode, replacing the survey's `-D__builtin_pulp_CoreCount()=8` shim with `-mPE=8` gives identical per-file results (324 ok / 84 fail both ways). So `-mPE=8` is a complete replacement for the shim.
- **GAP9 sweep** (`benchmarks/gap9-sweep/run.py` on a scratch copy, int-20 `ccfd68f6ac76` vs this branch): the disassembly of all 54 LLVM kernel objects (O2 and O3) is identical. The object files differ only in the embedded compiler version string. None of the kernels uses CoreCount.

# 20/T003: keep the instruction scheduler from moving FREP loop bodies across the frep instruction

## What upstream changed

Upstream commit `9122c5235ec8` "[RISCV] Enable bidirectional scheduling and tracking register pressure (#115445)" (between llvmorg-19.1.7 and llvmorg-20.1.8) added `RISCVSubtarget::overrideSchedPolicy`. It makes the pre-register-allocation instruction scheduler work in both directions and track register pressure for every RISC-V CPU, Snitch included. Before this commit the scheduler worked bottom-up only. In that mode it happened to leave the fork's `frep.o` loops alone. With the new policy it reorders instructions across `frep.o`.

`frep.o rs, N, ...` is Snitch's floating-point repeat instruction: the hardware repeats the **N instructions that immediately follow it**. The fork never told the scheduler this. `FREP_O`/`FREP_I` have no side effects and are not scheduling boundaries. The LLVM 19 output was correct only because of the old scheduling direction.

Observed at the step-20 integration head (`17009d29cc0e`, build/int-20). In `freploop-nested.ll`, the scheduler moved `fmul.d` from the loop body to **above** `li`/`frep.o`:

```
LLVM 19 (correct)          LLVM 20 before fix (miscompile)
  li     a2, 127             fmul.d fa4, ft0, ft1   <- runs once, not 128 times
  frep.o a2, 2, 0, 0         li     a2, 127
  fmul.d fa4, ft0, ft1       frep.o a2, 2, 0, 0
  fadd.d fa5, fa5, fa4       fadd.d fa5, fa5, fa4
  fmv.x.w a2, fa4            fmv.x.w a2, fa4        <- now repeated instead of fmul
```

This is a real miscompile, not only a test-text change. The multiply runs once instead of 128 times, and the repeated body now contains `fmv.x.w`. I confirmed the cause with `-print-after-all`: FMUL_D is after FREP_O up to the Register Coalescer, and in front of it after `machine-scheduler`. With `-misched-prera-direction=bottomup` the first function comes out correct again.

## Why this is equivalent

The fork already has a hunk in `RISCVInstrInfo::isSchedulingBoundary` (`llvm/lib/Target/RISCV/RISCVInstrInfo.cpp:3243`). It marks the PULP hardware-loop setup instructions `LOOP0setup`/`LOOP1setup`/`LOOP0setupi`/`LOOP1setupi` as scheduling boundaries for exactly this reason: the loop body position is fixed relative to the setup instruction. This change adds `FREP_O` and `FREP_I` to the same switch. A scheduling boundary splits the block into separate scheduling regions, so no instruction can be moved from one side of `frep` to the other. The rest of the upstream policy is untouched: bidirectional scheduling and pressure tracking still apply inside each region, for every CPU. I did not override `overrideSchedPolicy` for Snitch, because that would revert upstream's decision for a whole CPU to work around a missing constraint on two instructions.

Result: for all four RUN lines of `freploop-nested.ll` (default, -O1, -O2, -O3), the emitted instruction stream is now identical to the port-19-green `llc` (build/int-19). I compared the output with comment/attribute/section lines filtered out, and `diff` reports no difference.

**The test still fails, for a cosmetic reason only.** In `main1`, the assembler *comment* `# implicit-def: $f15_d` now prints between `li a0, 127` and `frep.o a0, 2, 0, 0`. At 19 it printed before the `li`. This comment comes from an IMPLICIT_DEF pseudo: it emits no machine instruction and no bytes. The bidirectional scheduler places the IMPLICIT_DEF and the `li` in the other order within the region above `frep.o`. The test's `CHECK-NEXT: frep.o` after `li` (line 60) then fails because of the comment line. Fixing this without editing the test would need a Snitch-specific scheduling-policy override (reverting `9122c5235ec8` for Snitch) only to move a comment. I did not do that. The remaining failure is escalated to the conductor as a test-expectation question (see the T003 result file).

## What breaks if this is wrong

- If the boundary were missing (the state before this change), FREP loops would silently compute wrong results on Snitch. The first body instruction(s) would be hoisted out of the repeat, and instructions after the body would be repeated instead. `llvm/test/CodeGen/RISCV/freploop-nested.ll` shows it as `fmul.d` above `frep.o`, and downstream Snitch kernels using `-snitch-frep-inference` or `#pragma frep` would produce wrong numerical results.
- If the boundary were too strong: code around FREP loops would be scheduled a little less freely (no reordering across `frep`). This affects performance only, and matches what the fork already does for the PULP `lp.setup` instructions.
- Not covered by this boundary: instructions *after* `frep` are still in one region with the body. If the scheduler ever interleaved a non-body instruction into the N-instruction body, that would also be wrong. No test shows this today, because the body instructions depend on each other. No fork test pins the body when it has independent instructions; such a test is missing.

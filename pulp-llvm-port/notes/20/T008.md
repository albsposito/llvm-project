# 20/T008: accept the implicit-def assembler comment before frep.o in freploop-nested.ll (owner exception T003)

Written for a reader who does not know LLVM. Test-only change made under the recorded owner exception `notes/20/owner-test-exceptions.md#t003`; regen report `notes/20/T008-regen.md`. It sits on top of the already-reviewed code fix 20/T003 (`8bcb70882fc6`) and is meant to land together with it.

## What upstream changed

Upstream commit `9122c5235ec8` "[RISCV] Enable bidirectional scheduling and tracking register pressure (#115445)" (in `llvmorg-19.1.7..llvmorg-20.1.8`) changed how the pre-register-allocation scheduler orders instructions for every RISC-V CPU. It caused a real FREP miscompile, which 20/T003 fixes by making `frep.o`/`frep.i` scheduling boundaries (see `notes/20/T003.md`). With that fix the emitted instructions are identical to the port-19-green compiler, but in function `main1` the scheduler now places an `IMPLICIT_DEF` placeholder after the `li a0, 127` instead of before it. `llc` prints that placeholder as the assembler comment `# implicit-def: $f15_d`, so the comment now appears on the line between `li` and `frep.o`.

## Why this is equivalent

`# implicit-def: $fN_d` is a comment: it emits no machine instruction and no bytes (it only says "this register holds an undefined value here"). The test line added is `; CHECK-NEXT:   # implicit-def: $f{{[0-9]+}}_d`, inserted between the existing `li ... 127` check and `CHECK-NEXT: frep.o` check of `main1`. Every existing check is unchanged and still strict (`CHECK-NEXT` for `frep.o`, `fmul.d`, `fadd.d`, `fmv.x.w`, `csrci`, `csrsi`), so the test still requires the loop body to follow `frep.o` immediately. The register number is a pattern because it is an allocation detail. The comment was checked at the same position in all four RUN lines (default, -O1, -O2, -O3); the four `llc` outputs of `build/20-T008` are byte-identical (`logs/20-T008.asm*.s`). No RUN line, input IR line, or other CHECK line changed.

## What breaks if this is wrong

If the FREP miscompile came back (the scheduler moving `fmul.d` above `frep.o`), this test still fails: with `build/int-20/bin/llc` (the integration compiler without the T003 fix) the edited test FAILS for all four RUN lines (`logs/20-T008.verify.log`), because `fmul.d` is no longer after `frep.o` and the comment is no longer after `li`. If a future scheduling change moved the comment again (for example back before `li`), the test would fail on the new `CHECK-NEXT` line with no instruction change; that would be a cosmetic failure to re-examine, not a miscompile. The test does not check the `implicit-def` in `main` or the second loop of `main1`.

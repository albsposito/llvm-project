# 20/F036: add the seven GAP9 f32 scalar builtins (`__builtin_pulp_f32max`, `f32min`, `f32abs`, `f32sqrt`, `rintsf2`, `rdownsf2`, `rupsf2`)

This fills a gap the fork already had (backlog B97, batch A of `benchmarks/builtins-spec/spec.md`). `toolchains/ref-18` also answers `use of unknown builtin` for these names. The work was done at step 20 because the GAP9 SDK needs them.

## What upstream changed

Nothing upstream broke this. The fork never defined these seven builtins. GAP9 GCC provides them, and the GAP9 SDK's DSP and CNN kernels call them through `FloatDefines.h:95-101` (`Absf32`, `Maxf32`, `Minf32`, `Sqrtf32`), `GapBuiltins.h:250-256` (`gap_f32*`) and `at_api.h:126` (`AT_SCALEF`). Clang rejected every file that uses them. The fork's other PULP builtins, their intrinsics and their selection were added by fork commit `f1b7aebff8c2` [LLVM/PULP/SNITCH] Support for PULP and Snitch cores/platforms (`git log pulp/integer_SIMD_fix -S'OffsetedWrite' -- clang/include/clang/Basic/BuiltinsRISCV.def`). The new builtins follow the same three-part pattern that 20/F016 used.

## Why this is equivalent

Each builtin is exactly one standard F/Zfinx instruction. GAP9 is Zfinx, so floats live in integer registers. Here is what GAP9 GCC emits for each one (`gcc/<name>.s` in the spec, re-checked with `riscv32-unknown-elf-gcc -march=rv32imcxgap9 -mPE=8 -mFC=1 -O2`):

| builtin | prototype | instruction |
|---|---|---|
| f32max / f32min | `float(float, float)` | `fmax.s` / `fmin.s` |
| f32abs | `float(float)` | `fabs.s` (= `fsgnjx.s rd,rs,rs`) |
| f32sqrt | `float(float)` | `fsqrt.s` (dynamic rounding mode) |
| rintsf2 / rdownsf2 / rupsf2 | `int(float)` | `fcvt.w.s rd,rs,rmm` / `rdn` / `rup` |

The change has three parts, with one commit per owning cluster:

1. **clang-builtins** (`clang/include/clang/Basic/BuiltinsRISCVXpulp.td`, in its own block at the end of the file): the seven `PULPBuiltin` records use GCC's prototypes, `NoThrow, Const`, and the feature `xpulpv,(f|zfinx)`. That feature means Xpulpv plus either F or Zfinx. `-march=rv32imc_xgap9` and `rv32imc_zfinx_xpulpv2` both satisfy it. Without it clang reports `needs target feature xpulpv,(f|zfinx)`. Sema needs no new code, because every operand is a plain float.
2. **intrinsics** (`llvm/include/llvm/IR/IntrinsicsRISCVXpulp.td`): `llvm.riscv.pulp.<name>` are declared with `PulpIntrinsic`, `IntrNoMem` and `IntrSpeculatable`. Each one is tied to its builtin by `ClangBuiltin`, so clang's existing generic path (`CGBuiltin.cpp`, `getIntrinsicForClangBuiltin`) emits the call. No clang CodeGen file is edited: `CGBuiltin.cpp` is an upstream file that other tasks are editing.
3. **codegen-core** (`RISCVISelLowering.cpp`, `LowerINTRINSIC_WO_CHAIN`, which is already Custom for every intrinsic): each intrinsic becomes the generic node that upstream already selects to the GCC instruction for both F and Zfinx:
   - f32max → `ISD::FMAXIMUMNUM`, f32min → `ISD::FMINIMUMNUM`. These are IEEE 754-2019 maximumNumber/minimumNumber, which is exactly what `fmax.s`/`fmin.s` compute: a NaN operand gives the other operand, two NaNs give the canonical NaN, and -0.0 < +0.0. They are Legal and selected at `RISCVInstrInfoF.td:628-629`.
   - f32abs → `ISD::FABS`, f32sqrt → `ISD::FSQRT`.
   - The rounding builtins → `RISCVISD::FCVT_X` with the rounding mode RMM, RDN or RUP. This is the saturating `fcvt.w.s`: NaN and values too large give INT_MAX, values too small give INT_MIN. `fptosi(round/floor/ceil)` would be poison for those inputs, so it was not used.

**Why lowering to generic nodes, and not TableGen patterns straight to the instructions:** the generic nodes reuse upstream's F and Zfinx selection unchanged, so no duplicate F/Zfinx pattern pairs are needed. They also get SelectionDAG constant folding of max/min/abs, which GCC also does. Upstream turns its own RISC-V intrinsics into nodes in the same function (`Intrinsic::riscv_clmul` → `RISCVISD::CLMUL`, `RISCVISelLowering.cpp:9812` at `llvmorg-20.1.8`). Upstream also builds the same fixed-rounding-mode `FCVT_X` in `performFP_TO_INTCombine` (`RISCVISelLowering.cpp:16081`), which turns `fp_to_sint(ffloor x)` into `FCVT_X` with RDN. The other option was generic IR emitted from clang, which is how CORE-V does it (`EmitRISCVBuiltinExpr`, `CGBuiltin.cpp:23417`). That was rejected because it needs an `Upstream-File-Edit` in `CGBuiltin.cpp` while other tasks are editing that file.

## What breaks if this is wrong

- A wrong prototype or feature string rejects the SDK's float kernels again, or converts their arguments wrongly. The SDK compile survey would drop back from 528 to 520 files.
- If `FMAXIMUMNUM`/`FMINIMUMNUM` were replaced by `FMAXNUM`/`FMINNUM`, constant folding and DAG combines could pick either zero for max(-0.0, +0.0). The GVSoC test `const` rows 2-5 would show it.
- If the rounding builtins were lowered through `fp_to_sint`, NaN or out-of-range inputs would give arbitrary values instead of the saturated INT_MAX/INT_MIN. The GVSoC `rint`/`rdown`/`rup` rows for NaN, ±inf and ±3e9 would show it.
- A wrong rounding mode (rmm/rdn/rup swapped) changes every half-integer result, which the `rint`/`rdown`/`rup` rows cover.
- NaN payload is the one documented difference. When clang folds `f32min(x, NaN)` to `x` at compile time and `x` is itself a NaN, the result keeps `x`'s payload, while the instruction would return the canonical NaN. Either way the result is a NaN; LLVM does not guarantee NaN payloads.
- No lit test covers these builtins yet. `proposed_test` in the result file lists a clang CodeGen test, a Sema test and an llc test.

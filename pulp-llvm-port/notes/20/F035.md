# 20/F035: `xgap9` implies Zhinx; new GAP9 fp16 extensions `xpulpf16alt` and `xpulpfvec` (registered, no instructions yet)

This is a gap the fork already had (backlog B90, fp16 design `benchmarks/fp16-design/design.md` tasks T0 and T1). GAP9 has three kinds of half-precision instruction: plain IEEE half (`float16`, GCC's Xf16), bfloat16 (`float16alt`, GCC's Xf16alt) and packed pairs of either in one register (`v2h`/`v2ah`, GCC's Xfvec). All of them keep their operands in the integer registers. On 2026-09-28 the owner decided (PROGRESS.md D6, question Q7) that the `xgap9` extension added by 20/F017 must turn all three on. This change does that at the registration level. It is two commits: the registration commit, and one commit that adds the two new names to the unit test that lists every extension (owner-approved, see `notes/20/owner-test-exceptions.md` "F035 xpulpf16alt/xpulpfvec" and `notes/20/F035-regen.md`).

## What upstream changed

Nothing upstream broke this. The fork never had GAP9 half-precision support. The `xgap9` extension (`FeatureVendorXgap9`) was added today by fork commit `8484a65ff2fc` "fixup! [pulp] registration: extensions, features, processors, CSRs" (task 20/F017; `git log -S'FeatureVendorXgap9' llvmorg-20.1.8..ccfd68f6ac76 -- llvm/lib/Target/RISCV/RISCVFeatures.td`). At that point it implied only xpulpv and Zfinx, with a TODO pointing at B90. Upstream already has everything needed for `float16`: the Zhinx extension (`FeatureStdExtZhinx`, `RISCVFeatures.td:346` at `llvmorg-20.1.8`, half precision in integer registers). Clang computes `_Float16` natively as soon as Zhinx is on (`clang/lib/Basic/Targets/RISCV.cpp:351-352` at `llvmorg-20.1.8`: `HasLegalHalfType` for `zfh` or `zhinx`). Upstream has nothing for GAP9's bfloat16-in-GPR or packed-fp16-in-GPR instructions. Its bfloat16 extension, Zfbfmin, has conversions only and uses the F registers.

## Why this is equivalent

Before, `-march=rv32imc_xgap9` turned on xpulpv and Zfinx only. `_Float16` code was computed in single precision, with a library call (`__extendhfsf2` / `__truncsfhf2`) around every operation (`logs/20-F035-f16/f16tiny-int20-before.s`: 25 + 11 calls, `fadd.s`, `fmadd.s`). Code without half-precision types did not depend on this.

Now `xgap9` implies, in `RISCVFeatures.td`:
- **Zhinx.** The design measured that GAP9's `float16` instructions are the same bytes as upstream Zhinx (`benchmarks/fp16-design/tests/xf16_equals_zhinx.s`: `llvm-mc -mattr=+zfinx,+zhinx` and GAP9 GNU `as` give identical encodings for 14 instructions). So no new instruction is needed for `float16`.
- **`xpulpf16alt`** (new, version 1.0): bfloat16 (`float16alt`) scalar operations in integer registers. It implies Zfinx, because its conversions read and write `float` in integer registers.
- **`xpulpfvec`** (new, version 1.0): packed 2 x 16-bit float operations (`v2h`, `v2ah`) in one integer register. It implies xpulpv, the PULP packed-integer set whose `pv.pack`/`pv.extract` it relies on (design 6.3), and Zfinx, because `vfcpka.h.s` reads `float` operands from integer registers.

The two new extensions are features only. They add no instruction, no register class and no lowering, and nothing in the backend reads them yet. Design task T2 adds their instructions behind the new predicates `HasVendorXpulpf16alt` and `HasVendorXpulpfvec`. The records follow CORE-V's vendor-extension pattern: `FeatureVendorXCVsimd` at `RISCVFeatures.td:1218` at `llvmorg-20.1.8` (`RISCVExtension<1, 0, ...>` plus a `HasVendor...` predicate). The implication lists follow SiFive's `FeatureVendorXSfvcp` at `RISCVFeatures.td:1113` (`RISCVExtension<..., [FeatureStdExtZve32x]>`). Name and description come from the record name, which upstream `d280a9c5e226` "Refactor class RISCVExtension" introduced.

**Names.** The design proposed `xpulpf16alt` and `xpulpfvec` (its Q7). I kept them for these reasons:
- They follow the `xpulp<subset>` naming the PULP team uses in its own LLVM 22 branch (`pulp/llvmorg-22.1.7-pulp:llvm/lib/Target/RISCV/RISCVFeaturesXpulp.td`: `xpulpabs`, `xpulpbitop`, `xpulpvect`, ...), and the fork's `xpulpv`.
- They name GCC's extension (Xf16alt, Xfvec).
- They end in a letter. Clang's ISA-string parser reads trailing digits (and `<digits>p<digits>`) as a version (`findLastNonVersionCharacter`, `llvm/lib/TargetParser/RISCVISAInfo.cpp:167`), which is why F017 had to spell `xgap9` as `xgap` version 9.0. Measured: `-march=rv32imc_xpulpf16alt` parses, and `-march=rv32imc_xpulpf16alt2` is rejected with "unsupported version number 2".
- They do not clash with the Snitch smallfloat extensions (`xfalthalf`, `xfvechalf`, `xfvecalthalf`, ..., defined in `RISCVInstrInfoXsmallfloatGen.td`). Those use the F registers and encode `.ah` differently (design 3.4), so they must stay separate.

**Snitch isolation.** No new record implies a Snitch `xf*` extension, and no Snitch extension implies a new one. Every Snitch smallfloat instruction is predicated only on its own `HasExtXf*` predicate: `grep Predicates RISCVInstrInfoXsmallfloat*.td` shows no Zhinx or Zfinx predicate. So `xgap9` enables no Snitch-only instruction. That matters because GAP9 has no 8-bit float and no Xfaux (design 3.1). Measured: `-march=rv32imc_xgap9 -dM` defines no `__riscv_xf*` macro.

Measured with this build (`logs/20-F035.verify.log`; before: `logs/20-F035.repro.log`, int-20 = integration head `ccfd68f6ac76`):
- `clang -march=rv32imc_xgap9 -dM -E`. Before: `__riscv_xgap`, `__riscv_xpulpv`, `__riscv_zfinx`, `__riscv_zicsr`, `__riscv_zmmul`. After: the same, plus `__riscv_zhinx 1000000`, `__riscv_zhinxmin 1000000`, `__riscv_xpulpf16alt 1000000` and `__riscv_xpulpfvec 1000000`. `__gap9__`, `__pulp__` and the other F017 macros are unchanged.
- ELF arch attribute. Before: `rv32i2p1_m2p0_c2p0_zicsr2p0_zmmul1p0_zfinx1p0_xgap9p0_xpulpv2p0`. After: `rv32i2p1_m2p0_c2p0_zicsr2p0_zmmul1p0_zfinx1p0_zhinx1p0_zhinxmin1p0_xgap9p0_xpulpf16alt1p0_xpulpfvec1p0_xpulpv2p0`. The explicit spelling `-march=rv32imc_zfinx_zhinx_xpulpv2_xpulpf16alt_xpulpfvec` gives the same string without `xgap9p0`. `llc -mattr=+xpulpf16alt,+xpulpfvec` prints `.attribute 5, "rv32i2p1_zicsr2p0_zfinx1p0_xpulpf16alt1p0_xpulpfvec1p0_xpulpv2p0"`. `rv32imfc_xpulpf16alt` is rejected ("'f' and 'zfinx' extensions are incompatible"), as with `xgap9`.
- `float16` on GVSoC. `logs/20-F035-f16/f16tiny.c` is a new probe: add, sub, mul, div, contracted `a*b+c` and `a*b-c`, neg, `<`, `<=`, `==`, to/from float, to int/unsigned, and from int/unsigned, over 512 inputs including ±0, ±inf, NaN, subnormals and random bit patterns. It was built with GAP9 GCC (`-DT=float16 -march=rv32imcxgap9 -mPE=8 -mFC=1 -O2`) and with this clang (`-DT=_Float16 -march=rv32imc_xgap9 -ffp-contract=fast -O2`), then run on `ri5ky_testbench`. The output is identical (16/16 hashes). The design's `tests/numeq.c` built the same way is also identical (12/12 lines). The clang assembly now uses `fadd.h fsub.h fmul.h fdiv.h fmadd.h fmsub.h fneg.h flt.h fle.h feq.h fcvt.s.h fcvt.h.s fcvt.w.h fcvt.wu.h fcvt.h.w fcvt.h.wu`, the same set of mnemonics GCC emits for the same file (GCC has one extra `fcvt.wu.h`), and calls no library routine (`logs/20-F035-f16/`, runner `run.sh`).
- GAP9 sweep. On a scratch copy, both compilers used `-march=rv32imc_xgap9`: base = int-20, mine = this build (`logs/20-F035-sweep/`). All 54 disassemblies (27 kernels x O2/O3) are identical. The 5 kernels that already fail to compile have identical diagnostics. None of the sweep kernels uses half-precision types.

## What breaks if this is wrong

- **Wrong implied set.** `-march=rv32imc_xgap9` code would change for programs that do not use fp16. The GAP9 sweep identity check shows it does not. `float16` code would also differ from GCC: if Zhinx were missing, `_Float16` would go back to single precision with library calls; if Snitch extensions leaked in, invalid instructions would run on GAP9. `f16tiny` and `numeq` on GVSoC, plus the `__riscv_xf*` check, show neither happens.
- **Wrong name spelling.** Wrong names would make the SDK's future `-march` strings and the arch attribute disagree with GCC's names. `RiscvExtensionsHelp.CheckExtensions` guards name and version.
- **Implications of the new extensions.** Implying Zfinx means neither extension can be combined with F. This is intended, because GAP9 keeps all float in integer registers, but it would reject a hypothetical F-register core using `xpulpfvec`. No such core exists.
- **ABI.** A `_Float16` in an ilp32 call was already passed in an integer register (soft-float ABI), and it still is. With Zhinx it is now computed natively. Only code that uses `_Float16` changes, and it now matches GCC bit for bit on GVSoC.
- **Missing tests.** No lit test checks `xgap9`'s implied set or the new names on the command line (`clang/test/Preprocessor/riscv-target-features.c` has no PULP RUN lines). A test is proposed in the result file.

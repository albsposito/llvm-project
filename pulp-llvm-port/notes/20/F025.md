# 20/F025: size hardware loops from real instruction sizes, repeat until stable, and fall back instead of failing when a loop is too long

Written for a reader who does not know LLVM. This is a pre-existing fork defect (backlog B81), not a port break.

## What upstream changed

Nothing upstream broke this. The code is the fork's `llvm/lib/Target/RISCV/PULP/PULPFixupHwLoops.cpp` (`fixupLoopInstrs`), added by fork commit `f1b7aebff8c2` "[LLVM/PULP/SNITCH] Support for PULP and Snitch cores/platforms" (`git log pulp/integer_SIMD_fix -S'offsetIncrease'` finds only this commit).

Background. A PULP hardware loop starts with a setup instruction. The setup gives the address of the loop's last instruction as a forward distance from the setup itself, counted in 2-byte units. The two short forms have fields of different widths (`RISCVInstrInfoXpulp.td`; the assembler checks them in `RISCVAsmBackend.cpp`, `fixup_pulpv2_loop_setupi`/`_setup`; GVSoC computes `end = pc + (uimm << 1)` in `lp_setup_exec`/`lp_setupi_exec`, `pulp_v2.hpp:895-918`):
- `lp.setupi` (loop count is a constant): 5-bit field, so the distance can be at most 62 bytes;
- `lp.setup` (loop count is in a register), and `lp.endi` in the long form: 12-bit field, so at most 8190 bytes.

If `lp.setupi` cannot reach, the pass replaces it with the long form (`lp.starti` + `lp.endi` + `lp.counti`, 12 bytes instead of 4). The pass also pads loops that are shorter than two instructions with nops.

What was wrong:
1. **Decision made too early.** The pass visited the setups once, in address order. An outer loop's setup comes before the loops nested inside it, so the outer loop's form was chosen before the inner loops got their padding nops or their long form. Those bytes land inside the outer loop afterwards, so its real distance ends up larger than the one used for the decision. The `bool offsetIncrease` named in B81 (it adds 1 instead of the number of inserted bytes) is part of the same bookkeeping, but on its own it never changed a decision: it only shifts blocks after the insertion point, and every loop whose setup and end both lie after that point shifts by the same amount.
2. **Alignment padding not counted.** After this step the pass moves each setup that is not the first instruction of its block into a new block aligned to 4 bytes. With compressed (2-byte) instructions the assembler may then insert a 2-byte `c.nop` before an inner setup, inside the outer loop. The sizing never counted it.
3. **Arbitrary limit.** `lp.setupi` was allowed only for loops of at most 50 bytes (`-pulp-loop-range-immediate=50`). The encoding allows 58 (62 minus the 4-byte setup). The 8 bytes of slack hid mistakes 1-2 in most cases, but not all. For example, an outer `lp.setupi` loop containing three one-instruction inner loops (each padded and aligned) is measured at 50 bytes and ends up at 68, and the build fails with `error: fixup value out of range` (`logs/20-F025.repro.log`, `logs/20-F025/near-limit-37-6-3.kern.c`, `-O3`, rv32imc).
4. **No way out when a loop is too long.** When a loop was longer than `lp.setup` or `lp.endi` can encode, the compiler aborted (`UNHANDLED: Hardware Loop length ...`) or the assembler failed (`fixup value out of range`), for example for a loop body of 2046-2050 four-byte instructions.

## Why this is equivalent

The generated code changes only for loops close to a limit. Everywhere else it is byte-identical (see the verification below).

- **Real sizes and a fixed point (1).** The fork already takes each instruction's size from `getInstSizeInBytes`, which knows which instructions will be compressed to 2 bytes. After each insertion (padding nops or long form), the pass now measures every loop again and repeats until nothing changes (`fixupOneLoopLength`, called in a loop). Upstream branch relaxation (`llvm/lib/CodeGen/BranchRelaxation.cpp:770-772` at `llvmorg-20.1.8`, `while (relaxBranchInstructions())`) works the same way. It also measures blocks with `getInstSizeInBytes` (`computeBlockSize`, line 204-211) and redoes the layout after each change. This terminates, because each setup can switch to the long form only once and each loop is padded only once, and neither step ever makes a loop shorter. The `bool offsetIncrease` bookkeeping is gone: no offsets are carried between iterations.
- **Alignment (2).** When a setup will move into a 4-byte aligned block, the measurement adds its padding. It also adds padding for blocks with an alignment larger than the instruction size. If the loop's own setup is 4-byte aligned (it is the one being moved, or its block is already aligned), later addresses are known modulo 4, and the padding is computed exactly. Otherwise the worst case is assumed (4 minus 2 bytes with compressed instructions), as upstream branch relaxation does when the function's placement is unknown (`BasicBlockInfo::postOffset`, `BranchRelaxation.cpp:68-78`).
- **Limit (3).** The decision uses the measured distance from the setup to the last instruction, with alignment padding included. The default limit is now the encoding limit: 58 bytes for `lp.setupi`, and 8186 bytes for `lp.setup` (8190 minus the setup). `-pulp-loop-range-immediate=N` and `-pulp-loop-range-register=N` still restrict further and are capped at the encoding limits (their help text now says "bytes"; it wrongly said "instructions"). GAP9 GCC also uses the whole field: it selects `lp.setupi` up to an end distance of 60 bytes (14 four-byte instructions) and stops at 64 (`riscv32-unknown-elf-gcc -march=rv32imcxgap9 -O2`, loop of N `xor`s). So loops of 52-58 bytes now keep the 4-byte `lp.setupi` instead of the 12-byte long form, as with GCC.
- **Fallback (4).** Before `fixupLoopLatch` removes the loop's compare-and-branch, the new `removeTooLongLoops` estimates the largest distance each loop could reach: all its instructions (including the counter update that may later be removed), worst-case alignment, and the most every nested loop can still grow (+8 long form or +4 padding, +4 end nop, +2 alignment). If that estimate exceeds what `lp.setup` or `lp.endi` can encode, the setup instruction is deleted and the loop stays a normal software loop. The fork's `removeUncountableLoops` in the same file already does this, and that software loop is still complete at this point. `PULPHardwareLoops` already refuses loops over 4095 bytes, counting 4 bytes per instruction (`PULPHardwareLoops.cpp:1538-1551`), so this only triggers for loops that grew afterwards, e.g. a large inline asm block. The old abort stays as an assertion-style safety net. After this check it cannot be reached. Because the estimate is conservative, loops within a few bytes of 8190 become software loops (e.g. 2045 `mul`s without compressed instructions, where the base build still fit at 8188).
- The layout bug that turned out to be behind fuzz seed 6635 (below) is detected and left alone: when the end label lies before the setup, the pass no longer computes a negative length. As before, the assembler still reports it.

Reference for the whole approach: upstream `llvm/lib/CodeGen/BranchRelaxation.cpp` at `llvmorg-20.1.8` (fixed-point loop, `getInstSizeInBytes`, worst-case alignment). CORE-V `XCV*` has no hardware-loop code generation upstream (only the assembler), so there is no closer RISC-V reference. The fork's Snitch FREP pass has no range selection.

## What breaks if this is wrong

- If the measurement underestimates, `lp.setupi` or `lp.setup` is chosen for a loop it cannot reach. The assembler then fails with `error: fixup value out of range` (the checks in `RISCVAsmBackend.cpp` stop a silently wrong encoding). Visible in the near-limit set and the fuzzer (compile failures).
- If it overestimates, loops that fit get the long form (8 more bytes and 2 more cycles before the loop) or become software loops, as before this change. Visible as `lp.starti` or a missing `lp.` instruction where GCC uses `lp.setupi`, and as cycle-count increases in the GAP9 sweep.
- If the fixed point were wrong (padding in the wrong place, or a loop measured twice), a loop's range would change: GVSoC results differ, or a loop runs the wrong number of iterations.
- No lit test covers loops near the limits (proposed in the result file). The fork's hardware-loop lit tests are all far from the limits and pass unchanged.

Verification (base = `build/int-20` at `ccfd68f6ac76`, a binary snapshot; new = `build/20-F025`):
- **Near-limit set** (`logs/20-F025/nearlimit/`: `gen.py K M CNT`, an outer loop with K non-compressible 4-byte `mul`s and M one-instruction inner loops that need padding and alignment; count constant 37 → `lp.setupi`, or `n` → `lp.setup`). K = 0..16 steps the outer body by 4 bytes and each inner loop adds about 12 bytes, so the new build's outer `lp.setupi` end distances cover every even value from 8 to 62 (the limit) and the long form takes over from 64 up (the `lp.endi` distances run from 60 to 132), with and without compressed instructions (rv32imc / rv32im), nested (M = 1..3), at -O2/-O3/-Os: 136 kernels, 816 builds, all built with `-verify-machineinstrs`. The new build compiles all of them. Every one runs on GVSoC with the same result as GAP9 GCC `-O2 -mnohwloop` (`logs/20-F025/nearlimit-gvsoc.txt`). The base build fails on 37-6-3 c -O3 (fixup out of range). The new build compiles it (outer loop in the long form, which reaches `lp.endi`+68) and runs it correctly. All 36 form differences from base go in one direction: the long form becomes `lp.setupi`, with end distances 52-62, each run on GVSoC. Nothing that fit before became longer.
- **Near 8190** (`logs/20-F025/near8190.txt`, one inline asm block of N `mul`s): N ≤ 2044 is identical to base. At N = 2045-2046 the base build still fit, and the new build keeps a software loop in 3 of 8 builds (the conservative bound, ≤ 6 bytes). Base fails in 12 of the 14 builds at N ≥ 2046, with `fixup value out of range` or the `UNHANDLED ... abort`. The new build compiles all of them as software loops, and 5 of these ran on GVSoC with results equal to GAP9 GCC `-mnohwloop`.
- **GAP9 sweep** (all `src/*.c` and `k12_*`, -O2/-O3/-Os, `logs/20-F025/gap9-sweep.sh`): assembly and disassembled objects are byte-identical to base for all 81 compiling builds (57 with hardware loops), with the same 15 compile failures (Sema/shim, `-file` TUs and k10b). All 81 pass the verifier. No SDK kernel is near a limit.
- **Fuzzer** (`benchmarks/hwloop-fuzz`, new reference: host gcc -O0 plus a GAP9 GCC `-mnohwloop` cross-check, 3 input sets). New seeds 9001-9400 × -O2/-O3/-Os with `-verify-machineinstrs`, run twice: with the fuzzer's `-pulp-loop-range-immediate=0` (all 1200 builds identical to base) and with the default range (`logs/20-F025/fuzz-one-default-range.sh`: 1198 identical, 2 changed, seeds 9005 and 9248 -Os, where a 52-58-byte loop now uses `lp.setupi` instead of the long form, both correct on GVSoC). No new crash, hang or wrong result. Seed 9301 -O3 gives a wrong result in both runs, with assembly identical to base (pre-existing, listed in the result file).
- **Lit**: `llvm/test/CodeGen/RISCV` + `llvm/test/MC/RISCV` (which include the fork tests): 2581/2582 pass. The only failure is `rvv/vsetvli-insert-zve64f.mir`, a known failure that is also red on int-20 (`logs/20-F025.lit.log`).
- **Seed 6635 -O3** (F013 review) is **not** this bug and still fails in the same way. Machine block placement put an inner loop (`.LBB0_5`) above its preheader, so its setup is followed by `j .LBB0_5` and its end label `.LBB0_34` lies *before* the setup (a negative distance). No range choice can encode that. It is a loop-layout defect (`fixupLoopLayout`/`fixupLoopPreheader` do not handle "loop placed above its setup"), reported in the result file.

# 20/T006: update the expected CSR diagnostic wording in rv32xmempool-invalid.s (owner exception T001)

Written for a reader who does not know LLVM. Test-only change made under the recorded owner exception `notes/20/owner-test-exceptions.md#t001`; regen report `notes/20/T006-regen.md`.

## What upstream changed

Upstream commit `107f3efdbede` "[RISCV][MC] Make error message of CSR with wrong extension more detailed (#104424)" (in `llvmorg-19.1.7..llvmorg-20.1.8`) changed the assembler error printed when a program uses a control/status register (CSR) whose extension is not enabled. The old generic text `system register use requires an option to be enabled` became a specific one naming the register and the missing extension, e.g. `system register 'trace' requires 'xmempool' to be enabled`. Upstream updated its own tests in the same commit (for example `llvm/test/MC/RISCV/machine-csr-names-invalid.s`, `rv32-only-csr-names.s`).

## Why this is equivalent

The fork test `llvm/test/MC/RISCV/rv32xmempool-invalid.s` checks that the PULP `trace` CSR (0x7D0, `RISCVSystemOperands.td:472` in the fork) is rejected when `+xmempool` is not enabled. The fork's behaviour is unchanged: the assembler still rejects `csrr t0, trace` at the same line and column (5:13), only the wording of the message is new; with `-mattr=+xmempool` the same instruction still assembles to encoding `[0xf3,0x22,0x00,0x7d]` (checked with build/int-20 `llvm-mc`). Exactly one CHECK line changed, only its message text; the `:[[@LINE+1]]:13: error:` prefix is kept in the format upstream's own updated tests use. No RUN line, other CHECK line or input line changed. The fork does not modify the diagnostic code path; it is upstream's `RISCVAsmParser::parseCSRSystemRegister`.

## What breaks if this is wrong

If the new expected text were wrong, `llvm-lit llvm/test/MC/RISCV/rv32xmempool-invalid.s` would fail (FileCheck no match). If the fork's feature gating of `trace` were ever lost (the CSR accepted without `+xmempool`), this test would still catch it, because `not llvm-mc` would fail and no error line at 5:13 would be printed. The test does not cover the positive case (`+xmempool` accepted); that is covered by the fork's valid xmempool MC tests.

# 20/F026: plain-C bit-field clear/set now selects p.bclr / p.bset (backlog B94, part)

Written for a reader who does not know LLVM. Four sections, all required (policy_check.py checks the headings).

## What upstream changed

Nothing upstream broke this. It is a fork defect that has been there since the fork added the patterns, in `f1b7aebff8c2` "[LLVM/PULP/SNITCH] Support for PULP and Snitch cores/platforms" (Federico Ficarelli, 2022-08-25). Found with `git -C /home/ubuntu/llvm-project log pulp/integer_SIMD_fix -S'def shiftedFlippedMask' -- llvm/lib/Target/RISCV/`. The pattern lines were later reformatted in `93e0fc427e93` "IN PROGRESS: Fixing the encoding of Xpulp instructions", without a change in behaviour. ref-18, the step-19 port and the step-20 integration head (`7459255b6120`) never emit `p.bclr`/`p.bset` for plain C: `logs/20-F026.repro.log`, and `logs/20-F026/idioms.ref18.s` shows 0.

The fork has patterns meant to turn `x & ~(field)` into `p.bclr` and `x | field` into `p.bset`, where the field is a contiguous run of bits. They check the constant with `shiftedFlippedMask` and `shiftedMask`, which are `TImmLeaf`. A `TImmLeaf` only matches the special constant form that builtin arguments take. In plain C the constant is an ordinary constant, so the patterns never fire. F008 fixed the same kind of defect for `p.clip`.

A second reason hides many of the remaining cases. When the same wide mask is used more than once in a function, LLVM's constant-hoisting pass loads it into a register once, and the `and`/`or` then sees a register, not a constant. That pass asks the target cost model (`RISCVTTIImpl::getIntImmCostInst`) whether an immediate is free for that instruction. The fork's cost model did not know about `p.bclr`/`p.bset`, so it said no.

## Why this is equivalent

This change is meant to alter the generated code, but only by replacing an instruction sequence with one instruction that computes the same value.

**Semantics.** `p.bclr rD, rs1, Is3, Is2` computes `rs1 & ~(((1 << (Is3+1)) - 1) << Is2)`. `p.bset` computes the same with `|`. Source: GVSoC `gap_sdk_release/gvsoc2/core/models/cpu/iss/include/isa/pulp_v2.hpp:1967` (`p_bclri_exec`) and `:2041` (`p_bseti_exec`), and `isa_lib/int.h:406-414` (`lib_BSET`/`lib_BCLR`). The immediates come from the fork's existing transforms, unchanged: `flippedMaskWidthMinus1`/`trailing1s` for bclr, and `maskWidthMinus1`/`trailing0s` for bset. The builtin patterns use the same transforms, and they already match GCC.

**Change 1, `RISCVInstrInfoXpulp.td` (insn-tablegen).** Two new `ImmLeaf` checks, `shiftedFlippedMask_imm` and `shiftedMask_imm`, match ordinary constants. They replace the `TImmLeaf` checks in the two plain-C patterns only. The builtin patterns (`int_riscv_pulp_bclr/bset/binsert`), the insert/extract/clip patterns and the old `TImmLeaf` definitions are not touched. The new checks leave alone any constant that fits a 12-bit signed immediate, so a single `andi`/`ori` stays. They also leave 0xffff to its existing `p.exthz`. This is the rule upstream uses for its own single-instruction bit clear/set: Zbs `BCLRMask`/`SingleBitSetMask` are `ImmLeaf`s with `!isInt<12>(Imm)`, `llvm/lib/Target/RISCV/RISCVInstrInfoZb.td:61-72`, used at `:526-529`, `llvm/lib/Target/RISCV/RISCVInstrInfoZb.td` at `llvmorg-20.1.8`. CORE-V (`RISCVInstrInfoXCV.td:730-741` at `llvmorg-20.1.8`) has `cv.bclr`/`cv.bset` patterns only for its intrinsics, not for plain C, so Zbs is the closest upstream reference for the plain-C part.

**Change 2, `RISCVTargetTransformInfo.cpp` (codegen-core).** `getIntImmCostInst` now reports a 32-bit `and` mask whose complement is a contiguous field as free on PULP, and likewise a 32-bit `or` mask that is a contiguous field. Constant hoisting then leaves the mask next to the instruction, so change 1 can use it. This is exactly how upstream treats `bclri`/`bseti` (same function, `llvm/lib/Target/RISCV/RISCVTargetTransformInfo.cpp:212` and `:225` at `llvmorg-20.1.8`). It only changes where a constant is materialised, never the value computed.

GAP9 GCC (`-march=rv32imcxgap9`) emits p.bclr/p.bset for every contiguous mask, including ones that fit `andi`/`ori`. We keep `andi`/`ori` there (same cost, and compressible), as the task requires. For all wider masks the output is now the same single instruction as GCC, with the same immediates and the same encoding word (`logs/20-F026/enc.after.txt` vs `enc.gcc.txt`; for example `p.bclr a0,a0,7,8` = `ce853533`).

  - p.bclr went from 0 to 26 and p.bset from 0 to 18. GCC has 560/71, but only 29/16 of GCC's have a mask too wide for andi/ori. The other 531/55 are cases where we deliberately keep andi/ori.

## What breaks if this is wrong

- A wrong width or offset would clear or set the wrong bits in plain C that masks register fields, flags or packed data. Examples are the `mbedtls` and PMSIS drivers in the spot check, and any `REG &= ~(FIELD_MASK)` / `REG |= BIT` code. Results would differ from the GCC build on GVSoC or hardware. `logs/20-F026/sim/sim.sh` would report mismatches.
- If the 12-bit guard were wrong, `andi`/`ori` would turn into `p.bclr`/`p.bset`. That gives the same value, but loses the compressed forms (code size only).
- If the patterns stopped matching again, only performance would regress: `lui;addi;and` would come back.
- No lit test covers these idioms today. `llvm/test/CodeGen/RISCV/intrinsics/xpulpv.ll` checks only the builtins. See `proposed_test` in the result file.

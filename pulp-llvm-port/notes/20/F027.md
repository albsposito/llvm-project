# 20/F027: let ld.lld link GCC-built objects that contain PULP hardware loops

Written for a reader who does not know LLVM. Four sections, all required (policy_check.py checks the headings).

## What upstream changed

Nothing upstream broke this. It is a **pre-existing fork defect** (backlog B53), present in every fork toolchain. A PULP hardware loop starts with `lp.setup`, `lp.setupi`, `lp.starti` or `lp.endi`. Each of them stores the distance to a loop label inside the instruction, counted in halfwords (12 bits wide, 5 bits for the end label of `lp.setupi`). LLVM's assembler works this distance out itself. The GAP9 GCC toolchain's assembler (GNU as, binutils 2.28) writes the value too, but it also leaves a **relocation**, a note that tells the linker to recompute the value once code has been placed and relaxed. It uses its own numbers: `R_RISCV_REL12` = 57 for the 12-bit field and `R_RISCV_RELU5` = 58 for the 5-bit field.

Upstream later assigned the same numbers to other relocations: 57 is `R_RISCV_32_PCREL` (upstream `67820e015fc7` "[RISCV] Recognize new relocation types", 2017-08, `RISCV.def:54`) and 58 is `R_RISCV_IRELATIVE` (`9f854c048997` "[ELF][RISCV] Add R_RISCV_IRELATIVE"). ld.lld has handled 57 as a 32-bit data word since its first RISC-V support (`5cd9c6bcd8a4` "Support RISC-V"). The fork's own numbers for these relocations, `R_PULPV2_LOOP_SETUP`/`SETUPI` = 66/67, come from fork commit `f1b7aebff8c2` "[LLVM/PULP/SNITCH] Support for PULP and Snitch cores/platforms" (found with `git log pulp/integer_SIMD_fix -S R_PULPV2_LOOP_SETUP`). That commit taught lld to *ignore* them (`R_NONE`).

Measured on the integration head (`logs/20-F027.repro.log`):
- An object with `lp.setupi` stops the link: "unknown relocation (58)".
- An object with only `lp.setup`/`lp.starti`/`lp.endi` is **silently mislinked**. lld writes a 32-bit PC offset over the whole instruction, so the loop instruction turns into garbage. 145 of the 158 GCC-compiled fuzzer objects that have loop relocations are like this. With int-20's lld, 20 of 20 such programs gave a wrong result or hung on GVSoC.
- An LLVM object that does carry 66/67 (a loop label that is external or in another section) links, but the field is left at 0 without any warning.

## Why this is equivalent

One file changes: `lld/ELF/Arch/RISCV.cpp`, a file the fork already touches (cluster mc).

- A new helper, `pulpLoopFieldBits`, identifies a PULP loop relocation and returns the width of its field. The fork's 66/67 always qualify. 57 and 58 qualify only when the 32-bit word they point at is a PULP loop instruction: major opcode `0x7b` with funct3 0, 1 or 4 (`lp.starti`, `lp.endi`, `lp.setup`) for 57, and funct3 5 (`lp.setupi`) for 58. Everything else keeps its upstream meaning. A real `R_RISCV_32_PCREL` points at a data word, which an LLVM (RELA) object stores as 0, so it never matches. Deciding from the instruction follows upstream's own precedent: lld's x86 port decides `R_386_GOT32/GOT32X` from the instruction bytes (`lld/ELF/Arch/X86.cpp:102-107` at `llvmorg-20.1.8`, "their calculations depend on the instructions they are applied to").
- `getRelExpr`: these relocations are PC-relative (`R_PC`, target minus the address of the loop instruction), like upstream `R_RISCV_BRANCH` (`lld/ELF/Arch/RISCV.cpp:285-291` at `llvmorg-20.1.8`). The fork's two `return R_NONE` cases are replaced. They made lld ignore the relocation. 57 already returned `R_PC` upstream. 58 no longer fails with "unknown relocation" when it sits on `lp.setupi`, and still fails anywhere else.
- `relocate`: writes `distance >> 1` into bits 31:20 (bits 19:15 for `lp.setupi`) and leaves the other bits of the instruction alone. This is the same "range check, alignment check, merge the field into the instruction" shape as upstream `R_RISCV_BRANCH` (`lld/ELF/Arch/RISCV.cpp:390-403` at `llvmorg-20.1.8`), except that the range is unsigned: the label must be ahead of the instruction. It uses the same limits and the same alignment rule as the fork's assembler (`RISCVAsmBackend.cpp`, task 20/F010) and as GNU as. The error names the PULP relocation, for example `relocation R_PULPV2_LOOP_SETUP out of range: 8192 is not in [0, 8191]`, and shows a label behind the instruction as `-2`. GNU ld 2.28 has no range check at all: it silently truncates (8192 becomes 0).

The encoding matches GNU ld exactly. Pure-LLVM links do not change: LLVM objects normally carry no loop relocations, and a genuine `R_RISCV_32_PCREL` in `.eh_frame` still resolves correctly.

Verified (evidence under `logs/20-F027-evidence/`, details in the result file):
- Hand-written GNU-as objects that use every form on both loop levels, with forward labels at the range limits (62 bytes for `lp.setupi`, 8190 bytes for `lp.setup`, 12-bit `lp.endi`), plus 4-byte and zero distances. The `.text` linked by ld.lld is byte-identical to GNU ld's, and every field equals the value GNU as had pre-filled.
- An external target placed with `--defsym`: 0, 4 and 8190 give bytes identical to GNU ld. 8192 and -2 give a range error, and 8191 gives an alignment error.
- 240 GCC-compiled random-loop programs (hwloop fuzzer seeds 1-80, O2/O3/Os, `-mPE=8 -mFC=1`; 396 loop relocations in total). The loop function is byte-identical between ld.lld and GNU ld, and all 240 print the same result on GVSoC, with relaxation both on and off.
- The F010 nested-loop kernel, assembled by GNU as with GCC `main`/`crt0` and linked by ld.lld, prints `RES 100237` on GVSoC. With `--no-relax` the whole `.text`, including libgcc, is byte-identical to GNU ld. A mixed link (clang `main`/`crt0` plus the GCC-assembled kernel) also gives 100237.
- GAP9 sweep objects: all 194 LLVM objects (ref18/port19/port20/...) link to byte-identical ELFs with int-20's lld and with this lld (compared without the `.comment` section, which records the lld git hash). All 62 GCC objects (331 loop relocations) now link with lld. Their loop instructions match GNU ld. The only differences are calls to symbols left undefined in this test, which the two linkers resolve differently.
- Reverse direction: LLVM objects linked by GNU ld work (llvm-mc kernel plus GCC main gives 100237, and clang `loop.c` runs correctly), because LLVM leaves no loop relocations. The exception is an LLVM object that carries 66/67, which GNU ld rejects ("unrecognized relocation (0x42)").
- Lit: `lld/test/ELF/riscv*` 44/44 pass, and `llvm/test/MC/RISCV` plus the fork MC tests 515/515 pass.

## What breaks if this is wrong

- **Wrong field or wrong base address:** GCC-built code linked by ld.lld would have loops that end at the wrong instruction, so GVSoC programs give wrong results or hang. `llvm-objdump -d` of the lld output would show an end offset that differs from the GNU ld link.
- **The instruction test misfires on data:** a real `R_RISCV_32_PCREL` data word would be treated as a loop field, and `.eh_frame` or a PC-relative table would get corrupted, visible as wrong unwinding or wrong data. The lld RISC-V tests and the 194 byte-identical sweep links would have shown this.
- **Range check too strict:** a valid GCC object would fail to link with "out of range". The limits are the same ones GNU as enforces, so GNU as would already have rejected any such object.

No lit test covers any of this: no lld test links an object with PULP loop relocations. The proposed test is in the result file.

# 20/F041: add GAP9's half-precision absolute-value builtins `__builtin_pulp_f16abs2`, `f16altabs2`, `f16abs`, `f16altabs`

Pre-existing fork gap (backlog B97, fp16 design task T6, SDK compile survey M2a checkpoint item 1). Two commits, both in the clang-builtins cluster, touching two files (`clang/include/clang/Basic/BuiltinsRISCVXpulp.td` and `clang/lib/CodeGen/CGBuiltin.cpp`): the first adds the four builtins; the second (review round 1) makes the `f16altabs2` lowering opaque (two `p.bclr`) so that no bfloat16 `fabs` can be formed.

## What upstream changed

Nothing upstream broke this. The fork never defined these builtins, which GAP9 GCC provides and the GAP9 SDK calls through `Absv2h`/`Absv2ah`/`Absf16`/`Absf16a` (`tools/autotiler_v3/BasicKernels/DSP_Libraries/FloatDefines.h:74-86`), in particular from `FastMathFunctions/FastFloatApprox16.h`, which almost every fp16 DSP and CNN kernel includes. That header silences `-Wimplicit-function-declaration`, so clang implicitly declared the unknown builtin as returning `int` and then rejected "passing 'int' to parameter of incompatible type 'v2h'": 77 of the 97 files that GAP9 GCC compiles and our clang did not (M2a checkpoint, `benchmarks/sdk-compile-survey/checkpoint-M2a-2026-09-29/report.txt`). The types they work on became available with fork commit `2c98caa32c1b` fixup! [pulp] clang-driver: target macros and driver flags (task 20/F039: `float16` = `_Float16`, `float16alt` = `__bf16`); the place the new code sits, the fork's RISC-V builtin dispatch in `CGBuiltin.cpp`, is from fork commit `7297b03551d0` fixup! [pulp] clang-builtins: RISC-V builtins and their Sema checks (task 20/F019, `__builtin_shuffle`).

One upstream fact decides the lowering: in LLVM 20, when the back end has no bfloat16 register type (our case: GAP9's `.ah` instructions are not implemented yet, fp16 design T3), a bfloat16 `fabs` (and `fneg`) is legalized by converting to `float`, clearing the sign there, and rounding back through a call to `__truncsfbf2` (`DAGTypeLegalizer::SoftPromoteHalfRes_UnaryOp`, `llvm/lib/CodeGen/SelectionDAG/LegalizeFloatTypes.cpp` at `llvmorg-20.1.8`). That call quiets signalling NaNs and does not exist in GAP9's libgcc (so programs do not link). Upstream fixed this after LLVM 20: `11571a005a38` "Fix legalizing `FNEG` and `FABS` with `TypeSoftPromoteHalf` (#156343)" (first in `llvmorg-22.1.0`) turns them into integer AND/XOR.

## Why this is equivalent

Before: the four builtins did not exist. Now:

1. **Prototypes** (`BuiltinsRISCVXpulp.td`, new block at the end of the file): exactly GAP9 GCC's (`benchmarks/builtins-spec/spec.json`): `float16 f16abs(float16)`, `float16alt f16altabs(float16alt)`, `v2h f16abs2(v2h)`, `v2ah f16altabs2(v2ah)`, where `v2h`/`v2ah` are GCC vectors of two `_Float16`/`__bf16` (`_Vector<2, ...>`, the same kind of vector the SDK typedefs in `Emulation/Gap.h:28-30`). Attributes `NoThrow, Const` like the other pure PULP builtins. Features: `f16abs` "xpulpv,(zhinx|zfh)" (the spec's choice for batch D), `f16altabs` "xpulpv,xpulpf16alt", `f16abs2` "xpulpfvec,zhinx", `f16altabs2` "xpulpfvec,xpulpf16alt"; `-march=rv32imc_xgap9` has all of them, and without them clang says "needs target feature ..." like every sibling (checked per builtin and per `-march`, `logs/20-F041-repro/gating.txt`). Diagnostics match GCC on `logs/20-F041-repro/d.c`: both reject an `int` argument to `f16abs2`, a `v2h` argument to `f16abs` and a second argument; both accept a same-size vector (`v2s`, `v2ah`) where `v2h` is expected, and `_Generic` sees the GCC result types.
2. **Semantics.** GAP9 GCC emits `fabs.h`, `fabs.ah`, `vfabs.h`, `vfabs.ah` (sign injection of a value with itself): each 16-bit lane gets its sign bit cleared, nothing else changes, NaN payloads (signalling ones too) are kept, no FP exception. Measured on GVSoC with GCC-built code, identical to a host C reference that does `x & 0x7fff7fff` (below).
3. **Lowering** (`CGBuiltin.cpp`, `EmitRISCVBuiltinExpr`, next to the fork's `__builtin_shuffle` dispatch). No new IR intrinsic and no back-end change:
   - `f16abs`: the generic `llvm.fabs.f16`, exactly how upstream emits `__builtin_fabs` (`emitBuiltinWithOneOverloadedType<1>(*this, E, Intrinsic::fabs)`, `clang/lib/CodeGen/CGBuiltin.cpp:3049` at `llvmorg-20.1.8`). With Zhinx it selects `fabs.h`, the instruction GCC emits.
   - `f16abs2`: the pair is one 32-bit register; bitcast it to `i32`, AND with `0x7fff7fff` (bits 15 and 31 are the two sign bits), bitcast back. This is exact and needs nothing from the unfinished packed-fp16 code generation (T5); `llvm.fabs.v2f16` would also be correct but scalarizes to two `lh`/`fabs.h`/`sh` from memory, where the AND is `lw`/`and`/`sw`. InstCombine may legitimately refold this AND: when a lane is extracted it narrows the AND to `i16` and turns it into `llvm.fabs.f16`, which is legal with Zhinx and selects `fabs.h` (GCC's own instruction), so no libcall and no change in result (review 20/F041, `logs/20-F041-rev/k3h.c`: no calls at -O0..-Oz).
   - `f16altabs2`: the same two sign bits, cleared with two `p.bclr` (bit 15, then bit 31) through the fork's existing Xpulpv intrinsic `llvm.riscv.pulp.bclr` (masks `0xffff7fff` and `0x7fffffff`, both contiguous `p.bclr` ranges). It must be opaque: a plain AND on the pair, as in the first version of this change, is narrowed by InstCombine to an `i16` AND once a lane is extracted and then folded into `llvm.fabs.bf16` (`InstCombinerImpl::visitAnd`, `m_ElementWiseBitCast` applies to the narrowed scalar), which hits the LLVM 20 legalizer bug above when the lane comes from memory (review 20/F041: 7 of 10 functions of `logs/20-F041-rev/k3.c`, e.g. `*p = __builtin_pulp_f16altabs2((v2ah){*p,*p})[0]`, called `__truncsfbf2` at -O1..-Oz). InstCombine cannot see through the intrinsic, so no bf16 `fabs` can be formed. Generic `llvm.fabs.v2bf16` is not used for the same reason (it scalarizes and calls `__truncsfbf2` per lane when the pair comes from memory).
   - `f16altabs`: `p.bclr` of bit 15 through the fork's existing Xpulpv intrinsic `llvm.riscv.pulp.bclr` (value zero-extended to 32 bits, result truncated). A plain `llvm.fabs.bf16` hits the legalizer bug, and a plain `i16` AND is folded by InstCombine into `llvm.fabs.bf16` (checked: even hand-written C `bits & 0x7fff` on a `float16alt` becomes `fabs.bf16` and then a `__truncsfbf2` call). The opaque intrinsic keeps the bit operation. Hence the "xpulpv" in its feature list (the `p.bclr` pattern needs it; `xgap9` has it).

   Upstream reference for mapping target builtins to generic IR in `EmitRISCVBuiltinExpr`: `__builtin_riscv_clz_32` → `llvm.ctlz` (`clang/lib/CodeGen/CGBuiltin.cpp:23349` at `llvmorg-20.1.8`); CORE-V (`BuiltinsRISCVXCV.td`) has no floating-point builtins to follow. When T3/T5 add GAP9's `vfsgnjx.h`/`.ah` and bfloat16 registers, and after the upstream legalizer fix arrives at step 22, the bf16 forms can switch to `llvm.fabs` and select the single GCC instruction.

Emitted code, `-O2` (`logs/20-F041-repro/gcc-t.O2.s` vs `mine-t.O2.s`): `f16abs` = `fabs.h a0,a0` in both (same encoding). `f16abs2`: GCC one `vfabs.h`, clang `lui`+`addi`+`and` (the constant is hoisted out of loops, leaving one `and` per pair). `f16altabs2`: GCC one `vfabs.ah`, clang `p.bclr`+`p.bclr`. `f16altabs` as a stand-alone function: GCC `fabs.ah`, clang `p.exthz`+`p.bclr`+`p.bset` (zero-extend, clear bit 15, and the ABI's NaN-boxing of a returned bfloat); inside a loop it is one `p.bclr` after the load. Same results, 1-3 instructions more than GCC until T3/T5.

## What breaks if this is wrong

- A wrong or missing prototype makes the 77 fp16 SDK files fail again with "passing 'int' to parameter of incompatible type 'v2h'" (SDK compile survey pe8 mode falls back to 520/617).
- A wrong mask (for example clearing bit 31 only, or clearing the whole upper half) changes every negative input of the SDK's fp16 abs, clip and approximation functions (`FastFloatApprox16.h`), so fp16 DSP/CNN kernels give wrong outputs. The GVSoC test `logs/20-F041-repro/gvsoc/` (driver `drv.c`, kernel `kern.c`, host reference `host.c`) checks all four builtins on 64 pairs, including +-0, +-inf, quiet and signalling NaNs of both formats, subnormals and random bits, both through registers and straight from memory, plus a float16 sum of `f16abs` values: clang -O0/-O1/-O2/-O3/-Os, GAP9 GCC -O0/-O2/-Os and host `gcc -O0` all print `RES1 0xcf58f5db RES2 0x00e89e7f RES3 0x00004728` (`logs/20-F041.gvsoc.log` first version, `logs/20-F041.gvsoc-rev2.log` this version, also -Oz). A second GVSoC test, `logs/20-F041-repro/lane/` (the review's `k3.c` shapes: lane 0/1 extracts from pairs built from a loaded bf16, `{x,0}`/`{0,x}` pairs, loops over bf16 arrays, extracts from loaded pairs, plus scalar `f16altabs` and an `f16abs2` lane extract; 16 inputs incl. bf16 sNaN `0xff81`/`0x7f81`, qNaN, inf, subnormals): clang -O0/-O1/-O2/-O3/-Os/-Oz, GAP9 GCC -O0/-O2/-Os and host all print `RESB 0xe9c275e1 RESH 0xdb2abd48 SNAN 0x00007f81`; the review's link test `lk2.c` with `k3.c` now links with GAP9 libgcc at -O1/-O2/-Os/-Oz and keeps the sNaN (`0xff81` -> `0x7f81`, as GAP9 GCC) (`logs/20-F041.gvsoc-lane.log`). `llvm-nm -u` finds no `__truncsfbf2`/`__extendbfsf2` in any of these objects nor the review's `k3.c`, `k3h.c`, `kern.c` at -O0..-Oz, and their IR has no `llvm.fabs.bf16` (`logs/20-F041-repro/lane/nm.out`).
- Had the bf16 forms used `llvm.fabs`, SDK programs would fail to link (`undefined symbol: __truncsfbf2`, seen with the first version of this change) and signalling NaNs would be quieted. The same happens if the `f16altabs2` lowering becomes a plain AND again (the review's `k3.c`). The GVSoC tests and the `llvm-nm` check above show neither.
- No lit test covers these builtins; `proposed_test` in the result file lists a clang CodeGen test and a Sema test.

# 20/F039: clang accepts GAP9's `float16` / `float16alt` type names (`_Float16` / `__bf16`), with per-operation bfloat16 rounding

This fills a gap the fork already had (backlog B90, fp16 design `benchmarks/fp16-design/design.md` task T4, owner decisions D5/D6 in PROGRESS.md). GAP9 GCC predeclares two half-precision type names in every file: `float16` (IEEE half: 1 sign, 5 exponent, 10 mantissa bits) and `float16alt` (bfloat16: 1/8/7). The GAP9 SDK uses them everywhere in its DSP and neural-network kernels, and builds the packed pairs `v2h`/`v2ah` on them (`tools/autotiler_v3/Emulation/Gap.h:28-30`, on its `__gap9__` path). Clang knew neither name, so 132 SDK files stopped at "unknown type name 'float16'". One commit, clang-driver cluster, one file: `clang/lib/Basic/Targets/RISCV.cpp`.

## What upstream changed

Nothing upstream broke this. The fork never had these names. The GAP9 half-precision extensions they depend on were added by fork commit `878ee13be29d` "fixup! [pulp] registration: extensions, features, processors, CSRs" (task 20/F035: `-march=...xgap9` implies Zhinx, `xpulpf16alt` and `xpulpfvec`; `git log -S'FeatureVendorXpulpf16alt' llvmorg-20.1.8..HEAD`). Upstream already provides both target types: `_Float16`, computed natively when Zhinx is on (`HasLegalHalfType`, `clang/lib/Basic/Targets/RISCV.cpp:352` at `llvmorg-20.1.8`), and `__bf16`, an arithmetic type since upstream `e62175736551` "[Clang][BFloat16] Upgrade __bf16 to arithmetic type, change mangling, and extend excess precision support" (clang 17). That commit also added the switch `TargetInfo::HasFullBFloat16`: when a target sets it, clang rounds `__bf16` arithmetic to bfloat16 after every operation instead of computing a whole expression in `float` (`QualType::UseExcessPrecision`, `clang/lib/AST/Type.cpp:1625` at `llvmorg-20.1.8`).

## Why this is equivalent

Before: `float16 x;` was an error with every `-march`. Now two changes are made, both in `RISCVTargetInfo`:

1. **Type names.** When a GAP9 half-precision extension is on (`xpulpf16alt` or `xpulpfvec`, both implied by `xgap9`), clang predefines `float16` as `_Float16` (only if Zhinx is also on, so `float16` is always the native Zhinx type) and `float16alt` as `__bf16` (only if `xpulpf16alt` is on). This is the design's decision 6.4. Plain RISC-V, plain Zhinx and plain Xpulpv2 get no new macro (checked with `-dM -E` for `rv32imc_zfinx_zhinx`, `rv32imc_xpulpv2`, `rv32imc_zfinx_zhinx_xpulpv2`). The layouts are the ones GAP9 uses: GCC encodes `(float16alt)3.14159f` as `0x4049`, the bfloat16 bit pattern (design section 1 and 3.2), and `sizeof`/`_Alignof` are 2 for both, as with GCC.

   *Macro or predeclared typedef?* In GAP9 GCC the names behave like predeclared typedefs (a local `int float16 = 3;` is accepted, `typedef short float16;` is a conflict, design section 1). A clang macro differs from that in three corner cases: the name cannot be reused as an identifier, a redundant `typedef <same type> float16;` becomes an error, and code can test `#ifdef float16`. A real predeclared typedef would need `Sema::Initialize` (`clang/lib/Sema/Sema.cpp`), an upstream file the fork does not touch (AGENT_RULES 11); `TargetInfo` can only add macros. I chose the macro because, for everything the SDK does with the names, both behave the same: a grep of the whole SDK (outside the GVSoC simulator) finds them only as type names in declarations, casts, `sizeof`, compound literals and `vector_size` typedefs, never as an identifier, member or `#ifdef` test. The only `typedef ... float16;` lines are in `Emulation/Gap.h:16-23` (skipped when `__gap9__` is defined, i.e. with `xgap9`) and in `tools/audio-framework/lib/components/fft/src/fft_int.h:89` (`typedef float float16;`, which GAP9 GCC rejects too, and which no GAP9 target build includes). The survey below found no file that compiled before and fails now.

2. **Per-operation rounding for `float16alt`.** `HasFullBFloat16 = true` when `xpulpf16alt` is on. GCC computes every `float16alt` operator in bfloat16 (one `fadd.ah`/`fmul.ah` per operator, design 2.2), and GVSoC rounds each of them to nearest-even (design 3.4, measured 2000/2000). Clang's default for a target without full bfloat16 is excess precision: `(a+b)*c-a` is computed in `float` and rounded once, which gives different results (design section 5, column `cl-bf16`). The design measured that `-fbfloat16-excess-precision=none` gives GCC's results except for multiply-add fusion; `HasFullBFloat16` is the target-side way to make exactly that the default (the option only has an effect when the target does not set `HasFullBFloat16`; clang 20's driver does not even expose it, and `clang/lib/Driver` is owned by another task). It is the switch upstream sets for targets with bfloat16 arithmetic: X86 for `avx10.2-256` (`clang/lib/Basic/Targets/X86.cpp:309`, upstream `83ad644afaac` "[X86][AVX10.2] Support AVX10.2-BF16 new instructions.") and ARM for `+bf16` (`clang/lib/Basic/Targets/ARM.cpp:611`). Clang now emits `fadd bfloat` / `fmul bfloat` with no `fpext`/`fptrunc`. The backend has no bfloat16 instructions yet (design task T3), so it still computes each operation in `float` and rounds after it through `__truncsfbf2` (compiler-rt; GAP9 libgcc does not have it, a T3 item). That is exact (24 >= 2*8+2 mantissa bits), so the results already equal GCC's rounding per operation.

   `float16` needs no such switch: with Zhinx, `_Float16` is already computed natively with no excess precision (`fmadd.h`, `fadd.h` in the kernels below).

Measured with this build (integration head `75b4639bf455`, build `build/20-F039`, int-20 clang snapshot of the same head as "before"):

- **Front end.** `-march=rv32imc_xgap9 -dM -E` adds `#define float16 _Float16` and `#define float16alt __bf16`; `rv32imc_zfinx_zhinx_xpulpv2_xpulpfvec` gives only `float16`, `rv32imc_zfinx_xpulpf16alt` only `float16alt`. `float16 f(float16 a, float16 b){return a*b+a;}` compiles to `fmadd.h a0, a0, a1, a0; ret`. `Gap.h`-style `v2h`/`v2ah` typedefs, `sizeof(float16)==2`, `_Alignof(float16alt)==2`, `__builtin_types_compatible_p(float16, float16alt)==0` all hold, as with GCC.
- **Numeric equivalence on GVSoC** (`benchmarks/fp16-design/tests/numeq.c` built with `-DT=float16` / `-DT=float16alt`, i.e. the new names, `-march=rv32imc_xgap9`, versus GAP9 GCC; runner = design `tests/run_numeq.sh` with the clang columns changed). `float16` with `-ffp-contract=fast` (D6): identical to GCC on all 12 lines. `float16alt`: identical to GCC `-ffp-contract=off` on every arithmetic line (expr, div, dot, dot_sep) and on fromf/fromi/tof/cmp, with and without `-ffp-contract=fast`. Remaining differences, both owned by T3: multiply-add fusion (GCC fuses into `fmadd.ah`) and `(int)float16alt` (GCC rounds to nearest, D6 Q1). Passing `-Xclang -fbfloat16-excess-precision=standard` no longer brings back the old once-per-expression rounding under `xpulpf16alt`, as on X86/ARM with full bfloat16.
- **SDK DSP kernels on GVSoC.** `DSP_Libraries/MatrixFunctions/MatAddDSP.c` and `MatMulDSP.c`, the source files unchanged, compiled with the SDK's own flags for that file (from the survey's compile database) by GAP9 GCC (`-march=rv32imcxgap9 -mPE=8 -mFC=1 -O2`) and by this clang (`-march=rv32imc_xgap9 -O2 -ffp-contract=fast`). A small wrapper includes each `.c` and maps the cluster calls to one core (`gap_coreid()`=0, `gap_ncore()`=1, no barrier). Tested: `KerParMatAdd_DSP_f16`, `KerParMatMulDSP_f16`, `KerParMatMulDSPT_f16` with even and odd sizes (9x14 * 14x11 and 8x13 * 13x10), random inputs. The output buffers are bit-identical to GCC's (5/5 hashes). Clang's `KerParMatMulDSP_f16` uses 45 `fmadd.h` + 15 `fadd.h` (the packed `v2h` operations are split into scalar Zhinx ops until T5). The `float16alt` versions: MatAdd identical, MatMul differs (fused multiply-add, T3). The clang build needed `-D__builtin_pulp_f16abs2(a)=__builtin_elementwise_abs(a)` (and the `f16alt` one) only so that an unused inline function in `FastFloatApprox16.h` parses. Those builtins are missing (T6); the tested kernels do not call them.
- **SDK compile survey** (private copy of `benchmarks/sdk-compile-survey/run.py` in a private `--work` dir, with a mode "xgap9" = `-march=rv32imc_xgap9`, no macro shim, like the M1 checkpoint's configuration B). Before (int-20 snapshot): 477/617 GCC-compilable files compile, 140 fail, and 132 of the 140 stop on `float16`/`float16alt`. After: 515/617. **38 of the 132 now compile** (DSP_Libraries 18, audio-framework 7, rtos/other 3, examples 6, nn_menu 2, libs/other 1, other kernels 1), which is the "+38" the survey's fix ranking predicted. No file that compiled before fails now. No crash or timeout in the strict or lenient runs. For the other 94, the first error is: 77 an unknown `__builtin_pulp_f16abs2`/`f16altabs2` (implicitly declared as returning `int`, then passed as a `v2h`/`v2ah`), 12 another unknown fp builtin, 5 `CoreCount()` in a static initializer. What they need, across all errors: fp builtins 86 files (T6 / B97), `CoreCount()` constant folding 68 (F018), non-constant `mulsN`/`clip` arguments 11, other builtins 2. No new front-end error kind comes from the type names.
- **GAP9 sweep** (scratch copy, base = int-20 snapshot, mine = this build). With the sweep's own flags (`-march=rv32imc_zfinx_xpulpv2`, where the new macros are off): 172/172 outputs identical at O2 and O3. With `-march=rv32imc_xgap9`: all disassemblies identical. The only difference is the error text of the three "-file" kernels that already failed before (they now fail on the missing `f16abs2` builtin instead of the missing type). One harness finding: the sweep's own shim `benchmarks/gap9-sweep/src/shim/at_api.h:11-13` does `typedef _Float16 float16;` under `#ifdef __clang__`, which the macro turns into an error with `xgap9`. With the guard changed to `#if defined(__clang__) && !defined(float16)` (in my scratch copy only), everything compiles. The official sweep configuration does not use `xgap9`, so it is unaffected.
- The Xpulpv2 f16/bf16 load-pair ISel hang reproducers (`benchmarks/sdk-compile-survey/hang-isel-*-xpulpv.c`) finish in well under a second with `-march=rv32imc_xgap9`.
- Lit: see the result file.

`v2h`/`v2ah` need nothing from this task: `Gap.h` builds them as `float16`/`float16alt` vectors, and those are accepted and compiled (scalarized). Native packed code (`vfadd.h`, `vfmac.h`, ...) is T5.

## What breaks if this is wrong

- **Wrong gating.** If the macros leaked into non-PULP configurations, any program with a variable or type named `float16` would stop compiling with plain `-march=..._zhinx`. The `-dM` checks above show they do not. If they were missing for `xgap9`, the 38 SDK files above would fail again with "unknown type name 'float16'".
- **Macro corner cases.** A GAP9 program that uses `float16`/`float16alt` as an identifier, or typedefs them again itself, compiles with GAP9 GCC but not with clang. The SDK has no such use (the grep above). The one known victim is the sweep harness's own shim, as described above. The fix belongs in the shim (`!defined(float16)`), not in clang.
- **Wrong `float16alt` rounding.** Without `HasFullBFloat16`, `numeq` `expr`/`div`/`dot_sep` would differ from GCC (design section 5, `cl-bf16` column). With it set wrongly for a target that does not have bfloat16 arithmetic, results would still be correct, because the backend rounds after every operation through `float`. The price is a `__truncsfbf2` call per operation until T3.
- **Wrong type mapping.** Swapping IEEE half and bfloat16 would change every result. The GVSoC bit-exact MatAdd/MatMul `float16` runs and the numeq `float16alt` lines (fromf, tof, fromi) would show it.
- **Missing tests.** No lit test covers these macros or `HasFullBFloat16` on RISC-V (`clang/test/Preprocessor/riscv-target-features.c` has no PULP RUN lines). A test is proposed in the result file.

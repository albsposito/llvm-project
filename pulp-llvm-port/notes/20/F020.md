# 20/F020: PULP hardware loops no longer use a register that does not exist yet where the loop count is computed

Written for a reader who does not know LLVM. Four sections, all required (policy_check.py checks the headings).

## What upstream changed

Nothing upstream broke this. It is a pre-existing fork defect (backlog B88, and B71 has the same root cause). It is present in the original LLVM 18 fork (`toolchains/ref-18`) and in `build/int-19`. The defective code came in with the fork's hardware-loop pass in `f1b7aebff8c2` (Federico Ficarelli, 2022-08-25) "[LLVM/PULP/SNITCH] Support for PULP and Snitch cores/platforms". It was found with `git -C /home/ubuntu/llvm-project log pulp/integer_SIMD_fix -S'if (!MDT->properlyDominates(DefBB, Header))' -- llvm/lib/Target/RISCV`.

The pass is a copy of `HexagonHardwareLoops.cpp`. When it looks for the loop's end value, it accepts a register that is defined inside the loop, as long as that register holds a known constant. Hexagon does the same, and then, at the start of `computeCount`, it replaces such a register by the constant itself. The fork left that replacement out. So the fork computed the loop count in the block before the loop (the "preheader") from a register that is only set inside the loop. The machine code is then invalid: a value is read before it is written. The register-liveness analysis stops with `LiveVariables.cpp:141 "Can't find reaching def for virtreg"`, and `-verify-machineinstrs` reports "Virtual register defs don't dominate all uses" right after "PULP Hardware Loops".

This happens when a constant such as 256 is both the loop's end value and a value used after the loop. The compiler then loads 256 into a register inside the loop, so that it is ready for the code after the loop. In the SDK this is `libs/gap_lib/img_io/ImgIO.c` (`GetInputImageInfos` with `ReadPPMHeader` inlined: `while (*i < 256 && ...)`). The same shape comes out of fuzz seed 256 (B71): the end value is `ADDI $x0, 1` inside the loop, and a phi after the loop uses it.

The loop count is computed even when the pass later decides not to form a hardware loop (here: the loop has two exits). So an invalid instruction is left behind in both cases.

Note on reproduction at the integration head `7459255b`: the 30-line reducer `crash-pulp-hwloops-GetInputImageInfos.ll` no longer crashes. That is only because 20/F007 now declines its `!=` loop earlier. The same file with `icmp ult` (or `slt`, `sge`, `uge`) still crashes, and so do the full `ImgIO.c` and the seed-256 MIR taken before the pass (`logs/20-F020.repro.log`). Seed 256 as C is hidden at the head by 20/F015's branch change.

## Why this is equivalent

The only file changed is `llvm/lib/Target/RISCV/PULP/PULPHardwareLoops.cpp` (passes cluster), in `computeCount`. The change follows `HexagonHardwareLoops::computeCount` at `llvmorg-20.1.8` (lines 743-756). There, a start or end register that is set to an immediate (`A2_tfrsi`, the Hexagon "load immediate") is replaced by the immediate before the count is computed.

- On RISC-V the "load immediate" is `ADDI $x0, imm`. The pass already recognises it, and copies of it, with `checkForImmediate`.
- The fork now replaces the register by its immediate only when the register's definition does not dominate the preheader, that is, when the register is not available there. This is the one case where the old code built invalid machine code. The count is then computed from the constant: an `li 256` or an `addi` is placed in the preheader, the same thing the pass already does for loops whose bounds are immediates.
- When the register is available, the pass keeps using it as before. So every loop that used to compile gets exactly the same machine code. The GAP9 sweep shows this below (54 of 54 objects byte-identical).
- The zero case (`$x0`) was already handled: a copy of `$x0` is placed in the preheader, and it is not changed.

Evidence (all logs under `logs/20-F020/`, `logs/20-F020-sweep/`, `logs/20-F020-oracle.log`):

- **GVSoC, loops that are now formed:** `logs/20-F020/gv/ir.ll` has 7 loops whose constant end value is loaded inside the loop and used by a phi after it (`ult`, `slt`, `ule` step 2, `ne`, `sgt` counting down, `ugt` step -4, `ult` step 4). - **F007 trip-count oracle** (1330 functions, `logs/20-F020/oracle`, a copy of `logs/20-F007/oracle.py`/`orun.sh` run with `build/20-F020`): 1330/1330 OK at O2, O3 and Os (`logs/20-F020-oracle.log`).
- **Fuzzer, fresh seeds 9001-9300 x O2/O3/Os** (`logs/20-F020/fuzz/summary.txt`; base = int-20 `7459255b`): 900 of 900 compiles give assembly identical to int-20. - **Lit** (`logs/20-F020-lit.log`): llvm/test/CodeGen/RISCV, MC/RISCV, clang/test/CodeGen/RISCV, clang/test/Sema, clang/test/Driver/riscv* and the fork tests give 5713 passed, 126 unsupported and 1 failed. ## What breaks if this is wrong

If the substituted constant were wrong, a hardware loop would run the wrong number of times, with no compiler message. Loop results would be wrong or the program would hang. The GVSoC checks above (`ir.ll` driver `BAD f=.. i=..` lines, and the ImgIO header hash) would show it. The F007 trip-count oracle (`BAD`/`HANG`) and the fuzzer would show it too. If the substitution were missing somewhere, the compiler would crash in LiveVariables (release builds may instead produce garbage counts) on SDK files like `ImgIO.c`. No lit test covers this shape. A test is proposed in the result file (`proposed_test`) and was not added, per the task.

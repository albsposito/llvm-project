# 20/F006: post-increment loads (p.lw) for 32-bit floats on Xpulpv2 + Zfinx

Written for a reader who does not know LLVM. This is a performance feature the owner asked for, not a port break.

## What upstream changed

Nothing upstream broke here. The limit comes from the fork. Fork commit `f1b7aebff8c2` "[LLVM/PULP/SNITCH] Support for PULP and Snitch cores/platforms" (Federico Ficarelli, 2022) marks post-increment loads and stores as legal only for i8/i16/i32/v2i16/v4i8. Fork commit `c0c1019168f9` "[wip] fix lsr + isel lowering for p.lw" (2024) added `getIndexedAddressPartsPulp` with the check "Xpulp supports i8, i16, and i32 post-increments only". Fork commit `c2f55316c07e` "Fix ISel" added `tryPulpIndexedLoad`, which picks the `p.lw`/`p.lh`/`p.lb` instruction. None of these list `f32`, so a float load never became a "load-and-advance-pointer" (`p.lw rd, 4(rs!)`). The compiler emitted a plain `lw` plus a separate `addi` on the pointer instead. GAP9 GCC does use `p.lw` for floats when floats live in integer registers (`-march=...zfinx`).

One upstream change matters for how the fix is written. Upstream `bc91f3cdd57c` "[RISCV] Add 32 bit GPR sub-register for Zfinx. (#108336)" (in `llvmorg-19.1.7..llvmorg-20.1.8`) keeps a Zfinx float in register class `GPRF32`, the 32-bit half (`X*_W`) of a normal integer register. The fork's `p.lw` writes the full integer register (class `GPR`).

## Why this is equivalent

Before: with `-march=rv32imc_zfinx_xpulpv2`, a float loaded in a loop compiled to `lw` + `addi`. Now it compiles to one `p.lw` with post-increment, exactly as an `int` load already did.

- `RISCVISelLowering.cpp`: with Xpulpv2 **and** Zfinx, a post-increment load of `f32` is legal, and `getIndexedAddressPartsPulp` accepts `f32` under the same condition. Without Zfinx, floats live in the F registers, which `p.lw` cannot write, so nothing changes there.
- `RISCVISelDAGToDAG.cpp` (`tryPulpIndexedLoad`): an `f32` post-increment load uses the same `P_LW_ri_PostIncrement` / `P_LW_rr_PostIncrement` instructions as `i32`. The loaded integer register is then handed to float users as its 32-bit sub-register (`EXTRACT_SUBREG ... sub_32`). This is how upstream turns an integer register into a Zfinx float, in the pattern `(f32 (bitconvert (i32 GPR:$rs1))) -> (EXTRACT_SUBREG GPR:$rs1, sub_32)` at `llvm/lib/Target/RISCV/RISCVInstrInfoF.td:721` (llvmorg-20.1.8). The copy is free (the register allocator merges it) and emits no instruction. The code reuses the existing `P_LW_*_PostIncrement` opcodes instead of adding a `GPRF32` copy of them (the way `LW_INX` copies `LW`, `RISCVInstrInfoF.td:313`), because the PULP hardware-loop pass recognises only those opcodes as a loop's pointer update (`PULP/PULPHardwareLoops.cpp:381`). A new opcode would silently stop hardware-loop formation.
- **Stores are deliberately not enabled.** I first enabled `f32` post-increment stores too (`p.sw` patterns with `INSERT_SUBREG`, the mirror of `RISCVInstrInfoF.td:722`). On GVSoC this made `y[i] += k*x[i]` **14% slower** (7190 to 8209 cycles). The PULP hardware-loop pass does not accept a `p.sw` as the loop's induction update, so a loop whose pointer is advanced by the store falls back to a compare-and-branch loop. The integer code already has this problem today (the `k12_copy_loop` kernel is 1.75x GCC). With loads only, every measured float loop got faster and none got slower (numbers below). Enabling float stores should wait for the hardware-loop pass to accept `P_SW_*_PostIncrement`. The rejected diff is kept at `logs/20-F006.loads-and-stores.diff`.
- `f64` is out of scope: under Zdinx on RV32 a double is a register pair, and `p.lw` cannot load one. Nothing changed for it.
- Other f32 loads cannot come through this path. Post-increment forms are created only after legalization, and by then an extending `f32->f64` load has already been expanded. The code still refuses anything but a plain `f32` load.

Measured (GVSoC ri5ky_testbench, cycles per call, -O2; O3 identical):

| kernel | before (6e4c7f2a) | after | GAP9 GCC |
|---|---|---|---|
| f32 dot product, 1024 | 5144 | 4120 | 4117 |
| f32 `o[i]=a[i]*b[i]`, 1024 | 8215 | 6167 | 5139 |
| f32 `y[i]+=k*x[i]`, 1024 | 7190 | 6168 | 5140 |
| SDK k06 KerParMatVectDSP_f32 | 66737 | 66737 (unchanged) | 50290 |

**k06 does not improve.** The type restriction was not what held k06 back. Its hot loop is unrolled by two: it loads `In1[2j]` and `In1[2j+1]` from one pointer at offsets -4 and 0, then adds 8 to the pointer. The LLVM combine that creates post-increment loads refuses when another load already uses the same pointer with a foldable offset. The `int` version of the same loop is not post-incremented either (checked). GCC instead keeps four separate pointers. Closing the k06 gap needs a loop-shape change (LSR or the post-increment combine). That would also change integer code, so it is a separate root cause, recorded in the result file.

## What breaks if this is wrong

- A wrong float value, or a pointer that advances wrongly, in any Zfinx+Xpulpv2 loop that reads floats. It would show as a checksum mismatch in the GVSoC runtime sweep (k06) or in float kernels such as a dot product.
- A compiler crash, "Cannot select" on an indexed load, if something other than a plain f32 load reached the new path.
- Loss of `lp.setup` hardware loops if the opcode were not one the PULP hardware-loop pass knows. That shows as more cycles, not a wrong result.
- No existing lit test checks float post-increment. The missing test is described as `proposed_test` in `tasks/20/F006.result.json`: an llc test with `-mattr=+xpulpv,+zfinx` that checks `p.lw aN, 4(aM!)` for a float dot product and a plain `sw` (not `p.sw`) for a float store loop, plus a `-mattr=+xpulpv,+f` RUN line that checks no `p.lw` appears.

Checked: all 40 other GAP9 sweep kernel builds (every integer kernel, O2 and O3) give byte-identical assembly before and after. The only difference is a cold path in k06 -O3. The llc output of all 303 `llvm/test/CodeGen/RISCV` RUN lines of tests mentioning xpulp/zfinx/zdinx is byte-identical. The GVSoC runtime sweep shows identical cycles and checksums for every kernel (42 kernel/opt pairs). The lit suite passes: 4720 PASS plus the one known, owner-approved `vsetvli-insert-zve64f.mir` failure, the same as `steps/20/lit-final`.

Fuzzer (`benchmarks/hwloop-fuzz`, logs in `logs/20-F006-fuzz/`):
- Integer generator, 300 seeds: every compiled program gives byte-identical assembly before and after.
- A float variant I wrote (`gen_f.py`/`drv_f.c`/`one_f.sh`, copied to `logs/20-F006-mb/`), 400 seeds, compared with the integration build (6e4c7f2a): **one seed (153, -O2 and -O3) gives a new wrong result**, and one seed (379, -O2/-Os) newly crashes in "PULP Hardware Loops".
  - Seed 153: the function's first loop contains no `p.lw`, but it gets a different induction variable, because loop-strength reduction asks whether post-increment f32 loads are legal. The PULP hardware-loop fixup then lays that loop out wrongly (`lp.setup` directly followed by `j`, a latch outside the repeated range). This is the known layout defect that 20/F005 fixes. It is independent of this change: the integration build already produces the same pattern in 61 of its 147 compiled float programs and in 21 of its 22 wrong integer results.
  - With my commit applied on top of 20/F005 (`d01e531f008b`, approved, not yet landed), the same 400 float seeds give **zero wrong results and no hang**: 206 changed builds, all matching F005 alone.
  - Seed 379 is a segfault in `PULPHardwareLoops::convertToHardwareLoop`, the pass that already crashes 247/400 float seeds and 210/300 integer seeds on the integration build. This pre-existing fork crash is triggered on a different input here. It is recorded in the result file as not fixed.
- So this change should land after 20/F005.

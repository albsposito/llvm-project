# 20/T009: correct the Round argument of 16 PULP `*RN` builtin calls in two fork tests (owner exception F001)

Written for a reader who does not know LLVM. Test-only change made under the recorded owner exception `notes/20/owner-test-exceptions.md#f001`; regen report `notes/20/T009-regen.md`. It sits on top of the fork defect fix 20/F001 (`8a8fab3863dc`, one commit on this same branch, unmodified) and is meant to land together with it.

## What upstream changed

Nothing upstream. The break is caused by the fork fix 20/F001, which repairs a defect in fork commit `f1b7aebff8c2` "[LLVM/PULP/SNITCH] Support for PULP and Snitch cores/platforms" (2022): the Sema check of the PULP "round and normalise" builtins (`__builtin_pulp_*RN(x, y, [acc,] Norm, Round)`) computed the required rounding constant from `Round` itself instead of from `Norm`. With the fix, clang enforces Round == 2^(Norm-1), the rule GAP9 GCC enforces. The two fork tests `clang/test/CodeGen/RISCV/riscv-xpulpv2-intrinsics.c` and `riscv-xpulpv2-intrinsics-diag.c` contain 16 calls (8 per file: `machhsRN`, `machhuRN`, `mulhhsRN`, `mulhhuRN`, `mulsRN`, `muluRN`, `subRN`, `subuRN`) with Norm=2, Round=1. GCC rejects those inputs; they were accepted only because of the defect, so with F001 both tests fail ("argument value 1 is outside the valid range [2, 2]").

## Why this is equivalent

In those 16 calls only the last argument changes, from 1 to 2 (2 = 2^(2-1), the one valid value for Norm=2). In `riscv-xpulpv2-intrinsics.c` the 8 matching expected-IR lines change their last operand the same way (`i32 2, i32 1` -> `i32 2, i32 2`), because clang passes the argument through to the `llvm.riscv.pulp.*RN` intrinsic unchanged. No RUN line, no other call, no other CHECK line or expected diagnostic changed (diff is 24 lines replaced, 24 added). The generated machine code does not change: the `p.*rn` instruction encodes only Norm and rounds implicitly with 2^(Norm-1), so the Round operand is not used by instruction selection. Compiled with the old integration compiler (which accepts both values), `mulsRN`, `machhsRN` and `subuRN` with Round=1 and Round=2 disassemble byte-identically (`p.mulsrn a0,a0,a1,0x2` etc., `logs/20-T009.codegen.log`). In the diag test every one of the 91 expected "needs target feature xpulpv" errors still fires and no other diagnostic appears (`-verify` passes, `logs/20-T009.lit.log`).

## What breaks if this is wrong

If the F001 check regressed to rejecting valid calls (the original defect for real SDK values like Norm=15, Round=16384), the SDK DSP kernels would fail to compile again; these two tests would not catch that on their own, because the old defective check happens to accept Round=2 for Norm=2 (the old build passes both edited tests, `logs/20-T009.oldbuild.log`). That gap is covered by the dedicated Sema test F001 proposes (`clang/test/Sema/riscv-xpulpv2-rn-builtins.c`, in `tasks/20/F001.result.json` "proposed_test"), which is not part of this task. If clang stopped passing Round through to the intrinsic, or changed the intrinsic operands, the 8 CHECK-NEXT lines in the intrinsics test would fail.

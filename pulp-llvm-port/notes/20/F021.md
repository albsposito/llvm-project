# 20/F021: stop instruction selection looping forever on adjacent 16-bit (and 8-bit) copies with Xpulpv2

Written for a reader who does not know LLVM. This is a pre-existing fork defect (backlog B89; present in ref-18, port-20 and the step-20 integration head), not a port break.

## What upstream changed

Nothing upstream broke this. The defect is the fork's answer to the question "may a v2i16 / v4i8 value be loaded or stored at this address alignment, and is it fast?" (`RISCVTargetLowering::allowsMisalignedMemoryAccesses` in `llvm/lib/Target/RISCV/RISCVISelLowering.cpp`). The fork made `v2i16` and `v4i8` (two 16-bit or four 8-bit lanes packed in one 32-bit general register, the PULP packed-SIMD types) legal types, and added `|| Subtarget.hasPULPExtV2()` to that function, in `f1b7aebff8c2` "[LLVM/PULP/SNITCH] Support for PULP and Snitch cores/platforms" (`git log pulp/integer_SIMD_fix -G'ElemVT.getStoreSize\(\) \|\| Subtarget.hasPULPExtV2' -- llvm/lib/Target/RISCV/RISCVISelLowering.cpp` finds only this commit). The upstream part of that function it relies on is the vector rule "all vector implementations must support element alignment" (`a5b07a221a57` "[RISCV] Initial support of LoopVectorizer for RISC-V Vector.", comment from `8a3b6ba7569e` "[RISCV] Add a subtarget feature to enable unaligned scalar loads and stores"), which is true for RVV vector loads but not for PULP packed values, which are loaded with a plain 32-bit `lw`.

How the hang happens (confirmed with `llc -debug-only=isel,dagcombine,legalizedag` on `benchmarks/sdk-compile-survey/hang-isel-bf16-pair-xpulpv.ll`):

1. The DAG combiner's store merging (`DAGCombiner::tryStoreMergeOfLoads`, `llvm/lib/CodeGen/SelectionDAG/DAGCombiner.cpp:21312`, vector candidate at `:21405` at `llvmorg-20.1.8`) sees two 16-bit loads from `a`, `a+2` stored to `b`, `b+2` (only 2-byte aligned). The 32-bit integer merge is refused (unaligned `i32` not allowed), but the `v2i16` merge is accepted, because `allowsMisalignedMemoryAccesses(v2i16, align 2)` answers "allowed and fast" (element alignment 2 is met, and the fork's `|| hasPULPExtV2()` would allow any alignment anyway). It replaces the four accesses by one `v2i16` load and one `v2i16` store.
2. Legalization turns the `v2i16` store/load into an `i32` store/load (the fork promotes `ISD::LOAD`/`ISD::STORE` of `v2i16`/`v4i8` to `i32`, `RISCVISelLowering.cpp:672-673` in the worktree), sees an unaligned `i32` access that the target does not support, and splits it back into two 16-bit accesses (`LegalizeDAG.cpp:503` "Expanding unsupported unaligned store").
3. The combiner runs again on the result, sees the same two 16-bit copies, and goes back to step 1. Forever.

It is not specific to `_Float16`/`__bf16`: a plain `short` pair copy (`b[0]=a[0]; b[1]=a[1];` on `short *`) and four adjacent `char` copies hang the same way with `-march=rv32imc_xpulpv2 -O2` in ref-18, port-20 and the integration head (`logs/20-F021.repro.log`). The task's "not with +zhinx for `_Float16`" is because with Zhinx the half values are no longer plain loads feeding stores after type legalization.

## Why this is equivalent

The fix adds one block at the start of the vector part of `allowsMisalignedMemoryAccesses`: when Xpulpv2 is on and the type is `v2i16` or `v4i8`, answer exactly what the function answers for a 32-bit scalar (`Subtarget.enableUnalignedScalarMem()`, i.e. "not allowed" unless unaligned scalar access is enabled). That is the truth for these types: they live in general registers and every load or store of them is a single `lw`/`sw` (or `p.lw`/`p.sw`) after the promotion to `i32`, so they have precisely the alignment requirements of an `i32` access. The question now gets the same answer at merge time (step 1) and at legalization time (step 2), so the combiner no longer builds a merged access that legalization must undo, and the loop cannot start.

- Code that compiled before should not change: an unaligned `v2i16`/`v4i8` access was already split by legalization (step 2) whatever this function said, so the answer only decides whether the combiner builds such an access in the first place; in the cases seen it then rebuilt it forever. Measured: GAP9 sweep objects byte-identical and the lit suite unchanged (below). 4-byte-aligned `v2i16`/`v4i8` accesses and aligned merges into `lw`/`sw` are unaffected (alignment 4 passes the scalar rule's alignment check before this hook is consulted).
- The fork's `|| Subtarget.hasPULPExtV2()` line is left in place; it now only affects real RVV vector types in the (unused) case where V and Xpulpv2 are both enabled. It is not deleted, so no fork behaviour is removed.
- Upstream reference: the scalar branch of the same function (`llvm/lib/Target/RISCV/RISCVISelLowering.cpp:21993-21997` at `llvmorg-20.1.8`), which answers `enableUnalignedScalarMem()` for every value held in general registers. Upstream at 20.1.8 has no vector types held in general registers on RISC-V (CORE-V `XCVsimd` has no legal packed types or ISel in `RISCVISelLowering.cpp`, only instruction definitions in `RISCVInstrInfoXCV.td`), so the scalar rule is the closest upstream behaviour for a value that is loaded with `lw`. GAP9 GCC (`-march=rv32imcxgap9 -mPE=8 -mFC=1 -O2`) compiles the same short-pair copy to two `lh` + two `sh`, which is what our compiler now emits.
- GVSoC check (ri5ky_testbench, `logs/20-F021-gvsoc/`): `_Float16`, `__bf16`, `short` pair copies, a 4 x `char` copy and a swapped `_Float16` pair, at source/destination offsets 0/2/4/6 (2-byte and 4-byte aligned), with NaN/Inf/denormal bit patterns (0x7c01, 0xfe00, 0x7f80, 0xffc1, 0x8001, ...): the clang build prints exactly the same 80 lines of bytes and checksum as the GAP9 GCC build (GCC uses `unsigned short` for the 16-bit float types; the comparison is byte-level).
- GAP9 sweep (`benchmarks/gap9-sweep/run.py` on a scratch copy, `GAP9_EXTRA_COMPILERS=base=build/int-20 clang,mine=build/20-F021 clang`): both compile 54 rows; all 54 objects byte-identical, including the integer SIMD kernels.

## What breaks if this is wrong

If the answer were too strict for some case, the combiner would stop forming a `v2i16`/`v4i8` access it used to form: an aligned packed-SIMD load/store would turn into halfword/byte accesses (more `lh`/`sh`/`lbu`/`sb` and `or`/shifts in the SIMD kernels), visible as a GAP9 sweep instruction-mix change (dotprod, matmul, FIR kernels) and in `llvm/test/CodeGen/RISCV` PULP SIMD tests; neither changed. If it were too loose, the hang comes back: `benchmarks/sdk-compile-survey/hang-isel-*-pair-xpulpv.*` time out, and the SDK survey's `DftLibraryf16a.c` times out in "RISC-V DAG->DAG Pattern Instruction Selection". No lit test covers this: a regression test compiling the short/half/bf16 pair copy and the 4 x char copy with `-mattr=+xpulpv` (expecting two `lh`/`sh` pairs, four `lbu`/`sb`, and termination) is proposed in the result file.

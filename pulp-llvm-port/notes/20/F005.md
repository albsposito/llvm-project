# 20/F005: make PULP hardware loops end at their latch after block placement, keep uncountable loops as software loops, and stop the fixup pass reading past block ends

Written for a reader who does not know LLVM. This is a pre-existing fork defect (present in ref-18, step 19 and step 20), not a port break; owner decision 2026-09-27 authorises fixing fork crashes that stop GAP9 SDK kernels compiling. Second attempt: the first (efe70bc94999) was rejected because it made two random loop programs hang (reasons in `tasks/20/F005.review.json`); this version fixes that and the related older defects the reviewer found.

## What upstream changed

Nothing upstream broke this. The defective code is the fork's `PULPFixupHwLoops.cpp`, added by `f1b7aebff8c2` (Federico Ficarelli, 2022-08-25, "[LLVM/PULP/SNITCH] Support for PULP and Snitch cores/platforms"); the later fork commits on the file (`8f9832300f0e`, `bded3e51fd64`) only touched includes and one API name. The -O3 crash became visible only after 20/F004 removed an earlier assertion on the same kernel.

How a PULP hardware loop works: `lp.setup` repeats the code from the instruction after it (the loop header) to the end of one block, the latch (the block that decides whether to go round again). The hardware counts iterations only when the end is reached; then it jumps back to the header, or falls out to the next instruction when the count is used up. The fork's PULPHardwareLoops pass picks the latch early; LLVM's block placement runs later and moves blocks around (upstream `MachineBlockPlacement::findBestLoopTop` puts the latch above the header; tail duplication copies the latch's code into another loop block). The fixup pass did not cope:

1. It called `MachineLoop::getBottomBlock()`, which reads past the end of the function when the loop is the last code in it: assertion `!NodePtr->isKnownSentinel()` (`KerParMatMulDSP_Fix16`, sweep kernel k05, -O3). Upstream still has this walk (`llvm/lib/CodeGen/MachineLoopInfo.cpp:104-117` at `llvmorg-20.1.8` and `llvmorg-23.1.0`).
2. When the latch was not the last loop block after the header (latch above the header, or other loop blocks placed after it), it moved the loop end to the last loop block. The latch then lay outside the repeated range: its work was skipped on some paths and the hardware and software exit tests disagreed. In ref-18 and step-20 -O2 code for k05 this ran the hottest loop about 1.7 times (results stayed right only because that loop body can be repeated harmlessly); on random loop programs it gives wrong results (reviewer's seed 270; see verification).
3. When tail duplication gave the loop a second back edge (a copy of the latch that also jumps to the header), iterations taking the copy were not counted: loop count and software condition out of sync (seed 61 wrong result; seed 22 and 13 in the first attempt of this task hung).
4. It asked `L->getExitBlock()` for where the loop goes when the count is used up. That is null as soon as the loop has an early exit or two exit edges to the same block; the latch's exit branch was then erased with nothing replacing it (the hang the reviewer found).
5. Reads past a block end: `LastI->getDebugLoc()` before checking that the latch still has a branch; the "remove the counter increment" rule counted branches as body instructions and could empty the latch; and a latch that is only a compare-and-branch (its counter folded into a post-increment load) becomes empty once the branch is removed. The last two then read before the start of the block in `fixupLoopInstrs` (reduced cases `notes/20/F005-reduced.ll`, `notes/20/F005-reduced-emptylatch.ll`; the second one also crashes the integration build).

## Why this is equivalent

- **`removeUncountableLoops` (new, runs first):** if the loop has more than one back edge (`L->getLoopLatch()` is null), or its latch can leave the loop to two different blocks, the hardware cannot count it: it has one counting point and one fall-out point. The setup instruction is deleted and the loop stays a normal software loop. This is safe because at this point the loop's own compare-and-branch instructions are still all there (only `fixupLoopLatch`, later, removes them); the count register computed for the setup becomes an unused value. This is a bail-out only for loops the hardware cannot express (rule 9); loops with one back edge and one latch exit are untouched by this step.
- **`fixupLoopLayout` (new):** if the latch is above the header, it moves the latch (with the loop blocks laid out directly before it) after the last loop block that follows the header; if the latch is the loop's only latch but other loop blocks follow it, it moves the latch alone to the end. The control-flow graph is unchanged: every fall-through that the move breaks becomes an explicit jump, and a jump that now goes to the next block is dropped. Same technique as upstream `ARMBlockPlacement::moveBasicBlock` (`llvm/lib/Target/ARM/ARMBlockPlacement.cpp:246-300` at `llvmorg-20.1.8`), which moves blocks so that ARM low-overhead (hardware) loops are laid out correctly. The old "move the end to the last block" path stays only for the case it was written for (the block named by the setup is no longer the latch, e.g. it was split).
- **Latch exit:** `fixupLoopLatch` now uses the latch's own exit block (the one successor of the latch outside the loop) instead of `L->getExitBlock()`. For a loop with a single exit edge this is the same block as before; with early exits elsewhere it is now found, so the latch's `Bcc exit; j header` pair is removed in the same round and replaced by `j exit` after the loop end.
- `getLayoutBottom` replaces `getBottomBlock()`: the same walk, but it stops at the end of the function (local helper; `MachineLoopInfo.cpp` is an upstream file the fork does not touch, rule 11).
- `LastI->getDebugLoc()` is read only when a branch exists (no behaviour change when it does).
- Counter-increment rule: for the latch it now keeps the increment when it is the latch's only non-branch instruction (for a latch with one branch this is exactly the old `size() <= 2`; it differs only for a latch ending in two branches, where the old rule emptied the block). For increments in any other loop block the old rule is kept unchanged.
- If the latch still ends up with no instruction to put the loop-end label on, a `nop` is placed there, exactly as the pass already does after inline asm.

## What breaks if this is wrong

A wrong layout or exit handling makes a hardware loop repeat the wrong range: wrong results, extra work or a hang, visible as GVSoC checksum mismatches against GAP9 GCC in the gap9-sweep kernels (k03, k05, k06, k09, k11) and in the random loop fuzzer (`benchmarks/hwloop-fuzz`). A wrong bail-out decision shows as a missing `lp.setup` (slower, still correct) where GCC has one. The end-of-block checks, if wrong, give `!NodePtr->isKnownSentinel()` assertions in "PULP Hardware Loop Fixup".

Verification: (1) k05 compiles at -O2/-O3/-Os; sweep driver checksum 0x56c64fd1 = GCC at all three; odd-size driver (`notes/20/F005-k05_odd-driver.c`, 7 sizes x 3 levels) 21/21 = GCC; -O2 31x31 cycles 84091 -> 48875 (GCC 45924). (2) Sweep: every other kernel's assembly is byte-identical to the integration build; no new compile failure; the remaining failures are PULPHardwareLoops (F003) and Sema/shim errors. (3) Fuzzer, seeds 1-600 at -O2/-O3/-Os: all 523 builds that compile run and match GCC (346 of them use hardware loops), no hang; reviewer seeds 22, 13, 61, 270 all match GCC; of the 82 builds whose assembly differs from the integration build, the integration build gives a wrong result on 52 (it has no hangs), this build on none. No build that compiles with the integration build fails with this one. (4) Lit: `llvm/test/CodeGen/RISCV` + fork tests 2148/2149, only the known `vsetvli-insert-zve64f.mir`. No lit test covers these layouts; a test is proposed in the result file, not added (task rule). The machine-verifier errors seen with `-verify-machineinstrs` on `xpulp-hwloop.ll` are unchanged and have a different cause (listed in the result file).

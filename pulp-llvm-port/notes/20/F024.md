# 20/F024: -mcpu=snitch and -mcpu=mempool-rv32 list the base I extension again

Written for a reader who does not know LLVM. Four sections, all required (policy_check.py checks the headings).

## What upstream changed

A processor name such as `-mcpu=snitch` is a shorthand for an ISA string (the `-march=` value). Clang looks up that string in a table generated at build time from each processor's feature list in `RISCVProcessors.td`, then parses it like a user-written `-march`.

Up to LLVM 18 the table generator ran the feature list through the full ISA parser (`RISCVISAInfo::parseFeatures`), which silently added the base integer set `i` (and all implied extensions such as `zicsr`). Upstream commit `b64e483785bf` "[RISCV][TableGen] Generate RISCVTargetParserDef.inc from the new RISCVExtension tblgen information. (#89335)" (in llvmorg-18.1.8..llvmorg-19.1.7) replaced that with a plain print of exactly the extensions listed in `RISCVProcessors.td`. Just before it, upstream `65b0cc610f80` "[RISCV] Add FeatureStdExtI to all CPUs in RISCVProcessors.td. NFC (#88805)" added `FeatureStdExtI` to every upstream processor so the printed string still starts with `rv32i`/`rv64i`. The fork's two processors (`mempool-rv32`, `snitch`) never got that line, so since LLVM 19 their table entries read `rv32m2p0_a2p1_...` and clang rejects them: `invalid arch name 'rv32m2p0_a2p1_...', first letter after 'rv32' should be 'e', 'i' or 'g'` (backlog B75). `llc -mcpu=` was never affected, because the backend does not re-parse the string.

## Why this is equivalent

The fix adds `FeatureStdExtI` right after `Feature32Bit` in both fork processor definitions, exactly the change `65b0cc610f80` made to every upstream processor (reference: `llvm/lib/Target/RISCV/RISCVProcessors.td` at llvmorg-20.1.8, e.g. `ROCKET_RV32` and `SIFIVE_E20` which list `Feature32Bit, FeatureStdExtI, ...`). The fork has no other processor definitions (the list differs from upstream 20.1.8 only by `MEMPOOL` and `SNITCH`; no PULP/GAP processor exists in the fork, at 18 or now).

Generated table now: `mempool-rv32` = `rv32i2p1_m2p0_a2p1_xmempool0p1`, `snitch` = `rv32i2p1_m2p0_a2p1_f2p2_d2p2_zfh1p0_x...` (same order as ref-18's llc build attribute, minus the implied extensions that clang adds back itself).

Checked (`logs/20-F024.verify.log`): `clang --target=riscv32-unknown-elf -mcpu=<cpu> -c -x c /dev/null` succeeds for both; the `-target-feature` set clang passes on is identical to toolchains/ref-18 except for `+zmmul +zaamo +zalrsc`, which LLVM 19+ implies from `m` and `a` for every target (`-march=rv32ima` on the same build gives the same three). `llc -mcpu=<cpu>` output is byte-identical to build/int-20 (the backend already treated I as present; upstream removed the I predicate in `43eb5e2d4054`).

## What breaks if this is wrong

If the feature list were wrong, `clang -mcpu=snitch` / `-mcpu=mempool-rv32` would fail with "invalid arch name" again, or compile with a different extension set: missing Snitch instructions (frep, SSR, DMA, smallfloat) would make builtins be rejected and code fall back to plain RISC-V. No lit test covers `-mcpu=snitch` or `-mcpu=mempool-rv32` through the clang driver, which is why the regression went unnoticed since 19; a regression test is proposed in the result file (`clang/test/Driver/riscv-cpus.c` style RUN lines).

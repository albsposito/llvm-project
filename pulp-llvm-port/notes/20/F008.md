# 20/F008: plain-C clamps now select one p.clip / p.clipu (backlog B24)

Written for a reader who does not know LLVM.

## What upstream changed

Nothing upstream broke this. It is a pre-existing fork defect, present in ref-18 and in every port step so far. The fork added the code in `f1b7aebff8c2` [LLVM/PULP/SNITCH] Support for PULP and Snitch cores/platforms (Federico Ficarelli, 2022-08-25). Found with `git -C /home/ubuntu/llvm-project log pulp/integer_SIMD_fix -S'def betweenu' -- llvm/lib/Target/RISCV/`; `-S'negativePowerOf2'` and `-S'getZExtValue() == ~bound2'` return the same commit.

LLVM picks instructions by matching patterns written in `RISCVInstrInfoXpulp.td`. The fork has two patterns meant to turn a C clamp such as `x < -128 ? -128 : x > 127 ? 127 : x` into one `p.clip`, and `x < 0 ? 0 : x > 255 ? 255 : x` into one `p.clipu`. Three defects in those patterns mean they never fire:

1. The bound checks (`powerOf2Minus1_pulp`, `negativePowerOf2`) are `TImmLeaf`. A `TImmLeaf` only matches the special constant form that builtin arguments take. The constants in a C clamp are ordinary constants, so the check always fails.
2. The `clip` pattern checks that lower bound == NOT(upper bound) with `getZExtValue()`. That function returns the 32-bit constant zero-extended to 64 bits, so NOT of it has the top 32 bits set and the check can never succeed.
3. The `p.clipu` pattern (`betweenu`) is written with unsigned min/max. The instruction compares signed (GVSoC `lib_CLIPU`: `a > hi -> hi`, `a <= 0 -> 0`), and the unsigned form `umax(x, 0)` is simplified away before matching anyway.

Result: plain-C clamps compiled to `li; p.min; li; p.max` (4 instructions), where GAP9 GCC emits one `p.clip`/`p.clipu`.

## Why this is equivalent

The builtin patterns (`__builtin_pulp_clip/clipu`, fixed in F002) are not touched. For the plain-C idioms only:

- New `ImmLeaf` checks `powerOf2Minus1_imm_pulp` and `negativePowerOf2_imm` match ordinary constants, as upstream CORE-V does (`powerOf2Minus1` is an `ImmLeaf`, `llvm/lib/Target/RISCV/RISCVInstrInfoXCV.td:723`, used with `trailing1sPlus1` at `:771-773`, llvmorg-20.1.8). They also cap the bound at 2^30-1, so the encoded field is at most 31 and always fits the 5-bit immediate.
- The `clip` predicate now compares sign-extended values, so [-2^(n-1), 2^(n-1)-1] is recognised.
- A new `clipu_idiom` fragment matches the signed clamp to [0, hi], in both orders, plus `umin(smax(x,0),hi)` (the same value, because `smax(x,0)` is never negative). It replaces `betweenu` in the immediate `p.clipu` pattern only.
- The immediate is computed by the same transform as before (`trailing1sPlus1_pulp`, the same as GCC and CORE-V): [-128,127] -> `p.clip 8`, [-32768,32767] -> `p.clip 16`, [0,255] -> `p.clipu 9`, [0,65535] -> `p.clipu 17`.
- This matches the ISA semantics (GVSoC `pulp_v2.hpp:1930` `p_clipi_exec`, `:1940` `p_clipui_exec`, `isa_lib/int.h:1291` `lib_CLIP`, `:1305` `lib_CLIPU`).
- Bounds that are not a power of two, asymmetric bounds, and `(unsigned)x > 255` still compile to `p.min`/`p.max`/`p.minu`.
- The register forms `p.clipr`/`p.clipur` are unchanged. They did not have the TImmLeaf defect; see the result file for a separate observation about them.

Evidence (all under `logs/20-F008-sim/` unless noted):

- C micro-test `clamps.c`: `clamps.before.clean.s`, `clamps.after.clean.s`, `clamps.gcc.clean.s`. Every int8/int16/uint8/uint16 clamp is now identical to GAP9 GCC.
- IR idiom test `idioms.ll`: all smin/smax orderings are matched; non-power-of-two and wrong-signedness forms are not.
- GVSoC: `clampsim.sh` runs 17 clamp functions over 48 inputs, including INT_MIN/INT_MAX and every bound ±1. Result: 816 checks, 0 mismatches for GCC, int-20 and this build (`sim_clamp.txt`). The two extra clamps that GCC does not use (`p.clip 31`, `p.clipu 31`, the [-2^30, 2^30-1] and [0, 2^30-1] ranges) are among them and correct.
- GVSoC clip kernel (`runk.py`, `sim_clip.txt`, same driver and checksum as `benchmarks/gap9-sweep/runtime`):
  - The builtin kernel is unchanged: 21535 cycles.
  - A plain-C version of the kernel went from 26655 to 21535 cycles (-19.2%). Its kernel code is now the same two instructions as GCC's builtin kernel (`p.clip 8`, `p.clipu 9`).
  - All runs give checksum 0x5ec4255d.

## What breaks if this is wrong

- Plain-C saturation code (image and DSP kernels that clamp to int8/uint8/int16) would compute wrong values. The GVSoC clamp test `logs/20-F008-sim/clampsim.sh` would report mismatches.
- A wrong immediate would saturate to the wrong range, for example [-64,63] instead of [-128,127].
- A wrong sign treatment in `p.clipu` would turn negative inputs into `hi` instead of 0.
- If the patterns stopped matching again, only performance would regress: `li; p.min; li; p.max` comes back.
- No lit test covers the idiom today. `xpulpv.ll` checks only the builtins, with wildcarded immediates. See `proposed_test` in the result file.

# 20/F008: plain-C clamps now select one p.clip / p.clipu (backlog B24)

Written for a reader who does not know LLVM.

## What upstream changed

Nothing upstream broke this. It is a pre-existing fork defect, present in ref-18 and in every port step so far. The fork added the code in `f1b7aebff8c2` [LLVM/PULP/SNITCH] Support for PULP and Snitch cores/platforms (Federico Ficarelli, 2022-08-25). Found with `git -C /home/ubuntu/llvm-project log pulp/integer_SIMD_fix -S'def betweenu' -- llvm/lib/Target/RISCV/`; `-S'negativePowerOf2'` and `-S'getZExtValue() == ~bound2'` return the same commit.

LLVM picks instructions by matching patterns written in `RISCVInstrInfoXpulp.td`. The fork has two patterns meant to turn a C clamp such as `x < -128 ? -128 : x > 127 ? 127 : x` into one `p.clip`, and `x < 0 ? 0 : x > 255 ? 255 : x` into one `p.clipu`. Three defects in those patterns mean they never fire:

1. The bound checks (`powerOf2Minus1_pulp`, `negativePowerOf2`) are `TImmLeaf`. A `TImmLeaf` only matches the special constant form that builtin arguments take. The constants in a C clamp are ordinary constants, so the check always fails.
2. The `clip` pattern checks that lower bound == NOT(upper bound) with `getZExtValue()`. That function returns the 32-bit constant zero-extended to 64 bits, so NOT of it has the top 32 bits set and the check can never succeed.
3. The `p.clipu` pattern (`betweenu`) is written with unsigned min/max. The instruction compares signed (GVSoC `lib_CLIPU`: `a > hi -> hi`, `a <= 0 -> 0`), and the unsigned form `umax(x, 0)` is simplified away before matching anyway.

Result: plain-C clamps compiled to `li; p.min; li; p.max` (4 instructions), where GAP9 GCC emits one `p.clip`/`p.clipu`.

## Why this is equivalent

The builtin patterns (`__builtin_pulp_clip/clipu`, fixed in F002) are not touched. For the plain-C idioms only:

- New `ImmLeaf` checks `powerOf2Minus1_imm_pulp` and `negativePowerOf2_imm` match ordinary constants, as upstream CORE-V does. There, `powerOf2Minus1` is an `ImmLeaf` (`llvm/lib/Target/RISCV/RISCVInstrInfoXCV.td:723`), used with `trailing1sPlus1` at `:771-773`, llvmorg-20.1.8. At 20.1.8 upstream uses them only for its `cv.clip` intrinsic, not for min/max idioms, so the idiom fragments are the fork's own, fixed. They also cap the bound at 2^30-1, so the encoded field is at most 31 and always fits the 5-bit immediate.
- The `clip` predicate now compares sign-extended values, so [-2^(n-1), 2^(n-1)-1] is recognised.
- A new `clipu_idiom` fragment matches the signed clamp to [0, hi], in both orders, plus `umin(smax(x,0),hi)` (the same value, because `smax(x,0)` is never negative). It replaces `betweenu` in the immediate `p.clipu` pattern only.
- The immediate is computed by the same transform as before (`trailing1sPlus1_pulp`, the same as GCC and CORE-V): [-128,127] -> `p.clip 8`, [-32768,32767] -> `p.clip 16`, [0,255] -> `p.clipu 9`, [0,65535] -> `p.clipu 17`.
- This matches the ISA semantics (GVSoC `pulp_v2.hpp:1930` `p_clipi_exec`, `:1940` `p_clipui_exec`, `isa_lib/int.h:1291` `lib_CLIP`, `:1305` `lib_CLIPU`).
- Bounds that are not a power of two, asymmetric bounds, and `(unsigned)x > 255` still compile to `p.min`/`p.max`/`p.minu`.
- The register forms `p.clipr`/`p.clipur` are unchanged. They do not have the TImmLeaf defect. `p.clipr` has a separate, pre-existing wrong-result bug when the bound register is negative (`logs/20-F008-v2/clipr_negative.txt`). It is reported in the result file as a separate task, not fixed here.

Evidence (re-run on the final commit; all under `logs/20-F008-v2/` unless noted):

- Before (build/int-20 at the integration head): `logs/20-F008.repro.log`. No clamp compiles to p.clip/p.clipu.
- C micro-test `clamps.c`: `clamps.before.clean.s`, `clamps.after.clean.s`, `clamps.gcc.clean.s`. Every int8/int16/uint8/uint16 clamp is now the same single instruction as GAP9 GCC, with the same immediate and encoding word (`p.clip a0,a0,8` = `0x14851533`). Clamps to [-2^30, 2^30-1] and [0, 2^30-1] become `p.clip 31` / `p.clipu 31` (GCC uses min/max there). INT_MIN..INT_MAX folds away, and [0, INT_MAX] stays `p.max x,0`, because 2^31-1 cannot be encoded.
- IR idiom test `idioms.ll` (`idioms.{before,after}.clean.s`, passes `-verify-machineinstrs`): all smin/smax/umin orderings are matched. Non-power-of-two bounds, asymmetric bounds, [1,255] and unsigned-only forms are not matched.
- GVSoC, fixed clamps (`clampsim.sh`, `sim_clamp.txt`): 17 functions x 48 inputs, including INT_MIN/INT_MAX and every bound +-1. That is 816 checks, with 0 mismatches for GCC, int-20 and this build.
- GVSoC, random clamps (`genclamp.py`, `rclamp.txt`): 8 seeds x 60 random bounds. The bounds are symmetric powers of two, [0, 2^n-1], asymmetric, and power-of-two +-1. Each function gets 55 inputs, including the edges. That is 26400 checks, with 0 mismatches for int-20 and this build. This build selected 309 p.clip/p.clipu instructions; int-20 selected 0.
- GVSoC clip kernel (`runk.py`, `sim_clip.txt`, `clip_kernel_dis.txt`; same driver and checksum as `benchmarks/gap9-sweep/runtime`, kernel `clip`):
  - The builtin kernel (`src/clip.c`) is unchanged: 21535 cycles at -O2 and -O3, the same as int-20.
  - A plain-C version of the kernel went from 26655 to 21535 cycles (-19.2%). Its kernel code is now the same two instructions as GCC's builtin kernel (`p.clip 8`, `p.clipu 9`).
  - All runs give checksum 0x5ec4255d. GCC's 17437 cycles differ only in the driver code, not in the kernel.
- GAP9 sweep (`sweep_compare.txt`): all 54 kernel disassemblies (27 kernels x O2/O3) are byte-identical between int-20 and this build. No SDK kernel contains a plain-C power-of-two clamp that this change picks up.
- hwloop fuzzer (`fuzz/res.txt`, seeds 5000-5299 x O2/O3/Os): all 900 compilations give assembly identical to int-20. No new crash, hang or wrong result. Seeds 5050 and 5183 mismatch GCC, but they compile identically with int-20, so the mismatch is pre-existing (see the result file).
- Lit (`logs/20-F008.lit.log`): 56/56 fork tests pass. llvm/test/CodeGen/RISCV + MC/RISCV pass 2629/2630; the only failure is the known `rvv/vsetvli-insert-zve64f.mir` (data/known-failures.txt, B41), which fails on int-20 too.

## What breaks if this is wrong

- Plain-C saturation code (image and DSP kernels that clamp to int8/uint8/int16) would compute wrong values. The GVSoC clamp tests `logs/20-F008-v2/clampsim.sh` and `genclamp.py` would report mismatches.
- A wrong immediate would saturate to the wrong range, for example [-64,63] instead of [-128,127].
- A wrong sign treatment in `p.clipu` would turn negative inputs into `hi` instead of 0.
- If the patterns stopped matching again, only performance would regress: `li; p.min; li; p.max` comes back.
- No lit test covers the idiom today. `xpulpv.ll` checks only the builtins, with wildcarded immediates. See `proposed_test` in the result file.

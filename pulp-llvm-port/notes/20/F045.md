# 20/F045: select bitcasts between `float` and the 32-bit PULP packed vectors (backlog B140)

This fixes a gap the fork already had. `toolchains/ref-18` and `toolchains/port-19` crash on the same input. It was fixed at step 20 because the packed bfloat16 builtins of 20/F042 run into it in three GAP9 SDK files.

## What upstream changed

Nothing upstream broke this. The PULP packed vector types `v2i16` (2 x short) and `v4i8` (4 x char) live in ordinary integer registers (register classes `GPRAV2`/`GPRAV4`). For converting them to and from a 32-bit integer, the fork only has the four `bitconvert` patterns at `RISCVInstrInfoXpulp.td:1756-1760`. These came from fork commit `93e0fc427e93` "IN PROGRESS: Fixing the encoding of Xpulp instructions" (found with `git log pulp/integer_SIMD_fix -S'(v2i16 (bitconvert (i32 GPR:$rs1)))'`). The fork never added the same conversion to and from a 32-bit `float`.

C code that reads a float's bits as a packed vector (a `union { float f; v2s v; }`, or a bf16 max/min whose result is used as a lane pair) produces an `f32 <-> v2i16` bitcast node. SelectionDAG treats that bitcast as legal because both types are legal and have the same size, so it reaches instruction selection, which has no pattern for it:

    fatal error: error in backend: Cannot select: t6: v2i16 = bitcast t5
      t5: f32 = fmaxnum t2, t4

`v2f16` and `v2bf16` are not legal types. The type legalizer turns them into `v2i16`, so they hit the same crash. The crash reproduces at `-march=rv32imc_xgap9`, `rv32imc_zfinx_xpulpv2` and `rv32imfc_xpulpv2`, at every optimisation level and in both directions (`logs/20-F045.repro.log`).

## Why this is equivalent

The fix adds the missing selection patterns in one block after the existing `i32` ones in `RISCVInstrInfoXpulp.td` (cluster insn-tablegen). A `foreach` covers `v2i16`/`GPRAV2` and `v4i8`/`GPRAV4`. `v2f16`/`v2bf16` need nothing of their own because they are legalized to `v2i16`. These are the patterns:

| config | float -> packed vector | packed vector -> float |
|---|---|---|
| F (float in an F register), `[HasPULPExtV2, HasStdExtF, IsRV32]` | `fmv.x.w` then a register class copy to GPRAV2/GPRAV4 | copy to GPR, then `fmv.w.x` |
| Zfinx (float in the 32-bit `X*_W` sub-register of an X register), `[HasPULPExtV2, HasStdExtZfinx, IsRV32]` | `INSERT_SUBREG` of the float into an undefined vector register at `sub_32` | `EXTRACT_SUBREG ... sub_32` |

A bitcast only reinterprets 32 bits and never changes them. With F, the only way to move bits between an F register and an X register is `fmv.x.w`/`fmv.w.x`, which copy the bits unchanged. With Zfinx the float already sits in the X register, so the bitcast becomes a sub-register copy and usually disappears. On GAP9 (`fmax.s a0,a0,a1` then `ret`) no instruction is emitted for it.

This follows upstream's own `f32 <-> i32` bitcast patterns at `llvm/lib/Target/RISCV/RISCVInstrInfoF.td:715-716` (F: `FMV_W_X`/`FMV_X_W`) and `:721-722` (Zfinx: `EXTRACT_SUBREG ... sub_32` / `INSERT_SUBREG (IMPLICIT_DEF) ... sub_32`) at `llvmorg-20.1.8`. The Zfinx form exists since upstream `bc91f3cdd57c` "[RISCV] Add 32 bit GPR sub-register for Zfinx. (#108336)" (in `llvmorg-19.1.7..llvmorg-20.1.8`). Upstream has no GPR-held packed vector type at 20.1.8: CORE-V `XCVsimd` works on `i32` only, so there is no closer reference. The only difference from the upstream patterns is the source or destination register class (GPRAV2/GPRAV4 instead of GPR).

Two TableGen details (checked in the generated `RISCVGenDAGISel.inc`):
- `EXTRACT_SUBREG (COPY_TO_REGCLASS RC, GPR), sub_32` gets an impossible type, and TableGen drops the pattern *silently*. The first attempt did this, and the Zfinx vector->float direction still crashed. The final pattern takes `sub_32` straight from GPRAV2/GPRAV4, whose registers are the X registers and so have the same `sub_32`.
- The intermediate `FMV_X_W`/`COPY_TO_REGCLASS` results carry an explicit `i32`. Without it TableGen infers `i16`, the first type of the fork's GPR class.

## What breaks if this is wrong

- If a pattern is missing or dropped (as the first Zfinx attempt was), compilation aborts with `Cannot select: ... bitcast` in any code that reinterprets a float as a packed vector or back. The three SDK files above would crash again once F042 lands.
- If the register mapping were wrong, for example the wrong sub-register or a missing `fmv`, the packed lanes would get the wrong bits. The GVSoC test `logs/20-F045-repro/gvsoc/bc.c` would show it: rows `repro`, `f2v2s`, `v2s2f`, `f2v4c`, `v4c2f`, `f2v2h`, `v2h2f`, `f2v2b`, `v2b2f` stop matching `host.txt`. `-verify-machineinstrs` would also flag a register class mismatch.
- Code that already compiled cannot change: the patterns only match nodes that crashed before. The GAP9 sweep confirms this (identical objects).
- No lit test covers these bitcasts. `proposed_test` in the result file describes one llc test.

# 20/F038: GAP9 complex / divide-by-N instructions and their 10 builtins, gated on xgap9

This fills a gap the fork already had (backlog B97, batch B of `benchmarks/builtins-spec/spec.md`). It is not a regression. The GAP9 SDK's FFT library (`tools/autotiler_v3/BasicKernels/DSP_Libraries/TransformFunctions/FftLibraryFix.c`) calls ten GAP9 builtins that clang did not know: `__builtin_pulp_add2div2`, `add2div4`, `sub2div2`, `sub2div4`, `sub2rotmj`, `cplx_conj`, `cplxmuls2`, `cplxmuls2div2`, `cplxmuls2div4` and `cplxmuls2div8`. They need GAP9-only instructions that the fork never defined. `llvm-mc` rejected the mnemonics, and the disassembler printed `<unknown>` for GCC-built objects (`logs/20-F038.repro.log`).

The change is four commits, one per owning cluster:
- **insn-tablegen** (`RISCVInstrInfoXpulp.td`): 19 new instruction definitions and the selection patterns for the 10 builtins.
- **mc** (`RISCVDisassembler.cpp`): one decoder-table line.
- **intrinsics** (`IntrinsicsRISCVXpulp.td`): 10 IR intrinsics.
- **clang-builtins** (`BuiltinsRISCVXpulp.td`): 10 builtin declarations.

Each file gets its own block at the end. No clang CodeGen or Sema file is edited.

## What upstream changed

Nothing upstream broke this. The fork never had these instructions. PULPv2 (`xpulpv`) came from fork commit `f1b7aebff8c2` "[LLVM/PULP/SNITCH] Support for PULP and Snitch cores/platforms", and it has no complex-arithmetic or divide-by-N SIMD. `git log pulp/integer_SIMD_fix -S'cplxmul'` on the fork's RISC-V target finds nothing. These instructions are GAP9 additions on top of PULPv2: GVSoC lists them in a separate "Gap9" ISA subset (`gvsoc2/gap9/models/ips/gap/cpu/gap9_isa.py:75-98` in the public GAP SDK). Upstream added the same operations for CORE-V, in a different opcode space, in `3c0604b224e3` "[RISCV] Add support for XCVsimd extension in CV32E40P" (before LLVM 19). That is the reference used here. `llvmorg-19.1.7..llvmorg-20.1.8` has no change to it. The feature that gates everything, `xgap9` (`FeatureVendorXgap9` / `HasVendorXgap9`), was added by task 20/F017 on the owner's decision.

## Why this is equivalent

The reference behaviour is GAP9 GCC 7.1.1 (`-march=rv32imcxgap9 -mPE=8 -mFC=1`), GAP9 GNU as, and GVSoC's GAP9 model.

**Instructions.** The change defines the 19 instructions of the GAP9 subset that belong to these families. The task and spec say 16, but the families listed there contain 19:
- `pv.add.h.div2/4/8`
- `pv.sub.h.div2/4/8`
- `pv.subrotmj.h` and `pv.subrotmj.h.div2/4/8`
- `pv.cplxconj.h`
- `pv.cplxmul.h.r` and `pv.cplxmul.h.r.div2/4/8`
- `pv.cplxmul.h.i` and `pv.cplxmul.h.i.div2/4/8`

The ones no builtin uses are still needed for inline asm and for disassembling GCC objects. `pv.pack.h.h` and `p.bitrev` are also in GVSoC's GAP9 subset. They belong to other families, no builtin in scope uses them, and they are left out.

All 19 are OP-V R-type with GPR operands. They follow the upstream CORE-V definitions `CV_CPLXMUL_R` .. `CV_SUB_DIV8` (`llvm/lib/Target/RISCV/RISCVInstrInfoXCV.td:467-491` at `llvmorg-20.1.8`):
- The plain ALU forms use the fork's `Pulp_ALU_rr` (like `CVSIMDRR`).
- `pv.cplxconj.h` is written like the fork's `pv.abs.h`, with rs2 = 0 (like `CVSIMDR`).
- `pv.cplxmul.h.r/.i` use the fork's tied-destination class `Pulp_ALU_rr_wb` (like upstream `CVSIMDRRWb`, `RISCVInstrInfoXCV.td:311`). Each of them writes one 16-bit half of rd and keeps the other, so rd is also an input. GVSoC models this the same way (`Format_RRRR`, `lib_CPLXMUL_H_R/I` merge with the old rd).

**Gating.** Every definition is under `Predicates = [IsRV32, HasVendorXgap9]`, not `xpulpv`, because RI5CY/PULPv2 cores lack these instructions. They sit in their own decoder namespace, `RV32Xgap9`. `RISCVDisassembler.cpp` tries that table only when `FeatureVendorXgap9` is on, placed just before the existing `RV32Xpulp` table. This is the same one-line pattern upstream uses for `DecoderTableXCVsimd32` (`RISCVDisassembler.cpp:700` at `llvmorg-20.1.8`).

**Builtins.** They use GAP9 GCC's exact prototypes: every argument and the result is `__vector(2) short`, and `cplx_conj` takes one argument. Each builtin requires target feature `xgap`. Each has a `ClangBuiltin` intrinsic (`PulpBinaryV2`/`PulpUnaryV2`, `<2 x i16>`, no memory access), so clang's generic builtin path emits it with no CodeGen code. This is how 20/F016 added its builtins. Selection:
- `add2divN` / `sub2divN` / `sub2rotmj` / `cplx_conj` each become one instruction.
- `cplxmuls2[divN]` becomes GCC's two-instruction sequence `pv.cplxmul.h.r[.divN] rd,a,b` then `pv.cplxmul.h.i[.divN] rd,a,b`. The first rd input is undefined (`IMPLICIT_DEF`) because `.r` overwrites the half that `.i` does not.
- `rd` cannot alias `a` or `b`. Both stay live until `.i` reads them, so the register allocator must give rd its own register (the spec's note on this pair).

Measured (artifacts in `logs/20-F038-verify/`):
- **MC.** All 19 instructions, plus the same mnemonics with other registers (21 lines, `all.s`), assemble with this `llvm-mc -mattr=+xgap` byte-identical to GAP9 GNU as `-march=rv32imcxgap9` (`mc.bin` = `gas.bin`). Disassembling and reassembling gives the same bytes. Examples: `pv.add.h.div2 a0,a0,a1` = `74b52557`, `pv.cplxmul.h.i a5,a0,a1` = `56b507d7`, as in `benchmarks/builtins-spec/gcc/encodings.json`. Without xgap9 (`+xpulpv`), all 21 are rejected with "instruction requires the following: 'Xgap9' (GAP9 chip)", and the disassembler prints `<unknown>` as before.
- **Codegen vs GCC.** The spec's ten `gcc/<builtin>.c` tests compile with clang `-march=rv32imc_xgap9 -O2` to the same instructions as GCC's `.s`, differing only in register choice (for example `cplxmuls2`: `pv.cplxmul.h.r a2,a0,a1; pv.cplxmul.h.i a2,a0,a1; mv a0,a2`, where GCC uses a5). The constant-argument variants differ only in how the constant is built (`li`+`pv.pack.h` instead of GCC's constant-pool load). The diagnostics probes (`gcc/diag`) behave as the spec requires: `int` argument → error; `v4s` and unsigned vectors → accepted (lax vector conversion, as GCC). Without xgap9 the call is rejected: "'__builtin_pulp_cplxmuls2' needs target feature xgap". `-verify-machineinstrs` passes at -O0/-O2/-O3.
- **Semantics on GVSoC** (`ri5ky_testbench`, which models the GAP9 subset). `sem.c` calls all ten builtins on every combination of 14 edge values for (a.re, a.im, b.re, b.im): 0, ±1, ±2, 0x7fff, -0x8000, 0x7ffe, -0x7fff, ±0x4000, 0x3fff, 12345, -23456. That is 38416 pairs, plus 20000 random pairs, hashed per builtin. The host reference (`gcc -O0 -DHOST`) is written from the spec text: 16-bit wrap before the shift, 64-bit products shifted by 15+k and truncated, no saturation, and `-(-32768)` wraps. Clang at -O0/-O1/-O2/-O3/-Os matches the host reference for all ten builtins. GAP9 GCC's build of the same file on GVSoC matches too, which cross-checks both the reference and the simulator.
- **SDK survey** (private work dir; baseline = the M2a checkpoint run with `build/int-20` at `de8abd20c921`, the same integration head).
  - `-march=rv32imc_xgap9`: 515 → 516/617.
  - `-march=rv32imc_xgap9 -mPE=8`: 520 → 521/617.
  - The one newly compiling file is `FftLibraryFix.c`. No regressions, and no other file's diagnostics change.
  - Its object has every family GCC's object has: `pv.add.h.div2/div4`, `pv.sub.h.div2`, `pv.subrotmj.h`, `pv.cplxconj.h`, and `pv.cplxmul.h.r/i` plain/div2/div4. The counts are higher because clang inlines and unrolls more.
  - GCC also emits 2 `pv.sub.h.div4` that it derives by folding `add2div4(-a, b)`. Clang keeps `pv.sub.h` + `pv.add.h.div4`, which gives the same result in 16-bit wrap arithmetic. This is a missed optimization, not a wrong result.
  - The `strict` mode (`rv32imc_zfinx_xpulpv2`) is unaffected by design: these builtins need xgap9.

GCC also has `add2div8` and `sub2div8` (`gcc/extras_unused_by_sdk.c`), which the SDK never calls. They are not in this task's list. Adding them later is two lines per file, reusing `PV_ADD_H_DIV8` / `PV_SUB_H_DIV8`.

## What breaks if this is wrong

- **Wrong encoding.** GAP9 hardware or GVSoC would execute a different instruction, or trap on an illegal instruction, in FFT kernels built by clang. The byte comparison with GAP9 gas and the GVSoC run would show it.
- **Wrong operand order or halves.** For example, if `.r` and `.i` were swapped, or `subrotmj` computed `(b-a)*j`, the FFT output would be wrong. `sem.c` on GVSoC would give a per-builtin hash mismatch against the host reference.
- **Tied rd modelled as a plain output.** The register allocator could then give `.i` a different rd than `.r`, and the result would lose its real half. The `cplxmuls2*` hashes would differ.
- **Wrong gate.** Gated on `xpulpv`, clang would emit these instructions for PULPv2/RI5CY targets that trap on them. Missing the gate, `-march=..._xgap9` code would fail with "cannot select".

No lit test covers these instructions or builtins yet (rule 2: tests are not added by workers). Proposed tests are in the result file:
- an MC round-trip test with the GAS encodings plus a no-xgap9 negative RUN line;
- a clang CodeGen test (builtin → intrinsic) with a Sema negative for missing xgap;
- an llc test (intrinsic → the instruction or the `.r`/`.i` pair).

# 20/F012: p.clipr / p.clipur picked from plain C only when the bound is known non-negative

Written for a reader who does not know LLVM. Four sections, all required (policy_check.py checks the headings).

## What upstream changed

Nothing upstream broke this. It is a pre-existing fork defect (backlog B14, wrong results), present in toolchains/ref-18, build/int-20 and after 20/F008. The wrong rules came in with fork commit `f1b7aebff8c2` "[LLVM/PULP/SNITCH] Support for PULP and Snitch cores/platforms" (found with `git log pulp/integer_SIMD_fix -S'def betweenu'` and `-S'(P_CLIPR (i32 GPR:$rs1), (i32 GPR:$rs2))'` on `llvm/lib/Target/RISCV/RISCVInstrInfoXpulp.td`). Fork commit `93e0fc427e93` "IN PROGRESS: Fixing the encoding of Xpulp instructions" later added `(i32 ...)` types to the same rules but did not change what they match.

The compiler has two "idiom" rules. They turn a plain-C clamp with a bound held in a register into one PULP instruction:

- `p.clipr rD, x, b` clamps x to [~b, b], that is [-b-1, b]. GVSoC `pulp_v2.hpp:1949` `p_clip_exec`: low = -b-1, high = b; then `int.h:1291` `lib_CLIP`: x < low gives low, x > high gives high, else x.
- `p.clipur rD, x, b` clamps x to [0, b] with signed compares. GVSoC `pulp_v2.hpp:1958` `p_clipu_exec` and `int.h:1305` `lib_CLIPU`: x > b gives b, x <= 0 gives 0, else x.

These match the C clamps `min(max(x, ~b), b)` and `min(max(x, 0), b)` only when b >= 0. When b is negative, the lower bound is above the upper bound:

- `t = x < ~b ? ~b : x; return t > b ? b : t;` returns b for every x. p.clipr returns ~b whenever x < ~b. With b = -5, x = 0 gives 4 where C gives -5. The other order, `max(min(x, b), ~b)`, returns ~b for every x, and p.clipr returns b whenever x >= ~b.
- `min(max(x, 0), b)` returns b for every x. p.clipur returns 0 whenever x <= b.

The old p.clipr rule matched any register bound, so any C clamp of this shape with a bound that could be negative at run time was miscompiled. The old p.clipur rule (`betweenu`) used *unsigned* min/max. That is a different function: `umin(umax(x, 0), b)` is just `umin(x, b)`, which differs from p.clipur for every negative x. The rule never fired, because LLVM folds `umax(x, 0)` away before instruction selection. If it had fired, it would have been wrong even with b >= 0.

## Why this is equivalent

Before: p.clipr for any register b; p.clipur never (the rule was dead and wrong).

Now, in `RISCVInstrInfoXpulp.td`:

- `clipr_idiom` wraps the same `between (not b), b, x` shape. It adds a check: LLVM's known-bits analysis (`SelectionDAG::SignBitIsZero`) must prove that b's sign bit is zero, that is b >= 0. Examples are `b & 0x7fff`, `(unsigned)b >> 1` and a zero-extended `unsigned short`. For those bounds p.clipr and the C clamp are the same function, so p.clipr is still selected. For a bound of unknown sign the compiler now emits `not` + `p.max` + `p.min`, which is exactly what GAP9 GCC (`riscv32-unknown-elf-gcc -march=rv32imcxgap9 -O2`) emits for these clamps (`logs/20-F012/gcc_probe.c`). GCC never uses p.clipr for them, even with a known non-negative bound.
- `clipur_idiom` replaces the dead unsigned `betweenu` fragment (deleted because nothing else used it). It reuses F008's signed `clipu_idiom` shapes (`smin(smax(x,0),b)`, `smax(smin(x,b),0)`, `umin(smax(x,0),b)`) with the same b >= 0 check. It also rejects a constant b. Constant bounds keep their current code: `p.clipu` for 2^n-1 through F008's immediate rule, and `p.max`/`li`/`p.min` otherwise. This keeps the change to the miscompile and to the register-bound case the rule was written for. The only new selection is p.clipur for a register bound proven non-negative. That is correct by the semantics above, and it takes one instruction where p.max + p.min took two.
- The builtin rules (`int_riscv_pulp_clip_r` -> P_CLIPR and `int_riscv_pulp_clipu_r` -> P_CLIPUR) are untouched, so `__builtin_pulp_clipr/clipur` still emit the instruction with its hardware meaning for any bound.

Upstream reference: CORE-V at llvmorg-20.1.8 (`RISCVInstrInfoXCV.td:231-233` `CV_CLIPR`/`CV_CLIPUR`, `:797-798` `PatCoreVAluGprImm`) selects `cv.clipr`/`cv.clipur` only from the `int_riscv_cv_alu_clip(u)` intrinsics, never from min/max idioms. Upstream therefore has no rule that could miscompile here. This fix keeps the fork's idiom rules, but only in the range where they are exact. The operand-reading predicate (`PredicateCodeUsesOperands = 1`, `Operands[0]`) follows upstream `RISCVInstrInfoZb.td:183-188` (`binop_with_non_imm12`) at llvmorg-20.1.8.

Evidence (all under `logs/20-F012/`):
- `clipr/before.sim.txt`, `clipr/after.sim.txt`: the B14 reproducer (b = -5) on GVSoC. Before: `p.clipr`, 5/8 wrong. After: `not; p.max; p.min`, 0 wrong.
- `sim/results.txt` (`sim/k.c`, `sim/ref.c`, `sim/m.c`, `sim/run.sh`): 13 kernels (both clipr orders and three clipur shapes, each with any-sign and known-non-negative bounds, the unsigned-compare clipur shape, and both builtins) x (36x36 edge values incl. INT_MIN/INT_MAX + 2000 random pairs), checked against an -O0 reference on GVSoC. int-20: 1677 mismatches at O2/O3/Os. This build: 0 of 42848 at O2/O3/Os. This build selects p.clipr for the 3 non-negative kernels + builtin, and p.clipur for 4 non-negative kernels + builtin.
- `idioms.ll`, `idioms.{before,after}.clean.s`: llc -verify-machineinstrs. The two any-sign p.clipr cases change to not/p.max/p.min. The three non-negative clipur shapes change from p.max+p.min to p.clipur. Everything else is identical: non-negative p.clipr, constant clamps c200/c201 (p.max/p.min), c8 (p.clip 8), cu9 (p.clipu 9), and the builtins.

## What breaks if this is wrong

If the known-bits check were too permissive, a C clamp with a negative run-time bound would again give wrong values. `sim/run.sh` and the B14 reproducer show that as MISMATCH lines on GVSoC, and DSP code that clamps to a computed bound would give wrong outputs. If it were too strict, p.clipr/p.clipur would disappear for non-negative bounds and code would grow by one or two instructions (a p.clipr/p.clipur count drop in the GAP9 sweep instruction mix), with no wrong results. The GAP9 sweep kernels contain no p.clipr/p.clipur from plain C: all 54 kernel `.dis` are byte-identical to int-20 (`sweep/compare.txt`). No lit test covers these idioms. Proposed regression test: `llvm/test/CodeGen/RISCV/xpulp-clipr-idiom.ll` built from `logs/20-F012/idioms.ll`, see the result file.

# 20/F028: hardware-loop setup instructions may no longer be copied by tail duplication

Written for a reader who does not know LLVM. Four sections, all required (policy_check.py checks the headings).

## What upstream changed

Nothing upstream broke this; it is a fork defect that exists since the ref-18 fork (backlog B03, and B82 is the same bug). A PULP hardware loop is started by one `lp.setup`/`lp.setupi` instruction placed just before the loop (in the "preheader" block); it tells the core where the loop body ends and how many times to repeat it. The fork's hardware-loop pass puts exactly one setup in front of each loop. Later, the generic LLVM optimisation "tail duplication" may copy a small block into each block that jumps to it, to save a jump. When it copied a preheader, one loop was entered by two setups. The fork's later fixup pass (`PULPFixupHwLoops`) handles every setup separately and splits off the loop's last instruction once per setup, so the second setup's loop end ended up one instruction early: the last instruction of the loop body ran once after the loop instead of on every iteration (wrong result on GVSoC; benchmarks/hwloop-fuzz/triage-2026-09-28/report.txt, group B).

The setup instructions were introduced by fork commit `f1b7aebff8c2` "[LLVM/PULP/SNITCH] Support for PULP and Snitch cores/platforms" (`git log pulp/integer_SIMD_fix -S'def LOOP0setup'`), without any marking that forbids copying them.

## Why this is equivalent

The fix adds `let isNotDuplicable = 1;` to the four setup instructions `LOOP0setup`, `LOOP1setup`, `LOOP0setupi` and `LOOP1setupi` in `RISCVInstrInfoXpulp.td` (these are the only hardware-loop instructions that exist before the fixup pass; `lp.starti/endi/counti` and `PseudoLOOPend` are created by the fixup pass itself, after every pass that could copy them). LLVM's tail duplicator refuses to copy a block that contains an instruction with this flag (`TailDuplicator::shouldTailDuplicate`, `llvm/lib/CodeGen/TailDuplicator.cpp:623` at llvmorg-20.1.8), and the block-placement pass uses the same check for its own tail duplication (`MachineBlockPlacement.cpp:808`). This is exactly how upstream protects ARM's low-overhead-loop start instructions, which have the same "one start per loop" requirement: `t2WLS`, `t2DLS`, `t2DoLoopStart`, `t2WhileLoopStart*`, `t2LoopEnd*` are inside `let isNotDuplicable = 1 in { ... }` in `llvm/lib/Target/ARM/ARMInstrThumb2.td:5588-5712` at llvmorg-20.1.8 (added by `a6fd919cb3f5` "[ARM] DLS/LE low-overhead loop code generation"). CORE-V `XCV*` has no hardware-loop code generation upstream, so ARM is the closest reference.

Other passes that honour the flag (IfConversion, MachineCSE PRE, BasicBlockPathCloning, rematerialisation) are either unused on RISC-V or never touch these instructions (they define no register). The machine outliner does not look at the flag, but it already cannot outline a setup: the setups are terminators of blocks with successors and carry a block operand, both of which make the generic `TargetInstrInfo::getOutliningType` return Illegal. Branch folding's tail merging does not copy instructions.

What changes in generated code: only functions where tail duplication used to copy a preheader holding a setup. Verified against the integration head ccfd68f6ac76 (log: `logs/20-F028-work/VERIFY.txt`):

- Reduced reproducer `seed27/two-setups-one-loop.c` on GVSoC: before 0xeb588f8a at -O2/-O3 (wrong), after 0xeb29973a at -O2/-O3/-Os (= host gcc -O0). Fuzz seeds 27 (3 input sets), 960 (2 sets) and 938 with m=4: wrong at -O2/-O3 before, correct at -O2/-O3/-Os after.
- Loops entered by two setups with different end labels, seeds 1-2000 x -O2/-O3/-Os: 9 compiles before (27 O2/O3, 318 O3, 371 O2/O3, 576 O2, 938 O3, 960 O3, 1470 O3), 0 after.
- Fuzzer `run.sh 1 2000` (host gcc -O0 reference with GAP9 GCC -mnohwloop cross-check, 3 input sets, -O2/-O3/-Os): 0 wrong results, 0 crashes. The assembly differs from the integration head only in exactly the 9 compiles above; each loses the duplicated `lp.setup` and 2 instructions.
- GAP9 SDK sweep: all 54 kernel objects byte-identical, all 54 runtime programs identical (same GVSoC cycles). F007 trip-count oracle: 1330/1330 at -O2/-O3/-Os, identical assembly.

## What breaks if this is wrong

If the flag were missing again, fuzz kernels such as seed 27 (-O2/-O3), 960 (-O3) and 938 (-O3 with m=4), and the reduced reproducer `benchmarks/hwloop-fuzz/triage-2026-09-28/seed27/two-setups-one-loop.c` (0xeb588f8a instead of 0xeb29973a on GVSoC at -O2), would give wrong results, and `scan/multisetup.py` would again report loops entered by two `lp.setup` with different end labels. If the flag blocked too much, hardware-loop code would get slower (a lost tail duplication costs one jump), which the GAP9 sweep cycle counts would show; they are unchanged. No lit test covers two setups for one loop; a regression test is proposed in the result file (it needs the `hwloopsfixup` pass registered first, triage side finding 1, for a `-run-pass` MIR test; an `llc` IR test of the reduced reproducer checking a single `lp.setup` per loop works today).

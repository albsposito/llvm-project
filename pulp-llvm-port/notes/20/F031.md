# 20/F031: with linker relaxation on, let the linker compute PULP hardware-loop end offsets

Written for a reader who does not know LLVM. Four sections, all required (policy_check.py checks the headings).

## What upstream changed

Nothing upstream broke this. It is a **pre-existing fork defect** (backlog B104), present in every fork toolchain. A PULP hardware loop starts with `lp.setup`, `lp.setupi`, `lp.starti` or `lp.endi`. Each of them stores the distance to a loop label inside the instruction, in halfwords. When the assembler knows both addresses it writes this distance itself. With **linker relaxation** on (`-mrelax`, which is clang's default for RISC-V), the linker shortens code after assembly: a 2-instruction `call` becomes a 1-instruction `jal`, a `lui`/`addi` address pair can become one instruction, and padding `nop`s in front of aligned code are removed when they are no longer needed. Every distance that crosses shortened code must then be recomputed by the linker. For that, the assembler leaves a **relocation** (a note that tells the linker to fill in the field) instead of writing the number itself.

Upstream makes this decision in `RISCVAsmBackend::shouldForceRelocation`: every fixup that is not explicitly exempted ends in `return STI->hasFeature(RISCV::FeatureRelax) || ForceRelocs;` (`RISCVAsmBackend.cpp:140` at `llvmorg-20.1.8`). "Relaxation on" means "leave a relocation". This is how upstream treats a conditional branch (`fixup_riscv_branch`, which becomes `R_RISCV_BRANCH`), the closest equivalent of a loop label: a PC-relative distance to a label in the same function.

Fork commit `f1b7aebff8c2` "[LLVM/PULP/SNITCH] Support for PULP and Snitch cores/platforms" (found with `git log pulp/integer_SIMD_fix -S'case RISCV::fixup_pulpv2_loop_setup:' -- llvm/lib/Target/RISCV/MCTargetDesc/RISCVAsmBackend.cpp`) exempted the two loop fixups with `return false`. So the loop distance was always frozen at assembly time. At that time lld ignored the fork's loop relocations (`R_NONE`), so leaving one would have zeroed the field. Task 20/F027 has since taught lld to apply them. With relaxation, the linker then shortened the loop body but left the old distance in the loop instruction. The loop ended at the wrong instruction, with no error.

Measured on the integration head (`logs/20-F031.repro.log`):
- `logs/20-F027-evidence/t4.s` (a `call` inside an `lp.setupi` body), `llvm-mc -mattr=+c,+xpulpv,+relax` then `ld.lld`: the `call` becomes `c.jal`, and `lp.setupi` still says 7 halfwords where the real end is 4.
- A hand-written kernel with calls inside `lp.setup`/`lp.setupi`/`lp.starti`/`lp.endi` loops on both levels, at the range limits (`logs/20-F031-evidence/kasm.s`): `-mrelax` + ld.lld gives no output on GVSoC (it hangs). `-mno-relax` gives the right result.
- Plain C, compiled by clang: `manyglob.c` (`-O2 -mrelax -mllvm -enable-global-merge=false`, ld.lld `--relax-gp`) prints `RES 0 4271986472`. The expected output is `RES 982367478 1033580172`. In the GAP9 sweep kernels built with `-mrelax` and run on GVSoC, 5 of 54 builds give a wrong result: k01_fir_fix16 O2/O3, k02_fir_f32 O2/O3 and k04_matmul_simple_f32 O3. In k01 the cause is a nested loop. clang puts a 2-byte alignment `nop` in front of the inner `lp.setup`, and ld.lld deletes it because it is not needed after placement. That shortens the outer loop body, so the outer `lp.setup` field has to change from 0x66 to 0x64.

## Why this is equivalent

One line changes, in `llvm/lib/Target/RISCV/MCTargetDesc/RISCVAsmBackend.cpp` (cluster mc, a file the fork already touches). In `shouldForceRelocation`, the fork's `case fixup_pulpv2_loop_setup / fixup_pulpv2_loop_setupi: return false;` becomes `break;` with a comment, so the loop fixups reach upstream's shared rule on line 140. Nothing is deleted: the case labels stay and document the decision.

- **Without relaxation (`-mno-relax`, what every GAP9 flow uses) nothing changes.** The rule returns false, exactly as the old `return false` did, and the assembler writes the distance as before (with F010's range check). Measured: the 54 GAP9 sweep objects (32 kernels, O2/O3, sweep flags with `-mno-relax`) are byte-identical to build/int-20, and so are `kasm.s`, `manyglob.c`, `relaxloop.c` and `t4.s` (without its `.option relax`).
- **With relaxation**, the loop instruction is written with a 0 field and gets `R_PULPV2_LOOP_SETUP` (66, the 12-bit field of `lp.setup`/`lp.starti`/`lp.endi`) or `R_PULPV2_LOOP_SETUPI` (67, the 5-bit field of `lp.setupi`). These are the fork's own relocation numbers, already produced by `RISCVELFObjectWriter.cpp`. Since 20/F027, ld.lld applies them after relaxation, as the distance in halfwords with range and alignment checks. This is what upstream does with `R_RISCV_BRANCH`. As upstream's ELF writer does for branches (`RISCVELFObjectWriter.cpp:30-35`, `needsRelocateWithSymbol` returns true), the relocation names the loop label itself (for example `.Lend0`), so lld moves it along when code shrinks.
- `ForceRelocs` (set by `.option relax` anywhere in an assembly file) now also covers loop labels, as it covers branches. `lp.counti` has no label and is not affected.
- **Range checking moves to the linker when relaxation is on.** The assembler no longer checks a loop distance that it leaves to the linker, the same as for branches. ld.lld checks the final distance (20/F027): `relocation R_PULPV2_LOOP_SETUPI out of range`. Relaxation only shortens code, so a loop that fits before relaxation still fits after.

Verified (`logs/20-F031.verify.log`, `logs/20-F031-evidence/`):
- `t4.s`: the object now carries `R_PULPV2_LOOP_SETUPI .Lend0` and `R_PULPV2_LOOP_SETUP .Lend1`. After ld.lld relaxes `call g` to `c.jal`, `lp.setupi x0, 0x64, 0x4` points at the real end (int-20: 0x7).
- GVSoC (`gvsoc-new.txt`), all with ld.lld:
  - `kasm.s` (calls inside `lp.setup` level 1, `lp.setupi` level 0 at the 62-byte limit, `lp.setup` level 0 at the 8190-byte limit, and `lp.starti`/`lp.endi` level 1 around a nested `lp.setupi`) prints `RES 4013948565` with `-mrelax`, with `-mrelax` + `--relax-gp`, and with `-mno-relax`. This equals GNU as + GNU ld 2.28. The linked loop-instruction words are identical to the GNU ld link.
  - `manyglob.c` prints the host `gcc -O0` result with `-mrelax` (with and without `--relax-gp`) and with `-mno-relax`.
  - `relaxloop.c` (globals and calls around loops, nested loops, `lp.setupi` and `lp.setup`, also with `-pulp-loop-range-immediate=0`) prints the host result in every mode.
- GAP9 runtime sweep with `-mrelax` + ld.lld (`sweep-relax-runtime.txt`): this build gives 54/54 correct results on GVSoC (GAP9 GCC reference 54/54), where int-20 gives 49/54. The `-mrelax` objects carry 134 loop relocations.
- Hardware-loop fuzzer, new seeds 7001-7120, O2/O3/Os, `CLANG_EXTRA=-mrelax`, linked by ld.lld (`relax.txt`, `relax.sum`): 360 builds, 1219 `lp.*` instructions and 1184 loop relocations in the objects. 0 mismatches against the host reference, 0 crashes. The assembly is identical to int-20 in all 360 builds.
- Lit: `llvm/test/MC/RISCV`, `llvm/test/CodeGen/RISCV` (these include the fork tests), `clang/test/CodeGen/RISCV`, `clang/test/Driver/riscv*`, `lld/test/ELF/riscv*` and the step's other lit paths: 4791/4792 pass. The one failure, `rvv/vsetvli-insert-zve64f.mir`, is a known failure that is also red on int-20. No test builds a hardware loop with `+relax`, so no CHECK line changes.

**GNU ld.** GNU ld 2.28 (GAP9 toolchain) does not know 66/67. An LLVM `-mrelax` object with a hardware loop now fails to link with "unrecognized relocation (0x42)" (`gnu-ld.txt`). Before, it linked and ran wrong: the int-20 `-mrelax` `kasm` object linked by GNU ld gives no output on GVSoC. **`-mrelax` + GNU ld stays unsupported for hardware-loop code; use `-mno-relax` (unchanged, links and runs: `RES 4013948565`) or ld.lld.** Emitting GNU's numbers 57/58 instead is not possible without a clash: upstream uses 57 for `R_RISCV_32_PCREL` and 58 for `R_RISCV_IRELATIVE` (see 20/F027).

## What breaks if this is wrong

- **The relocation is emitted but applied wrongly:** `-mrelax` programs with hardware loops end their loops at the wrong instruction. They hang or give wrong results on GVSoC, and `llvm-objdump -d` of the ld.lld output shows a loop field that differs from the GNU ld link of the same GNU-as source. `kasm.s`, `manyglob.c` and the `-mrelax` GAP9 runtime sweep show this directly.
- **`-mno-relax` output changes:** the GAP9 sweep objects would stop being byte-identical to int-20, and GNU ld links of LLVM objects would start failing on 0x42. Both were checked.
- **A linker that does not apply 66/67** (an lld older than 20/F027, or GNU ld) either rejects the object or, for an lld before F027, silently writes 0. Only `-mrelax` objects are affected.

No lit test covers this: nothing assembles or compiles a hardware loop with `+relax`. The proposed test is in the result file.

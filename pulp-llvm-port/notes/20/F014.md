# 20/F014: stop the scheduler from moving other floating-point code into an frep loop body

## What upstream changed

Nothing upstream broke this. It is a **pre-existing fork defect**: `toolchains/ref-18` and `port-19` show it too (below). It became more urgent at step 20 because of upstream `9122c5235ec8` "[RISCV] Enable bidirectional scheduling and tracking register pressure (#115445)". That commit made the scheduler move instructions around `frep`, and 20/T003 already stopped it from moving anything *across* the `frep` itself. The code that creates `frep` is fork commit `f1b7aebff8c2` "[LLVM/PULP/SNITCH] Support for PULP and Snitch cores/platforms" (`FREP_O` in `Snitch/SNITCHFrepLoops.cpp` and `RISCVInstrInfoXfrep.td`, found with `git log pulp/integer_SIMD_fix -SFREP_O`). It never told the scheduler that the loop body after the `frep` must stay as it is.

**What the hardware repeats.** Snitch has a pseudo-dual-issue design. `frep.o rs, N` hands the **next N floating-point instructions** to the FPU sequencer, which repeats them. Integer instructions never enter the sequencer: they run once, on the integer core, and do not count towards N. The same holds for FP instructions that read or write an integer register. I checked this in the Snitch model in the GAP SDK sources:
- In `/home/ubuntu/gap_sdk_release/gvsoc/gvsoc/models/cpu/iss/src/snitch_fast/sequencer.cpp:37-52`, only instructions tagged `fp_op` go to the sequence buffer. Instructions also tagged `nseq` go around it (`direct_branch_handler`), and so does everything else.
- In `.../iss/isa_gen/isa_riscv_gen.py:712-789`, `fld/fsd/flw/fsw`, `fadd/fsub/fmul/fdiv/fsqrt/fmadd...`, `fsgnj*` and `fmin/fmax` are `fp_op`. `feq/flt/fle`, `fclass`, `fmv.x.*`/`fmv.*.x`, integer<->FP `fcvt`, and also `fcvt.s.d`/`fcvt.d.s` are `nseq`.
- In `.../iss/isa_gen/isa_smallfloats.py`, every conversion between FP formats is `nseq` too: Zfh `fcvt.h.s`/`fcvt.s.h` (lines 60-61), the Xsmallfloat `fcvt.b.s`, `fcvt.h.ab` and so on, and the vector compares and moves. `fcvt.h.d`/`fcvt.d.h` are commented out, so they are not modelled at all.
- I cross-checked against the LLVM instruction definitions (TableGen JSON dump). Of the 159 `nseq` mnemonics, 115 exist in this LLVM. Every one of them either has an integer register operand or has `CVT` in its opcode name.

So integer code landing between the body instructions is harmless. The real miscompile is an **unrelated FP instruction** landing in the body. The sequencer then repeats the intruder N times, while a real body instruction slides out of the repeated group and runs once.

**Reproducer** (from the reviewer): `logs/20-F014-review/fpintr.ll`. It is an outer loop around an frep loop with body `fdiv; fmul; fadd`. Independent FP work (`fmul`, `fadd` on other values) follows the loop. It is built with `target-cpu=snitch` and `tune-cpu=sifive-7-series`. With step-20 `llc -O2 -misched=ilpmax` at the integration head (`1cb8d139f7d3`; same on current `build/int-20`), the sequencer repeats the three FP instructions after `frep.o`:

```
before (integration head)            after (this change)
  frep.o  a5, 3, 0, 0                  frep.o  a5, 3, 0, 0
  fdiv.d  fa2, ft0, ft1   <- repeated   fdiv.d  fa2, ft0, ft1   <- repeated
  slli    a6, a2, 3                    fmul.d  fa2, fa2, fa2   <- repeated
  fmul.d  fa0, fa4, fa1   <- repeated, NOT the body   fadd.d  fa5, fa5, fa2   <- repeated
  slli    a7, a2, 2                    fmv.x.w a5, fa2
  fadd.d  fa4, fa4, fa3   <- repeated, NOT the body   slli ...
  ...                                  fmul.d  fa0, fa4, fa1
  fmul.d  fa2, fa2, fa2   <- body, runs once
```

This is a silent wrong result. `fpintr-e76.ll` (`-mcpu=sifive-e76 -mattr=+xfrep`) shows the same thing. Under the reviewer's flag matrix (-O1/-O2/-O3 × default, `-enable-post-misched`, `-misched=ilpmin`, `-misched=ilpmax`, pre-RA top-down/bottom-up, post-RA bidirectional), the integration head breaks `fpintr` in the three `-misched=ilpmax` runs. `ref-18` hoists the whole body above `frep.o` on the same input, and `port-19` hoists `fdiv.d` above it.

With the default Snitch tuning and default scheduler flags, I found no input where an FP instruction enters the body. Earlier versions of this note claimed the body was "intact by luck" and headlined a case where only integer instructions moved in. That case is not a wrong result on Snitch, and I withdraw the claim. The defect needs a scheduling heuristic or a tuning that interleaves FP work. Nothing in the compiler forbade it, and this change forbids it.

## Why this is equivalent

`RISCVInstrInfo::isSchedulingBoundary` already makes `frep.o`/`frep.i` (and the PULP `lp.setup` instructions) scheduling boundaries (20/T003). This change also makes each of the frep's N sequenced instructions a boundary, through three pieces:

- **`isFrepSequenced(MI)`** answers "does the Snitch sequencer certainly repeat this instruction?". Yes requires all three of:
  - the opcode name does not contain `CVT`, so no conversion of any kind is counted (fcvt.s.d, fcvt.h.s, fcvt.h.d, the Xsmallfloat and vector conversions);
  - all explicit register operands are FP registers of one width (FPR16, FPR32 or FPR64); the one exception is the integer address register of an FP load/store;
  - it is not a COPY, branch, call, pseudo, meta instruction or `frep` itself.

  Everything else answers no, including any FP instruction whose FP operands have different widths. Revision 3 still counted `fcvt.h.s` and the other FP-to-FP conversions apart from `fcvt.s.d`/`fcvt.d.s`, which is the unsafe direction. Example: for a body `[fa, fcvt.h.s, fb]` with N = 2, `fb` got count 3 and was left unprotected.
- **`isInFrepBody(MI, MaxN)`** is true when MI is sequenced and an earlier `frep` covers it. It walks backwards, counting only sequenced instructions. It returns true if it meets an `frep.o`/`frep.i` whose N is at least MI's count. Such an MI becomes a boundary.
- **The walk crosses blocks.** The hardware counts in program order, whatever the block boundaries. The frep pass marks the loop control block address-taken, and branch folding never merges such a block into its predecessor. So when an inner loop's header and latch are separate blocks, `frep.o` ends one block and the body starts the next (`logs/20-F014-review/split.ll`). When the walk reaches the top of a block, it continues into the previous block in the layout if that block lists this one as a successor. A block that ends in `frep.o` with no branch always falls through to the next block in the layout, so the walk always finds the frep when a scheduler runs. Block placement runs after both schedulers (`O3-pipeline.ll`). If it ever moved the body block away, the frep would repeat the wrong code whatever the scheduler did (see residual risks).

**Why nothing can enter or leave the body.** The frep and its N sequenced instructions are fixed points. Everything else stays schedulable, but a scheduler only reorders instructions inside a region between two boundaries, so nothing crosses a fixed point. In particular, no FP instruction from before the frep or after the Nth can get between them. Integer instructions inside the gaps may still be reordered among themselves, which the sequencer does not see.

**Why the count errs on the safe side.** `isFrepSequenced` answers no whenever in doubt: for every conversion, for mixed FP widths, and for any instruction with an integer operand. Leaving out an instruction the hardware does count means the walk reaches its Nth instruction later than the hardware does. So the protected range can only grow; it never ends before the real body. The first two versions counted integer instructions too. That was the unsafe direction: for a body `[fa, integer reload, fb]` with N = 2, `fb` got count 3 and was left unprotected. Their code comment claiming "can only over-protect" was false, and is replaced.

**Compile time.** The frep pass now records the largest N it creates in the function, in `RISCVMachineFunctionInfo` (`noteFrepBody`/`getMaxFrepBody`). The fork already keeps its `UsedSSR` field there, set by the SSR pass and read elsewhere. In a function without frep, `isSchedulingBoundary` checks this one field and returns. In a function with frep, the walk runs only for sequenced (FP) instructions and stops after the function's largest N sequenced instructions. Measured with `llc -O2` (user time, loaded host; numbers in the result file):
- The reviewer's `manyblk.ll`, 8000 blocks without frep: 1.40 s before, 1.40 s after. Revision 2 took 3.8–6.0 s.
- A 40000-instruction single FP block, with and without an frep loop in front: 0.84 s both before and after.
- 40000 integer instructions after an frep loop: 0.35 s both before and after.

**Half-precision example.** `logs/20-F014/rev3/fcvth.ll` is Snitch with Zfh (on by default) and SiFive-7 tuning. Its body is `fdiv.d; fadd.d; fcvt.s.d; fcvt.h.s; fadd.h`, and half-precision and double FP work follows the loop. With default flags, the integration head moves an unrelated `fsh` from after the loop into the body, so the sequencer repeats `fdiv.d, fsh, fadd.h, ...`. Revision 4 keeps `fdiv.d, fadd.d, fadd.h` as the first three sequenced instructions under the whole flag matrix. The frep pass gives this loop N = 5, because it counts the two `fcvt` instructions. So the sequencer also takes the next two FP instructions after the loop. That is the frep-pass N defect described below, not an intrusion.

**Output.** The four fork FREP tests (`freploop.ll`, `freploop-nested.ll`, `sdma-intrinsics.ll`, `ssr-register-reserving.ll`) give byte-identical output to the integration head at -O0 to -O3, and so do my other reproducers (with and without `-enable-post-misched`). All of the reviewer's inputs now keep the exact body under the whole flag matrix: `split*`, `bigbody*`, `fpintr*`, `intbody`, `nested-lat2`, and also `fcvth`. For `intbody` and `fcvth`, the slots beyond the real body come from the frep pass counting integer or `fcvt` instructions in N; see below.

**Upstream reference for the technique.** ARM keeps the Thumb-2 `IT` instruction and the instructions it predicates together through `isSchedulingBoundary`, by looking at neighbouring instructions (`llvm/lib/Target/ARM/ARMBaseInstrInfo.cpp:2084` at llvmorg-20.1.8). RISC-V/CORE-V has no repeat instruction, so there is no XCV reference (rule 12 does not apply).

I rejected bundling for two reasons. Before register allocation, frep and body are often in different blocks (`freploop.ll` `hwloop1`), and bundles cannot span blocks. After allocation, a new bundling pass changes `O0/O3-pipeline.ll`. That option is backlog B79.

**Is the frep pass's own N consistent with the hardware? No** (reported, not fixed; this is a separate defect). `SNITCHFrepLoops::containsInvalidInstruction` counts every loop instruction except PHIs, COPYs, loop branches, debug instructions and instructions using the induction variable. Integer instructions and `nseq` FP instructions are counted, and `isInvalidLoopOperation` does not reject them: its FPR test `RC != FPR64 || RC != FPR32` is always true. Example, `logs/20-F014/rev3/ncount.ll` (`llc -O2`): the body `fadd.d; fcvt.w.d; xor` gets `frep.o a1, 3`. The sequencer repeats only `fadd.d`, then takes the next two FP instructions after the loop. The integer `xor` of the loop runs once instead of 64 times. This check does not rely on the pass's N being right. It uses N only as an upper bound, and with that N it still protects at least the real body.

## What breaks if this is wrong

- **If the boundary is missing** (before this change): with a scheduling heuristic or tuning that interleaves FP work (`-misched=ilpmax`, SiFive-7 tuning, a future real Snitch latency model), frep loops silently compute wrong results. An unrelated FP instruction is repeated N times and a body instruction runs once. There is no crash or diagnostic, only wrong numbers in Snitch kernels built with `-snitch-frep-inference` or `llvm.riscv.frep.infer`.
- **If `isFrepSequenced` wrongly answered yes** for an instruction the sequencer skips: the protected range could end before the last body instruction. This was the defect of revisions 1–2 for integer instructions, and of revision 3 for FP-to-FP conversions such as `fcvt.h.s`.
- **If the walk did not cross into the fallthrough predecessor:** loops with separate header and latch stay unprotected (`split*.ll`).
- **If the MaxFrepBody flag were not set** (for example, a MIR test that contains `FREP_O` and runs the scheduler, since the flag is not serialised to MIR): no protection in that function. No such test exists. Only `SNITCHFrepLoops` creates `FREP_O`, and it sets the flag.
- **Too strong:** FP code right after an frep loop is scheduled slightly less freely. This affects performance only, and no fork test output changed.
- **Residual risks (pre-existing, not addressed):**
  - Block placement could in principle separate the frep block from its fallthrough body block; not observed. Bundles would not help here either.
  - Machine copy propagation could delete a copy-like body `fmv.d`/`fsgnj`.
  - `RISCVMakeCompressible` (only with C) can insert instructions.
  - At -O0 the frep pass miscounts and the fast register allocator spills inside the body.
  - Nested frep would under-protect the outer body; the frep pass never creates it.
  - No fork lit test pins a body with FP work after it; see `proposed_test`.
- **GVSoC cannot show it:** the only built GVSoC target, `ri5ky_testbench`, is a RI5CY/GAP9 core with Zfinx and no FREP/SSR. The Snitch models exist in the SDK source (the files above), but no Snitch platform is built. I verified structurally in assembly, counting what the sequencer repeats (`logs/20-F014/rev3/body.py`).

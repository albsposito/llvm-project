# 20/F046: select between two PULP packed vectors on a scalar condition (backlog B144)

This fixes a gap the fork already had. `toolchains/ref-18`, `toolchains/port-19` and the integration head all crash on the same input.

## What upstream changed

Nothing upstream broke this. The PULP packed vector types `v2i16` (2 x short) and `v4i8` (4 x char) live in ordinary integer registers (register classes `GPRAV2`/`GPRAV4`, which hold exactly the X registers). The fork made them legal types in fork commit `f1b7aebff8c2` "[LLVM/PULP/SNITCH] Support for PULP and Snitch cores/platforms" (2022-08-25; found with `git log pulp/integer_SIMD_fix -S'addRegisterClass(MVT::v2i16' -- llvm/lib/Target/RISCV/RISCVISelLowering.cpp`). That commit told the legalizer what to do with many operations on these types (loads and stores are promoted to `i32`, `vselect`, `mul`, divisions are expanded) but not with `select` (choose one of two whole vectors on a scalar condition) or `select_cc` (the same with the comparison folded in).

An operation the target does not mention is treated as "legal", so it reaches instruction selection unchanged, and there is no instruction pattern for it:

    LLVM ERROR: Cannot select: t8: v2i16 = select t14, t4, t6
    LLVM ERROR: Cannot select: t16: v4i8 = select_cc t2, Constant:i32<0>, t7, t8, setne:ch

C code such as `if (k) v = a + b; else v = a - b;` on `v2s`/`v4s` values at -O1 and above produces these nodes. At -O0 the if/else stays as branches and does not crash. The llc matrix (`logs/20-F046-matrix/`, see below) crashes in 120 of 360 runs. All 120 are `v2i16`/`v4i8` select or select_cc, for xgap9, zfinx+xpulpv and f+xpulpv, at O0 (IR select), O2, O3 and Os (`logs/20-F046.repro.log`). `v2f16`/`v2bf16`, element-wise `vselect` and vector `setcc` already worked.

## Why this is equivalent

Two lines in the fork's per-type block for `v2i16`/`v4i8` in `RISCVISelLowering.cpp` (cluster codegen-core, next to the existing `LOAD`/`STORE` promotion):

- `setOperationPromotedToType(ISD::SELECT, VT, MVT::i32)`: the legalizer bitcasts both vectors to `i32`, selects the `i32`, and bitcasts the result back (`SelectionDAGLegalize::PromoteNode`, `case ISD::SELECT`, uses `BITCAST` for vector types). The bitcasts are free because the four `bitconvert` patterns at `RISCVInstrInfoXpulp.td:1757-1760` map them to plain register reuse. The `i32` select then takes the normal upstream XLenVT path: `lowerSELECT` makes `RISCVISD::SELECT_CC`, which becomes the `Select_GPR_Using_CC_GPR` pseudo, which expands to a conditional branch around a register move (or to `czero` with Zicond).
- `setOperationAction(ISD::SELECT_CC, VT, Expand)`: `select_cc` is split into a `setcc` plus a `select`, and the `select` is then promoted as above. Upstream does the same for every type it selects in registers (`RISCVISelLowering.cpp:288` for XLenVT, `:494`/`:525` for f16/f32, at `llvmorg-20.1.8`).

A select only chooses which 32-bit register value wins. It never looks inside the lanes. So selecting the vector's bits as an `i32` gives the same result bit for bit. On GAP9 `if (k) v=a+b; else v=a-b;` becomes `bnez a0; pv.sub.h a0,a1,a2; ret; pv.add.h a0,a1,a2; ret`.

Why Promote rather than a `Custom` action plus new `Select_GPRAV2/GPRAV4_Using_CC_GPR` pseudos, as upstream does for Zfinx/Zhinx floats (`RISCVInstrInfoF.td:702`, `RISCVInstrInfoZfh.td:447`): upstream's `lowerSELECT` (`RISCVISelLowering.cpp:8344-8348` at `llvmorg-20.1.8`) turns every *vector* SELECT into a VSELECT with a splat condition. That is right for RVV but, for a GPR-held vector, would give a mask-and/or sequence instead of a branch. Promoting to `i32` needs no change to upstream code or to the instruction tables, and it reuses the exact upstream `i32` code. Upstream uses the same Promote-by-bitcast action for vector SELECT in `llvm/lib/Target/AMDGPU/AMDGPUISelLowering.cpp:553-554` (`v2f32` -> `v2i32`). Upstream has no GPR-held packed vector at 20.1.8: CORE-V `XCVsimd` works on `i32` (`RISCVInstrInfoXCV.td`), so there is no closer RISC-V reference. `v2f16`/`v2bf16` need nothing of their own, because they do not reach instruction selection as select nodes. The matrix shows they already compiled, and their output is unchanged.

The change is inside `if (Subtarget.hasPULPExtV2())`, so configurations without PULP cannot see it.

## What breaks if this is wrong

If the promotion picked the wrong operand, a branchy SIMD kernel would return the other arm: `k1a`/`k1b`, `k3`, `k5` or `k6` in `selk.c` would differ from the host reference on GVSoC, and GAP9 SDK code with `if (...) v = ...; else v = ...;` on `v2s`/`v4s` would compute wrong lanes. If the actions were missing, as before, clang stops with "Cannot select: v2i16 = select" / "v4i8 = select_cc". No lit test covers this today. Proposed test: an llc test, `llvm/test/CodeGen/RISCV/xpulp-select-packed.ll`, with the 30 matrix functions for `-mattr=+xgap` and `+m,+f,+c,+xpulpv` at O0/O2, checked by `update_llc_test_checks.py`.

# 20/F023: the frep pass only turns a loop into an frep when the hardware will really repeat the whole body

## What upstream changed

Nothing upstream broke this. It is a **pre-existing fork defect** (backlog B84, and the second half of B78). The code comes from fork commit `f1b7aebff8c2` "[LLVM/PULP/SNITCH] Support for PULP and Snitch cores/platforms", which added `Snitch/SNITCHFrepLoops.cpp` with `containsInvalidInstruction` and `isInvalidLoopOperation` (found with `git log pulp/integer_SIMD_fix -SisInvalidLoopOperation -- llvm/lib/Target/RISCV/Snitch/SNITCHFrepLoops.cpp`). `ref-18`, `port-19` and the step-20 integration head all behave the same way.

**What the hardware does.** `frep.o rs, N` hands the **next N floating-point instructions** to the Snitch FPU sequencer. The sequencer repeats them `rs+1` times. Integer instructions never enter the sequencer. They run once, on the integer core, and do not count towards N. The same holds for FP instructions that read or write an integer register (`fcvt.w.d`, `fmv.x.w`, `feq`...) and for every conversion between FP formats. The source is the GVSoC Snitch model in the GAP SDK: `gvsoc/gvsoc/models/cpu/iss/src/snitch_fast/sequencer.cpp:37-52` (only `fp_op` instructions go to the sequence buffer, and `nseq` instructions go around it), plus the `nseq` tags in `isa_gen/isa_riscv_gen.py` and `isa_gen/isa_smallfloats.py`. 20/F014 put exactly this into `RISCVInstrInfo::isFrepSequenced`.

**What the pass did.** Two checks were meant to keep integer work out of an frep body, and both failed:

1. `isInvalidLoopOperation` was meant to reject an instruction unless all its operands are FP registers. Its test `RC != FPR64 || RC != FPR32` is true for every register, so the function really returned "invalid" only for instructions with **no** virtual register operand at all. Integer instructions, FP compares and conversions were all accepted.
2. `containsInvalidInstruction` counted every accepted instruction in N, integer or not. It also silently skipped (neither counted nor rejected) every instruction that used the loop counter, even address arithmetic that had to run on each iteration.

Example: `logs/20-F014/rev3/ncount.ll` with `llc -O2` (log `logs/20-F023.repro.log`). The body `fadd.d; fcvt.w.d; xor` became

```
  li      a1, 63
  frep.o  a1, 3, 0, 0
  fadd.d  fa5, fa5, ft0     <- repeated 64 times (correct)
  fcvt.w.d a1, ft0, rtz     <- runs once (not sequenced), but counted in N
  xor     a0, a0, a1        <- runs once instead of 64 times: wrong result
  fmv.x.w a1, fa4           <- not sequenced either
  fcvt.w.d a1, fa5, rtz     <- not sequenced either
```

N = 3, but only one body instruction is sequenced. The hardware therefore also takes the next two FP instructions after the loop into the repeat, if there are any. The integer `xor` runs once instead of 64 times.

## Why this is equivalent

The pass now converts a loop only if every instruction in it is one of these:

- **an instruction the sequencer certainly repeats**, which is `RISCVInstrInfo::isFrepSequenced` (from 20/F014; see below). Only these are counted in N;
- **loop control that the frep replaces**: the induction PHI and induction update, the trip-count values that `getLoopTripCount` already collects (`OldInsts`), the exit branch on the counter, and the loop's own unconditional branches;
- **a loop-carried PHI that needs no copy** (revision 2, see below).

Anything else makes the pass leave the loop as an ordinary loop. That includes an integer instruction, an FP instruction with an integer operand, any FP conversion, **any COPY**, a call, or another branch. The loop counter may be used only by the PHI, the update and the exit branch. Any other user needs the counter's value on each iteration, which no longer exists once the loop is an frep. That covers address arithmetic in the body and a use of the counter after the loop. In both cases the pass declines. Declining is always safe, because the loop then runs as normal code.

The fix has three pieces:
- `isInvalidLoopOperation` now returns `!RISCVInstrInfo::isFrepSequenced(MI)`. This is B78's always-true check, replaced rather than patched: the same test also decides which instructions after an frep the schedulers must leave in place (20/F014). One classification serves both, so they cannot drift apart.
- `isFrepSequenced` changed from a file-local `static` function in `RISCVInstrInfo.cpp` into a public static member of `RISCVInstrInfo`. This is a separate `codegen-core` commit, and the function body is unchanged.
- `containsInvalidInstruction` has three changes:
  - it takes `OldInsts`;
  - it checks the users of the counter up front;
  - it replaces "skip anything that uses the counter" with "skip the loop control in `OldInsts`";
  - revision 2: it rejects every COPY, and every loop-carried PHI that would need a copy (`phiMayNeedCopy`).

**Copies that appear after the pass (revision 2, from the review).** The frep pass runs before PHI elimination and register allocation, and those two can still add instructions to the body. A loop-carried value is a PHI at pass time. It becomes a copy in the body when its old value is still needed after the new one exists. Example, reviewer's `logs/20-F023-review/swap.ll`: `a, b = b, a + b` gave `frep.o a0, 1` over `fadd.d fa1, fa0, fa1; fmv.d fa0, fa4`, and a three-value rotation gave N = 1 over `fmul.d; fmv.d; fmv.d`. The GVSoC model tags `fsgnj.d` (`fmv.d`) as `fp_op` and not `nseq` (`isa_riscv_gen.py:767`), so the sequencer repeats these copies and N had to count them. It did not, so the `fmv.d` ran once and the result was wrong. The copy of an integer value (`mv`) would run once. The pass cannot know before register allocation which copies survive, so it declines every loop that may need one. A non-induction PHI with result R and back-edge value V needs no copy only if all of these hold:
- V is R itself, or V is defined by a non-PHI instruction D inside the loop;
- no other PHI of the same loop header also carries V;
- every use of R comes before or at D in the iteration (a use in D's block before D, or in a block that dominates D's block);
- if R is used after the loop, every loop exit is taken before D is reached.

Then R and V can share one register, and there is no copy. Otherwise the pass declines. This covers swaps, rotations, a loop-invariant back-edge value, R used after its update, R feeding another PHI, and R live out of a loop that exits after D. Plain accumulators (`s = s + x`, as in the fork tests, `@inv` and the F014 inputs) satisfy the rule and still convert. The reviewer's scan found no COPY in any frep candidate at pass time, so declining every COPY costs nothing measurable.

`isFrepSequenced` answers "yes" only when it is certain. It says no to any opcode with `CVT` in its name, to mixed FP widths, and to any integer register operand except the address of an FP load/store. A pass that trusts it can therefore only decline too often, never repeat too much. At pass time every body instruction is now counted and every counted instruction is sequenced. The instructions that later passes can still add to the body are copies from PHIs (now declined when they may be needed) and spills or reloads from register allocation. For a loop the pass accepts at -O1..-O3, N is therefore the number of instructions the hardware repeats, **provided register allocation adds no spill or reload inside the body**. I found no such case at -O1..-O3 in any input. At -O0 the fast register allocator does add them; see residual risks. FP loads/stores can only use a loop-invariant address. The only ways to change the address from one iteration to the next are integer work or the counter, and the pass now declines both.

Second example, `logs/20-F023/ivuse.ll` `@addr` (`llc -O2 -disable-lsr`, body `x[i] *= c`). Before this change the pass produced `frep.o a2, 4` over `slli; add; fld; fmul.d; fsd`. The address arithmetic runs once, so all 64 repetitions load and store the same element `x[0]`, and N = 4 counts the integer `add`. Now it stays an ordinary loop. `@inv` in the same file has a pure FP body and still becomes `frep.o a1, 1` exactly as before.

**What the pass declines now that it accepted before:**
- loops with integer arithmetic in the body (`ncount.ll`: `xor`; the reviewer's `intbody.ll`: `mul`);
- loops with FP instructions that read or write an integer register (`fcvt.w.d`, `fmv.x.w`, `feq`/`flt`/`fle`, `fclass`, int<->FP `fcvt`);
- loops with FP format conversions (`fcvt.s.d`, `fcvt.h.s` and so on). Example: `logs/20-F014/rev3/fcvth.ll`, where the pass used to give N = 5 while the hardware repeats 3;
- loops whose counter is used by anything other than its update and the exit branch (address arithmetic, a use after the loop);
- loops with any COPY, another branch, or a call in the body;
- loops with a loop-carried value that needs a copy (revision 2): `logs/20-F023-review/swap.ll` `@swap` (swap) and `@rot` (three-value rotation) are now ordinary loops at -O0..-O3 (`logs/20-F023/swap.O2.new.s`).

**What stays the same:** loops with pure FP arithmetic, sign injection, min/max, FP loads/stores and SSR reads are converted exactly as before.

**One count changes, at -O0 only.** At -O0 the end-of-count constant (`li a0, 128`) sits inside the loop. It is in `OldInsts` (loop control) and used to be counted. So N drops by one to the real number of FP instructions. For example, `freploop.ll` `hwloop2` at `-O0` goes from `frep.o a0, 2` to `frep.o a0, 1`, and the body is `fmadd.d` only. The same happens in `freploop-nested.ll` at -O0 (3 to 2) and in the F014 reproducers at -O0 (for example `bigbody` goes from 8 to 7). No fork test runs frep at -O0. -O0 frep output was already wrong for another reason: the fast register allocator spills inside the body, which is noted in 20/F014.

**Checked output** (`logs/20-F023/gen.sh`, which compares `logs/20-F023/base` from `build/int-20` against `logs/20-F023/new`. At the time, `build/int-20` was built from `e21026f4903f`, which is the task's integration head `7459255b6120` plus one registration fixup; that fixup changes no loop code. Flags: -O0..-O3 × {default, `-misched=ilpmax`, `-enable-post-misched`}):
- The four fork FREP tests (`freploop.ll`, `freploop-nested.ll`, `sdma-intrinsics.ll` as asm and as `-stop-after=riscv-expand-sdma` MIR, `ssr-register-reserving.ll`) give **byte-identical** output at -O1/-O2/-O3, which covers all their RUN lines. Only the untested -O0 `freploop*.ll` output changes, as described above.
- 20/F014's reproducers and reviewer inputs (`logs/20-F014/rev3/*.ll`, `logs/20-F014-review/*.ll`) are byte-identical at -O1..-O3, except the three whose loops contain non-sequenced work: `ncount`, `intbody` and `fcvth`. These are now ordinary loops with `addi`/`bnez` loop control, and each keeps its full body. So the F014 body protection is untouched wherever an frep is still created.
- Revision 2 (`logs/20-F023/new2`, from the rebuilt `build/20-F023`) is byte-identical to revision 1 (`logs/20-F023/new`) on every input above at every level and flag, ignoring the `.option arch` line. So the four fork FREP tests are still byte-identical to the integration head at -O1..-O3, and the F014 matrix is unchanged. The first draft of the PHI rule also rejected a PHI whose back-edge value feeds a PHI of an *outer* loop, which changed `freploop-nested.ll`. That was too strict, and the rule now looks only at PHIs of the same header.
- The B83 `removeSuccessor` assertion occurs in the same 21 runs before and after (`reord2-e76`, and `split*` at -O0). This change does not fix it or make it worse. B78's verifier errors are not touched.

There is no upstream reference implementation: RISC-V/CORE-V has no repeat instruction, so rule 12 has no XCV equivalent. The closest upstream analogue is the "hardware loop may only contain what the hardware supports" check of the Hexagon hardware-loop pass (`HexagonHardwareLoops::containsInvalidInstruction` / `isInvalidLoopOperation`, `llvm/lib/Target/Hexagon/HexagonHardwareLoops.cpp`, at `llvmorg-20.1.8`), from which this fork pass was derived. It rejects a loop as soon as it finds one invalid instruction, which is the rule applied here.

## What breaks if this is wrong

- **If the pass still accepted non-sequenced work** (before this change): Snitch kernels built with `-snitch-frep-inference` or `llvm.riscv.frep.infer` silently compute wrong numbers. Integer work in the body runs once instead of once per iteration, and N is too large, so the sequencer also repeats FP instructions from after the loop. There is no crash or diagnostic. `ncount.ll` shows it.
- **If `isFrepSequenced` said "yes" to something the hardware skips:** the pass would convert that loop, and N would be too large by one for each such instruction. The same function also drives the F014 scheduling protection, so both would be wrong together.
- **If the pass now declined something it should accept:** a Snitch FP kernel loses its frep and runs as an ordinary loop. That is slower but correct. The four fork FREP tests would catch it for their cases (`frep.o` would disappear from the CHECK lines). They pass unchanged.
- **If `phiMayNeedCopy` wrongly said "no copy":** register allocation would put an `fmv.d` in the body. The sequencer would repeat it without counting it in N, so a body instruction would fall out of the repeat and the copy would run once (the `swap.ll` symptom).
- **Residual risks (pre-existing, not addressed):**
  - Register allocation could still spill or reload inside an accepted body at -O1..-O3 under high FP register pressure. This was not observed, and the pass cannot see it before allocation.
  - At -O0 the fast register allocator spills and reloads around the body. Example: `ivuse.ll` `@inv` at -O0 reloads `x` into `fa4` before `frep.o` and the body `fmul.d fa4, fa4, fa4` overwrites it, both before and after this change (before: N = 3). -O0 frep is not tested by any fork test.
  - No fork lit test has integer work or a conversion in an frep candidate loop; see `proposed_test` in the result file.
- **GVSoC cannot show it:** the only built GVSoC target is a RI5CY/GAP9 core with no FREP/SSR. I verified it in assembly and by the Snitch model source cited above. The change cannot affect targets without Xfrep: the frep pass returns immediately without `Xfrep`, and `isSchedulingBoundary` is unchanged apart from calling the renamed function. The GAP9 sweep (`benchmarks/gap9-sweep/run.py` on a scratch copy) compared the `build/int-20` clang then at `e21026f` (`base`) with revision 1 (`mine`). It gives identical disassembly for all 54 kernel builds (27 kernels × -O2/-O3). Revision 2 changes only `SNITCHFrepLoops.cpp`, which returns before doing anything on targets without Xfrep.

# 20/T007: rename PulpV2/PulpV4 to GPRAV2/GPRAV4 so GPR and the packed-SIMD classes are interchangeable again

Written for a reader who does not know LLVM. This is a name-order bridge made on owner decision D3 (PROGRESS.md, 2026-09-27). The step-23 redesign removes these classes in favour of upstream's approach (packed types held directly in GPR), and this rename goes away with them.

## What upstream changed

Upstream `bc91f3cdd57c` "[RISCV] Add 32 bit GPR sub-register for Zfinx. (#108336)" rebuilt the `GPRF32` register class from new 32-bit sub-registers (`X*_W`) instead of from `GPR`. So `GPRF32` no longer has exactly the same registers as `GPR`, but it still has the same size and register count. TableGen orders classes of the same size and count by name. So `GPRF32` now sorts between `GPR` and the fork's `PulpV2`/`PulpV4` (IDs 7 GPR, 8 GPRF32, 9 PulpV2, 10 PulpV4).

The fork's `PulpV2` (v2i16) and `PulpV4` (v4i8) classes hold exactly the registers x0-x31, like `GPR`. TableGen treats identical classes as mutual sub-classes only while they sit next to each other in this order (`llvm/utils/TableGen/Common/CodeGenRegisters.cpp`, `TopoOrderRC` at lines 973-994, and the "Sweep up missed clique members" loop in `computeSubClasses` at llvmorg-20.1.8). With `GPRF32` in between, `GPR` stopped being a sub-class of `PulpV2`/`PulpV4`, and the relation became one-way. That broke two fork tests. The machine verifier rejected a `gpr` value on a PulpV4 operand (`pulp-expand-pseudo.mir`, found by T004). Instruction selection gave the splat pseudos class `pulpv2` instead of `gpr` (`pulp-select-pseudo.ll`, found by T005).

## Why this is equivalent

The classes are renamed only. Their registers, value types, allocation order and alignment are unchanged: `PulpV2` becomes `GPRAV2` and `PulpV4` becomes `GPRAV4`. TableGen compares names byte by byte (`StringRef::operator<`). Because `"GPR" < "GPRAV2" < "GPRAV4" < "GPRF32"` ('A' 0x41 sorts before 'F' 0x46), the three identical classes are adjacent again (IDs 7 GPR, 8 GPRAV2, 9 GPRAV4, 10 GPRF32). They are also in the same relative order as at port/19 (GPR first). Every use is renamed: 185 lines in `RISCVInstrInfoXpulp.td` (insn-tablegen), the class definitions in `RISCVRegisterInfo.td` and `addRegisterClass` in `RISCVISelLowering.cpp` (codegen-core), and the `Decode<Class>RegisterClass` hooks that the generated disassembler calls by class name in `RISCVDisassembler.cpp` (mc). No other file names these classes.

Evidence:
- The generated `RISCVGenRegisterInfo.inc` now has identical `GPRSubClassMask`, `GPRAV2SubClassMask` and `GPRAV4SubClassMask` arrays (first word `0x7f6bf380`, bits 7, 8 and 9 all set). This matches port/19, where `GPR`, `PulpV2` and `PulpV4` masks were identical (`0x03fbbff8`). Before the fix, the step-20 PulpV masks lacked the GPR bit (`0x7f6bf600` vs GPR `0x7f6bf680`).
- `pulp-expand-pseudo.mir` and `pulp-select-pseudo.ll` pass with no test edit.
- llc output for `intrinsics/xpulpv.ll`, `pulp-select-pseudo.ll` and `xpulp-hwloop.ll` (at -O0 and the default level) is byte-identical before and after the rename. In the post-ISel MIR of `xpulpv.ll`, virtual-register classes are now 435 gpr / 19 gprav2 / 22 gprav4. That is exactly port/19's 435 gpr / 19 pulpv2 / 22 pulpv4. Step 20 before the fix had 327 gpr / 127 pulpv2 / 22 pulpv4.
- No fork test spells `pulpv2`/`pulpv4` as a class name, so the printed-name change is invisible to the tests. All fork CodeGen and MC tests pass, except `freploop-nested.ll`, which is a known step-20 failure owned by another task (T008) and also fails without this change.

There is no upstream reference implementation for this. Upstream (and PULP's LLVM 22 fork) instead put packed vector types directly into `GPRRegisterClass` (`llvm/lib/Target/RISCV/RISCVRegisterInfo.td:248-252` at llvmorg-22.1.7). That is the planned step-23 redesign. This rename is the owner-approved temporary fix until then.

## What breaks if this is wrong

If the classes stopped being mutual sub-classes of GPR again, `pulp-expand-pseudo.mir` would fail with "Expected a GPRAV4 register, but got a GPR register", and `pulp-select-pseudo.ll` would show `:gprav2` instead of `:gpr`. If a use had been missed, TableGen or the C++ build would fail (undefined class `PulpV2` or missing `DecodeGPRAV2RegisterClass`). This bridge is fragile: any upstream class added later with the same size and register count, whose name sorts between "GPR" and "GPRAV2", would break it again. The same two tests would catch that.

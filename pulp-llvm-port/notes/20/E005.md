# 20/E005: remove a duplicated closing brace left by the step-20 merge in RISCVISelDAGToDAG.cpp

Written for a reader who does not know LLVM. Four sections, all required (policy_check.py checks the headings).

## What upstream changed

Commit `22f98740b618` "[llvm][RISCV] Support RISCV vector tuple CodeGen and Calling Convention (#97995)" added a new helper function, `getSegInstNF`, to `llvm/lib/Target/RISCV/RISCVISelDAGToDAG.cpp`. It went in right after `selectSF_VC_X_SE`, which is where the fork's PULP instruction-selection helpers (`tryPulpIndexedLoad`, `tryPulpVectorShuffle`) start. When the fork was replayed onto LLVM 20, the conflict resolution put the PULP helpers after `getSegInstNF`, which is correct. But it also copied the closing brace `}` of `selectSF_VC_X_SE`, which was the fork hunk's context line at LLVM 19, as an extra line. The result was an unmatched `}` at line 841 and the compiler error `extraneous closing brace ('}')`. This is a merge artifact: no LLVM API changed.

## Why this is equivalent

At LLVM 19 (port/19, `wt/int-19`) the fork hunk begins right after `selectSF_VC_X_SE`'s closing brace. At LLVM 20 it now begins right after `getSegInstNF`'s closing brace, and the one stray `}` line (plus its blank line) is gone. No fork line and no upstream line was removed or changed. The PULP block from `tryPulpIndexedLoad` up to `Select` is byte-for-byte the same as in port/19 (checked with `diff`). The code outside that block matches `llvmorg-20.1.8` exactly. This is a misplacement fix, so no vendor-extension reference was needed. The conflict note `notes/20/conflict-codegen-core.md` already names the intended order ("Kept getSegInstNF ... then the complete PULP indexed-load/shuffle helpers"), and this change makes the file match it.

## What breaks if this is wrong

If a brace were removed from the wrong place, the file would fail to compile or a function body would change. The file now compiles with no errors or warnings (`logs/20-E005.fix.log`). If PULP code had been lost, PULP post-increment loads (`p.lb`/`p.lh`/`p.lw` with post-increment) and packed-SIMD shuffles (`pv.shuffle*`, `pv.pack*`) would disappear from llc output. That would show up in the fork's CodeGen lit tests for Xpulp post-increment and SIMD, and in downstream instruction-mix checks.

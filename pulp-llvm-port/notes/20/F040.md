# 20/F040: assembler, disassembler and printer for GAP9's bfloat16 (`.ah`) and packed half-precision (`vf*.h`, `vf*.ah`) instructions

This is a gap the fork already had (backlog B90/B96, fp16 design `benchmarks/fp16-design/design.md` task T2). GAP9 keeps half-precision floats in the integer registers. It has three kinds of half-precision instruction:
- plain IEEE half (`float16`): these are the same bytes as upstream Zhinx, which is already on with `xgap9` (20/F035);
- scalar bfloat16 (`float16alt`, suffix `.ah`);
- packed pairs of either in one register (`v2h`, `v2ah`, mnemonics `vf*.h` / `vf*.ah`).

Before this change, LLVM could not assemble or disassemble any `.ah` or `vf*` instruction for GAP9. `llvm-mc -mattr=+xgap` rejected `fadd.ah a0,a1,a2` and printed GCC's `04c5d553` as `<unknown>` (`logs/20-F040.repro.log`). The fork's only `.ah`/`vf*` definitions are Snitch's. Snitch keeps the operands in the F registers and gives `.ah` the same bytes as `.h`, so they are wrong for GAP9 (design 3.4, backlog B96). This change adds the GAP9 instructions for the assembler, disassembler and printer only. No compiler pattern uses them yet: the design's tasks T3/T5 add those.

There are two commits: `insn-tablegen` (the new file `RISCVInstrInfoXpulpfloat.td`, plus one `include` line in `RISCVInstrInfo.td`) and `mc` (6 lines in `RISCVDisassembler.cpp` that try the new decoder table).

## What upstream changed

Nothing upstream broke this. The fork never had these instructions. The features they depend on, `xpulpf16alt` and `xpulpfvec`, were added by fork commit `878ee13be29d` "fixup! [pulp] registration: extensions, features, processors, CSRs" (task 20/F035; `git log -S'FeatureVendorXpulpfvec' llvmorg-20.1.8..HEAD -- llvm/lib/Target/RISCV/RISCVFeatures.td`). That commit added the extensions with no instructions and left a note saying the instructions would come with B90 T2, which is this task. Upstream LLVM 20 has no bfloat16 arithmetic in integer registers and no packed float instructions in integer registers. Its bfloat16 extension, Zfbfmin, has conversions only and uses the F registers.

## Why this is equivalent

Before, GAP9 assembly with `.ah` or `vf*` instructions could not be assembled or disassembled by LLVM. Now every such instruction that GAP9 GNU `as` accepts is accepted by `llvm-mc` and produces the same bytes. `llvm-objdump` prints the same mnemonic and operands as GNU `objdump`.

**What is defined** (110 instructions, list and encodings from GVSoC's `gvsoc2/core/models/cpu/iss/isa_gen/isa_smallfloats.py`, classes `Xf16alt` (line 82) and `Xfvec` (line 231)):
- Gated on `xpulpf16alt` (scalar bfloat16, operands in integer registers):
  - `fmadd/fmsub/fnmsub/fnmadd.ah`, `fadd/fsub/fmul/fdiv.ah`, `fsqrt.ah`
  - `fsgnj/fsgnjn/fsgnjx.ah`, `fmin/fmax.ah`, `feq/flt/fle.ah`, `fclass.ah`
  - `fcvt.w/wu.ah`, `fcvt.ah.w/wu`, `fcvt.s.ah`, `fcvt.ah.s`
  - `fcvt.h.ah` and `fcvt.ah.h` (these also need Zhinx)
- Gated on `xpulpfvec` (packed), plus Zhinx for the `.h` lanes and `xpulpf16alt` for the `.ah` lanes, as GVSoC tags them (`f16vec`/`f16altvec`) and as design decision 6.3 says. Each op below exists in `.h` and `.ah` form, and the first group also in the `.r` form (rs2 is a scalar copied to both lanes):
  - with `.r` form: `vfadd, vfsub, vfmul, vfdiv, vfmin, vfmax, vfmac, vfmre, vfsgnj, vfsgnjn, vfsgnjx, vfeq, vfne, vflt, vfge, vfle, vfgt`
  - without `.r` form: `vfsqrt`, `vfclass`, `vfcvt.x/xu.*`, `vfcvt.*.x/xu`, `vfcpka.h.s`, `vfcpka.ah.s`, `vfcvt.h.ah`, `vfcvt.ah.h`
- Assembler-only aliases that GNU `as` accepts: `fneg.ah`, `fabs.ah`, `fgt.ah`, `fge.ah`, `vfneg.h/.ah`, `vfabs.h/.ah`. They are never used for printing, because GNU `objdump` prints the underlying `fsgnjn.ah` etc.

**What is not defined, and why:**
- `.b` (Xf8), `vfdotp*`, `vfavg`, `fmulex`, `fmacex` (Xfaux): GAP9 has no Xf8 and no Xfaux (design 3.1). GNU `as` accepts `fmulex.s.ah`/`fmacex.s.ah`, but the task excludes them.
- `fmv.x.ah`, `fmv.ah.x`, `vfmv.*`, `vfcpkb.*`: GNU `as` rejects them. The fmv forms make no sense when the operands are already in integer registers; Zhinx has no `fmv.x.h` either. GVSoC gates `vfcpkb.h.s` on the D extension, which GAP9 does not have.
- RV64 forms (`fcvt.l.ah` ...): GAP9 is RV32.

**One decision the conductor should confirm: `vfdiv`/`vfdiv.r`/`vfsqrt` (.h and .ah) are defined, although GAP9 GNU `as` rejects them.** The task lists them. GVSoC models them, and I used GVSoC's encodings (op `00100` and `00111`, which fit the pattern of the other ops). GCC never emits them (design Q9). If the hardware lacks them, the only effect is that hand-written assembly using them would assemble. Deleting the 12 lines is enough to drop them.

**How the encodings are built.**
- Scalar `.ah` instructions reuse upstream's own F-extension classes (`FPALU_rr`, `FPUnaryOp_r`, `FPCmp_rr`, `FPUnaryOp_r_frm` at `llvm/lib/Target/RISCV/RISCVInstrInfoF.td:198,226,277,241`). The only difference from `.h` is that the funct3 field is fixed: `0b101` for ops that round, and `.h`'s funct3 with bit 2 set for the others. The operands are upstream's Zhinx operand `FPR16INX` (`RISCVInstrInfoZfh.td:42`).
- `.ah` ops have no rounding-mode operand, because funct3 already holds the format. They always round to nearest-even (measured on GVSoC, design 3.4). GNU `as` rejects `fadd.ah a0,a1,a2,rne`, and so does LLVM now. The one exception is `fcvt.h.ah`, whose funct3 is a real rounding mode (default dynamic), exactly like `fcvt.h.s`.
- Packed ops are R-type on opcode OP, with funct7 = `10` followed by the op, and funct3 = r bit followed by the format (`10` = .h, `01` = .ah).
- `vfmac`/`vfmre`/`vfcpka` read rd, so rd is a tied operand. This follows CORE-V's `cv.mac` (`CVInstMac`, `llvm/lib/Target/RISCV/RISCVInstrInfoXCV.td:72` at `llvmorg-20.1.8`), so the later codegen tasks get the right dataflow. In the `.r` forms rs2 is typed `FPR16INX` (a scalar half), so T5 can fold a splat into it.

**Keeping Snitch unchanged.** Snitch and GAP9 share mnemonics and several encodings (for example `vfadd.h` = `82c5a533` in both, but with F registers on Snitch). Upstream solves the same problem between Zfh (F registers) and Zhinx (integer registers): separate record names with an `_INX` suffix, and a separate decoder table `RVZfinx` (`RISCVInstrInfoZfh.td:55`, `RISCVDisassembler.cpp:630` at `llvmorg-20.1.8`). This change does the same:
- records are named `FADD_AH_INX`, `VFADD_H_INX`, ...;
- they live in a new decoder namespace `Xpulpfloat`;
- the disassembler tries that table only when `xpulpf16alt` or `xpulpfvec` is on. The call sits just before the PULP table, placed the way the CORE-V tables are called (`RISCVDisassembler.cpp:694`).

The Snitch definitions and their predicates are untouched. Their MC tests (`llvm/test/MC/RISCV/xsmallfloat/*`) pass unchanged. With the Snitch features on, the new GPR forms are rejected.

**No codegen change.** The file has no selection patterns. The generated `RISCVGenDAGISel.inc`, `RISCVGenGlobalISel.inc` and `RISCVGenCompressInstEmitter.inc` contain none of the 110 new records. `clang -march=rv32imc_xgap9 -O2` output for the design's `tests/numeq.c` (`_Float16` and `__bf16`) is byte-identical to int-20. The GAP9 sweep gives 54/54 identical disassemblies. Scheduling info is `Sched<[]>`, like the fork's Snitch definitions; T3/T5 should give real scheduling classes when they add patterns.

**Measured** (`logs/20-F040-verify/verify.log`; inputs are in the same directory):
- `exhaustive.s`: 431 lines covering every GVSoC Xf16alt/Xfvec op GNU `as` accepts (4 random register sets each), all aliases, and every `fcvt.h.ah` rounding mode. GNU `as -march=rv32imcxgap9` and `llvm-mc -mattr=+m,+c,+xgap` give byte-identical `.text` (1724 bytes). Disassembling the GNU object, GNU `objdump` and `llvm-objdump` agree on the encoding, mnemonic and operands of all 431 instructions.
- The design's `tests/gcc_vector.s` (GCC output) assembles to byte-identical `.text`. `tests/gcc_scalar.s` is identical except for one standard instruction: GNU `as` 2.x does not compress `mv a5,zero` to `c.li`, and LLVM does. This is unrelated to this task. Disassembly of both GCC objects agrees on every `f*`/`vf*` instruction.
- Feature gating over `exhaustive.s`. With `+xgap`, or `+zhinx,+xpulpf16alt,+xpulpfvec`: 0 errors and 0 `<unknown>`. With only `+zhinx,+xpulpv`: 431/431 rejected and 431/431 `<unknown>`. The partial feature sets reject exactly the groups they lack. With the Snitch features: 431/431 rejected.
- Encodings that do not exist are rejected: `fmv.x.ah`, `vfcpkb.h.s`, `vfdotp.h`, `fmulex.s.ah`, and an rm operand on `fadd.ah`/`fcvt.w.ah`/`vfcvt.x.h`.
- PULP integer instructions: GCC GAP9 objects of `benchmarks/builtins-spec/gcc/*.s` (57 files) disassemble the same with `+xpulpv` and with `+xgap`, except that fp16 instructions now decode instead of printing `<unknown>`.
- The regex check the task asked for: `RISCVInstrInfoXpulpfloat.td` matches the insn-tablegen pattern `RISCVInstrInfoX(pulp|...)[A-Za-z]*\.td` (`scripts/fork_anatomy.py owner` answers `insn-tablegen`).
- Lit: `llvm/test/MC/RISCV` + `llvm/test/CodeGen/RISCV` give 2581/2582. The only failure is the known `rvv/vsetvli-insert-zve64f.mir` (B41). The clang lit paths of `LIT_PATHS` give 2149/2149.

**GVSoC model bug seen on the way.** `isa_smallfloats.py` lists `vfsgnj.ah` with funct3 `101` and `vfsgnj.r.ah` with `001`. That is the reverse of every other `.ah` pair. GNU `as` encodes `vfsgnj.ah` as `9ac59533` (funct3 `001`), which matches the pattern, and LLVM follows GNU `as`. So GVSoC runs `vfsgnj.ah` as if it were `vfsgnj.r.ah`, and the other way round. Any T5/T6 GVSoC comparison that uses `vfsgnj.ah` (copysign on `v2ah`) will see this. `vfsgnjn.ah`/`vfsgnjx.ah` (neg, abs) are listed correctly. Reported in the result file.

## What breaks if this is wrong

- **Wrong encoding.** GAP9 would execute a different instruction than the one written (for example `.h` instead of `.ah` arithmetic, or the `.r` form instead of the plain one). Once T3/T5 select these instructions, GVSoC runs of `tests/numeq.c` and `vnumeq.c` would differ from GCC. Today it shows as a byte mismatch with GNU `as` on `exhaustive.s` or the GCC test files, which the comparison above rules out for every instruction except `vfdiv`/`vfsqrt` (no GNU reference).
- **Wrong gating.** If the new instructions were available without `xpulpf16alt`/`xpulpfvec`, Snitch or plain Zhinx targets would accept GAP9-only encodings. If Snitch instructions decoded under GAP9 features, `llvm-objdump` would print `fa0`-style registers for GAP9 code. The feature-gating table above covers both cases.
- **Snitch regression.** Snitch assembly or disassembly would change. The `xsmallfloat` MC tests catch this, and they pass.
- **Tied accumulator.** If `vfmac`/`vfmre`/`vfcpka` did not mark rd as read, a later codegen task could keep a value in rd across these instructions and lose it. There is no pattern yet, so nothing shows it today. T5's lit tests must cover it.
- **Missing tests.** No lit test covers these instructions yet. Proposed (in the result file): `llvm/test/MC/RISCV/xpulp/xpulpfloat-valid.s` (the 431 lines of `exhaustive.s` with `CHECK-ASM-AND-OBJ` encodings, taken from GNU `as`), `xpulpfloat-invalid.s` (the rejected forms and the feature-gating cases), and a disassembler round-trip test.

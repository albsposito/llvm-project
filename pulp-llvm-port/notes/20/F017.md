# 20/F017: GAP9 target identity (`-march=..._xgap9`) and the GAP/PULP GCC predefined macros

This is a gap the fork already had (backlog B93, macros half). It is present in `toolchains/ref-18` and in the PULP 22 branch too: `git grep '__pulp__\|__gap9__\|__riscv__'` finds nothing in `clang/lib` on `pulp/integer_SIMD_fix` or `pulp/llvmorg-22.1.7-pulp`. This change has two parts. (1) When Xpulpv is enabled, clang predefines the macros GAP/PULP GCC defines for any PULP core. (2) After an escalation, the owner decided on 2026-09-28 that GAP9 is selected by a new extension spelled like GCC's `-march=rv32imcxgap9`: clang `-march=rv32imc_xgap9`. That extension implies Xpulpv and Zfinx, and clang predefines `__gap9__` for it. The work is four commits: clang-driver macros; registration `xgap9`; clang-driver `__gap9__`; the registration unit-test list entry, owner-approved, see `notes/20/owner-test-exceptions.md` "F017 xgap9" and `notes/20/F017-regen.md`.

## What upstream changed

Nothing upstream broke this. Upstream clang has never defined these GCC-toolchain macros: at `llvmorg-20.1.8`, `clang/lib/Basic/Targets/RISCV.cpp` defines `__riscv` (line 148) and one `__riscv_<ext>` macro for each enabled extension (loop at line 179). CORE-V gets its macros from that loop, as `__riscv_xcv*`. The fork's own preprocessor-macro code is the `-mno-fdiv` handling in the same function, added by fork commit `d9510d4f257d` "[CLANG/LLVM/RISCV] Add -mno-fdiv to RISCV targets" (`git log pulp/integer_SIMD_fix -SHasNoFdiv -- clang/lib/Basic/Targets/RISCV.cpp`). The `xpulpv` extension this change keys on came from fork commit `f1b7aebff8c2` "[LLVM/PULP/SNITCH] Support for PULP and Snitch cores/platforms". No upstream commit in `llvmorg-19.1.7..llvmorg-20.1.8` touches these macros; the only macro-related commits there are `dee058f9e3ae` "[RISCV] Emit predefined macro __riscv_cmodel_large for large code model" and `d1e28e2a7bd4` (`__builtin_cpu_supports`).

## Why this is equivalent

The reference is GAP9 GCC (`riscv32-unknown-elf-gcc -dM -E`). Compared with plain `-march=rv32imc`, `-march=rv32imcxgap9 -mPE=8 -mFC=1` adds `__gap9__`, `__pulp__`, `__pulp`, `_pulp`, plus `__riscv_flen 32`, `__riscv_fdiv`, `__riscv_fsqrt` and `__FP_FAST_FMAF` (its xgap9 implies single-precision float). `-march=rv32imcxgap8` adds `__gap8__` and the same three pulp macros. `-march=rv32imcxgap10` adds `__gap10__` and the pulp macros. `-mchip=gap9` gives the same result as `-march=...xgap9`. `-mcpu=gap9` is rejected ("Use -march to pass pulp cpu info and not -mcpu"). `-mPE` and `-mFC` add no macros at all. GAP9 GCC defines `__riscv__` and `_riscv` for **every** RISC-V target, even plain `rv32imc`.

So GCC keys `__pulp__`/`__pulp`/`_pulp` on "a PULP core is targeted", and this clang already has an exact equivalent for that: the `xpulpv` extension (`-march=..._xpulpv2`, `RISCVFeatures.td` `FeaturePULPExtV2`, `let Name = "xpulpv"`). The change defines the five macros in `RISCVTargetInfo::getTargetDefines` when `ISAInfo->hasExtension("xpulpv")`. It sits next to the upstream extension-macro loop and uses the same `ISAInfo->hasExtension` test that upstream uses for `zmmul`, `a` and `c` (`RISCV.cpp:187` at `llvmorg-20.1.8`). The block is self-contained and does not reformat anything shared.

`__riscv__` and `_riscv` are limited to Xpulpv on purpose. Defining them for every RISC-V target, as GAP GCC does, would change upstream clang's behaviour for all RISC-V users: upstream defines neither (`git grep '__riscv__' llvmorg-20.1.8 -- clang/lib clang/test/Preprocessor` finds nothing), and non-PULP code that tests `__riscv__` would change meaning. The SDK headers that test `__riscv__` (autotiler NE16 HALs, `examples/gap9/libs/fastmath/utils.c`, GVSoC archi `utils.h`) use it to mean "GAP/PULP builtins are available", which is what Xpulpv means here.

Measured effects:
- Macro set with the survey's flags (`--target=riscv32-unknown-elf -march=rv32imc_zfinx_xpulpv2 -mabi=ilp32`). Before (`logs/20-F017.repro.log`): only `__riscv` and `__riscv_xpulpv`. After: also `__pulp__ __pulp _pulp __riscv__ _riscv`. Plain `-march=rv32imc` and `rv64gc` are unchanged.
- SDK compile survey (scratch work dirs, int-20 clang = integration head `7459255b6120` as the baseline):
  - strict with the shim: 209 of 617 compile, both compilers, identical error sets.
  - strict without the shim (`nodefs` run over all 617 GCC-compilable files): 209 of 617, both compilers. Every object is byte-identical, and every failing file has the same error set.
  - 132 files preprocess differently without the shim once the change is in. All 132 already fail for other reasons (mostly the missing PMSIS builtins), so the change unblocks no file today and adds no error.
  - Before xgap9, the remaining shim difference was `__gap9__` alone. Adding it changes the error set of 131 failing files and leaves all 209 successes byte-identical. It exposes the `float16`/`float16alt` type errors, and `use of unknown builtin` for fp16 builtins, that `Emulation/Gap.h` hides by taking the emulation path.
- GAP9 sweep (scratch copy, `GAP9_EXTRA_COMPILERS=base=int-20,mine=this build`): all 54 disassemblies are identical between base and mine. The sweep passes `-D__gap9__ -D__GAP9__ -D__pulp__` itself.

### The `xgap9` extension (owner decision, 2026-09-28)

GCC keys `__gap9__` on the chip named in `-march` (`xgap8`/`xgap9`/`xgap10` each give their own `__gapN__`, and all give `__pulp__`). GCC's multilib name for this target is `RV32IMFCXgap9`: `xgap9` brings single-precision float. GAP9 keeps that float in the integer registers; GCC compiles `a*b+a` to `fmadd.s a0,a0,a1,a0` and `a/b` to `fdiv.s a0,a0,a1`, so the clang equivalent is Zfinx. The new record `FeatureVendorXgap9` in `RISCVFeatures.td` is written like CORE-V's vendor extensions (`FeatureVendorXCVbi`, `RISCVFeatures.td:1225` at `llvmorg-20.1.8`, `RISCVExtension<1, 0, ...>` plus a `HasVendor...` predicate). It implies `FeaturePULPExtV2` (xpulpv) and `FeatureStdExtZfinx`. It adds no instructions; a later task will put the GAP9-only instructions behind `HasVendorXgap9`.

One spelling detail: clang's ISA-string parser reads trailing digits as the extension version (that is how the fork's `xpulpv2` is `xpulpv` version 2.0). An extension literally named `xgap9` could therefore not be written `-march=..._xgap9`. The extension is named `xgap` with version 9.0, which makes `-march=rv32imc_xgap9` parse and print as `xgap9p0` in the object's arch attribute (`rv32i2p1_m2p0_c2p0_zicsr2p0_zmmul1p0_zfinx1p0_xgap9p0_xpulpv2p0`). Consequences: `xgap8`/`xgap10` are rejected ("unsupported version number"), and a bare `xgap` means GAP9 too. `rv32imfc_xgap9` is rejected because F and Zfinx are incompatible, whereas GCC accepts it. `RISCV.cpp` defines `__gap9__` when `xgap` is enabled. GCC defines no other chip macro for xgap9: no `__GAP9__`, which the SDK's cmake passes itself.

TODO (backlog B90): GCC's xgap9 also has fp16 (float16/float16alt). `xgap9` does not imply Zhinx or the smallfloat extensions until clang supports those types. GCC also defines `__riscv_flen 32`, `__riscv_fdiv`, `__riscv_fsqrt` for xgap9. Clang with Zfinx does not (upstream behaviour for Zfinx), and the SDK outside GVSoC tests none of them.

Measured with `-march=rv32imc_xgap9`:
- `-dM -E` gives `__gap9__ __pulp__ __pulp _pulp __riscv__ _riscv`, plus `__riscv_xgap 9000000`, `__riscv_xpulpv 2000000`, `__riscv_zfinx 1000000`.
- GAP9 sweep (scratch copy, `logs/20-F017-survey/sweep2.log`): the 54 disassemblies of `rv32imc_xgap9` and `rv32imc_zfinx_xpulpv2` are identical.
- SDK survey, strict, **no macro shim**, all 617 GCC-compilable files (`logs/20-F017-survey/cmp-xgap9.txt`, `xgap9_compile_nodefsall.json`): 209/617 compile.
  - Error sets are identical to the old run with `rv32imc_zfinx_xpulpv2` plus the shim, and the disassembly and relocations of all 209 objects are identical to it. Only the arch attribute differs. So the shim is no longer needed.
  - Compared with the integration head without the shim, 131 already-failing files change error set: `__gap9__` now switches `Emulation/Gap.h` off the emulation path. They now fail loudly on the missing float16/float16alt types and f16 builtins instead of hiding that behind the emulation types.

## What breaks if this is wrong

If the macros were keyed on the wrong condition, PULP SDK code would silently switch implementations. For example, `GapBuiltins.h` and `GapSystem.h` pick the emulation versus the PULP-builtin paths on `__pulp__`, and the NE16 HALs pick `__builtin_pulp_*` bit-field helpers on `__riscv__`. The symptom would be a builtin being rejected, or portable C being compiled where GCC uses a PULP instruction. The survey (strict without the shim) and the GAP9 sweep would show it. If they leaked to non-PULP targets, upstream RISC-V preprocessor behaviour would change, and code testing `__riscv__` would change meaning. If `xgap9` implied the wrong set, `-march=rv32imc_xgap9` code would differ from `rv32imc_zfinx_xpulpv2`: PULP instructions would be missing, or float would be in F registers, breaking the ilp32 soft-float ABI GAP9 uses. The GAP9 sweep identity check shows neither happens. If `__gap9__` were missing, fp16 kernels would silently compile the emulation path (`float16` = `short`). `RiscvExtensionsHelp.CheckExtensions` guards the extension's name and version. No lit test checks these macros today (`clang/test/Preprocessor/riscv-target-features.c` has no xpulpv RUN line). A test is proposed in the result file.

# 20/F001: PULP `*RN` builtins check the rounding constant against the norm argument, not against itself

## What upstream changed

Nothing. This is a defect in fork code, not a port break. The code was introduced by fork commit `f1b7aebff8c2` "[LLVM/PULP/SNITCH] Support for PULP and Snitch cores/platforms" (Federico Ficarelli, 2022-08-25; then in `clang/lib/Sema/SemaChecking.cpp`, found with `git log -S'ArgValue(*RoundArgNum)' e6c3289804a6..pulp/integer_SIMD_fix`). It is unchanged in the LLVM 18 fork (`toolchains/ref-18`), in the step-19 port, and in the step-20 integration head `b6cd96bd3726` (`clang/lib/Sema/SemaRISCV.cpp:1450`). The owner decided on 2026-09-27 to fix it on the port so that the GAP9 SDK DSP kernels compile (survey `benchmarks/gap9-sweep-survey.md` section 4, item 1).

## Why this is equivalent

This change is a bug fix, so the behaviour is meant to change. The PULP "round and normalise" builtins (`__builtin_pulp_{add,addu,sub,subu,muls,mulu,mulhhs,mulhhu}RN(x, y, Norm, Round)` and `__builtin_pulp_{macs,macu,machhs,machhu}RN(x, y, acc, Norm, Round)`) take a shift amount `Norm` (0..31) and a rounding constant `Round`. The fork's own comment says `Round` must equal 2^(Norm-1). GAP9 GCC enforces the same rule: "expects Norm and Round cst, Norm<=31, Round==2^(Norm-1)". The SDK header `GapBuiltins.h` always passes `(n), (1<<((n)-1))`.

Before the change, the fork computed the expected rounding value from the `Round` argument itself (`ArgValue(*RoundArgNum)`) instead of from `Norm`. For `Norm=15, Round=16384` it evaluated `1u << (16384-1)`, which is an undefined shift (in practice `1<<31`), so it demanded that `Round` equal -2147483648. It then rejected every real call with "argument value 16384 is outside the valid range [-2147483648, -2147483648]". The only calls it accepted were those with `Round` equal to 1 or 2, whatever `Norm` was. After the change, the expected value is computed from `Norm` (`ArgValue(*NormArgNum)`), which is a one-token change. The `Norm` range check [0, 31] that runs first is unchanged, and so is the code generated for accepted calls. The hardware instruction encodes only `Norm`: `p.mulsRN rd, rs1, rs2, Norm` rounds implicitly with 2^(Norm-1).

Evidence (probe files are quoted in `logs/20-F001.repro.log` and `logs/20-F001.verify.log`):

| Call | GAP9 GCC | ref-18 and 20 before | 20 after |
|---|---|---|---|
| `mulsRN(a,b,15,1<<14)` (as in `gap_mulsRN(x,y,15)`) | accepted, `p.mulsRN a0,a0,a1,15` | rejected (16384 not in [-2^31,-2^31]) | accepted |
| `macsRN(a,b,c,15,1<<14)` | accepted | rejected | accepted |
| `adduRN(a,0,8,1<<7)` (as in `gap_roundnormu`) | accepted | rejected | accepted |
| `mulsRN(a,b,15,1<<13)` (wrong round) | rejected | rejected | rejected, range [16384,16384] |
| `mulsRN(a,b,32,1<<14)` (norm > 31) | rejected | rejected, [0,31] | rejected, [0,31] |
| `macsRN(a,b,c,15,1<<15)` (wrong round) | rejected | rejected | rejected |
| `mulsRN(a,b,2,1)` (wrong round) | rejected | **accepted** | rejected, range [2,2] |

SDK files: `WindowFunctions/PreProcessingFix.c` and `FastMathFunctions/MathFuncsFix.c` (through `FastFixedApprox.h`) fail with the 16384/262144 diagnostic on ref-18 and on the 20 build before the fix. After the fix, no diagnostic of that kind is left. Any remaining errors are the separate missing GAP9 builtins (for example `__builtin_pulp_mul64hu`) listed in the survey.

One difference from GCC remains, and this task leaves it alone: for `Norm=0` the fork expects `Round=1`, while GCC rejects `Norm=0` for the RN forms. The SDK macro `1<<((0)-1)` is not a valid constant anyway, so no SDK code reaches this case.

Upstream reference: CORE-V's equivalent builtins (`__builtin_riscv_cv_alu_addRN` etc., `clang/include/clang/Basic/BuiltinsRISCVXCV.td:35` at llvmorg-20.1.8) and intrinsics (`int_riscv_cv_mac_mulsRN`, `llvm/include/llvm/IR/IntrinsicsRISCVXCV.td:82`) take only the norm and no rounding argument, so upstream has no rounding check to copy. The GCC-compatible rule above is the reference.

## What breaks if this is wrong

If the check were wrong in the other direction, valid SDK calls such as `gap_mulsRN(x, y, 15)` would again fail to compile with a range error. You would see this in `PreProcessingFix.c` and `MathFuncsFix.c` in the GAP9 sweep. If it were too loose, a mismatched rounding constant would be accepted and silently ignored, because codegen uses only `Norm`.

Known consequence: both fork tests that exercise these builtins use inputs that break the rule. `clang/test/CodeGen/RISCV/riscv-xpulpv2-intrinsics.c` (lines 332, 350, 440, 467, 494, 521, 548, 584) and `clang/test/CodeGen/RISCV/riscv-xpulpv2-intrinsics-diag.c` (lines 42, 44, 54, 57, 60, 63, 66, 70) each have 8 calls with `Norm=2, Round=1`, to `machhsRN`, `machhuRN`, `mulhhsRN`, `mulhhuRN`, `mulsRN`, `muluRN`, `subRN` and `subuRN`. The `addRN/adduRN` calls (`2,2`) and the `macsRN/macuRN` calls (`1,1`) are valid. GCC rejects the `2,1` inputs, and they passed only because of this bug. With the fix both tests fail (`logs/20-F001.lit.log`). In the -diag test, the new Sema errors also stop compilation before codegen, so none of its expected "needs target feature xpulpv" errors are printed. Both tests pass on the unfixed integration head. Changing test inputs needs owner approval, so the task is escalated (see `tasks/20/F001.result.json`). No regression test exists for the valid SDK form (`Norm=15, Round=1<<14`). A proposed one is in the result file.

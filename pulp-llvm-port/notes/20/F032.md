# 20/F032: register the PULP hardware-loop fixup pass so llc can start, stop or run at it

Written for a reader who does not know LLVM. Four sections, all required (policy_check.py checks the headings).

## What upstream changed

Nothing upstream broke this. It is a **pre-existing fork defect** (backlog B102). LLVM keeps a table of named compiler passes, the "pass registry". The testing options of `llc` look passes up in that table by name: `-run-pass=<name>` runs one pass on a MIR file, `-stop-before`/`-stop-after=<name>` write the program out as MIR at that point, and `-start-before`/`-start-after=<name>` resume from MIR. Each RISC-V pass adds itself to the table in the RISC-V start-up function `LLVMInitializeRISCVTarget` (`RISCVTargetMachine.cpp`). The fork does this for its other passes (PULP hardware loops, PULP pseudo expansion, SSR, SDMA, Snitch FREP). The PULP hardware-loop fixup pass (`hwloopsfixup`, the pass that places `lp.setup` and splits loop blocks) was left out. It added itself only when the compiler created it, which happens after `llc` has already looked up the names. So all five options failed with `"hwloopsfixup" pass is not registered` (`logs/20-F032.repro.log`), and nobody could write a MIR test for a fixup-pass bug. The omission dates from fork commit `f1b7aebff8c2` "[LLVM/PULP/SNITCH] Support for PULP and Snitch cores/platforms". That commit added both the pass and the registration calls for the others (found with `git log pulp/integer_SIMD_fix -S initializePULPFixupHwLoopsPass`).

## Why this is equivalent

This change adds two lines, both in files of the passes cluster:
- `RISCV.h`: declares `initializePULPFixupHwLoopsPass`, next to `createPULPFixupHwLoops`. This is the same pattern as every other RISC-V pass in that header.
- `RISCVTargetMachine.cpp`: calls `initializePULPFixupHwLoopsPass(*PR)` in `LLVMInitializeRISCVTarget`, after `initializePULPHardwareLoopsPass`.

This is how upstream registers all its RISC-V passes. For example, `initializeRISCVExpandPseudoPass` is declared in `llvm/lib/Target/RISCV/RISCV.h` and called in `LLVMInitializeRISCVTarget` (`llvm/lib/Target/RISCV/RISCVTargetMachine.cpp:120-146` at `llvmorg-20.1.8`). The pass file (`PULPFixupHwLoops.cpp`, owned by task 20/F025) is not touched. Its own declaration and its constructor call to the same function stay. Registering a pass twice is harmless, because the registration function runs its body only once (`llvm::call_once` in `INITIALIZE_PASS`). The pass pipeline is unchanged: the pass is added by the same `addPass(createPULPFixupHwLoops())` as before, and only its name lookup changes. The other fork passes were checked. Every `INITIALIZE_PASS` in `llvm/lib/Target/RISCV` was compared with the initializer list, and `hwloopsfixup` was the only fork pass missing. The other four missing entries (`RISCVExpandAtomicPseudo`, `RISCVLandingPadSetup`, `RISCVRedundantCopyElimination`, `RISCVZacasABIFix`) are upstream passes that upstream itself does not register.

Verified (evidence under `logs/20-F032-evidence/`, log `logs/20-F032.verify.log`):
- With `-mtriple=riscv32 -mattr=+xpulpv -O2`, on the four fork hardware-loop tests (`xpulp-hwloop.ll`, `-layout`, `-countdown`, `-obj`), `-stop-before`, `-stop-after`, `-run-pass`, `-start-before` and `-start-after=hwloopsfixup` all exit 0.
- `-run-pass=hwloopsfixup` on the stop-before MIR gives the same function bodies as `-stop-after`.
- The MIR round-trips: parse and print (`-run-pass=none`) reaches a fixed point.
- `-start-before=hwloopsfixup` from MIR gives objects byte-identical to a normal compile.
- Normal `llc` output is byte-identical to the unfixed compiler on the four tests.
- GAP9 sweep (scratch copy, `base`=int-20 clang vs this clang): 54/54 objects byte-identical.
- hwloop fuzzer seeds 9101-9140 (O2/O3/Os): 120/120 assembly identical to int-20 ("same"), 0 mismatches against the host reference.
- Lit: LIT_PATHS plus `data/fork-tests.txt`, 4792/4793 pass (`logs/20-F032.lit.log`). The only failure is `rvv/vsetvli-insert-zve64f.mir`, which is already listed in data/known-failures.txt.

## What breaks if this is wrong

- If the registration were missing or pointed at the wrong pass, `llc -run-pass=hwloopsfixup` / `-stop-before=hwloopsfixup` would again fail with "pass is not registered", and any MIR test written for the fixup pass would fail at its RUN line.
- If registration changed the pipeline, the pipeline tests (`O0-pipeline.ll` and `O3-pipeline.ll`, which list "PULP Hardware Loop Fixup") would fail, and the GAP9 sweep objects would stop being byte-identical. Neither happened.
- No lit test runs `llc` with `hwloopsfixup` named on the command line. The proposed test is in the result file.

Known limitation, not fixed here: `-start-after=hwloopsfixup` produces assembly that does not assemble ("Undefined temporary symbol .LBB0_3"). The MIR format at `llvmorg-20.1.8` does not save a block's "label must be emitted" flag (`MachineBasicBlock::setLabelMustBeEmitted`). The fork sets that flag on loop-end blocks (`PULPFixupHwLoops.cpp:746,867`, `PULPHardwareLoops.cpp:1598`, `SNITCHFrepLoops.cpp:561`). When the MIR is reloaded, the flag is lost, so the label that `lp.setup` points to is never printed. `-start-before=hwloopsfixup` is not affected, because the fixup pass sets the flag again. This is reported in the result file.

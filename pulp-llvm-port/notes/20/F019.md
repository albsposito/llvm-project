# 20/F019: support GCC's `__builtin_shuffle` (and fix the ISel crash on two-vector PULP shuffles)

This is a gap the fork already had (backlog B92). `toolchains/ref-18` has it too. It is fixed at step 20 because the GAP9 SDK needs it: 1258 call sites in 28 SDK source files use the builtin.

## What upstream changed

Nothing upstream broke this. GCC has a generic builtin, `__builtin_shuffle(v, mask)` or `__builtin_shuffle(v1, v2, mask)`, that reorders the lanes of a vector: result lane i is lane `mask[i] mod N` of `v`, or lane `mask[i] mod 2N` of `v1` and `v2` placed end to end (N is the number of lanes). Clang never had it, up to `llvmorg-23.1.2`. Clang only has `__builtin_shufflevector`, which accepts only constant indices written out as separate arguments. So every SDK file that uses the builtin failed with "use of unknown builtin '__builtin_shuffle'". The fork added the PULP shuffle instructions and their `__builtin_pulp_shuffle*` builtins in fork commit `f1b7aebff8c2` [LLVM/PULP/SNITCH] Support for PULP and Snitch cores/platforms, but never added the generic builtin.

This work exposed a second defect that the fork already had. In the back end, a two-vector shuffle of 4 x 8-bit or 2 x 16-bit vectors crashed the compiler. The crash was an assertion in `RISCVDAGToDAGISel::tryPulpVectorShuffle` (`APInt ... Value is not an N-bit signed value` for bytes, "This target-independent node should have been selected" for halfwords). It is present in ref-18 and int-20 (`logs/20-F019.repro.log`). The code was written in fork commit `f1b7aebff8c2` and moved into `tryPulpVectorShuffle` by fork commit `c2f55316c07e` "Fix ISel". It had two bugs. First, it built the lane-selector constant with the vector type instead of the 32-bit integer type. Second, it dropped the bit that tells `pv.shuffle2` which of the two vectors to read (`& 1` / `& 3` instead of `& 3` / `& 7`). Plain C with a constant two-vector `__builtin_shuffle` reaches this code, so the builtin cannot work without the fix.

## Why this is equivalent

**How the SDK uses the builtin** (every call in `tools/`, `rtos/`, `libs/`): 1039 calls have a constant mask written as a compound literal (975 with two vectors, 64 with one). 219 calls take the mask from a local variable initialised with a constant (`v4s Mask = (v4s){1,2,4,0};`, 3-argument form, CNN kernels). No mask is really computed at run time. Types: `v4s`/`v4u` (4 x 8-bit) and `v2s` (2 x 16-bit), plus the fp16 `v2h`/`v2ah` in the FFT/MatMul f16 kernels.

**What GAP9 GCC emits** (`-march=rv32imcxgap9 -O2`):
- One vector, constant mask: `pv.shuffleI<k>.sci.b` or `pv.shuffle.sci.h`.
- Two vectors, constant mask: the mask reduced mod 2N and loaded from `.rodata`, then `pv.shuffle2.b/.h rD=v1, rs1=v2, rs2=mask`.
- Run-time mask: a single `pv.shuffle.b/.h` or `pv.shuffle2.b/.h`.

These instructions read only the low 2 (1) bits of each byte (halfword) mask lane, plus one more bit that chooses the vector for `shuffle2`. That is exactly GCC's modulo rule: see GVSoC `getShuffleByte`/`getShuffleHalf` and `lib_VEC_SHUFFLE2_8/16` in `gvsoc2/core/models/cpu/iss/include/isa_lib/int.h:877-965`.

**What this change does.** The builtin is a PULP target builtin with its own type checking. The fork-owned files carry the declaration and the checks: `def shuffle` in `BuiltinsRISCVXpulp.td`, its spelling is `"__builtin_" # NAME`, and `CheckPULPBuiltinShuffle` in `SemaRISCV.cpp`. It is declared the same way upstream declares its own RISC-V builtins that need custom checks, `__builtin_riscv_ntl_load/store`: `CustomTypeChecking` in `clang/include/clang/Basic/BuiltinsRISCV.td:145` at `llvmorg-20.1.8`, checked in `SemaRISCV.cpp` and lowered in `CGBuiltin.cpp`. There is no CORE-V equivalent: CORE-V has no generic permute builtin.

The type rules are GCC's:
- the one or two vector arguments have the same type;
- the mask is an integer vector with the same number of lanes, and each mask lane has the size of a vector lane;
- the result has the type of the first vector.

Clang accepts and rejects exactly what GAP9 GCC does, on the 8 error shapes and 3 valid ones in `logs/20-F019-sim/diag.c` (GCC and clang messages in `logs/20-F019-sim/diag.txt`).

In `CGBuiltin.cpp`, one static function and a two-line dispatch at the top of `EmitRISCVBuiltinExpr` lower the call:
- **The mask is a compile-time constant:** a normal `shufflevector` with each index reduced mod N (2N). The back end then picks the same `sci` or `shuffle2` instructions as GCC. This works at -O0 too.
- **The mask is not constant, the target has Xpulpv and the type is 4 x 8-bit or 2 x 16-bit:** the existing intrinsics `llvm.riscv.pulp.shuffleb/shuffleh` (one vector) or `shuffle4b/shuffle2h` (two vectors, v1 in rD). These are the same intrinsics behind `__builtin_pulp_shuffle*`. The generated code is the same single instruction as GCC. The SDK's local-variable masks take this path and become `pv.shuffle2.b` with a materialised constant, as in GCC.
- **Otherwise** (no Xpulpv, or another vector shape such as 8 x 8-bit): a generic lane-by-lane sequence. Each lane does an extract with the index reduced mod N (2N), then an insert. The reduction is done in the mask lane's own integer type (8 to 128 bits) and only then narrowed to a 32-bit index; it is skipped when the lane type cannot hold 2N (8-bit lanes with 128 lanes, 2N = 256), because every lane value is then already below 2N. The constant path reduces with `APInt::urem`, which works for any lane width, including negative 128-bit constants. This is correct for any vector, and the optimiser folds it to a `shufflevector` when the mask turns out to be constant. I chose it over an error so that the builtin behaves the same on every RISC-V configuration, as GCC's does.

In `RISCVISelDAGToDAG.cpp`, the two-vector branch of `tryPulpVectorShuffle` now does two things:
- It builds the selector as an XLen integer, the same way the fork's other `selectImm` calls do.
- It keeps the vector-select bit (index mod 4 for halfwords, mod 8 for bytes).

With v1 in `rD` and v2 in `rs1`, each `shufflevector` index is then exactly the `pv.shuffle2` selector. GCC uses the same operand order.

## What breaks if this is wrong

- **Wrong constant reduction or wrong `shuffle2` selector bits:** SDK kernels built with `__builtin_shuffle` (CNN convolutions, f16 FFT/MatMul) would silently put the wrong lanes in their outputs. The GVSoC test (`logs/20-F019-sim/run.sh`, patched simulator) shows it as a `bad=` count other than 0.
- **Swapped `shuffle2` operand order:** every two-vector shuffle would take lanes from the wrong vector. It would differ from GCC's hashes and fail the reference.
- **Sema too strict:** SDK files would fail again with "arguments to __builtin_shuffle must ...".
- **Sema too loose:** code that GCC rejects would compile.
- **Broken ISel fix:** two-vector shuffles of `v4i8`/`v2i16` would crash `llc` again.

- **Mask lanes wider than 32 bits (revision 2, after review):** the first version crashed clang ("Illegal ZExt") on valid GCC code such as `__builtin_shuffle` of a `long long` or `double` vector with a run-time mask on riscv32, and ("Too many bits for uint64_t") on a negative constant in an `__int128` mask on riscv64. `logs/20-F019-review/q.c`, `q2.c` and `logs/20-F019-sim/wide.c` (64-bit lanes, 128 x 8-bit with 2N = 256, riscv64 `__int128`, run-time and constant masks) now compile on riscv32 with and without Xpulpv and on riscv64, at -O0 and -O2 (`wide.txt`; GAP9 GCC compiles `wide.c` too). A regression here would show as a clang crash on those files.

No lit test covers any of this today. Tests are proposed in the result file (`proposed_test`):
- a clang CodeGen test for the three lowerings;
- a Sema test for the diagnostics;
- an llc test for two-vector `shufflevector` on `v4i8`/`v2i16`;
- in the CodeGen test, lanes wider than 32 bits: 2 x i64 and 2 x double run-time masks (urem in i64, then trunc), 128 x i8 two-vector (no urem), and a riscv64 `__int128` constant mask with a negative lane.

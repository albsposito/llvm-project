# 20/F003: PULP hardware-loop pass crashed on loops that count down to zero

Written for a reader who does not know LLVM. Four sections, all required (policy_check.py checks the headings).

## What upstream changed

Nothing upstream broke this: it is a pre-existing fork defect, present in the original LLVM 18 fork (`toolchains/ref-18`) and in the step-19 and step-20 ports (AGENT_RULES rule 8 applies to the fork commit instead, per the task). The defective code came in with the fork's hardware-loop pass in `f1b7aebff8c2` (Federico Ficarelli, 2022-08-25) "[LLVM/PULP/SNITCH] Support for PULP and Snitch cores/platforms", found with `git log pulp/integer_SIMD_fix -S'OldInsts.push_back(MRI->getVRegDef(R))' -- '*PULPHardwareLoops.cpp'`. That pass was copied from the Hexagon one. The Hexagon code never meets this case, because Hexagon has no zero register. RISC-V does. Since upstream `450edb0b3766` "[RISCV] Explicitly select second operand of branch condition to X0." (2022, already in the fork's LLVM 18 base: `RISCVInstrInfo.td:1592-1594` at `llvmorg-20.1.8`, "Explicitly select 0 to X0"), a comparison with the constant 0 in a branch uses the physical register `$x0` directly.

The trigger: a loop whose counter goes down and stops at zero, `do { ... } while (--n != 0)`. The loop optimizer (LSR) turns many ordinary `for (i = 0; i < n; i++)` loops into this shape, so its end-of-loop branch reads `BNE %n.next, $x0` (or `BEQ ..., $x0`). `PULPHardwareLoops::getLoopTripCount` then treats the loop bound (`$x0`) as an ordinary compiler variable and asks for the instruction that defines it (`MRI->getVRegDef`). A physical register has no such instruction, so the lookup returns null and the next line dereferences it, which is a segfault. The backtrace reports it in `convertToHardwareLoop` because `getLoopTripCount` is inlined.

Reproducers: the task's SDK DSP kernels (`FirBasicKernelsFix.c` KerFirSeq, `FirBasicKernelsf32.c`, `ComplexMathFunctions/CmplxFunctionsFix.c`), the five `benchmarks/19-vs-18` loop kernels (their ref-18/port-19 IR has `BEQ %5, $x0`), and the conductor's `benchmarks/gap9-sweep/sim/repro/hwloop_var_tripcount_crash.c` (`BEQ %6, $x0`). All are the same root cause. Reduced IR: `notes/20/F003-repro/reduced.ll` (llvm-reduce of KerFirSeq) and `notes/20/F003-repro/countdown.ll` (hand-written count-down loop). Both crash `build/int-20/bin/llc -O2 -mtriple=riscv32 -mattr=+xpulpv` and compile with the fix. `countdown.ll` becomes an `lp.setup` loop. `reduced.ll` stays a branch loop. llvm-reduce shrank it to a one-iteration loop whose two bounds are constants (1 and `$x0`), and the pass's existing constant-count path (`computeCount`, `startIsImm && endIsImm`) accepts only `EQ` comparisons, so it declines this `NE` loop. That behaviour predates this change: it is a missed optimisation, not a crash, and is listed in the result file.

## Why this is equivalent

Before: whenever the loop's start or end value was a register, the pass looked up its defining instruction without checking what kind of register it was. After: if the start or end value is a physical register, the pass asks `checkForImmediate` (which already existed and already recognised `$x0` as the constant 0) whether its value is a known constant. For `$x0` it is (0, available everywhere), so the pass continues to `computeCount`. `computeCount` already handled this case: it copies `$x0` into a fresh register in the preheader, sees the start is zero after the down-count swap, and uses the original counter `n` as the trip count. The physical register is not added to the "old instructions to delete" list, because there is no instruction to delete. For any other physical register the value at the loop entry is unknown and cannot be proven to dominate the loop, so the pass declines to form a hardware loop and the loop stays an ordinary branch loop. That bail-out is justified (rule 9): it matches `checkForImmediate`'s existing rule that non-zero physical registers are not known values, and `HexagonHardwareLoops::checkForImmediate` (`llvm/lib/Target/Hexagon/HexagonHardwareLoops.cpp:1550` at `llvmorg-20.1.8`) likewise rejects physical registers. Virtual registers take exactly the same path as before.

Results with the fix (`logs/20-F003.verify.log`):
- **SDK kernels:** `FirBasicKernelsFix.c` -O2/-Os, `FirBasicKernelsf32.c` -O2/-O3/-Os and `CmplxFunctionsFix.c` -O2/-O3/-Os now compile. All of them crash ref-18 in PULP Hardware Loops. `FirBasicKernelsFix.c -O3` now stops at a different, known bug (the `getMinRVVVectorSizeInBits` assertion, bug 3 in the survey). ref-18 hits that same assertion at -O3, so it is not part of this task.
- **Conductor reproducer and 19-vs-18 kernels:** `hwloop_var_tripcount_crash.c` crashes ref-18, port-19 and int-20, and compiles with the fix into an `lp.setup x0, a0, ...` loop whose count is `n`. The five 19-vs-18 kernels no longer crash at 20 even without the fix, because the LLVM 20 middle end produces a different loop shape. Their ref-18 IR still crashes int-20 llc and compiles with the fixed llc, with one `lp.setup` each.
- **Runtime check:** a GVSoC `ri5ky_testbench` run of `work`, `sum_loop`, `dot16` and a `do/while(--n)` countdown at n = 1, 2, 3, 7, 64, 1000 gives output identical to GAP9 GCC. Each of these four functions uses `lp.setup`. The test program is `notes/20/F003-repro/hwl.c`.
- **R001 reviewer shapes** (`notes/20/F003-repro/const-shapes.c`): the constant-count single loop `for (i = 0; i < 31; i++) { x = x*3 + (y >> 5); y ^= x; cnt++; }` and a nested constant-count loop crash ref-18, port-19 and int-20. This is the same root cause (latch `BNE %n.next, $x0`). With the fix both compile. The single loop becomes `lp.setupi x0, 31`. In the nested one, -O2 unrolls the inner 20-iteration loop completely, which leaves ten 100-iteration constant loops (at `nested2`), and the pass declines those. The decline comes from a separate limitation that predates this change: the constant-count path accepts only `EQ`, not `NE`. The result file lists it.
- **Nested loops, both levels:** in the SDK kernels the fixed compiler forms nested loops at both levels. `FirBasicKernelsFix.c` gets 9 `lp.setup x0` and 3 `lp.setup x1`, and `FirBasicKernelsf32.c` gets 13 and 3. A GVSoC run of a nested FIR (`notes/20/F003-repro/nest.c`, which becomes `lp.setup x1` plus `lp.setup x0`) with 20 (n, m) pairs, plus the 31-iteration loop, matches GAP9 GCC output exactly. The simulator builds use `-mllvm -pulp-loop-range-immediate=0` because of the separate R001 `lp.setupi` object-emission assertion.
- **Existing tests:** the fork hwloop tests (`xpulp-hwloop.ll`, `freploop.ll`, `intrinsics/xpulpv.ll`, `riscv-xpulpv2-intrinsics.c`) still pass, so the `lp.*` code they check is still produced (`logs/20-F003.lit-fork.log`).

The open verifier finding (`xpulp-hwloop.ll` with `-verify-machineinstrs`) is a different problem. The errors are reported "After PULP Hardware Loop Fixup" (`PULPFixupHwLoops.cpp`: "Using an undefined physical register", "MBB has unexpected successors"), not after this pass. The test has no `$x0` loop bound, and the error set is unchanged by this fix. It is not fixed here.

## What breaks if this is wrong

If `$x0` were handled wrongly, a count-down loop would get a wrong hardware-loop count: it would run the wrong number of times (off by one, or 0 or 2^32 iterations) with no compiler error. The GVSoC run above would show different sums from GCC, and SDK DSP kernels such as the FIR filters would compute wrong outputs. If the bail-out for other physical registers were too broad, loops would silently lose `lp.setup` and get slower. The existing `xpulp-hwloop.ll` checks would catch that for its loop shapes, but no lit test covers a count-down-to-zero loop. That is a missing test (proposed in the result file, not added, per the task).

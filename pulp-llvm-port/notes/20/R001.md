# 20/R001: give the lp.setupi end-of-loop label its own operand so it encodes with the PULP loop fixup again

Written for a reader who does not know LLVM. Four sections, all required (policy_check.py checks the headings).

## What upstream changed

`lp.setupi x0, <count>, <end-label>` starts a PULP hardware loop with a constant trip count; its last operand is a label (the loop end), stored as a 5-bit PC-relative offset. The fork declared that operand with upstream's generic `uimm5` ("unsigned 5-bit immediate"). Upstream commit `95c5386ddb8a` "[RISCV][NFCI] Rationalize Immediate Definitions (#120718)" changed every generic `uimmN` operand: it now encodes through `getImmOpValue` (previously the default `getMachineOpValue`) and its `MCOperandPredicate` accepts constants only. `getImmOpValue` picks a relocation ("fixup") from the instruction format and does not know PULP's loop instructions, so when clang writes an object file for any loop with a constant trip count it hits `Assertion 'FixupKind != RISCV::fixup_riscv_invalid && "Unhandled expression!"'` (RISCVMCCodeEmitter.cpp:555). Printing assembly (`-S`) was unaffected.

## Why this is equivalent

Before (LLVM 19): `uimm5` used the default encoder `getMachineOpValue`, where the fork's MC hunk turns a label operand of `LOOP0setupi`/`LOOP1setupi` into `fixup_pulpv2_loop_setupi` (bits 19-15, value >> 1), resolved locally by the assembler backend. Now: the label operand of `LOOP0setupi`/`LOOP1setupi` is the new fork operand `uimm5pcrel` in `RISCVInstrInfoXpulp.td`, declared exactly like the fork's existing `uimm12pcrel` (the label operand of `lp.setup`/`lp.starti`/`lp.endi`, which never broke because it is not a generic `uimmN`): no `EncoderMethod`, so it again uses `getMachineOpValue` and the fork's unchanged fixup code. Parser class (`UImmAsmOperand<5>`), decoder (`decodeUImmOperand<5>`), operand type (`OPERAND_UIMM5`, so the machine verifier still range-checks a constant) and the 5-bit ImmLeaf are the same as the old `uimm5`, so asm parsing, disassembly and ISel are unchanged. No other instruction changes operand.

This follows upstream's own design for PC-relative label operands of vendor instructions: CORE-V `cv.beqimm`/`cv.bneimm` (`llvm/lib/Target/RISCV/RISCVInstrInfoXCV.td:505-510` at `llvmorg-20.1.8`) take their label through a dedicated label operand `simm13_lsb0` (`llvm/lib/Target/RISCV/RISCVInstrInfo.td:271`, with its own encoder and `isBareSymbolRef()` predicate), not through a generic constant-only `simmN`/`uimmN`, which after `95c5386ddb8a` is reserved for constants.

Verified: the reproducer `benchmarks/gap9-sweep/sim/repro/lp_setupi_mc_crash.c` compiles (rc 0) and `llvm-objdump -dr` of the object is byte-identical to port-19 (`lp.setupi x0, 0x3e8, 0x6` = `3e83507b`, no relocations, both resolve locally). Other hardware loop forms (`lp.setup`, `lp.starti`/`lp.endi`/`lp.counti`, via `-mllvm -pulp-loop-range-immediate=0`) were also checked against port-19 (see result file). Assembling the `.s` form of `lp.setupi` with a label fails with "immediate must be an integer in the range [0, 31]" in ref-18, port-19 and port-20 alike; the asm parser never accepted a label there, so it is a pre-existing fork limitation, not a step-20 regression, and this change keeps that behaviour.

## What breaks if this is wrong

If the operand encoded wrongly, every PULP hardware loop with a constant trip count would either crash clang/llc when writing an object (the symptom this fixes) or place the loop end at the wrong address: the GVSoC/GAP9 benchmarks would loop over the wrong instructions or hang, and `llvm-objdump -d` of `lp.setupi` would show a different last operand than port-19. No lit test catches this: no fork test produces an object file for `lp.setupi` (`xpulp-hwloop.ll` only checks `-S` output of `lp.setup`, and `MC/RISCV/xpulp/xpulp-asm-parser.s` contains no `lp.*` instruction). That is the missing test, proposed in the result file.

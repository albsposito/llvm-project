# 20/F042: add GAP9's remaining half-precision builtins (f16max/min/sqrt, f16altmax/min/sqrt, the packed max2/min2 forms, v2hftov2ohf/v2ohftov2hf)

A gap the fork already had (backlog B97, builtin spec batches D and E1-E3, M2a checkpoint item 3). GAP9 GCC provides twelve half-precision builtins that the SDK's DSP and CNN kernels call, mostly through the `Maxf16`/`Minv2ah`/`Sqrtf16a`-style macros in `DSP_Libraries/FloatDefines.h` and `CNN_Defines_fp16.h`. Clang did not know them ("use of unknown builtin"). This change adds them in three commits, one per owning cluster: clang-builtins (`BuiltinsRISCVXpulp.td`), intrinsics (`IntrinsicsRISCVXpulp.td`) and codegen-core (`RISCVISelLowering.cpp`). Each file gets its own new block, placed last (after the F036/F037/F038/F041/F043 blocks). No clang code generation or Sema file is edited. `f16abs2`/`f16altabs2` are task F041 and are not included here.

## What upstream changed

Nothing upstream broke this. The fork never had these builtins: `git log pulp/integer_SIMD_fix -S'f16max'` over the builtin and intrinsic files finds nothing. They depend on fork work done at this step: the GAP9 half-precision extensions `xpulpf16alt`/`xpulpfvec`, which `xgap9` implies (fork commit `878ee13be29d` "fixup! [pulp] registration: extensions, features, processors, CSRs", task F035), and the `float16`/`float16alt` type names (`2c98caa32c1b` "fixup! [pulp] clang-driver: target macros and driver flags", task F039). Relevant upstream history in the 19.1.7..20.1.8 range: `fb9e685fc41b` "Intrinsic: introduce minimumnum and maximumnum for IR and SelectionDAG (#96649)" introduced the generic `fmaximumnum`/`fminimumnum` nodes, and `2b84fe6f16bf` "RISC-V: Add fminimumnum and fmaximumnum support (#104411)" selects them as `fmax`/`fmin`. The first version of this change used those generic nodes. Review round 1 showed that the DAG combiner folds `fmaximumnum(X, NaN constant)` to `X` (`DAGCombiner.cpp:18554`), which is not the instruction's result when `X` is itself a NaN. The lowering now uses the RISC-V target nodes `RISCVISD::FMAX`/`FMIN` instead, as upstream does for its own RISC-V-semantics min/max (`lowerFMAXIMUM_FMINIMUM`, `RISCVISelLowering.cpp:6223` at `llvmorg-20.1.8`).

## Why this is equivalent

**Prototypes** are GAP9 GCC's (spec `benchmarks/builtins-spec/spec.md` section 4): `float16 f16max(float16, float16)` becomes `_Float16(_Float16, _Float16)`, `float16alt` becomes `__bf16`, `v2h`/`v2ah` become `_Vector<2, _Float16>`/`_Vector<2, __bf16>`. Feature gates: scalar float16 needs `xpulpv,(zhinx|zfh)`, scalar float16alt needs `xpulpf16alt`, the packed forms need `xpulpfvec` plus `zhinx` and/or `xpulpf16alt`. All are on with `-march=rv32imc_xgap9`. Without them, clang reports "needs target feature ...". I compared 29 diagnostic probes with GAP9 GCC (`logs/20-F042-repro/diag/`, `gcc-summary.txt` vs `clang-summary.txt`). Clang accepts and rejects exactly the same ones. It accepts float/int/float16 arguments where float16alt is expected (converted), v2s where v2h is expected, and v2ah where v2h is expected (bit reinterpretation), as GCC does. It rejects pointers, structs, int for a vector, scalar for a vector, the wrong argument count, and use in a static initializer. `_Generic` sees the GCC result types.

**Semantics.** GCC emits one GAP9 instruction per builtin: `fmax.h`/`fmin.h`/`fsqrt.h`, `fmax.ah`/`fmin.ah`/`fsqrt.ah`, `vfmax.h`/`vfmin.h`/`.ah`, `vfcvt.ah.h`/`vfcvt.h.ah`. fmax/fmin compute IEEE 754-2019 maximumNumber/minimumNumber: a NaN operand gives the other operand, two NaNs give the canonical NaN, and -0.0 < +0.0. That is not C `fmaxf`. The conversions round once to nearest. Each builtin maps to a `ClangBuiltin` intrinsic, so clang's existing generic path emits it, the same way F016 added builtins. The backend then lowers it (`lowerPULPFP16Intrinsic`, called from `LowerINTRINSIC_WO_CHAIN`, and from `ReplaceNodeResults` for the i16 results):

- **max/min, every form**: the target nodes `RISCVISD::FMAX`/`RISCVISD::FMIN`. They select exactly `fmax`/`fmin` (`RISCVInstrInfoZfh.td:372-373`, `RISCVInstrInfoF.td:630-631`), and the DAG combiner never folds them, so the instruction always runs and always gives its own NaN result. The generic `fmaximumnum`/`fminimumnum` nodes would let the combiner fold `max(X, NaN constant)` to `X`. At -O2, a run-time NaN `X` would then come back with its payload (an sNaN even stays signalling), where GCC and the hardware return the canonical NaN (reviewer test `logs/20-F042-rev/gv/t3.c`).
- **float16** (`f16max/min/sqrt`): `fmax.h`/`fmin.h`/`fsqrt.h`, GCC's instructions with the same encodings.
- **packed v2h** (`f16max2/min2`): one `fmax.h`/`fmin.h` per lane, repacked with shifts. The packed `vfmax.h` instruction is fp16 design task T5.
- **bfloat16** (`f16alt*`, `*2` alt forms, `v2hftov2ohf`): the computation is done on f32 with integer operations, and no bfloat16 node is created. A bfloat16 value placed in the high half of an f32 *is* that f32 value, exactly. `fmax.s`/`fmin.s` return one of their inputs or the canonical NaN `0x7fc00000`, so the upper 16 bits of the result are already the bfloat16 result (canonical bfloat16 NaN `0x7fc0`, as the hardware gives). `fsqrt.s` results and f16->f32 conversions are rounded to bfloat16 with the integer round-to-nearest-even formula `(u + 0x7fff + ((u >> 16) & 1)) >> 16`. `fsqrt.s` and `fcvt.s.h` only produce the canonical NaN, and this formula maps it to `0x7fc0`. The constant-operand shapes in the reviewer's `t3.c` (NaN constants into `f16altsqrt`, `f16sqrt` and `v2hftov2ohf`) give the hardware's result as well. The rounding is also correct: sqrt computed in 24 bits and then rounded to 8 bits cannot double-round, because 24 >= 2*8+2. `v2ohftov2hf`: bfloat16->f32 is a shift, then `fcvt.h.s`. A compile-time-constant operand is folded in the lowering itself, with the canonical NaN, because the generic `fp_round` constant fold would keep a NaN's payload where `fcvt.h.s` returns `0x7e00` (review round 1 observation; GAP9 GCC -O2 ICEs on such constant conversions, `simplify-rtx.c:1927`). Native `.ah` instructions are fp16 design task T3.
- **Why integer operations and integer intrinsic types for bfloat16/packed** (coordinator heads-up from F041). LLVM 20's generic bfloat16 handling rounds back from f32 through the libcall `__truncsfbf2`. GAP9's libgcc does not have it, so programs fail to link. The first version of this change used generic bfloat16 nodes and `bfloat`/`<2 x bfloat>` intrinsic types. It hit the libcall, and a loop that carries a `v2ah` value through `f16altmax2` crashed ISel ("Cannot select v2i16 = bitcast f32"). The intrinsics therefore take the bits instead: `i16` for float16alt and `i32` for the packed pairs (clang's generic builtin path bitcasts the C types). InstCombine then turns loop-carried values into integer PHIs, so no bfloat value lives across blocks inside the builtins' data flow.

**Emitted code vs GCC** (`logs/20-F042-repro/asm/*.{O0,O2,Os}.s`, from the spec's GCC test files). float16 scalars: identical to GCC (`fmax.h a0,a0,a1; ret`). bfloat16 scalar max: `slli; slli; fmax.s; srli; ret` (+ NaN-boxing `p.bset` of the return value, which clang's ABI does for every `__bf16` return), where GCC emits one `fmax.ah`. Packed: 2 scalar ops + 3-5 shift/pack instructions where GCC emits one `vf*`. There is no call in any output at any level.

**Results on GVSoC** (final build, branch on integration head `4b76df2c70d0`; `logs/20-F042-repro/gvsoc-final.txt`). Three tests, every result compared line by line with GAP9 GCC on GVSoC:
- `logs/20-F042-repro/gvsoc/f16b.c` (mine): all 12 builtins; every pair from 36 half and 36 bfloat16 edge values (±0, ±inf, quiet and signalling NaNs of both signs, subnormals, min normal, max, rounding-boundary values); sqrt of each; packed forms with different pairs per lane; both conversions over all 65536 bit patterns of each format. 13034 lines. GAP9 GCC on GVSoC equals a host C model of the instruction semantics (`-DHOST`) on every line, so the model is the hardware semantics. Clang equals both at -O0/-O1/-O2/-O3/-Os and with the wrappers inlined at -O3.
- The reviewer's independent `t.c` (8834 lines, noinline and `-DINL` inlined, -O0..-Oz): identical to GCC at every level. In round 1 the inlined -O2/-O3 builds differed in the NaN chunks.
- The reviewer's `t3.c` (constant operands: NaN constants against run-time NaNs, constant conversions and sqrt): identical to GCC -O0 (the hardware) at -O0/-O1/-O2/-O3/-Os/-Oz. GCC -O2 cannot compile it (ICE). In round 1, `f16altmax(0x7f81 var, 0x7fc5)` gave `0x7f81` and now gives `0x7fc0`, `f16max(0x7c01 var, 0x7e05)` now gives `0x7e00`, and `v2ohftov2hf(0x7fff7f81 const)` now gives `0x7e007e00`.

So the results are bit-exact with GAP9 GCC and the hardware in every shape tested. The one known difference: when *both* operands are constants, GCC -O2 folds some cases itself (and gets lane 1 of `f16altmax2(0x7f817fc5, 0x7fc53f80)` wrong, `0x7fc57fc5`), while clang computes what the instruction computes. All builds link against GAP9 libgcc alone, with no compiler-rt, and have no undefined symbols. A second test of mine (`gvsoc/red.c`) carries values across loop iterations through the packed and scalar builtins, the shape of the SDK's pooling kernels, and matches GCC at every level. None of the tests uses the GVSoC defects B113 or B127.

Upstream reference (rule 12): the builtin records follow CORE-V's `clang/include/clang/Basic/BuiltinsRISCVXCV.td:31` (already mirrored by the fork's `PULPBuiltin`). Turning an intrinsic into a generic or target node in `LowerINTRINSIC_WO_CHAIN` follows upstream's `riscv_clmul` case, and type-legalizing an intrinsic result in `ReplaceNodeResults` with an `INTRINSIC_WO_CHAIN` Custom action for that type follows upstream's `riscv_orc_b` handling (`RISCVISelLowering.cpp:640`, `:9812`, `:13430` at `llvmorg-20.1.8`). CORE-V has no floating-point builtins, so it offers no closer reference.

## What breaks if this is wrong

- **A wrong prototype or gate** makes the SDK's fp16 kernels fail to compile again. SDK compile survey (private `run.py` copy and work dir, as in the M2a checkpoint; `logs/20-F042-survey/final-on-4b76df2/`), clang on integration head `4b76df2c70d0` without vs with this change: `-march=rv32imc_xgap9 -mPE=8` goes from **586 to 610 of 617** (98.9%), 24 new files and 0 regressions:
  - DSP: `CmplxFunctionsf16(a).c`, `PiecewiseMathf16(a).c`
  - CNN fp16: `Bias_Linear_Activation` x3, `MatAlgebra` x3, `MatMul_Conv` x3, `Pooling_BasicKernels` x3, `SoftMax` x3, `SSD_BasicKernels` x3
  - `CNN_Copy.c`, `CNN_Pooling_SQ8.c`

  Without `-mPE` (xgap9): 534 -> 542, also no regressions. The 7 files still failing are the known clang-only implicit-declaration errors (M2a queue item 5). No crash or timeout in the strict or lenient runs. `CNN_Copy.c` and `CNN_Pooling_BasicKernels_fp16/f16a.c` crashed in the round-1 survey ("Cannot select: v2i16 = bitcast f32", the fork gap that also crashed plain C union code). With F045's bitcast patterns in the integration head, they now compile.
- **Wrong NaN, signed-zero or rounding behaviour** would show up in the GVSoC table test as differing lines. For example, C `fmaxf` semantics would return either zero for `max(-0, +0)`, and truncating instead of rounding in `v2hftov2ohf` would change about half of the 65536 conversion results and the `allconv` hash.
- **A bfloat16 libcall coming back** makes GAP9 programs fail to link ("undefined symbol __truncsfbf2"). The link of the GVSoC tests against GAP9 libgcc guards against it. One general limitation remains, and T3 owns it: a `float16alt` *variable* whose value lives across basic blocks (for example the scalar result of a reduction loop, returned as `float16alt`) is still kept as f32 by LLVM 20 and rounded back through `__truncsfbf2`. That happens with or without these builtins (`logs/20-F042-repro/red1.c`).
- GAP9 sweep (scratch copy, base = int-20 clang at `4b76df2c70d0`, mine = this branch): 60 kernel objects at -O2/-O3, disassembly identical. Lit: see the result file.
- No lit test covers these builtins. `proposed_test` in the result file lists the clang CodeGen, Sema and llc tests to add.

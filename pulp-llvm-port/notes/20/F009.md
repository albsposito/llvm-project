# 20/F009: keep PULP immediate branches (p.beqimm/p.bneimm) intact when a pass reverses or rebuilds them

Pre-existing fork defect (backlog B07), fixed at step 20 on the owner's request instead of waiting for step 21.

## What upstream changed

Nothing upstream broke this; the defect is in the fork since `f1b7aebff8c2` [LLVM/PULP/SNITCH] Support for PULP and Snitch cores/platforms. That commit taught the compiler's branch analysis to read `p.beqimm`/`p.bneimm` ("branch if register equals / differs from a 5-bit constant") but reported them with the same condition code as a plain `beq`/`bne` (compare two registers). Later passes (branch folding, block placement, tail duplication, branch relaxation) that turn a branch around or re-create it pick the instruction from that condition code alone, so the constant 3 in `p.bneimm a0, 3` came back as register 3 (`gp`): `bne a0, gp`. That is what `toolchains/ref-18` does. Upstream `f4d2f7a3b798` [RISCV] Codegen support for XCVbi extension (#89719) (in 18..19) changed the rebuild so an equality branch with a constant becomes the CORE-V `cv.bneimm`, so from step 19 the same case gives a CORE-V instruction that PULP targets do not have (llc aborts "Feature_HasVendorXCVbi predicate(s) are not met", or, with XCVbi forced, GAP9 traps on the unknown encoding). Upstream fixed exactly this problem for CORE-V in `0439a4eca78f` [RISCV] Add new CondCode COND_CV_BEQIMM/COND_CV_BNEIMM for CV immediate branch (#135771), which is in 20.1.8..21.1.8.

## Why this is equivalent

Following `0439a4eca78f`, the fork's two immediate branches get condition codes of their own, `COND_P_BEQIMM` and `COND_P_BNEIMM` (`RISCVInstrInfo.h`). Branch analysis now reports them with those codes (`getCondFromBranchOpc`), the rebuild maps them back to `P_BEQIMM`/`P_BNEIMM` (`RISCVCC::getBrCond`, used by `insertBranch`), and reversing a branch swaps one for the other (`getOppositeBranchCondition`, used by `reverseBranchCondition`). The constant operand is carried unchanged, so a reversed `p.beqimm a0, 3` becomes `p.bneimm a0, 3` (same test, opposite outcome), which is exactly what reversing means. `optimizeCondBranch` only rewrites register-register `blt/bge` pairs; the new codes are excluded there just as the old `COND_EQ/COND_NE` were, which is what upstream later made explicit for CORE-V in `cca44e030ddd` [RISCV] Explicitly check for supported opcodes in optimizeCondBranch. NFC (#145622). CORE-V's own behaviour at 20 (`COND_EQ` + immediate gives `CV_BEQIMM`) is left as it is; upstream changes that itself at step 21.

Two fork passes read these condition codes to work out a loop's trip count: `PULPHardwareLoops::getComparisonKindFromCC` and `SNITCHFrepLoops::getComparisonKindFromCC`. They used to see `p.beqimm`/`p.bneimm` as `COND_EQ`/`COND_NE`; the new codes are added to the same `EQ`/`NE` cases so both passes classify these loops exactly as before (separate `passes` commit, two lines each). Nothing else in the fork or upstream RISC-V code compares a condition code with `COND_EQ`/`COND_NE` in a way the new codes could reach (checked: `RISCVRedundantCopyElimination` only matches register operands, select pseudos never carry the new codes, the verifier accepts any code below `COND_INVALID`).

Reference: CORE-V at `0439a4eca78f`: `llvm/lib/Target/RISCV/RISCVInstrInfo.h:44-45` (`COND_CV_BEQIMM/BNEIMM`), `RISCVInstrInfo.cpp:990-992` (`getCondFromBranchOpc`), `:1046-1048` (`getBrCond`), `:1073-1076` (`getOppositeBranchCondition`). GAP9 GCC (`riscv32-unknown-elf-gcc -march=rv32imcxgap9 -O2`) keeps reversed branches as `p.beqimm`/`p.bneimm` with the constant.

Verification (logs under `logs/`): `20-F009.repro.log` / `20-F009.after.log` built by `logs/20-F009-repro/run.sh`. `llc -run-pass=branch-folder rev.mir` gives `CV_BNEIMM $x10, 3` (int-20), `BNE $x10, 3` (ref-18), `P_BNEIMM $x10, 3` (this change); `llc -run-pass=branch-relaxation relax.mir` (a `p.beqimm` whose target is 5000 bytes away, so it is inverted around a `j`) gives `CV_BNEIMM`/`BNE`/`P_BNEIMM` likewise. Both functions linked with `drv.c` and run on GVSoC `ri5ky_testbench` over x in [-16,16): ref-18 `bad=2` (wrong results), int-20 does not compile (with `+xcvbi` forced: trap, invalid access), this change `checks=64 bad=0`. Lit (`LIT_PATHS`, 4721 tests): all pass except the known failure `rvv/vsetvli-insert-zve64f.mir` (20/T002). Random-loop fuzzer and GAP9 sweep: see the result file.

Note that clang never produces `p.beqimm` from C at step 20 (nor at ref-18): the fork's selection patterns (`RISCVInstrInfoXpulp.td:1312-1315`) match `brcond (seteq ...)`, which RISC-V lowers to `riscv_brcc` before selection, so they never fire. The defect is therefore latent for C input today (reachable from MIR, or as soon as those patterns are fixed); it is listed separately in the result file.

## What breaks if this is wrong

If a reversed or rebuilt PULP immediate branch still came out wrong, a program would branch on the wrong register (silent wrong result, ref-18 behaviour) or the compiler would abort emitting a CORE-V `cv.beqimm`/`cv.bneimm` (int-20 behaviour). The reproducer above shows either immediately; no lit test covers it today (proposed test in the result file). If the hardware-loop/FREP hunks were wrong, loops whose exit test is a `p.bneimm` would stop becoming `lp.setup`/`frep` loops (visible as missing `lp.` instructions in the fork hardware-loop lit tests and the GAP9 sweep). At step 21 upstream `c8243251cb25` removes immediate condition codes altogether (`Cond[0]` becomes the branch opcode); the step-21 worker must then move the `P_BEQIMM`/`P_BNEIMM` pair into the opcode switch in `reverseBranchCondition` and drop `COND_P_*` (see `steps/21/leads.md` row "Branch condition-code refactor"; at step 23 into `RISCVCC::getInverseBranchOpcode`, `steps/23/leads.md`).

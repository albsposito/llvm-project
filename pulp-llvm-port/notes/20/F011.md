# 20/F011: PULP clip and bit-extract builtins reject the arguments GAP9 GCC rejects

## What upstream changed

Nothing. This is a defect in fork code, not a port break (backlog B12, owner-approved 2026-09-27, `notes/20/owner-test-exceptions.md#b12`). The checks were introduced by fork commit `f1b7aebff8c2` "[LLVM/PULP/SNITCH] Support for PULP and Snitch cores/platforms" (Federico Ficarelli, 2022-08-25). It was found with `git log -S'NegPow2ArgNum'` and `git log -S'err_riscv_pulp_builtin_bextract_range'` over `e6c3289804a6..pulp/integer_SIMD_fix -- clang/lib/Sema clang/include`, both of which return only that commit. The checks are the same in the LLVM 18 fork (`toolchains/ref-18`), and at the step-20 integration head `abe1ba6bf62d` they are in `clang/lib/Sema/SemaRISCV.cpp:1416-1428`. Task 20/F002 found the hole while it fixed the immediates these builtins encode (`tasks/20/F002.result.json`, `tasks/20/F002.review.json`).

## Why this is equivalent

This is a bug fix, so behaviour changes on purpose, but only for calls that GAP9 GCC rejects. Accepted calls generate exactly the same code.

The PULP instruction `p.clip rd, rs1, N` clamps a value to [-2^(N-1), 2^(N-1)-1], and `p.clipu rd, rs1, N` clamps it to [0, 2^(N-1)-1]. N is a 5-bit field. The builtins `__builtin_pulp_clip(x, Min, Max)` and `__builtin_pulp_clipu(x, Min, Max)` take both bounds, but the instruction can only hold N, and the backend takes N from Max. Before this change the fork checked each bound on its own: Min had to be a negative power of two and Max a power of two minus one. So:

- `clip(x, -4, 15)` was accepted and clamped to [-16, 15], which silently ignored Min. Two fork tests used exactly this call.
- `clip(x, INT_MIN, INT_MAX)` and `clipu(x, 0, INT_MAX)` produced N = 32. That does not fit the 5-bit field and silently encoded 0 in a release build (`-verify-machineinstrs` reports "Invalid immediate").
- `clip`/`clipu` with Max = 2^30-1 (N = 31) was accepted. GCC rejects it.

`__builtin_pulp_bextract[u](x, Size, Offset)` accepted Size = 0. After 20/F002 that call died in the backend with "Cannot select", and before 20/F002 it silently extracted 1 bit.

Now, `clang/lib/Sema/SemaRISCV.cpp` (the new `CheckPulpClipBounds` lambda, called from the `BI__builtin_pulp_clip` and `BI__builtin_pulp_clipu` cases) requires Min = -(Max+1) for clip, or Min = 0 for clipu, with Max = 2^(N-1)-1 and 1 <= N <= 30. Anything else gets the new error `err_riscv_pulp_builtin_clip_bounds` ("bounds must be -2^(N-1) and 2^(N-1)-1 with 1 <= N <= 30 (got -4 and 15)"; for clipu the message says "0" instead of "-2^(N-1)"). The bextract Size range is now [1, 32] instead of [0, 32]. The existing Offset range [0, 32] and the existing Size+Offset <= 32 check are unchanged, and together with Size >= 1 they give exactly GCC's rule. The existing per-bound checks (negative power of two, power of two minus one, clipu Min in [0, 0]) are kept unchanged. The new check only adds a condition.

The reference is GAP9 GCC (`/home/ubuntu/gap_riscv_toolchain_ubuntu/bin/riscv32-unknown-elf-gcc -march=rv32imcxgap9`). Its diagnostics are "Builtin __builtin_pulp_clip (X, Min, Max) expects Min and Max cst, Min=-2^(N-1), Max=2^(N-1)-1", the same with "Min=0" for clipu, and "Builtin __builtin_pulp_bextract(X, Size, Offset) Expects Size and Offset immediate constants, Size>0, Offset>=0, (Size+Offset)<=32". GCC accepts N up to 30 (Max = 536870911, `p.clip a0,a0,30`) and rejects Max = 1073741823. That is why the cap is 2^29-1 and not the 2^30-1 written in the task: the task asked for GCC's exact rule, which is the stricter one.

Upstream has no equivalent check to follow. CORE-V's `__builtin_riscv_cv_alu_clip(x, bound)` takes a single bound (`clang/include/clang/Basic/BuiltinsRISCVXCV.td:31` at `llvmorg-20.1.8`) and has no Sema immediate check. Its ISel uses the immediate form when the bound is 2^k-1 and falls back to the register form otherwise (`llvm/lib/Target/RISCV/RISCVInstrInfoXCV.td:723,771`). The fork's three-argument builtin mirrors GCC's, so GCC's rule is the reference. The check is written in the file's existing style (`BuiltinConstantArg`, `Diag(TheCall->getBeginLoc(), ...)` with a source range, as the neighbouring `err_riscv_pulp_builtin_negpow2` check does).

## What breaks if this is wrong

If the check were too strict, valid SDK code such as `gap_clip(x, 7)`, which is `__builtin_pulp_clip(x, -128, 127)`, or `gap_bitextractu(x, 1, 31)` would stop compiling with "bounds must be ..." or "outside the valid range [1, 32]". The GAP9 sweep, the SDK kernels above and `clang/test/CodeGen/RISCV/riscv-xpulpv2-intrinsics.c` would show it. If it were too loose, a mismatched or oversized clip bound would again compile silently to a clamp with the wrong range, which GVSoC would show as wrong results (`sim/tests/clip.c`).

Two fork tests called `__builtin_pulp_clip(-10, -4, 15)`, which is now rejected. Under the owner exception they were changed to `(-10, -16, 15)` in a separate commit (`fixup! [pulp] tests: ...`, report `notes/20/F011-regen.md`). Max stays 15, so the generated `p.clip a0, a0, 5` is unchanged. No existing test checks that invalid bounds are rejected. A negative regression test is proposed in the result file (`proposed_test`).

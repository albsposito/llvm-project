# 20/F010: let hand-written assembly use labels in PULP hardware-loop instructions

Written for a reader who does not know LLVM. Four sections, all required (policy_check.py checks the headings).

## What upstream changed

Nothing upstream broke this. It is a **pre-existing fork defect**, present in every PULP toolchain (ref-18, port-19, port-20, int-20; backlog B11). A PULP hardware loop starts with `lp.setup`, `lp.setupi`, `lp.starti`, `lp.endi` or `lp.counti`. All but `lp.counti` name a label: the loop start or end, stored in the instruction as a forward distance in halfwords (12 bits wide, 5 bits for the end label of `lp.setupi`). The compiler path (clang or llc writing an object file directly) has always handled these labels. The **assembler** (`llvm-mc`, or `clang -c file.s`) never did:

- `lp.setupi x0, 100, .Lend` was rejected with "immediate must be an integer in the range [0, 31]".
- `lp.setup`, `lp.starti` and `lp.endi` with a label crashed with "UNREACHABLE: Unknown match type detected!".

As a result the `.s` that clang itself writes (`clang -S`) could not be assembled back whenever it contained a hardware loop.

The code comes from fork commit `f1b7aebff8c2` "[LLVM/PULP/SNITCH] Support for PULP and Snitch cores/platforms" (2022-08-25, found with `git log pulp/integer_SIMD_fix -S uimm12pcrel`). That commit declared the label operand `uimm12pcrel` with the generic parser class `UImmAsmOperand<12>`, which accepts only numbers, and it added no parser error message for that class. The unhandled error is what crashes. Step-20 task R001 copied the same pattern into `uimm5pcrel`, the `lp.setupi` end label, to fix a compiler crash, so that operand was number-only too.

## Why this is equivalent

The compiler path is unchanged. For valid input the assembler now emits exactly the bytes that the compiler path and GAP9 GCC's assembler emit. Three files change, in two clusters.

1. `RISCVInstrInfoXpulp.td` (insn-tablegen): the label operands `uimm12pcrel` and `uimm5pcrel` get a new parser class, `UImmAsmOperand<12/5, "PCRel">`. This follows upstream CORE-V `cv.beqimm`: its branch target `simm13_lsb0` (`RISCVInstrInfo.td:271` at `llvmorg-20.1.8`, used at `RISCVInstrInfoXCV.td:506`) has the parser class `SImmAsmOperand<13, "Lsb0">`, which accepts either a bare symbol or a constant. Encoder, decoder, printer, operand type and ImmLeaf do not change, so the object bytes from clang and llc stay the same.
   The loop **count** operand of `lp.setupi` and `lp.counti` was also declared `uimm12pcrel`, although it is a plain number. It becomes the fork's `uimm12` (`RISCVInstrInfo.td:270`, the same 12-bit field and decoder). Otherwise the new parser class would accept `lp.counti x0, .L` and encode a distance as the trip count. For a constant the encoder `getImmOpValue` returns the value unchanged, exactly as the old default encoder did. Clang and llc only ever put constants in this operand.
2. `RISCVAsmParser.cpp` (mc): two predicates, `isUImm5PCRel` and `isUImm12PCRel`, accept "a bare symbol with no `%lo`-style modifier, or a constant that fits the field". Their shape copies upstream's `isBareSimmNLsb0` (`RISCVAsmParser.cpp:523` at `llvmorg-20.1.8`). The change also adds error messages for `InvalidUImm5PCRel`, `InvalidUImm12PCRel` and `InvalidUImm12`, modelled on upstream's `Match_InvalidSImm13Lsb0` (`RISCVAsmParser.cpp:1631`). The missing `InvalidUImm12` message is what caused the crash. It also crashed out-of-range numbers in the fork's Xssr `scfgri`, which now get a normal error. A constant keeps its old meaning, the raw field value, so `.s` files that use numbers assemble to the same bytes as before.
3. `RISCVAsmBackend.cpp` (mc): the two PULP loop fixups now check the range and the 2-byte alignment before they encode, the same checks upstream does for `fixup_riscv_branch` (`RISCVAsmBackend.cpp:461-465` at `llvmorg-20.1.8`). This check is required. `applyFixup` does not mask the value, so a hand-written label that is too far away, or behind the instruction, silently corrupted the neighbouring fields. Measured: `lp.setupi x0, 100, .Lfar` with `.Lfar` 104 bytes ahead assembled to `lp.setupi x0, 0x65, 0x14`, so the trip count 100 became 101. GNU as rejects the same input ("BFD_RELOC_RISCV_RELU5 Overflow"). The limits accepted now match GNU as exactly: a 62-byte `lp.setupi` distance and an 8190-byte `lp.setup` distance assemble byte-identically to GNU as, and 64 and 8192 are rejected by both. The returned value (`Value >> 1`) is unchanged, so every in-range encoding is the same. The compiler path only produces in-range forward distances. The GAP9 sweep and the fuzzer (below) produce identical objects, and none of them hits the new error.

Verified:
- Hand-written `.s` using every form on both loop levels (`lp.starti`/`lp.endi`/`lp.counti`/`lp.setup`/`lp.setupi`, x0 and x1, plus a parenthesised label): `llvm-mc -filetype=obj` gives `.text` bytes identical to GAP9 `riscv32-unknown-elf-as -march=rv32imcxgap9`.
- C loops, run with the default settings and with `-mllvm -pulp-loop-range-immediate=0` (together they cover all five forms on both levels): the object from `clang -c` equals `clang -S` followed by assembling that `.s` with `clang -c`, and also equals GNU as on the same `.s` (with `.option norelax`). All of these objects are byte-identical to build/int-20.
- GVSoC: a hand-written nested-loop kernel using all five forms returns `100237` (the expected value) both when assembled by llvm-mc and linked with ld.lld, and when assembled by GNU as and linked with GNU ld.
- Numeric operands assemble byte-identically to int-20.
- GAP9 sweep: all 32 kernels × O2/O3 give byte-identical objects to int-20.
- Hardware-loop fuzzer: seeds 1-60, O2/O3/Os, with and without `-pulp-loop-range-immediate=0` (360 builds, 1154 `lp.*` instructions). All objects are identical to int-20, and assembling clang's `.s` gives the same object as `clang -c` in all 360.
- Lit: see the result file.

## What breaks if this is wrong

- **Wrong label encoding:** hand-written or `clang -S` assembly with hardware loops would assemble to loops over the wrong instructions, and GVSoC programs would give wrong results or hang. Comparing `llvm-objdump -d` against the GNU as object would show a different offset field.
- **Changed count operand:** compiled code would get a different trip count. The GAP9 sweep and fuzzer objects would stop being byte-identical to int-20.
- **Backend check misfiring:** clang would fail with "fixup value out of range" on a valid loop.

No lit test covers any of this: no test assembles `lp.*` with labels, and none checks `lp.*` encodings in an object. The proposed test is in the result file.

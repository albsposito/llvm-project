# 20/F037: add GAP9 builtins batch C: the 12 `mulf*`/`macf*` aliases, `mul64hs/hu/hus`, `trunch`, `truncb`

Pre-existing fork gap (backlog B97, builtins spec batch C, queue item 8), present in `toolchains/ref-18` too (`use of unknown builtin`); filled at step 20 on the owner's request.

## What upstream changed

Nothing upstream broke this. GAP9 GCC has 17 builtins the fork never defined, and the GAP9 SDK calls two of them in files that need nothing else: `libs/gap_lib/jpeg/dct.c` (11 `__builtin_pulp_mulfsN`, 16 `__builtin_pulp_trunch`) and `tools/autotiler_v3/BasicKernels/DSP_Libraries/FastMathFunctions/MathFuncsFix.c` (`__builtin_pulp_mul64hu` via `gap_mul64uh`, `FastFixedApprox.h:271-274`). The other 15 are reached through the SDK's `gap_*` wrappers in `tools/autotiler_v3/Emulation/GapBuiltins.h:71-119`. The sibling builtins they alias (`muls`, `mulsN`, ..., `macuRN`), their intrinsics, patterns and Sema range checks were added by fork commit `f1b7aebff8c2` [LLVM/PULP/SNITCH] Support for PULP and Snitch cores/platforms; the intrinsics were moved to their own file by `97efefdcc54e` Move our own intrinsics to dedicated td files (`git log pulp/integer_SIMD_fix -S'mul_mac_N_RN'`, `-S'BI__builtin_pulp_mulsRN'`).

## Why this is equivalent

Each builtin is added the way the fork adds its siblings, in one new block per file (nothing reordered), one commit per owning cluster:

1. **clang-builtins** (`BuiltinsRISCVXpulp.td`, new block at the end; `SemaRISCV.cpp`, new case labels in the existing N/RN groups). Prototypes are GAP9 GCC's (read from its diagnostics, `benchmarks/builtins-spec/spec.json`): every argument and result `int`, except `trunch` returns `short` and `truncb` returns `char` (plain char is unsigned on RISC-V, as in GCC). The N and R arguments are `unsigned _Constant int`, as for the existing `mulsN`/`mulsRN`/`macsN`/`macsRN`, and the new `mulfsN/mulfuN` (N at argument 2), `mulfsRN/mulfuRN` (R at 3), `macfsN/macfuN` (N at 3), `macfsRN/macfuRN` (R at 4) join the same Sema lists, so they get the same checks: N must be a constant 0..31, R must equal 2^(N-1). Features: `xpulpv`; `mul64h*` also `m` (their instructions are the M extension's; GAP9 has M).
2. **intrinsics** (`IntrinsicsRISCVXpulp.td`, new block): one `ClangBuiltin`-tied intrinsic per builtin, built with the file's existing multiclasses (`PulpBinary32`, `PulpTernary32`, and `mul_mac_N_RN` for `fs`/`fu`, which also gives `mulfuRN`; GAP9 GCC has that builtin too). `trunch`/`truncb` return `i16`/`i8`, because clang's generic builtin path (`CGBuiltin.cpp`, `getIntrinsicForClangBuiltin`) only bitcasts the result, so the intrinsic type must be the C return type. All are `IntrNoMem` (pure), like their siblings.
3. **insn-tablegen** (`RISCVInstrInfoXpulp.td`, after the sibling patterns): `mulfs`→`p.muls`, `mulfu`→`p.mulu`, `macfs`/`macfu`→`p.macs`/`p.macu rd(acc), rs1, rs2` (the siblings' patterns copied), `defm : int_mul_mac_N_RN<"fs","S">` / `<"fu","U">` (`p.mulsN` ... `p.macuRN`, the sibling multiclass). `mul64hs`→`mulh`, `mul64hu`→`mulhu`, `mul64hus(x, y)`→`mulhsu y, x`: x is the unsigned and y the signed operand, and `mulhsu` takes the signed one in rs1 (GCC emits `p.mulhsu a0,a1,a0` for `mul64hus(a0,a1)`; GCC's `p.mulh*` spellings have the standard M encodings, e.g. `02b51533` = `mulh`).
4. **codegen-core** (`RISCVISelLowering.cpp`, 2 hunks): with Xpulpv, an `i8`/`i16` intrinsic result is custom-legalized, and `ReplaceNodeResults` turns `trunch`/`truncb` into a plain truncate of the operand. The truncated value then goes wherever C puts it: sign-extended to `int` it selects `p.exths` (the existing `sext_inreg` pattern), zero-extended `andi 0xff`, stored `sh`/`sb`, exactly as GCC.

Semantics (verified, below): `mulf*`/`macf*` are the same instruction as `mul*`/`mac*`, so the same result by construction; `mul64h*` return the high word of the 64-bit signed x signed / unsigned x unsigned / unsigned x signed product; `trunch`/`truncb` are `(short)x`/`(char)x`.

Differences from GAP9 GCC (GCC defects, backlog B98; clang does what the spec asks):
- `macfs`/`macfu`: GCC prints a 4-operand `p.macs a0,a0,a1,a2` that GAP9 gas rejects ("illegal operands"), so any use fails to build with GCC. Clang emits what `macs`/`macu` emit (`p.macs rd, rs1, rs2`, accumulator in rd).
- `mulfsN(a,b,32)` / `mulfsN(a,b,-1)`: GCC internal compiler error (`extract_insn, recog.c:2311`); clang: "argument value 32 (resp. 4294967295) is outside the valid range [0, 31]", the existing `mulsN` check.
- New finding: `macfsRN(a,b,c,0,1)` is also a GCC ICE (same place). `mulfsRN` with a wrong R (`(5,3)`) or N=0 is accepted by GCC, which ignores R; GCC's own `mulsRN` rejects both ("expects ... Round==2^(Norm-1)"). Clang applies the existing `mulsRN` check to both spellings (R must be 2^(N-1); N=0 needs R=1, as for the existing `mulsRN` in clang).
- Non-constant N/R: an error in both ("argument to '...' must be a constant integer" vs GCC's "invalid argument to built-in function"); same for `mulsN` today (B93 is the separate "accept what GCC accepts after inlining" question).
- GCC constant-folds `mul64h*` and `trunch/truncb` of constants; clang folds the truncations (plain truncate in the DAG) but emits `mulh*` for constant `mul64h*` operands (same result, one instruction). `mul64hu` with a `long long` argument truncates it like GCC; a pointer argument is a `-Wint-conversion` error in C99+ in clang, a warning in GCC 7 (SDK flag parity is item 5 of the queue).

Upstream reference: CORE-V's equivalent builtins (`clang/include/clang/Basic/BuiltinsRISCVXCV.td:26` `alu_exths`, `:29` `alu_extbz` at `llvmorg-20.1.8`) are lowered to generic IR in `clang/lib/CodeGen/CGBuiltin.cpp:23438-23441` (sext/zext of a trunc); the task asked for no clang CodeGen edits unless a builtin needs custom handling (`CGBuiltin.cpp` is fork-touched and mapped to the clang-builtins cluster, so that route was allowed in principle, but the concurrent tasks 20/F019 and F041 were editing it), so these builtins use the fork's usual ClangBuiltin intrinsic route and the truncate happens during type legalization instead; the emitted instructions are the same as the CORE-V sext/zext-of-trunc route would give. The builtin records follow `BuiltinsRISCVXCV.td` (`RISCXCVBuiltin<"int(int, int)", "xcvalu">`), already mirrored by the fork's `PULPBuiltin` class.

## What breaks if this is wrong

- A wrong prototype or missing builtin makes `dct.c` and `MathFuncsFix.c` fail to compile again (SDK compile survey), or silently changes C types (`trunch` must be `short`, sign-extended when used as int; `truncb` unsigned `char`).
- A wrong operand order in `mul64hus` or `macf*` gives wrong numbers in fixed-point DSP code (JPEG DCT, fast math): the GVSoC test `logs/20-F037-repro/sem/sem.c` would show a hash mismatch for that builtin.
- A wrong truncation (e.g. zero- instead of sign-extending `trunch`) corrupts DCT coefficients stored as `short` or compared as int; the same test checks the value used as int, stored, and compared.
- Checks run on the branch rebased onto integration head `e7f97bbd0f05` (lit, policy check, per-commit builds and the assembly comparison repeated after the final rebase onto `7ddac1d3b507`; details in the result file): the spec's 16 GCC test files give the same instruction and encoding as GAP9 GCC in every function (`logs/20-F037-repro/cmp/`), apart from register choice, the `macf*` fix above, `truncb` selecting the equivalent `p.extbz` where GCC writes `andi 0xff`, and constant `mul64h*` not folded; diagnostics match the spec's expectations for all 16 probes (`logs/20-F037-repro/diag/summary.txt`); GVSoC: all 17 builtins over 484 edge-value triples + 1500 random triples, N in {0,1,5,11,15,16,30,31}, result hashes equal to a host `gcc -O0` reference at clang -O0/-O2/-Os/-O3, and GAP9 GCC -O0/-O2 gives the same hashes for the builtins it can compile (`logs/20-F037-repro/sem/`, `logs/20-F037.gvsoc.log`); SDK compile survey (checkpoint M2a mode P, -mPE=8): 576 -> 578 of 617, newly compiling `libs/gap_lib/jpeg/dct.c` and `MathFuncsFix.c`, no regression, no crash (`logs/20-F037.survey.log`); GAP9 sweep: 60 objects identical to the integration-head clang except the `.comment` version string; lit: only the known failure.
- No lit test covers these builtins today; `proposed_test` in the result file lists clang CodeGen, Sema and llc tests.

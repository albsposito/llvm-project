# 20/F007: PULP hardware loops now run exactly the source's iteration count

Written for a reader who does not know LLVM. Four sections, all required (policy_check.py checks the headings).

## What upstream changed

Nothing upstream broke this. It is a pre-existing fork defect (backlog B01 and B02, found by the 20/F003 reviewer). It is present in the original LLVM 18 fork (`toolchains/ref-18`) and in every port since. The defective code came in with the fork's hardware-loop pass in `f1b7aebff8c2` (Federico Ficarelli, 2022-08-25) "[LLVM/PULP/SNITCH] Support for PULP and Snitch cores/platforms". It was found with `git -C /home/ubuntu/llvm-project log pulp/integer_SIMD_fix -S'loopCountMayWrapOrUnderFlow(Start, End' -- llvm/lib/Target/RISCV` (the same commit also added the `AdjV` FIXME). The pass is a copy of `HexagonHardwareLoops.cpp`. When the fork copied it, it left out three parts of Hexagon's trip-count logic:

1. **The branch direction (`Negated`).** Hexagon negates the comparison when the loop's end branch jumps to the exit instead of back to the loop. The fork dropped this, so a latch that continues while `i.next == m` was counted as if it continued while `!=`.
2. **The adjustment for comparisons that include equality (`AdjV`).** The fork kept only a FIXME. Because of that, `i >= m` loops ran n-m times instead of n-m+1, and `(i -= 2) >= 0` ran one iteration short.
3. **The check for a zero or negative distance.** `loopCountMayWrapOrUnderFlow` was commented out, and the fork never had a runtime check. A do/while body always runs once. When the first comparison already fails (`do {} while (--i >= 0)` with i = -5, or `++i < m` with i > m), the computed count was negative. The hardware reads a negative count as a huge unsigned number, so the loop hung.

Upstream Hexagon has since made its own version of point 3 stronger. `89adc2d4f93b` "[HEXAGON] Fix corner cases for hwloops pass (#135439)" (a cherry-pick of `da8ce56c53fe`, in `llvmorg-19.1.7..llvmorg-20.1.8`, fixing issue #133241) adds a runtime check that the distance has the right sign (`DistCheck` + `MUX`). It also swaps `CmpLess`/`CmpGreater` when the counter goes down. This change ports that fix too.

## Why this is equivalent

The only file changed is `llvm/lib/Target/RISCV/PULP/PULPHardwareLoops.cpp` (passes cluster). Each change follows `llvm/lib/Target/Hexagon/HexagonHardwareLoops.cpp` at `llvmorg-20.1.8`:

- **Branch direction.** `getLoopTripCount` negates the comparison when the taken branch target is not the loop header (Hexagon line 649 and lines 695-696). RISC-V branches have no negated-predicate form, so only the direction counts. The comparison kind for unsigned `>=` (`BGEU`/`COND_GEU`) is now unsigned; it used to be treated as signed. The `COND_P_BEQIMM`/`COND_P_BNEIMM` labels that 20/F009 added are kept.
- **Loops that continue while `==`.** These run once or twice. They are not counting loops, so they are declined, as Hexagon does (line 740). This covers the reviewer's `eqm` (`BEQ` back to the header), which used to get count n-m.
- **Both bounds constant.** This path now uses Hexagon's code (lines 786-826). It handles `!=`, `<`, `<=`, `>`, `>=` with the equality +1 and ceiling division by the step. It compares with the signedness of the comparison. It declines a `!=` loop whose step does not divide the distance or points the wrong way. Before, only one form was accepted (`EQ`, i.e. a `!=` loop written with the branch to the exit), and it had no direction check.
- **At least one bound in a register.** For `!=` the count is unchanged: (End - Start) >> log2(step), with the same instructions as before. For the ordered comparisons the count is Hexagon's `(End - Start + step - 1 [+1 for <=]) / step` (lines 868-894). It is emitted as `((Dist - 1) >> s) + 1`, or `(Dist >> s) + 1` for `<=`. This is the same value, and it only overflows for a count of 2^32.
- **Runtime guard (the port of `89adc2d4f93b`'s DistCheck/MUX).** If the loop's first comparison can fail, the count must be 1, not a negative number. RISC-V has no mux, so the pass emits `Valid = (first compared value) < End` (or `<=`) with `SLT`/`SLTU`, then `count = ((Q & -Valid) + 1)`. This is 4-6 extra instructions in the preheader, run once per loop entry. It checks the first compared value (`Start + step`, or `End - step` for a count-down loop), not only the sign of End - Start. That way a first step that wraps around (unsigned 0xffffffff counting up, or 0 counting down) is also counted exactly. The guard is left out when a dominating branch already proves the distance is in range. This is the usual guard in front of a rotated `for` loop. It is found by walking the dominator tree for a branch edge that dominates the preheader and compares the same two values. A `Start != End` check also counts as proof when Start is `End & mask`, the remainder loop after an unrolled one.
- **`loopCountMayWrapOrUnderFlow` is back on (ported).** It is called for `!=` loops. That is the only kind where the count can still be 0 after the guard: Start == End means the source loop goes all the way around the 32-bit range, and a PULP hardware loop with count 0 runs its body once. The port makes three changes. On RISC-V the end value is `$x0` or a register loaded with a constant, not an immediate operand, so constants are recognised through `checkForImmediate`. RISC-V has no `analyzeCompare`, so the range check is the conditional branch itself, and the TODO'd negation is restored. A dominating branch that proves Start != End is accepted first.
- The fork's old placement of the `$x0` copy at the top of `computeCount` is kept as it was. Every loop whose count does not change therefore gets exactly the same machine code as before.

Evidence (all logs under `logs/20-F007/`, `logs/20-F007-sweep/`, `logs/20-F007-fuzz/`):
- **Trip-count oracle on GVSoC** (`logs/20-F007/oracle.py`, `orun.sh`; results in `res/`). It covers 1330 functions: the reviewer's 18 C do/while shapes plus 7 more with steps of 2 and 4, each for `int` and `unsigned`, and 1280 hand-written IR loops covering every `icmp` predicate, continue/exit orientation, steps of +-1/+-2/+4, and end values `%m`, 0 (`$x0`: BNE/BEQ/BGE/BLT with `$x0`), 3 and -1, with and without an entry guard. Each runs for n = -5..100 and m in {-3,0,1,7,50,100}. Expected counts are computed on the host with C/IR semantics. That means host C semantics, not GAP9 GCC, because GCC 7.1.1 miscompiles `do{c++;}while(--i>0)`. Baseline: 239 BAD + 108 HANG out of 1330 at O2, both at integration head `e2bc52b3dbd5` (O3 and Os the same) and at `b0f18c5a6b88` (`logs/20-F007.repro.log`). With the fix: 1330/1330 OK at O2, O3 and Os.
- **Reviewer shapes:** `ge0` (`BGE iv.next, $x0`) now gets count n+1, `gem` gets n-m+1, `eqm` is declined, and `ne0`/`eq0exit` still get n.
- **GAP9 sweep:** all 54 kernel TUs that compile (27 x O2/O3) give byte-identical disassembly with and without the fix (baseline built at integration head `b0f18c5a6b88`, `logs/20-F007/basebin2`). The 5 TUs that fail, fail the same way on both (front-end errors).
- **SDK drivers on GVSoC** (FIR k01/k02, MatMul k03-k07, FFT k10a, and the rest): 54 kernel/opt pairs, checksums equal to GAP9 GCC, and cycles and kernel objects identical to the baseline (`logs/20-F007/runtime_summary.txt`).
- **Fuzzer, seeds 1-240, O2/O3/Os** (`logs/20-F007-fuzz/summary.txt`; base = integration head `b0f18c5a6b88`, simulated both): no program that the baseline compiles and runs correctly gets a wrong result, hang or crash. The one pre-existing MISMATCH (seed 27 O2/O3, a tail-duplication layout defect named by the F003 reviewer) is unchanged. Assembly changed in 24 of 720 compiles. 7 of 2292 hardware loops are no longer formed (see below).
- **Lit:** the 65 fork tests pass, including `xpulp-hwloop-countdown.ll` (count `n`, `lp.setupi 31` unchanged). CodeGen/RISCV + MC/RISCV: 2581/2582 pass. The one failure is `rvv/vsetvli-insert-zve64f.mir`, which is listed in `data/known-failures.txt`.

Known limits, stated honestly:
- A `!=` loop whose start value cannot be proven different from the end value is declined when the Hexagon heuristic finds no range check. This is why the 7 fuzzer loops are not formed; there the proof needs `(m & 3) != 0 => m != 0`. It also covers unguarded `do {} while (--u != 0)`. Declining keeps the correct branch loop.
- A count of 2^32 cannot be held by the 32-bit counter. An ordered loop whose counter would go past the type's maximum only happens when End is within `step` of INT_MAX/UINT_MAX. That is undefined behaviour for C `int`, and for `unsigned` it is an effectively endless loop. Hexagon has the same limits.

## What breaks if this is wrong

A wrong count makes a loop run the wrong number of times without any compiler message. Loop results come out wrong (FIR/MatMul checksums differ from GCC), or the program hangs when the count wraps to a huge number. The oracle above shows either symptom immediately: `BAD fn n=.. got=.. want=..` or HANG. If the guard or its proof were too weak, loops would get slower (extra preheader instructions) or lose `lp.setup`. The sweep byte-identity and the runtime cycle comparison would show that. No lit test pins trip counts for these shapes yet. A test is proposed in the result file (`proposed_test`) and was not added, per the task.

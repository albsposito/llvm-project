# 20/F044: a 32-bit PULP SIMD vector (v2s, v4s/v4u, v2h, v2ah) is accepted as an inline-asm "r" operand, in one integer register, as in GAP9 GCC

Backlog B131, M2a checkpoint item 6. The GAP9 SDK's `vfcvt_h_x` / `vfcvt_x_h` / `vfcvt_ah_x` / `vfcvt_x_ah` macros (`tools/autotiler_v3/Emulation/GapBuiltins.h:258-285`) are inline assembly whose operands are packed pairs: `asm("vfcvt.h.x %0, %1" : "=r"(v2h_dst) : "r"(v2s_src))`. Our clang stopped with "couldn't allocate output register for constraint 'r'" (or "... input reg ..."); GAP9 GCC accepts it. This blocked `CNN_Libraries/CNN_Copy.c` and `CNN_Libraries_SQ8/CNN_Pooling_SQ8.c`. One commit, codegen-core cluster, one file: `llvm/lib/Target/RISCV/RISCVISelLowering.cpp` (a file the fork already changes).

## What upstream changed

Nothing in `llvmorg-19.1.7..llvmorg-20.1.8` broke this; the fork never handled it (the fork's LLVM 18 branch `pulp/integer_SIMD_fix` has the same code, and `git log -S'Support fixed vectors up to XLen' llvmorg-19.1.7..llvmorg-20.1.8` finds nothing). The rejection comes from upstream `0a35211b3488` "[RISCV] Don't allow vector types to be used with inline asm 'r' constraint" (LLVM 15, D115810): for the `r` constraint (any integer register) `getRegForInlineAsmConstraint` now returns "no register class" for every vector type, with a `TODO: Support fixed vectors up to XLen for P extension?`. The commit message gives the reason: generic code can already bitcast a non-integer operand to the register's integer type, but that crashes for scalable (RVV) vectors, and "fixed vectors might work without crashing, but it doesn't seem worthwhile to allow". Upstream still has the same TODO at `llvmorg-22.1.7` (no packed-SIMD extension upstream uses GPRs for vectors yet).

## Why this is equivalent

Before: any vector type with `r` was refused. Now, in the `r` case, before the upstream "vectors are refused" line, one new rule: if Xpulpv2 is on (Xpulpfvec and Xgap9 imply it), the target is 32-bit, and the operand is a fixed-length vector of exactly 32 bits (`v2i16`, `v4i8`, `<2 x half>`, `<2 x bfloat>`), return the integer register class without `x0` (`GPRNoX0`), exactly the class plain integers get. Everything else (RVV vectors, 64/128-bit fixed vectors, non-PULP targets, RV64) keeps upstream's refusal; upstream's test `llvm/test/CodeGen/RISCV/inline-asm-invalid.ll` (a `<4 x i32>` and scalable vectors, no Xpulpv2) still passes.

The operand is then handled by the generic inline-asm code in `SelectionDAGBuilder::getRegistersForValue` (`llvm/lib/CodeGen/SelectionDAG/SelectionDAGBuilder.cpp:9799` at `llvmorg-20.1.8`): because the register class holds `i32` and the operand has the same size, it bitcasts the operand to `i32` (and the result back), which is a no-op on the bits. So the asm sees exactly the 32 bits GCC puts in the register: element 0 in the low half. This is the same mechanism upstream uses when it maps a non-integer type to a GPR class for `r`: the Zfinx/Zhinx lines right below (`f16`/`f32` -> `GPRF16NoX0`/`GPRF32NoX0`, `RISCVISelLowering.cpp:21189-21195` at `llvmorg-20.1.8`, from `03dcd88c781d` "[RISCV][ISel] Ensure 'in X' Constraints prevent X0 (#112563)"). I return `GPRNoX0` (not the fork's `GPRAV2`/`GPRAV4` classes, which include `x0` and do not cover the half-precision pairs) so that a vector output never lands in `x0`, like the other "in X" types after `03dcd88c781d`. `<2 x half>` / `<2 x bfloat>` are not legal types in the backend yet (fp16 design T5); the bitcast from `i32` is legalised like any other, which the checks below exercise.

## What breaks if this is wrong

- **Too narrow**: an SDK file with `vfcvt_*` macros would fail again with "couldn't allocate ... register for constraint 'r'" (`CNN_Copy.c`, `CNN_Pooling_SQ8.c`, and the reproducer above).
- **Too wide**: if the rule matched RVV or larger vectors, upstream's `llvm/test/CodeGen/RISCV/inline-asm-invalid.ll` (`constraint_r_fixed_vec`, `constraint_r_scalable_vec`) would stop reporting the error and could crash instead, as described in `0a35211b3488`.
- **Wrong bits**: if the element order or the conversion to `i32` were wrong, the GVSoC test above would print different values from GCC and from the host reference (halves swapped, or garbage in one half); a program like `CNN_Copy.c`'s float16 conversion kernels would produce wrong outputs.
- **`x0` chosen**: with a class containing `x0` an output could be assigned to `x0` and be lost; `GPRNoX0` prevents it.
- **Missing test**: no lit test covers a vector `r` operand with Xpulpv2. A test is proposed in the result file.

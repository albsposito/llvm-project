# 20/F029: zero-extended vector lanes were sign-extended (backlog B112, wrong code)

A defect the fork has had since it was written. It is not a porting break. With Xpulpv at -O1 and above, reading an unsigned lane of a packed vector (`v4u x; ... x[1]`), or comparing lanes for equality, could give a wrong value for lanes whose top bit is set (0x80..0xff for bytes, 0x8000..0xffff for halfwords). The lane came back sign-extended (0x80 read as 0xffffff80) where the program needed it zero-extended (0x00000080). One side of a compare was then sign-extended and the other zero-extended, so equal lanes compared unequal.

## What upstream changed

Nothing upstream caused this. The wrong patterns come from the fork's first commit, `f1b7aebff8c2` [LLVM/PULP/SNITCH] Support for PULP and Snitch cores/platforms (`git -C /home/ubuntu/llvm-project log pulp/integer_SIMD_fix -S'uimm6:$index), 255)' -- llvm/lib/Target/RISCV/` finds only that commit). They are the same in ref-18, port-19 and int-20.

In LLVM's instruction selector, "take lane i of a 4 x 8-bit vector and zero-extend it to 32 bits" is written as `(and (vector_extract v, i), 255)`, and for 2 x 16-bit lanes `(and (vector_extract v, i), 65535)`. The front end and the optimiser produce this shape for every `unsigned char` or `unsigned short` lane read. They also produce it for every lane equality compare, because LLVM compares the two lanes after zero-extending both. The fork mapped these two shapes to `pv.extract.b` and `pv.extract.h`. Those instructions sign-extend the lane. The PULP ISA has the zero-extending forms, `pv.extractu.b` and `pv.extractu.h`, and the fork already defines them (`PV_EXTRACTU_B/H`, `RISCVInstrInfoXpulp.td:879-880`). No pattern selected them.

The variable-index path (`pv.shuffle.b` followed by `p.extbz`) was right. That is why a compare of a constant-index lane with a variable-index lane mixed the two extensions (the `count()` function in `logs/20-F019-sim/gat.c`).

## Why this is equivalent

The change is two lines in `RISCVInstrInfoXpulp.td` (lines 1531-1536): the two `and`-masked lane patterns now select `PV_EXTRACTU_H` and `PV_EXTRACTU_B` instead of `PV_EXTRACT_H` and `PV_EXTRACT_B`. The same instruction count and form is used, so there is no cost change. The other extract patterns were checked and are right:
- plain lane read with undefined upper bits, where either extension is fine: `pv.extract`;
- sign-extended lane (`sext_inreg`): `pv.extract`;
- variable index: `pv.shuffle` + `p.extbz/p.exthz` or `p.extbs/p.exths`.

So every extract's extension now matches what the DAG asks for: zext → `pv.extractu.b/.h`, sext → `pv.extract.b/.h`, anyext → `pv.extract.b/.h`. `logs/20-F019-review/zext-extract.ll` gives `pv.extractu.b`, `pv.extract.b` and `pv.extractu.h` for its zext 8-bit, sext 8-bit and zext 16-bit functions (it was `pv.extract.*` for all three). Vectors wider than 32 bits (8 x 8, 4 x 16, 16 x 8) are split into 32-bit halves before selection, so they reach the same patterns and are fixed the same way. GAP9 GCC (`-march=rv32imcxgap9 -O2`) does the same: it emits `pv.extractu.b`/`pv.extractu.h` ("vect extract, with zero ext") for `unsigned char`/`unsigned short` lanes and `pv.extract.b` for `signed char` lanes. Clang may still choose shifts when those are cheaper.

Upstream reference: at `llvmorg-20.1.8`, CORE-V SIMD, the upstream PULP-derived extension, defines the same pair: sign-extending `cv.extract.h/.b` and zero-extending `cv.extractu.h/.b` (`llvm/lib/Target/RISCV/RISCVInstrInfoXCV.td:427-430`). It has no lane-extract selection patterns. For scalars, though, CORE-V selects the zero-extending instruction for exactly this `and`-mask shape: `(and GPR, 0xff) → CV_EXTBZ` and `(and GPR, 0xffff) → CV_EXTHZ` (`RISCVInstrInfoXCV.td:794-795`). The sign-extending ones are only used for `sext_inreg` (`:792-793`). The new patterns follow the same rule. Encoding check: `llvm-mc` and GAP9 GCC's assembler encode `pv.extractu.b a0,a1,3` as `0x9215f557` and `pv.extractu.h a0,a1,1` as `0x9205e557`.

## What breaks if this is wrong

If the zero-extending pattern were wrong, programs would read unsigned lanes wrongly: `lanes.c` groups such as `v4u_get1`, `v8u_eq_k80`, `v4hu_self` and every `*_count` would mismatch on GVSoC, as they do with int-20. No lit test guards these patterns today. A regression test is proposed in the result file (`proposed_test`): an llc test on `zext`/`sext`/anyext of a constant-index `extractelement` of `<4 x i8>` and `<2 x i16>`, and a lane `icmp eq` of a constant-index lane against a variable-index lane. It would check for `pv.extractu.b`, `pv.extract.b`, `pv.extractu.h` and `pv.extract.h`.

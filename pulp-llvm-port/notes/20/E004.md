# 20/E004: keep half-precision conversions/loads/stores unsupported in the Mempool scheduling model

Written for a reader who does not know LLVM. Four sections, all required (policy_check.py checks the headings).

## What upstream changed

A scheduling model tells the compiler how long each kind of instruction takes on a given core, and it must say something about every "scheduling class": give it a cost or declare it unsupported. Upstream keeps ready-made lists ("multiclasses") that declare a whole extension unsupported. Commit `9fa517208fbf` "[RISCV] Use inheritance to simplify usage of the UnsupportedSched* multiclasses. NFC (#120329)" split the old half-precision list `UnsupportedSchedZfh` in two: `UnsupportedSchedZfh` now covers only the full Zfh arithmetic, and the half-precision conversions, loads, stores and moves (Zfhmin: `WriteFCvtF32ToF16`, `WriteFCvtF16ToF32`, `WriteFCvtF16ToF64`, `WriteFCvtF64ToF16`, `WriteFLD16`, `WriteFST16`, `WriteFMovI16ToF16`, `WriteFMovF16ToI16` and their reads) moved to a new `UnsupportedSchedZfhmin`, which includes `UnsupportedSchedZfh`. The fork's Mempool model still used `UnsupportedSchedZfh`, so those classes lost their "unsupported" declaration and llvm-tblgen stopped with `RISCVSchedMempool.td:15: Processor does not define resources for WriteFCvtF32ToF16`. No scheduling class was added; only the list was split.

## Why this is equivalent

Before (LLVM 19): `defm : UnsupportedSchedZfh;` marked every half-precision class unsupported on Mempool. Now: `defm : UnsupportedSchedZfhmin;`, which by inheritance marks exactly the same set unsupported (Zfh arithmetic plus the Zfhmin conversions/loads/stores/moves), plus `ReadFMA16Addend`, which upstream `e3fe41cdf558` "[RISCV] Add missing ReadFMA16Addend in UnsupportedSchedZfh" added to the list (it is an unsupported read of an unsupported half-precision FMA, no effect on Mempool). This is the same one-line change the NFC commit made to upstream's in-order Rocket model (`llvm/lib/Target/RISCV/RISCVSchedRocket.td:262` at `llvmorg-20.1.8`, `-defm : UnsupportedSchedZfh;` / `+defm : UnsupportedSchedZfhmin;` in `9fa517208fbf`).

After this change `llvm-tblgen -gen-subtarget` on RISCV.td exits cleanly; no further missing classes appeared, so this was the only gap for Mempool at 20. In the generated `MempoolModelSchedClasses` (scratch output `logs/20-E004.scratch-subtarget.inc`) the entries `WriteFCvtF32ToF16_ReadFCvtF32ToF16`, `WriteFCvtF16ToF32_...`, `WriteFLD16_...`, `WriteFST16_...`, `WriteFMovI16ToF16_...` have NumMicroOps 8191 (the "invalid/unsupported" marker), as they were at 19, and the existing Mempool entries are untouched (for example `WriteIDiv` and `WriteIRem` still both `7, 2, 34, 1, 1, 2`). `RISCVSchedSnitch.td` defines no `WriteRes` at all and needs no change. No latency or resource of any existing fork entry was changed.

## What breaks if this is wrong

If the wrong list were used and a half-precision class were left undeclared, llvm-tblgen would fail and nothing would build (the error this task fixes). If instead the Mempool model gave half-precision instructions a cost, `-mcpu=mempool-rv32` code using Xsmallfloat/Zfh-style FP16 conversions would be scheduled differently from LLVM 19: instruction order around `fcvt.h.s`/`fcvt.s.h`/`flh`/`fsh` in llc output would change. No fork test is known to check Mempool scheduling of FP16 conversions specifically; that is a missing test.

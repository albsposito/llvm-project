# 20/E001: Preserve smallfloat registration with LLVM 20 constructors

## What upstream changed

Upstream d280a9c5e22662fd24708245add50b152ab10fc8, `[NFC] [RISCV] Refactor class RISCVExtension (#120040)`, removed the explicit extension-name argument and derives Name and Desc from FeatureVendor/FeatureStdExt record names. The 21 fork smallfloat records still passed the old arguments, producing all three E001–E003 parser signatures in steps/20/errors-r1.json. A worker RISCVCommonTableGen build reproduced them in logs/20-E001.repro.log.

## Why this is equivalent

All 21 records now pass version 0.1 and the description body through the new constructor. Each explicitly retains its original Name and complete Desc, because the fork's FeatureExt prefix does not match upstream's automatic naming prefixes. Record IDs, HasExt subtarget fields, value true, empty implications, nonexperimental status, predicates, instructions and encodings are unchanged. This follows the same preservation strategy used for the five legacy records during conflict-registration, without growing the changed-file scope or renaming consumers.

Upstream CORE-V records use the new constructor at llvm/lib/Target/RISCV/RISCVFeatures.td:1183 (FeatureVendorXCVelw) and :1204 (FeatureVendorXCVmem). The base class at :29 exposes Name/Desc fields and continues deriving fieldname by replacing Feature with Has. Explicit field overrides preserve the legacy naming that automatic FeatureVendor derivation cannot express without renaming records and their users.

## What breaks if this is wrong

A wrong Name loses -march/-mattr recognition and generated ISA information. A wrong field name disconnects feature predicates from the subtarget. Wrong descriptions alter extension-help output. The integration smallfloat MC/ISAInfo suite is the final behavior gate; no test has been changed here. The narrow worker build reaches every RISCV TableGen backend, but does not claim full integration codegen/lit success.

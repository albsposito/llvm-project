Speaker notes. A short tour of the LLVM 18 to 20 port of the PULP compiler fork. No compiler background needed. Every number comes from the step reports (steps/19/report.md, steps/20/report.md), the change notes and PROGRESS.md.

The starting point

A compiler for PULP's extra instructions

Hardware loops

The chip repeats a loop without extra jump instructions.

Packed SIMD

One instruction works on 2 or 4 small numbers at once.

Load-and-step memory access

Read a value and advance the pointer in one go.

FREP and data streams (Snitch)

Repeat floating-point instructions; stream data in automatically.

The fork (67 changes, 124 files, ~17,000 added lines) was stuck on LLVM 18. Goal: reach LLVM 23 and keep every feature.

LLVM = the open-source compiler toolkit the fork is built on · Source: PORTING.md §1 · 2

Speaker notes. PULP chips (including GAP9) have extra instructions that ordinary RISC-V compilers do not use. The PULP fork of LLVM teaches the compiler to use them: hardware loops, packed SIMD (Xpulpv2), post-increment loads and stores, multiply-accumulate, C builtins (__builtin_pulp_*), Snitch SSR/SDMA/FREP including #pragma frep, and small-float formats. The fork is branch integer_SIMD_fix: 67 commits, +16,960 / -18 lines in 124 files, on LLVM 18. Upstream LLVM has moved on, so the fork is being carried forward release by release to LLVM 23.

Speaker notes. Route 1 (decision D0): rebase the fork release by release, 18 to 19, 20, 21, 22, 23, with a green checkpoint after each. Within a step: cherry-pick the one-commit-per-group stack onto the new upstream release; build; cluster the errors by signature; one worker fixes each cluster in its own worktree; an independent reviewer approves or rejects each fix; approved fixes land one at a time through integrate.py, which rejects anything that breaks policy, adds a build error or fixes nothing. The same loop then runs for the test suite. The step is tagged port-N-green. Only the owner decides on test changes and route choices.

Every break traces to one group.

All 124 fork files map to exactly one group · Source: PORTING.md §3 · 4

Speaker notes. Phase 0 restacked the 67 fork commits into one commit per group ("cluster"), in this order. Each group has a known risk profile: registration and clang-builtins were high risk at 19 because upstream relocated those files; codegen-core is high risk every step because it touches the most edited RISC-V files upstream. At the end of each step the fixes are folded back so the stack is again exactly 11 commits.

"Records" = entries the build turns into tables · Source: steps/19/leads.md; notes/19/E002, E004, conflict-clang-builtins · 5

Speaker notes. Extension list: upstream 80628ee0d555 deleted the hand-written SupportedExtensions table in RISCVISAInfo.cpp and now generates it from RISCVExtension records in RISCVFeatures.td. The fork's 27 rows (xpulpv, xdma, xfrep, xssr, xmempool and 21 smallfloat xf* extensions) had to become RISCVExtension definitions (E004 restored the 21 smallfloat ones). Because default -march for a CPU is built only from those records, the snitch and mempool-rv32 CPUs would otherwise have lost their extensions silently. Builtins: a8d4a024e6be turned BuiltinsRISCV.def into a .td; the fork's 181 TARGET_BUILTIN lines became records with explicit spellings. The 64 packed-vector builtins needed a small backport of later upstream support for GCC-style vector types (E002, 508263824f4e, which arrived upstream in 20). Builtin checks moved from SemaChecking.cpp to SemaRISCV.cpp (a640a2e0205f).

LLVM 19 → 20 · 2 of 3

A real bug surfaced: the FREP loop

FREP tells the chip: "repeat the next N instructions". LLVM 20's reordering step (the "scheduler") now moves code both ways.

LLVM 19: correct

FREP: next 2, ×128

multiply · repeated

add · repeated

move

LLVM 20, before fix: wrong

multiply · runs once

FREP: next 2, ×128

add · repeated

move · wrongly repeated

The fix

FREP is now a wall the scheduler cannot move code across.

Output is again identical to the LLVM 19 compiler.

Still open: a stronger guarantee is proposed.

Found by the test suite, not in the field · Source: notes/20/T003.md, T008.md; PROGRESS.md escalations · 8

Speaker notes. Upstream 9122c5235ec8 made the pre-register-allocation scheduler bidirectional for every RISC-V CPU, Snitch included. The fork had never told the scheduler that frep.o repeats the N instructions after it; LLVM 19 was correct only because the scheduler worked bottom-up. In fork test freploop-nested.ll the scheduler moved fmul.d above frep.o: the multiply ran once instead of 128 times and fmv.x.w was repeated instead. Fix T003: FREP_O and FREP_I join the hardware-loop setup instructions as scheduling boundaries. Emitted instructions are identical to port-19-green; one test line changed for a moved assembler comment (T008, owner approved). Open (reviewer finding, pre-existing): nothing stops an unrelated instruction being mixed into the N repeated ones; bundling frep with its body is proposed as its own task.

LLVM 19 → 20 · 3 of 3

A naming-order quirk, bridged by a rename

  • A "register group" names a set of the chip's registers.
  • The fork's packed-SIMD groups hold the same registers as GPR.
  • LLVM links identical groups only when their names sort side by side.

Before: link lost

GPR

GPRF32 (changed upstream)

PulpV2

PulpV4

After: linked again

GPR

GPRAV2

GPRAV4

GPRF32

Owner decision (D3): rename only, no behaviour change. Temporary: planned redesign at step 23.

Source: notes/20/T007.md; PROGRESS.md decision D3 · 9

Speaker notes. Upstream bc91f3cdd57c rebuilt the GPRF32 register class (used for Zfinx) from new 32-bit sub-registers. It still has the same size and count as GPR, and TableGen orders such classes by name, so GPRF32 now sat between GPR and the fork's PulpV2/PulpV4. TableGen treats identical classes as mutual sub-classes only when they are adjacent in that order, so the link was lost: the machine verifier rejected a GPR value on a PulpV4 operand and one test showed the wrong class. Renaming to GPRAV2/GPRAV4 puts them next to GPR again ('A' sorts before 'F'). Registers, types and allocation order are unchanged; llc output is byte-identical for the checked tests. The bridge is fragile if upstream adds another class whose name sorts in between; the step-23 plan is to remove these classes and hold packed types directly in GPR, as upstream and PULP's LLVM 22 branch do.

Simulator (GVSoC) cycle counts, not silicon · Source: benchmarks/gap9-sweep runtime_report.md, report.md; PROGRESS.md · 12

Speaker notes. GAP9 SDK sweep on the GVSoC simulator (instruction-accurate with a timing model, not cycle-exact silicon; ratios meaningful, absolute cycles indicative). Speed: geometric mean of cycle ratios on SDK/loop kernels (3 kernels where every LLVM build ran correctly): port19/ref18 1.000 and port20/ref18 1.000 at O2 and O3. Over all 12 comparable kernels port20 is 0.949 of ref18, but the gain comes from the driver's call loop, not from PULP kernel code (kernel code identical). GAP9 GCC is faster on these (0.80 to 0.89 of ref18). Coverage: port20 builds, runs and matches the reference on six kernels where ref18 and port19 crash in the PULP Hardware Loops pass (k09_cmplx_fix, k12_sum_loop, dot8_loop, dot16_loop, copy_loop, packed_add8_loop). Static sweep: SDK kernels compiling at O2: 4/12 on 18 and 19, 5/12 on 20; anchor functions 10/15 vs 15/15. Correctness: p.clip immediate off-by-one (clip and k05_matmul_dsp_fix16) and p.extractu size off-by-one (k12_bit_extract) give wrong results on 18, 19 and 20 alike; fix task 20/F002. New at 20 (R001): constant-trip-count hardware loops crash at object emission; fix in progress. Also: port-19 only, a hardware-loop miscompile on k05 at O2 doubles work (+70% cycles); port-20 does not have it.
